# ステアリング（タスク管理）

このスキルは実装フェーズの進捗管理ルールである。

## いつ読むか

- `/implement` コマンドの毎セッション開始時
- `/fix` コマンドの実装フェーズ開始時
- タスク管理のルールをリマインドするために読む

## .steering/ の構造

```
.steering/YYYYMMDD-機能名/
  requirements.md   ← スコープ宣言 + 受入条件
  design.md         ← 実装方針の要約
  tasklist.md       ← タスクリスト（進捗管理の正）
  session-log.md    ← セッション履歴（判断と進捗の記録）
```

## tasklist.md のルール

### 書き方

```markdown
## Phase0: 実装前プレチェック
> 実装ループ開始前に完了させること。全項目 [x] になるまで実装タスクに着手しない。

- [ ] 適用スキルの確認（impl-planner の計画書 Phase0 参照）
- [ ] 利用する ref 型・callback 型のメソッド一覧を確認した
- [ ] Upstream* 型の配置先（*.type.ts）を確認した（BFF実装の場合）
- [ ] 既存 Zod スキーマのバリデーションパターンを確認した（BFF実装の場合）

※ 該当しない項目は削除してよい

## Phase1: タスク

- [ ] タスク1の説明
- [ ] タスク2の説明
  - [ ] サブタスク2-1
  - [ ] サブタスク2-2
- [ ] タスク3の説明

## 完了済み

（実装中に上から移動してくる）
```

### MUST（必須）

- タスク完了時、即座に `[ ]` → `[x]` に更新する
- セッション終了時に tasklist.md の状態が最新であること
- タスクが大きすぎたらサブタスクに分割してから実装する

### NEVER（禁止）

- tasklist.md を更新せずに次のタスクへ進む
- 「後でやる」「別タスクにする」でタスクをスキップする
- 仕様変更を勝手に行う（designフェーズに戻って人間に報告する）

### 例外: タスクが不要になった場合

技術的理由（設計変更、依存変更）で不要になった場合のみ:
```markdown
- [x] ~~タスク名~~ (理由: APIの仕様変更によりこの処理は不要になった)
```

## session-log.md のルール

セッション間の判断と進捗を追跡するための追記専用ログ。

### 書き方

```markdown
## YYYY-MM-DD セッション{{N}}

### 実施内容
- {{やったことの箇条書き}}

### 判断・決定事項
- {{セッション中に下した判断とその理由}}

### 発見した課題
- {{技術的負債、仕様の曖昧さ、未考慮のケース等}}

### 次セッションへの引き継ぎ
- {{次のAIが知るべきこと}}
```

### MUST（必須）

- 毎セッション終了時に session-log.md にエントリを追記する
- 判断事項は「何を」「なぜ」の両方を記録する
- 技術的負債を発見したら `docs/meta/debt.md` にも転記する

### NEVER（禁止）

- 過去のエントリを編集・削除する（追記専用）

## セッション終了時の確認

1. tasklist.md が最新の状態か
2. session-log.md にエントリを追記したか
3. CLAUDE.md の progress が更新されているか
4. 次のセッションのAIが「何から始めればよいか」わかるか
