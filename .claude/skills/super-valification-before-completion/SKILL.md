# 完了前の検証

## 概要

検証なしに作業が完了したと主張することは、効率化ではなく不誠実である。

基本原則:主張よりも証拠が優先されます。

**この規則の文言に違反することは、この規則の精神に違反することである。**

## 鉄の掟

```
新鮮な検証証拠なしに完了を主張してはならない
```

このメッセージ内で検証コマンドを実行していない場合、それが通ったと主張することはできない。

## ゲート関数

```
ステータスを主張したり満足を表明したりする前に:

1. 特定: どのコマンドがこの主張を証明するか？
2. 実行: 完全なコマンドを実行する（新鮮に、完全に）
3. 読取: 完全な出力、終了コード、失敗数を確認
4. 検証: 出力は主張を裏付けているか？
   - NO の場合: 証拠とともに実際の状態を述べる
   - YES の場合: 証拠とともに主張を述べる
5. その後のみ: 主張する

いずれかのステップをスキップ = 嘘をつくこと、検証ではない
```

## /implement コマンドで呼び出された場合の自動検証

このスキルが `/implement` コマンドから呼び出された場合、以下を自動実行する:

### 1. Prettier 自動フォーマット（最優先）

**必ず最初に実行する**

**Phase変更ファイルのみを対象とする:**

```bash
# ステージング済みの frontend 配下ファイル（ts/tsx/json/md）を抽出
STAGED_FILES=$(git diff --cached --name-only --diff-filter=ACMR | grep '^product/frontend/' | grep -E '\.(ts|tsx|json|md)$')

if [ -z "$STAGED_FILES" ]; then
  echo "[SKIP] Prettier整形対象のステージング済みファイルがありません。"
else
  FILE_COUNT=$(echo "$STAGED_FILES" | wc -l)
  echo "[Prettier] 整形対象ファイル (${FILE_COUNT}件):"
  echo "$STAGED_FILES"
  
  # ファイルリストをPrettierに渡して整形
  echo "$STAGED_FILES" | xargs npx prettier --write
  
  # 修正されたファイル一覧を確認
  echo "[Prettier] 整形完了。修正されたファイル:"
  git diff --name-only
fi
```

**理由:**
- Phase変更ファイルのみを整形し、不要なファイルを除外
- ステージング状態から動的に対象を取得
- 対象がゼロの場合はスキップし、時間を節約

### 2. Prettier 検証

```bash
# ステージング済みの frontend 配下ファイル（ts/tsx/json/md）を抽出
STAGED_FILES=$(git diff --cached --name-only --diff-filter=ACMR | grep '^product/frontend/' | grep -E '\.(ts|tsx|json|md)$')

if [ -z "$STAGED_FILES" ]; then
  echo "[SKIP] Prettier検証対象のステージング済みファイルがありません。"
else
  # ファイルリストをPrettierに渡して検証
  echo "$STAGED_FILES" | xargs npx prettier --check
  
  # 0 errors を確認
  # エラーがある場合はステップ1を再実行
  # 証拠（コマンド出力）を提示
fi
```

**注意:**
- エラーがある場合はステップ1を再実行
- エラーがゼロになるまで繰り返す

### 3. ESLint 実行

**Phase変更ファイルのみを対象とする:**

```bash
# ステージング済みの frontend 配下ファイル（ts/tsx のみ）を抽出
STAGED_TS_FILES=$(git diff --cached --name-only --diff-filter=ACMR | grep '^product/frontend/' | grep -E '\.(ts|tsx)$')

if [ -z "$STAGED_TS_FILES" ]; then
  echo "[SKIP] ESLint対象のステージング済みファイルがありません。"
else
  FILE_COUNT=$(echo "$STAGED_TS_FILES" | wc -l)
  echo "[ESLint] 検証対象ファイル (${FILE_COUNT}件):"
  echo "$STAGED_TS_FILES"
  
  # ファイルリストをESLintに渡して検証
  cd product/frontend && echo "$STAGED_TS_FILES" | sed 's|^product/frontend/||' | xargs npx eslint
  
  # 0 errors / 0 warnings を確認
  # エラーがある場合は修正してから再実行
  # 証拠（コマンド出力）を提示
fi
```

**注意:**
- ESLintは自動修正しない（`--fix` オプションを使わない）
- エラーがある場合は手動で修正する必要がある
- Phase変更ファイルのみを検証し、不要な全ファイルスキャンを回避

### 4. 型チェック（Phase 1 以降）

**Phase変更ファイルのみを対象とする:**

```bash
# ステージング済みの frontend 配下ファイル（ts/tsx のみ）を抽出
STAGED_TS_FILES=$(git diff --cached --name-only --diff-filter=ACMR | grep '^product/frontend/' | grep -E '\.(ts|tsx)$')

if [ -z "$STAGED_TS_FILES" ]; then
  echo "[SKIP] TypeScript型チェック対象のステージング済みファイルがありません。"
else
  FILE_COUNT=$(echo "$STAGED_TS_FILES" | wc -l)
  echo "[TypeScript] 型チェック対象ファイル (${FILE_COUNT}件):"
  echo "$STAGED_TS_FILES"
  
  # ファイルリストをTypeScriptに渡して型チェック
  cd product/frontend && echo "$STAGED_TS_FILES" | sed 's|^product/frontend/||' | xargs npx tsc --noEmit
  
  # 0 errors を確認
  # 型エラーがある場合は修正してから再実行
  # 証拠（コマンド出力）を提示
fi
```

**注意:**
- Phase変更ファイルのみを型チェック
- 依存ファイルの型エラーは検出されない可能性がある（トレードオフ: 速度 vs 完全性）
- より厳密なチェックが必要な場合は、Phase 10 完了後に全プロジェクトの型チェックを実行する

### 5. 修正があった場合のコミット

検証中に自動修正・手動修正があった場合、追加コミットを作成する:

```bash
# 修正されたファイルを確認
git status

# 修正があった場合のみコミット
if [ -n "$(git status --porcelain)" ]; then
  git add .
  git commit -m "style: Phase N 完了後の自動検証による修正

- Prettier 自動フォーマット適用
- ESLint エラー修正（該当する場合）
- TypeScript 型エラー修正（該当する場合）"
fi
```

**理由:**
- 検証による修正は、機能実装のコミットとは別に記録する
- 履歴を見たときに「何が機能実装で、何が検証による修正か」が明確
- PR レビュー時に修正内容が追跡しやすい

**注意:**
- 修正がゼロの場合、このステップはスキップされる
- 大量の修正がある場合は、Phase の実装自体に問題がある可能性があるため、ユーザーに報告する

### 検証ゲート

```
1. 特定: どのコマンドがこの主張を証明するか？
2. 実行: 完全なコマンドを実行する（新鮮に、完全に）
3. 読取: 完全な出力、終了コード、失敗数を確認
4. 検証: 出力は主張を裏付けているか？
   - NO の場合: 証拠とともに実際の状態を述べる → 修正 → 再検証
   - YES の場合: 証拠とともに主張を述べる → 呼び出し元へ戻る
5. その後のみ: 主張する
```

## よくある失敗

| 主張 | 必要なもの | 不十分なもの |
|-------|----------|----------------|
| Prettierがクリーン | Prettier出力: 0 errors | 部分的チェック、推定 |
| Linterがクリーン | Linter出力: 0 errors | 部分的チェック、推定 |
| 型チェックが通った | tsc出力: 0 errors | 部分的チェック、推定 |

## レッドフラグ - 停止

- "〜すべき"、"おそらく"、"〜のようだ"の使用
- 検証前に満足を表明（"素晴らしい！"、"完璧！"、"完了！"など）
- 検証なしでcommit/push/PRしようとしている
- エージェントの成功報告を信頼
- 部分的な検証に依存
- "今回だけは"と考える
- 疲れていて作業を終えたい
- **検証を実行せずに成功を暗示するあらゆる表現**

## 合理化の防止

| 言い訳 | 現実 |
|--------|---------|
| "今度は動くはず" | 検証を実行せよ |
| "自信がある" | 自信 ≠ 証拠 |
| "今回だけは" | 例外なし |
| "Linterが通った" | Linter ≠ コンパイラ |
| "エージェントが成功と言った" | 独立して検証せよ |
| "疲れている" | 疲労 ≠ 言い訳 |
| "部分的チェックで十分" | 部分的では何も証明しない |
| "別の言葉なので規則は適用されない" | 精神が文言に優先 |

## 重要パターン

**要件:**
```
✅ 計画を再読 → チェックリスト作成 → 各項目検証 → ギャップまたは完了を報告
❌ "テストが通った、フェーズ完了"
```

**エージェント委譲:**
```
✅ エージェント成功報告 → VCS diffを確認 → 変更を検証 → 実際の状態を報告
❌ エージェント報告を信頼
```

## なぜこれが重要か

24件の失敗記憶から:
- あなたの人間パートナーは"あなたを信じない"と言った - 信頼が壊れた
- 未定義関数が出荷された - クラッシュする
- 欠けた要件が出荷された - 不完全な機能
- 誤った完了 → リダイレクト → 再作業で時間浪費
- 違反: "誠実さは核心的価値観。嘘をつけば、あなたは交代させられる。"

## いつ適用するか

**常に以下の前に:**
- 成功/完了主張のあらゆるバリエーション
- 満足のあらゆる表明
- 作業状態についてのあらゆる肯定的陳述
- コミット、PR作成、タスク完了
- 次のタスクへの移動
- エージェントへの委譲

**規則が適用されるもの:**
- 正確なフレーズ
- 言い換えや同義語
- 成功の暗示
- 完了/正確性を示唆するあらゆるコミュニケーション

## 結論

**検証にショートカットはない。**

コマンドを実行せよ。出力を読め。その後に結果を主張せよ。

これは交渉の余地がない。
