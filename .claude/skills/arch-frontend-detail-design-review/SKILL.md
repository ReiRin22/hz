# 詳細設計書 更新レビュー ワークフロー

このスキルは、フロント基盤の詳細設計書（フォルダ型構造化済み）を更新した **直後** に、3観点で並列レビューを実施し、品質を担保する。

## いつ使うか

- `arch-frontend-detail-design-update` で章を更新した直後（必須）
- `arch-frontend-detail-design-chapter-reform` で章をリファクタした直後（必須）
- 過去更新分の品質を一括チェックしたい場合（任意）

---

## 前提

- 対象パス: `docs/02_アプリ基盤/01_フロントエンド/02_詳細設計書/{XX}_{章名}/`
- 上位設計書: `docs/02_アプリ基盤/01_フロントエンド/01_フロントエンド方式設計書/` 配下のシート群（sheet_05〜sheet_30）
- ブランチ: 設計書参照は `develop_fix_docs` を正とする（最新の上位設計書を取得すること）

---

## ワークフロー

### ステップ 0: レビュー対象の確認

ユーザーから対象章のパスを受け取る。複数章を一度にレビューしないこと（1章 = 1レビュー）。

```
対象例: docs/02_アプリ基盤/01_フロントエンド/02_詳細設計書/04_状態管理設計/
```

### ステップ 1: 3エージェント並列レビューの起動

以下の **3エージェントを単一メッセージで並列起動** する（依存関係なし）。
すべて `subagent_type: app-impl-reviewer`、`model: opus` を指定。

> モデル指定: 設計書レビューは推論密度が高いため Opus 4.6 を使用する（コスト効率より品質優先）。

#### エージェント A: ADR 品質レビュー

```
description: ADR品質レビュー（{章名}）
subagent_type: app-impl-reviewer
model: opus

prompt:
あなたは設計書ADR品質レビュー担当です。以下の観点で {対象パス}/adr/ 配下の全ADRファイルをレビューしてください。
コードの修正は行わず、レビュー結果のみを返してください。

## レビュー対象
- {対象パス}/adr/README.md
- {対象パス}/adr/*.md（全ADRファイル）

## レビュー観点

### A1. ADR 必須セクションの充足
各ADRに以下が揃っているか確認:
- [ ] ステータス（Accepted / Superseded / Deprecated のいずれか）
- [ ] 決定日（YYYY-MM-DD）
- [ ] 関連設計書（双方向リンクの片側）
- [ ] 関連 ADR（または「なし」）
- [ ] 背景（何が課題か。前提・制約）
- [ ] 検討した選択肢（最低2案。各案のメリット・デメリット）
- [ ] 決定（採用案と理由。否定した案が落ちた理由）
- [ ] 影響（正の影響・負の影響・見直しトリガー）

### A2. ADR 起票基準への適合
- [ ] その判断は本当に ADR に値するか（代替案が存在 / 後戻りコストが高い / 表面コードから理由が読めない）
- [ ] 自明な実装詳細を ADR に書いていないか
- [ ] 「〜のため採用」という説明だけで終わっておらず、却下理由まで明記されているか

### A3. ADR 一覧表との整合
- [ ] adr/README.md の一覧表に全 ADR が登録されているか（漏れなく）
- [ ] 一覧表の連番（ADR-N）が各ファイルの本文と一致しているか
- [ ] ステータス・決定日・タイトルが本文と一致しているか

### A4. 双方向リンク
- [ ] 各 ADR の「関連設計書」リンク先が実在するか
- [ ] 関連設計書側に `> 根拠: [ADR-N](adr/{slug}.md)` の逆参照があるか

### A5. Superseded 関係
- [ ] 旧 ADR の「ステータス」が `Superseded by [ADR-N](slug.md)` 形式になっているか
- [ ] 新 ADR の「背景」に旧判断を覆した理由が明記されているか

## 出力形式

# ADR 品質レビュー結果

## 判定: PASS / FAIL

## レビュー対象ファイル一覧
- {ファイルパス}: {一行サマリ}

## 問題一覧（FAIL時のみ）

### [No.X] タイトル
- 観点: A1 / A2 / A3 / A4 / A5
- 重要度: ブロッカー / 高 / 中
- 対象ファイル: {パス} L{行番号}
- 問題の詳細:
- 修正提案:

## OK だった観点
- A1: 必須セクション充足 / A2: 起票基準 / ...
```

#### エージェント B: 設計書品質レビュー

```
description: 設計書品質レビュー（{章名}）
subagent_type: app-impl-reviewer
model: opus

prompt:
あなたは設計書品質レビュー担当です。以下の観点で {対象パス} 配下の規約ファイル・基盤詳細設計ファイルをレビューしてください。
コードの修正は行わず、レビュー結果のみを返してください。

## レビュー対象
- {対象パス}/{章名}規約.md（または規約.md）
- {対象パス}/{モジュール}設計.md（複数ある場合は全て）
※ adr/ 配下は対象外（エージェント A が担当）

## レビュー観点

### B1. 規約ファイルの記述ルール
- [ ] Why・経緯・選択理由が書かれていない（書かれている場合は ADR へ移すべき）
- [ ] 冒頭に関連する基盤設計書へのリンク表がある
- [ ] Do/Don't が具体的なコードまたは設計書参照で示されている
- [ ] 末尾に「責務サマリ表」がある
- [ ] アプリチームが何をすれば良いかが1ページでわかる構成

### B2. 基盤詳細設計ファイルの記述ルール
- [ ] Why・経緯・「〜のため」の説明が書かれていない（ADR へのリンクのみ）
- [ ] ADR が必要な判断には末尾に `> 根拠: [ADR-N](adr/xxx.md)` がある
- [ ] 公開 I/F に TypeScript 型定義 + JSDoc（@param/@returns/@throws/@remarks）がある
- [ ] 複数コンポーネントをまたぐフローに mermaid `sequenceDiagram` がある
- [ ] データ構造（State 型・LocalStorage キー一覧・クエリキー構造等）が定義されている
- [ ] ファイルパスと役割の対応表がある

### B3. JSDoc の品質
- [ ] 引数・戻り値の説明が1行で済まされず、非自明な挙動・副作用・順序制約が記述されているか
- [ ] @throws が網羅されているか（例外発生条件）
- [ ] 既存の JSDoc と書き方（語尾・主語・項目順）が統一されているか

### B4. シーケンス図の品質
- [ ] participant 名が他図と統一されているか
- [ ] 順序を間違えると動作が変わる箇所が図示されているか
- [ ] エラー分岐がある場合に alt/opt で表現されているか

### B5. データ構造の整合
- [ ] State 型の追加が `Store 一覧表` に反映されているか
- [ ] LocalStorage キー追加が `LocalStorage キー一覧表` に反映されているか

### B6. 残件（TBD）の扱い
- [ ] TBD・「確定後に更新」が残っている場合、`残件` テーブルに集約されているか
- [ ] 解消済みの TBD が残件テーブルに残留していないか

## 出力形式

# 設計書品質レビュー結果

## 判定: PASS / FAIL

## レビュー対象ファイル一覧
- {ファイルパス}: {一行サマリ}

## 問題一覧（FAIL時のみ）

### [No.X] タイトル
- 観点: B1 / B2 / B3 / B4 / B5 / B6
- 重要度: ブロッカー / 高 / 中
- 対象ファイル: {パス} L{行番号}
- 問題の詳細:
- 修正提案:

## OK だった観点
- B1: 規約ファイル / B2: 基盤詳細設計 / ...
```

#### エージェント C: 上位設計書整合性レビュー

```
description: 方式設計書整合性レビュー（{章名}）
subagent_type: app-impl-reviewer
model: opus

prompt:
あなたは上位設計書（フロントエンド方式設計書）整合性レビュー担当です。
詳細設計書 {対象パス} が、上位設計書 docs/02_アプリ基盤/01_フロントエンド/01_フロントエンド方式設計書/ の方針と整合しているかをレビューしてください。
コードの修正は行わず、レビュー結果のみを返してください。

## レビュー対象
- {対象パス} 配下の全 .md（規約・設計書・ADR）
- 比較先: docs/02_アプリ基盤/01_フロントエンド/01_フロントエンド方式設計書/ 配下の関連シート

## 関連シートの特定
章のテーマに応じて以下のいずれかのシートが該当する。該当シートを必ず読んで照合すること。

| 詳細設計書のテーマ | 関連する方式設計書シート |
|---|---|
| 状態管理 | sheet_11_【方式検討】状態管理方式.md |
| レンダリング | sheet_12_レンダリング方式の選定.md / sheet_13_レンダリング方式の比較資料.md |
| UIライブラリ・コンポーネント | sheet_14_【方式検討】React UIライブラリ.md |
| バリデーション | sheet_16_バリデーションについて.md |
| 自動テスト | sheet_18_自動テストについて.md |
| 通信・BFF | sheet_19_3.通信方針.md |
| セキュリティ・認証 | sheet_15_画面入力データやリクエストの改ざんについて.md / sheet_20_4.セキュリティ・アクセス統制.md |
| エラーハンドリング | sheet_21_5.エラー方針.md |
| 性能・パフォーマンス | sheet_22_6.性能・リソース設計.md |
| 運用・保守・ロギング | sheet_09_画面側の操作ログ管理について.md / sheet_23_7.運用・保守設計.md |
| 技術スタック・OSS選定 | sheet_10_【方式検討】技術スタック.md / sheet_08_主要OSS 技術健全性チェックリスト.md |
| 開発環境・Storybook 等 | sheet_17_【方式検討】隔離開発環境・ドキュメンテーションツール.md |
| 全体方針 | sheet_05_1.目的と基本方針.md / sheet_06_2.アーキテクチャと構成.md |

複数該当する場合はすべて読むこと。判別困難な場合は sheet_25_4.方式・設計書一覧.md と sheet_06_2.アーキテクチャと構成.md を起点に探索する。

## レビュー観点

### C1. 方針との不整合
- [ ] 詳細設計書の判断が、方式設計書で決定された方針に反していないか
  例: 方式で「Zustand 採用」と決まっているのに詳細で別ライブラリを使っていないか
- [ ] 方式設計書で禁止されている技術・パターンを詳細設計書で採用していないか

### C2. 用語・定義の整合
- [ ] 用語集（sheet_30_用語集.md）の定義と、詳細設計書での用語の使い方が一致しているか
- [ ] アーキテクチャ用語（Server Component / Client Component / Store / Hook 等）の意味付けが揃っているか

### C3. ライブラリ選定の整合
- [ ] 詳細設計書で名指ししているライブラリが、方式設計書の技術スタック（sheet_10）と一致しているか
- [ ] バージョン方針（メジャー固定・マイナー自動アップデート）に反する記述がないか

### C4. 上位方針の根拠リンク
- [ ] 詳細設計書の重要な判断について、方式設計書のどのセクションに紐づくかが追跡可能か
- [ ] ADR の「参考」または「背景」で方式設計書を引用しているか（必要な場合）

### C5. 方式設計書側の更新漏れ
- [ ] 詳細設計書で新たに導入した方針が、方式設計書に反映漏れになっていないか
  （詳細で追加された方針は、原則として方式設計書側にも記載が必要）

## 出力形式

# 上位設計書整合性レビュー結果

## 判定: PASS / FAIL

## 読んだ方式設計書シート
- {シートパス}: {一行サマリ}

## 問題一覧（FAIL時のみ）

### [No.X] タイトル
- 観点: C1 / C2 / C3 / C4 / C5
- 重要度: ブロッカー / 高 / 中
- 詳細設計書側: {パス} L{行番号} `{引用}`
- 方式設計書側: {パス} L{行番号} `{引用}`（または「記載なし」）
- 不整合の詳細:
- 修正提案:
  - 案①: 詳細設計書を修正する場合の内容
  - 案②: 方式設計書を修正する場合の内容（C5 に該当する場合）

## OK だった観点
- C1: 方針整合 / C2: 用語整合 / ...
```

### ステップ 2: 結果の統合

3エージェントの結果を以下の形式で統合してユーザーに提示する。

```markdown
# 詳細設計書 更新レビュー結果（{章名}）

## 総合判定
- ADR品質: PASS / FAIL
- 設計書品質: PASS / FAIL
- 上位整合性: PASS / FAIL
- **総合**: PASS（全PASS）/ FAIL（1つでもFAIL）

## サマリー
| 観点 | ブロッカー | 高 | 中 |
|---|---|---|---|
| ADR品質 | N | N | N |
| 設計書品質 | N | N | N |
| 上位整合性 | N | N | N |

## FAIL 項目一覧（重要度順）

### [A-No.X] {タイトル}
- 観点: ADR / 設計書 / 上位整合性
- 重要度: ブロッカー
- 対象: {パス} L{行番号}
- 問題: {1〜2行で要約}
- 修正提案: {具体的な修正内容}

（以下、重要度順に列挙）
```

### ステップ 3: FAIL 時の対応（修正提案 → ユーザー確認）

総合判定が FAIL の場合：

1. **問題ごとに修正提案を提示** する（上記出力に含まれる）
2. **ユーザーに採否を確認** する（一括採用 / 個別採否 / 全保留）

```
以下のレビューFAIL項目について、対応方針を選んでください:

[1] {問題タイトル}
  → 提案: {修正内容}
[2] ...

選択肢:
A. 全項目を提案通り修正する
B. 個別に判断する（番号指定）
C. 今は修正せず保留する（理由を記録）
```

3. ユーザーが採用と回答した項目のみ、メインエージェントが修正を実施
4. 修正後、**該当エージェントだけ再レビュー** （全並列再起動はしない）
5. PASS まで繰り返す

### ステップ 4: PASS 時の処理

総合判定が PASS の場合：
- レビュー結果を1行サマリでユーザーに通知（保存は不要）
- 必要に応じて該当章を含むコミットメッセージのドラフトを提示

---

## 各観点の重要度ガイド

### ブロッカー（即修正）
- ADR の必須セクション欠落
- 上位方針に明確に反する判断
- 双方向リンクの片側欠損
- ADR 一覧表との連番不一致

### 高（修正推奨）
- JSDoc の `@throws` 欠落
- シーケンス図の participant 名不統一
- 用語の不整合

### 中（任意修正）
- Do/Don't の例が不足
- 残件テーブルの整理漏れ
- 文体・語尾の揺れ

---

## アンチパターン

| やりがちなこと | 正しい対応 |
|---|---|
| 3エージェントを直列で起動する | **必ず単一メッセージで並列起動**（依存関係なし） |
| FAIL時に勝手に修正する | 修正提案を出して **ユーザー確認後** に修正 |
| 全観点まとめて1エージェントに投げる | 観点ごとに分けないと深さが落ちる。**3エージェント並列が必須** |
| 上位整合性を見ずに合格にする | sheet_11等の関連シートを **必ず照合**。「読まずに判定しない」 |
| 方式設計書を `develop_fix_docs` 以外から読む | ドキュメントは必ず `develop_fix_docs` を参照 |
| FAILを部分修正してすぐ全エージェント再実行 | **該当観点のエージェントのみ** 再起動。並列は初回のみ |
