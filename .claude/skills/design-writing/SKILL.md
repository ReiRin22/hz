# 設計書品質基準

このスキルは設計書の「書き方ガイド」である。テンプレートは `docs/templates/design.md`。

## いつ読むか

- `/design` コマンドの設計書作成・推敲時
- PRD完成後に読み込む（PRDの要件を技術的に実現する方法を書くため）

## 設計書の品質チェックリスト

### PRDとの整合性（最重要）

- [ ] PRDの全受入条件に対して、実現方法が書かれている
- [ ] PRDのスコープ外に含まれるものを設計に入れていない
- [ ] PRDの非機能要件を満たす設計になっている

### 技術方針

- [ ] なぜこの技術/パターンを選んだか理由がある
- [ ] 既存アーキテクチャとの整合性が説明されている
- [ ] 代替案を検討した形跡がある（重要な判断の場合）

### 異常系・境界

- [ ] APIのエラー契約が定義されている（エンドポイントがある場合）
- [ ] 入力の境界値に対する処理が定義されている
- [ ] 外部サービス障害時の振る舞いが定義されている（依存がある場合）

### 実装可能性

- [ ] ファイル構成が列挙されている（何をどこに作るか）
- [ ] データモデルが定義されている（該当する場合）
- [ ] テスト方針が記載されている（何をどうテストするか）

### 依存・影響

- [ ] 他機能への影響が記載されている
- [ ] 横断変更の場合、ADR番号が記載されている
- [ ] 未決定事項が残っていない（残っているならレビュー前に解消する）

### 条件付きセクション

- [ ] 機能の特性に対して必要な設計考慮が選定されている
- [ ] 不要な設計考慮が含まれていない（テンプレートにあるからと全展開しない）
- [ ] 各条件付きセクションが対応する `docs/core/` の規約と整合している
- [ ] データ設計: テーブル名だけでなくカラム・型・制約・インデックスまで定義されている
- [ ] API設計: エンドポイント + リクエスト/レスポンス例 + エラー契約が揃っている
- [ ] 外部連携: 障害時の振る舞い（タイムアウト・リトライ・フォールバック）が定義されている
- [ ] テンプレートにない設計考慮を追加した場合、同じフォーマット（`> 参照:` `> 条件:`）で書かれている

## アンチパターン

- PRDを書き直す → 設計書はHOWのみ。WHATを変えたいならPRDを修正する
- 実装の詳細（コード）を書く → 設計書は方針レベル。コードは実装フェーズ
- 1つのファイルに全コンポーネントの詳細を書く → 300行超えたら分割する
