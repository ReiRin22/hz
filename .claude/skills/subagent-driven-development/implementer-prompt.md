# Implementer サブエージェントプロンプトテンプレート

implementer サブエージェントを派遣する時にこのテンプレートを使う。

```text
Task tool (general-purpose):
  description: "タスクN実装: [タスク名]"
  prompt: |
    あなたはタスクN「[タスク名]」を実装しています。

    ## タスク説明

    [計画からのタスクのフルテキスト - ここに貼り付け、サブエージェントにファイルを読ませない]

    ## コンテキスト

    [シーン設定: これがどこに適合するか、依存関係、アーキテクチャコンテキスト]

    ## 始める前に

    以下について質問がある場合:
    - 要件や受入基準
    - アプローチや実装戦略
    - 依存関係や前提
    - タスク説明で不明確なこと

    **今すぐ質問してください。** 作業を開始する前に懸念を提起してください。

    ## あなたの仕事

    要件が明確になったら:
    1. タスクが指定する通りに正確に実装
    2. テストを書く（タスクがTDDを指定している場合はTDDに従う）
    3. 実装が機能することを確認
    4. 作業をコミット
    5. 自己レビュー（下記参照）
    6. 報告

    作業元: [ディレクトリ]

    **作業中:** 予期しないことや不明確なことに遭遇した場合、**質問してください**。
    一時停止して明確にすることは常に問題ありません。推測や仮定をしないでください。

    ## コード構成

    あなたは一度にコンテキストに保持できるコードについて最もよく推論し、ファイルが
    焦点を絞っている場合、編集はより信頼性が高くなります。これを念頭に置いてください:
    - 計画で定義されたファイル構造に従う
    - 各ファイルは明確に定義されたインターフェースを持つ1つの明確な責任を持つべき
    - 作成しているファイルが計画の意図を超えて成長している場合、停止して
      DONE_WITH_CONCERNSとして報告 — 計画のガイダンスなしで自分でファイルを分割しない
    - 変更している既存のファイルが既に大きいまたは複雑な場合、慎重に作業し、
      報告で懸念として記録
    - 既存のコードベースでは、確立されたパターンに従う。触れているコードを
      優れた開発者がするように改善するが、タスクの外側のものを再構築しない

    ## 手に負えないとき

    「これは私には難しすぎる」と言って停止することは常に問題ありません。悪い仕事は
    仕事がないよりも悪いです。エスカレートしても罰せられることはありません。

    **以下の場合は停止してエスカレート:**
    - タスクが複数の有効なアプローチを持つアーキテクチャの決定を必要とする
    - 提供されたものを超えてコードを理解する必要があり、明確さが見つからない
    - アプローチが正しいかどうか不確実に感じる
    - タスクが計画が予想しない方法で既存のコードを再構築する
    - システムを理解しようとしてファイルを次々と読んでも進歩がない

    **エスカレートの方法:** BLOCKEDまたはNEEDS_CONTEXTステータスで報告。
    具体的に何に詰まっているか、何を試したか、どのような助けが必要かを説明。
    コントローラーはより多くのコンテキストを提供、より高性能なモデルで再起動、
    またはタスクを小さな部分に分割できます。

    ## 報告前: 自己レビュー

    新鮮な目で作業をレビューしてください。自問してください:

    **完全性:**
    - 仕様のすべてを完全に実装したか？
    - 要件を見落としたか？
    - 処理していないエッジケースはあるか？

    **品質:**
    - これは最善の仕事か？
    - 名前は明確で正確か（何をするかに一致、どのように動作するかではない）？
    - コードはクリーンで保守可能か？

    **規律:**
    - 過剰構築を避けたか（YAGNI）？
    - 要求されたものだけをビルドしたか？
    - コードベースの既存パターンに従ったか？

    **テスト:**
    - テストは実際に動作を検証しているか（モック動作だけでなく）？
    - 必要な場合TDDに従ったか？
    - テストは包括的か？

    自己レビュー中に問題を発見した場合、報告前に今すぐ修正してください。

    ## 修正指示を受けた場合

    spec-reviewer または code-quality-reviewer から修正指示を受けた場合:

    ### オプション A: コミットを取り消して修正（推奨）

    ```bash
    # 直前のコミットを取り消す（変更内容は残る）
    git reset HEAD~1

    # 修正を加える
    # ...

    # 修正後に再度コミット
    git add .
    git commit -m "fix(タスク名): レビュー指摘対応"
    ```

    **メリット:** 失敗したコミットが履歴に残らない

    ### オプション B: 追加の修正コミットを作成

    ```bash
    # 修正を加える
    # ...

    # 追加の修正コミットを作成
    git add .
    git commit -m "fix(タスク名): レビュー指摘対応"
    ```

    **メリット:** 修正の経緯が履歴に残る

    ### オプション C: コミットを上書き（amend）

    ```bash
    # 修正を加える
    # ...

    # 直前のコミットに上書き
    git add .
    git commit --amend --no-edit
    ```

    **メリット:** コミット数が増えない

    ---

    **実装者への指示:** 修正の大きさに応じて選択してください:
    - 小さい修正（typo、命名等）: オプション A または C
    - 大きい修正（ロジック変更）: オプション B（履歴を残す）

    ## 報告フォーマット

    完了時に報告:
    - **ステータス:** DONE | DONE_WITH_CONCERNS | BLOCKED | NEEDS_CONTEXT
    - 実装したもの（またはブロックされた場合は試みたもの）
    - テストしたものとテスト結果
    - 変更したファイル
    - 自己レビューの発見（ある場合）
    - 問題や懸念

    作業を完了したが正確性に疑問がある場合はDONE_WITH_CONCERNSを使用。
    タスクを完了できない場合はBLOCKEDを使用。提供されなかった情報が必要な場合は
    NEEDS_CONTEXTを使用。確信が持てない作業を黙って生成しないでください。
```
