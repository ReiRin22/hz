# PoC品質基準

このファイルはPoCフェーズの「成果物の書き方ガイド」である。
`SKILL.md`（/poc コマンド）の各ステップで参照する。

---

## items.md の品質チェックリスト

### 合否基準（最重要）

- [ ] 各項目の合否基準が「測定可能」である（「動作すること」は不可）
- [ ] 数値目標がある場合、具体的な値が記載されている（例: 「p99 < 200ms」）
- [ ] 合否基準が実行結果に依存する場合、`[要実行確認]` と明記されている

### 網羅性

- [ ] 高優先度項目が「採用判断に必須」な検証のみに絞られている
- [ ] 「業界標準で確立済み」な項目が混入していない
- [ ] 方式設計書レビューで検出したTBD・曖昧記述の影響が反映されている

### 前提条件

- [ ] PoCを実施するために必要な環境・ツール・バージョンが記載されている
- [ ] 不明な前提は `[要確認: ...]` として残されている

---

## report.md の品質チェックリスト

### 設計への引き継ぎ（最重要）

- [ ] 「詳細設計への引き継ぎ事項」が `/design 02_アプリ基盤/` で即座に使えるレベルで書かれている
- [ ] 採用/不採用の判断理由が「なぜ」の観点で明確に記述されている
- [ ] 本実装で参照すべきPoCソースのファイル・目的が記載されている

### 完結性

- [ ] 未解決事項が残っている場合、詳細設計フェーズで解決する旨が明示されている
- [ ] 300行以内に収まっている

---

## state.md の管理ルール

### MUST（必須）

- 各ステップ完了時に `next_step` と `completed` を即座に更新する
- Gate（人間の判断）の結果を `decisions` に必ず記録する
- `notes` には「次のセッションのAIが知るべきこと」だけを書く

### NEVER（禁止）

- state.md を更新せずに次のステップへ進む
- `decisions` に「検討中」「未定」を残したまま先へ進む
- state.md の past entries を削除する（`completed` は追記専用）

---

## アンチパターン

- 合否基準を「〜できること」で終わらせる → 何をもって「できた」とするか数値・動作で定義する
- 実行せずに「合格」と判定する → 実行が必要な項目は必ず `[要実行確認]` とする
- report.md を result.md のコピーにする → report.md は「設計への引き継ぎ文書」であり、評価詳細ではない
- state.md を省略する → セッションをまたぐ作業で状態が失われる
