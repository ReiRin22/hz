# 計画の作成

## 概要

エンジニアがコードベースの文脈をゼロから持ち、疑わしいセンスを持っていると仮定して、包括的な実装計画を作成します。各タスクでどのファイルに触れるか、コード、テスト、確認が必要なドキュメント、テスト方法など、エンジニアが知る必要のあるすべてを文書化します。一口サイズのタスクとして全体の計画を提供します。DRY。YAGNI。TDD。頻繁なコミット。

エンジニアは熟練した開発者だが、ツールセットや問題領域についてはほとんど何も知らないと仮定します。優れたテスト設計についてもあまり知らないと仮定します。

**開始時のアナウンス:** 「writing-plans スキルを使用して実装計画を作成します。」

**文脈:** 分離された worktree で作業している場合は、実行時に `using-git-worktrees` スキルによって作成されているはずです。

**計画の保存先:** `.steering/実装中の機能/superpowers/plans/YYYY-MM-DD-<feature-name>.md`
- （計画の場所に対するユーザーの設定がこのデフォルトを上書きします）
- 「実装中の機能」部分は実際の機能フォルダ名（例: `YYYYMMDD-機能名`）に置き換えます

**Phase プランファイルの命名規則:**
- Phase 別に実装計画を作成する場合: `phase0-plan.md`, `phase1-plan.md`, `phase2-plan.md` などを使用
- この命名規則は `plan-progress-viewer` スキルの自動起動トリガーとなる

## スコープチェック

仕様が複数の独立したサブシステムをカバーする場合、ブレインストーミング中にサブプロジェクトの仕様に分割されているべきです。分割されていない場合は、これを個別の計画に分割することを提案します — サブシステムごとに1つ。各計画は、単独で動作し、テスト可能なソフトウェアを生成する必要があります。

## ファイル構造

タスクを定義する前に、作成または変更されるファイルと各ファイルの責任をマッピングします。ここで分解の決定が固定されます。

- 明確な境界と明確に定義されたインターフェースを持つユニットを設計します。各ファイルは1つの明確な責任を持つべきです。
- 一度にコンテキストに保持できるコードについて最もよく推論でき、ファイルが焦点を絞っている場合は編集がより信頼できます。多くのことを行う大きなファイルよりも、小さく焦点を絞ったファイルを優先します。
- 一緒に変更されるファイルは一緒に配置する必要があります。技術レイヤーではなく、責任で分割します。
- 既存のコードベースでは、確立されたパターンに従います。コードベースが大きなファイルを使用している場合は、一方的に再構成しないでください - ただし、変更しているファイルが扱いにくく成長している場合は、計画に分割を含めることが妥当です。

この構造はタスクの分解に情報を提供します。各タスクは、独立して意味をなす自己完結型の変更を生成する必要があります。

## 規約の遵守（Harz プロジェクト専用）

**計画作成前に規約を読み込み、計画内で規約を明示的に参照すること。**

### Phase ごとの規約ファイル

`.claude/commands/implement.md` または `.claude/commands/synchronizer.md` の「0-1. 規約ファイルの存在確認」セクションを参照して、対象 Phase の規約ファイル一覧を取得する。

**規約読み込み手順:**
1. `implement.md` または `synchronizer.md` から Phase の規約ファイル一覧を抽出
2. 各規約ファイルを `Read` で **全文** 読み込み（要約・部分読み禁止）
3. 規約から参照されている前提 I/F・基盤設計書も確認
4. 規約の重要なルール・構文・命名規則を抽出

**共通規約（全 Phase で確認）:**
- `.claude/rules/cross-layer-rules.md` — フロント・BFF・BE 横断ルール
- `.claude/rules/test-rules.md` — テスト設計ルール
- `.claude/commands/bff_structure.md` — BFF 構造ルール（synchronizer の場合）

### 計画への反映

**1. 計画の冒頭に規約セクションを追加:**

```markdown
## この Phase で参照する規約ファイル

| # | パス | 役割 |
|---|---|---|
| 1 | `docs/02_アプリ基盤/.../規約ファイル名.md` | 規約の役割（簡潔に） |
| 2 | `docs/02_アプリ基盤/.../規約ファイル名.md` | 規約の役割（簡潔に） |

**共通規約:**
- `.claude/rules/cross-layer-rules.md` — 型安全性・層の責務・環境変数
- `.claude/rules/test-rules.md` — テスト設計・モック・非同期テスト
```

**2. 各タスクに規約参照を明記:**

```markdown
### タスク N: [コンポーネント名]

**ファイル:**
- 作成: `exact/path/to/file.py`

**参照規約:**
- `規約ファイル名.md` の「## セクション名」

- [ ] **ステップ1: 規約を確認**

**参照**: `規約ファイル名.md` の「## セクション名」

```bash
# 規約の該当箇所を確認
grep -A 10 "## セクション名" docs/02_アプリ基盤/.../規約ファイル名.md
```

期待: [規約の重要な内容を引用]

- [ ] **ステップ2: 失敗するテストを書く**
...
```

**3. 規約の重要な内容を引用:**

実装コードを書くステップの前に、規約の構文・命名規則・禁止事項を具体的に引用する。

**例（コメントアウト構文）:**
```markdown
**規約引用（開発規律と品質管理規約）:**
```typescript
// =============================================================================
// SCOPE-OUT: 未実装機能（Phase 0 ではプレースホルダーのみ）
// =============================================================================
/*
// 将来実装する機能のコード
*/
```
```

**例（shared 昇格条件）:**
```markdown
**規約引用（フロントエンド・BFF共通基盤規約 - shared 昇格条件）:**
- 2機能以上で使用される
- ドメイン横断である
- BFF との型共有が必要
```

### 規約違反の防止

計画内の各タスクのコード例・実装ステップは、規約に準拠した形で記述すること。

**チェック項目:**
- [ ] ファイル配置が規約の許可フォルダ一覧に含まれているか
- [ ] 命名規則が規約のパターンに従っているか
- [ ] 禁止事項（`any` 型、`try-catch` 内の `redirect()` 等）を使用していないか
- [ ] 経由必須 I/F（axiosClient、storeRegistry 等）を使用しているか

## 一口サイズのタスク粒度

**各ステップは1つのアクション（2〜5分）:**
- 「失敗するテストを書く」 - ステップ
- 「失敗することを確認するために実行する」 - ステップ
- 「テストを通すための最小限のコードを実装する」 - ステップ
- 「テストを実行して通ることを確認する」 - ステップ
- 「コミット」 - ステップ

## 計画ドキュメントのヘッダー

**すべての計画はこのヘッダーで開始する必要があります:**

```markdown
# [機能名] 実装計画

> **エージェントワーカー向け:** 必須サブスキル: この計画をタスクごとに実装するには superpowers:subagent-driven-development（推奨）または superpowers:executing-plans を使用してください。ステップは追跡のためにチェックボックス（`- [ ]`）構文を使用します。

**目標:** [構築内容を説明する1文]

**アーキテクチャ:** [アプローチに関する2〜3文]

**技術スタック:** [主要な技術/ライブラリ]

---
```

## タスク構造

````markdown
### タスク N: [コンポーネント名]

**ファイル:**
- 作成: `exact/path/to/file.py`
- 変更: `exact/path/to/existing.py:123-145`
- テスト: `tests/exact/path/to/test.py`

- [ ] **ステップ1: 失敗するテストを書く**

```python
def test_specific_behavior():
    result = function(input)
    assert result == expected
```

- [ ] **ステップ2: テストを実行して失敗することを確認**

実行: `pytest tests/path/test.py::test_name -v`
期待: "function not defined" で FAIL

- [ ] **ステップ3: 最小限の実装を書く**

```python
def function(input):
    return expected
```

- [ ] **ステップ4: テストを実行して通ることを確認**

実行: `pytest tests/path/test.py::test_name -v`
期待: PASS

- [ ] **ステップ5: コミット**

```bash
git add tests/path/test.py src/path/file.py
git commit -m "feat: add specific feature"
```
````

## プレースホルダーなし

すべてのステップには、エンジニアが必要とする実際のコンテンツが含まれている必要があります。これらは**計画の失敗**です — 決して書かないでください:
- "TBD"、"TODO"、"後で実装"、"詳細を埋める"
- "適切なエラー処理を追加" / "バリデーションを追加" / "エッジケースを処理"
- "上記のテストを書く"（実際のテストコードなし）
- "タスクNと同様"（コードを繰り返す — エンジニアはタスクを順不同で読んでいる可能性がある）
- コードを示さずに何をすべきかを説明するステップ（コードステップにはコードブロックが必要）
- どのタスクでも定義されていない型、関数、またはメソッドへの参照

## 覚えておくこと
- 常に正確なファイルパス
- すべてのステップで完全なコード — ステップがコードを変更する場合は、コードを示す
- 期待される出力を含む正確なコマンド
- DRY、YAGNI、TDD、頻繁なコミット

## 自己レビュー

完全な計画を書いた後、新鮮な目で仕様を見て、計画を仕様に照らし合わせて確認します。これはあなた自身が実行するチェックリストです — サブエージェントの派遣ではありません。

**1. 仕様カバレッジ:** 仕様の各セクション/要件をざっと見ます。それを実装するタスクを指し示すことができますか? ギャップをリストアップします。

**2. プレースホルダースキャン:** 計画で警告フラグを検索します — 上記の「プレースホルダーなし」セクションのパターンのいずれか。修正します。

**3. 型の一貫性:** 後のタスクで使用した型、メソッドシグネチャ、プロパティ名は、以前のタスクで定義したものと一致していますか? タスク3で `clearLayers()` と呼ばれる関数がタスク7で `clearFullLayers()` になっているのはバグです。

**4. 規約準拠チェック（Harz プロジェクト専用）:** 計画内のすべてのタスクについて、以下を確認します:
- [ ] 計画の冒頭に「## この Phase で参照する規約ファイル」セクションがあるか
- [ ] 各タスクに「**参照規約:**」フィールドがあるか
- [ ] 規約確認ステップが実装ステップの前にあるか
- [ ] 規約の重要な内容（構文・命名規則・禁止事項）が引用されているか
- [ ] コード例が規約に準拠しているか（ファイル配置・命名・禁止パターン回避）

問題を見つけた場合は、インラインで修正します。再レビューの必要はありません — 修正して先に進みます。タスクのない仕様要件を見つけた場合は、タスクを追加します。

## 実行の引き継ぎ

計画を保存した後、**まず worktree 作成を提案し**、その後で実行の選択肢を提供します:

### ステップ1: Worktree 作成の提案

**"計画が完成し、`.steering/実装中の機能/superpowers/plans/<filename>.md` に保存されました。**

**実装を始める前に、isolated worktree のセットアップをお勧めします。現在のブランチを保護し、安全に作業できます。**

**Worktree をセットアップしますか？ (推奨)"**

**ユーザーが同意した場合:**
- **必須サブスキル:** using-git-worktrees を invoke する
- Worktree 作成完了後、次のステップ2へ進む

**ユーザーが拒否した場合:**
- 現在の作業ディレクトリで実行することを確認し、次のステップ2へ進む

### ステップ2: 実行オプションの提示

Worktree のセットアップ（または現在のディレクトリでの作業確認）が完了したら、実行の選択肢を提供します:

**"2つの実行オプション:**

**1. サブエージェント駆動（推奨）** - タスクごとに新しいサブエージェントを派遣し、タスク間でレビューし、迅速な反復

**2. インライン実行** - executing-plans を使用してこのセッションでタスクを実行し、チェックポイント付きのバッチ実行

**どちらのアプローチにしますか?"**

**サブエージェント駆動が選択された場合:**
- **必須サブスキル:** subagent-driven-development を使用する
- タスクごとに新しいサブエージェント + 2段階レビュー

**インライン実行が選択された場合:**
- **必須サブスキル:** executing-plans を使用する
- レビューのためのチェックポイント付きのバッチ実行
