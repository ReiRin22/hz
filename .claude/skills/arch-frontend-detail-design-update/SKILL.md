# 詳細設計書 更新ワークフロー

このスキルは、フォルダ型に構造化済みの詳細設計書章（例: `04_状態管理設計/`）に対して、新要件・仕様変更・設計判断の変化を正確に反映する手順を定義する。

## 構造化済み章のファイル構成

```
{XX}_{章名}/
  {章名}規約.md          ← アプリチームルール（Do/Don't・配置・命名）
  {モジュール}設計.md    ← 基盤実装 I/F仕様（1〜複数）
  adr/
    README.md            ← ADR一覧表・テンプレート
    {slug}.md            ← 個別の設計判断記録
```

---

## 更新の種類と対応表

| 更新内容 | 更新するファイル | ADR 必要？ |
|---|---|---|
| アプリチームのルール変更（命名・配置・Do/Don't） | `規約.md` | 不要（自明な修正の場合）/ 必要（廃止・大幅変更） |
| I/F の追加（新しい関数・型） | `{モジュール}設計.md` | 不要（既存方針の延長） |
| I/F の破壊的変更（引数・戻り値・挙動の変更） | `{モジュール}設計.md` + ADR | **必要** |
| 新しいモジュールの追加（新規 Store・新規フック等） | 新規 `{モジュール}設計.md` | 必要（なぜ分離するか） |
| 既存判断の見直し（ADR の覆し） | 新規 ADR + 旧 ADR のステータス更新 | **必要**（新 ADR を起こす） |
| バグ修正・誤記修正 | 該当ファイルのみ | 不要 |
| 残件の確定（TBD の解消） | 該当設計書 + 必要に応じて規約 | 状況次第 |

---

## ワークフロー

### ステップ 0: 変更種別の確認

```
Q0: ADR が制約を課している領域の変更か？
  → 必ずステップ 1 で既存 ADR を読んでから Q1 へ進む
  （変更種別は ADR を読まないと正確に判断できない）

Q1: 既存の判断（ADR）を覆す変更か？
  Yes → ステップ 4（ADR の更新）から先に着手する
  No  → Q2 へ

Q2: I/F の破壊的変更か？（引数・戻り値・型シグネチャの変更）
  Yes → ステップ 3（ADR 起票）を行ってから ステップ 2 へ
  No  → ステップ 2 へ直接
```

### ステップ 1: 対象ファイルの確認

変更前に必ず以下を読む。

```bash
# 章フォルダ全体の構造を確認
ls docs/.../02_詳細設計書/{XX}_{章名}/
ls docs/.../02_詳細設計書/{XX}_{章名}/adr/

# 変更対象ファイルの現在の内容を確認
# （特に I/F 定義・型定義の既存記述と整合させる）
```

#### 既存 ADR の読み込み（必須）

1. `adr/README.md` を読み、ADR 一覧表で **Accepted** ステータスの全 ADR を把握する
2. 各 ADR ファイルを読み、現在有効な設計制約（「このライブラリを使う」「この順序で実行する」「このアプローチは禁止」等）を洗い出す
3. 提案された変更が、これらの制約に **抵触しないか** をチェックする

> 抵触が見つかった場合: ステップ 0 の Q1（既存判断の覆し）に該当する。ステップ 4 から先に着手すること。

### ステップ 2: 設計書・規約の更新

#### 規約ファイルの更新

**追加**:
- ルールが増える場合は既存のセクション構成に従って追記
- 末尾の「責務サマリ表」を必ず更新

**変更・廃止**:
- 既存ルールを変える場合は、なぜ変えるかを確認しADRが必要か判断（ステップ 0 参照）

#### 基盤詳細設計ファイルの更新

**I/F の追加**:
```typescript
/**
 * {関数の概要を1行で}
 *
 * @param {引数名} - {説明}
 * @returns {戻り値の説明}
 * @throws {例外が起きる条件}
 *
 * @remarks
 * {非自明な挙動・順序制約・副作用があれば記述}
 */
export declare function {関数名}({引数}: {型}): {戻り値型}
```

**シーケンス図の追加・更新**:
- 追加する場合: 既存の `sequenceDiagram` ブロックを参照し、参加者（participant）の名前を統一する
- 更新する場合: フローの変更箇所のみ編集し、変更していない分岐は現状維持

**型定義の更新**:
- TypeScript 型の変更は I/F 破壊的変更に該当する → ADR を先に起票（ステップ 3）
- Store の State 型に追加する場合は、`LocalStorage キー一覧表`・`Store 一覧表` も一緒に更新する

### ステップ 3: ADR の起票（必要な場合）

#### 3-0. 起票前の情報収集チェック（必須）

ADR ファイルを作成する前に、以下の情報が揃っているかを確認する。**不足している場合は作業を止めてユーザーに確認する。**

| 必要な情報 | 確認内容 | 不足時の質問例 |
|---|---|---|
| **背景・課題** | なぜ今この変更が必要か。何が問題か | 「この変更の背景（何が問題で、なぜ今変える必要があるか）を教えてください」 |
| **検討した選択肢** | 他にどんな案を考えたか（最低1つ） | 「この方針以外に検討した代替案はありますか？」 |
| **採用理由** | なぜこの案を選んだか。他の案を却下した理由 | 「この案を選んだ理由と、他の案を採用しなかった理由を教えてください」 |
| **負の影響** | この判断のトレードオフ・リスク | 「この決定によるデメリットや将来の見直しが必要になる条件はありますか？」 |

> **なぜ確認が必要か**: ADR は「将来の開発者が判断を覆さないための防御線」。背景なしで書かれた ADR は読んでも理由が分からず、誤って変更されるリスクがある。

`{XX}_{章名}/adr/` に新しいファイルを作成する。

**ファイル名**: `{kebab-case-slug}.md`（既存ファイルと重複しないこと）

**連番の確認**:
```bash
# adr/README.md の「ADR 一覧」テーブルで現在の最大連番を確認
grep "ADR-" docs/.../adr/README.md | tail -5
```

**ADR ファイルの必須セクション**:
```markdown
# ADR-{連番}: {決定内容の要約}

* **ステータス**: Accepted
* **決定日**: {今日の日付}
* **関連設計書**: [{設計書名}](../{ファイル名}.md) §{セクション名}
* **関連 ADR**: {関連するADRがあればリンク、なければ「なし」}

## 背景
{何が課題か。前提条件・制約}

## 検討した選択肢
### 案A: ...
### 案B: ...

## 決定
{採用案と理由。否定した案が落ちた理由}

## 影響
### 正の影響
### 負の影響
### 見直しトリガー

## 参考
```

**ADR 起票後に必ずやること**:
1. `adr/README.md` の「ADR 一覧表」に新規行を追加
2. 関連する設計書に `> 根拠: [ADR-N](adr/{slug}.md)` の1行を追加（双方向リンク）

### ステップ 4: 既存 ADR の更新（判断の覆しの場合）

ADR は本文を書き換えず、新しい ADR を起こして旧 ADR のステータスを変更する。

```markdown
<!-- 旧 ADR の先頭を変更 -->
* **ステータス**: Superseded by [ADR-{新連番}](新slug.md)
```

新 ADR の「背景」セクションに、旧判断を覆した理由（状況変化・制約解除等）を明記する。

---

## 残件（TBD）の解消手順

設計書に `TBD`・`確定後に更新` 等が残っている箇所を解消する際。

1. **前提条件を確認**: 何の確定待ちだったかを読む（多くは認証基盤連携サービス詳細設計等の外部依存）
2. **確定内容を確認**: 確定した内容が記載された外部仕様書・議事録等を参照
3. **更新箇所の特定**: `grep -n "TBD\|確定後\|暫定" {対象ファイル}` で全箇所を列挙
4. **設計書を更新**: TBD を確定値に置き換え、コード例・表・シーケンス図を一致させる
5. **ADR 判断が必要か確認**: 複数案のうち1つに確定した場合は ADR を起票（ステップ 3）
6. **残件テーブルを削除**: 解消した行を「残件」テーブルから削除する（テーブルが空になった場合はセクションごと削除）

## 品質チェックリスト（更新後に確認）

### 設計書の一貫性
- [ ] 追加・変更した I/F の JSDoc が他の I/F と書き方が統一されている
- [ ] シーケンス図の participant 名が既存図と統一されている
- [ ] 追加した型定義が既存の State 型・LocalStorage キー一覧表と整合している

### ADR の双方向リンク
- [ ] 新規 ADR から設計書へのリンクがある
- [ ] 設計書から新規 ADR へのリンク（`> 根拠:` 行）がある
- [ ] `adr/README.md` の一覧表に新規行が追加されている

### 規約の整合性
- [ ] 設計書の変更がルールに影響する場合、規約ファイルも更新されている
- [ ] 末尾の「責務サマリ表」が現状の設計書構成と一致している

## 更新完了後の必須アクション

更新作業が完了したら、**必ず `arch-frontend-detail-design-review` スキルを呼び出して並列レビューを実施する**。
レビューが PASS するまで本作業の完了とみなさないこと。

```
更新対象: docs/02_アプリ基盤/01_フロントエンド/02_詳細設計書/{XX}_{章名}/
→ Skill: arch-frontend-detail-design-review を呼び出し
```

---

## アンチパターン

| やりがちなこと | 正しい対応 |
|---|---|
| ADR を覆す内容を既存 ADR に上書きする | 新 ADR を起こして旧 ADR のステータスを `Superseded by` に変更 |
| I/F 変更を設計書だけに書いてADR を起票しない | 破壊的変更は必ず ADR が必要。後から理由が分からなくなる |
| JSDoc を書かずに型定義だけ追加する | 引数・戻り値・throws・非自明な挙動は JSDoc で必ず記述 |
| TBD を解消したのに残件テーブルを残す | 解消した行を削除。テーブルが空なら §残件 セクションごと削除 |
| シーケンス図の participant 名を新しい関数名に合わせずに変更しない | 既存図の参加者名を確認して統一する |
