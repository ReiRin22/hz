# 判断ゲート（Decision Gate）プロトコル

人間に判断を委ねる際のルール。AIは判断ポイントに到達したら、
このプロトコルに従って人間に選択肢を提示する。

## いつ読むか

- 全コマンドのセッション開始時（暗黙的に適用）

## 原則

1. **AIは判断しない。選択肢を提示する。**
2. **選択肢は具体的に。** 「どうしますか？」ではなく「A, B, Cのどれにしますか？」
3. **推奨を示す。** 最初の選択肢に `(推奨)` をつける
4. **判断を飛ばさない。** ゲートを通過せずに次のステップに進んではいけない

## 判断ゲートの種類

### Gate: SCOPE — スコープ確認

**タイミング**: 作業開始時、要件が固まった直後
**目的**: 何を作る/直すかの範囲を確定する

```
提示形式:
  header: "スコープ"
  question: "以下のスコープで進めてよいですか？"
  options:
    - "このスコープでOK (推奨)"
    - "スコープを広げたい"
    - "スコープを絞りたい"
  multiSelect: false
```

### Gate: APPROACH — 方針選択

**タイミング**: 複数の技術的アプローチが存在するとき
**目的**: 実装方針・設計方針を決定する

```
提示形式:
  header: "方針"
  question: "どのアプローチで進めますか？"
  options:
    - "{推奨案の概要} (推奨)"  ← 理由を description に記載
    - "{代替案1の概要}"         ← トレードオフを description に記載
    - "{代替案2の概要}"         ← トレードオフを description に記載
  multiSelect: false
```

### Gate: CONFIRM — ドラフト承認

**タイミング**: サブエージェントがドラフトを作成した後
**目的**: 作成物の品質を確認し、次のステップへ進むか判断する

```
提示形式:
  header: "承認"
  question: "ドラフトを確認してください。どうしますか？"
  options:
    - "承認して次へ進む"
    - "修正指示を出す"
    - "最初からやり直す"
  multiSelect: false
```

### Gate: RESOLVE — 未決定事項の解決

**タイミング**: ドラフト内に `[要確認]` `{{要決定}}` がある場合
**目的**: AIが勝手に決められない事項を人間が決定する

```
提示形式:
  question ごとに1つの未決定事項を解決する。
  複数の未決定事項がある場合は、まとめて提示してよい（multiSelect対応）。

  header: "要決定"
  question: "{未決定事項の内容}?"
  options:
    - "{選択肢A} (推奨)"
    - "{選択肢B}"
    - "{選択肢C}"
  multiSelect: false（排他的選択の場合） / true（複数選択可の場合）
```

### Gate: PHASE — フェーズ遷移

**タイミング**: レビューPASS後、次のフェーズへ進む前
**目的**: フェーズの切り替えを人間が明示的に承認する

```
提示形式:
  header: "次のフェーズ"
  question: "レビューがPASSしました。次のステップは？"
  options:
    - "{次フェーズへのアクション} (推奨)"  ← 例: /review に進む / /implement に進む
    - "追加の修正をする"
    - "一旦保留して別の機能へ"
  multiSelect: false
```

### Gate: ESCALATE — 想定外の事態

**タイミング**: 実装中に仕様外の問題が見つかった、影響が想定以上に大きいなど
**目的**: 続行するか中断するかを人間が判断する

```
提示形式:
  header: "確認"
  question: "{問題の概要}。どうしますか？"
  options:
    - "このまま続行する"
    - "/design に戻って仕様を修正する"
    - "作業を中断して相談する"
  multiSelect: false
```

## 各コマンドの判断ゲート一覧

### /init

| ステップ | ゲート | 内容 |
|---------|--------|------|
| 1. プロダクト概要ドラフト後 | CONFIRM | プロダクト概要の承認 |

### /design（機能設計）

| ステップ | ゲート | 内容 |
|---------|--------|------|
| 1. ヒアリング後 | SCOPE | スコープの確定 |
| 3. 調査結果提示後 | APPROACH | ドメイン配置・設計方針の選択 |
| 5. PRDドラフト後 | RESOLVE | `[要確認]` の解決 |
| 5. PRDドラフト後 | CONFIRM | PRDの承認 |
| 7. 設計書ドラフト後 | RESOLVE | `[要確認]` の解決 |
| 7. 設計書ドラフト後 | APPROACH | 技術選択（複数案がある場合） |
| 7. 設計書ドラフト後 | CONFIRM | 設計書の承認 |
| 9. 検証後 | PHASE | /review に進むか |

### /implement

| ステップ | ゲート | 内容 |
|---------|--------|------|
| 2. タスク分解後 | CONFIRM | タスクリストの承認 |
| 実装中（仕様外の問題発生時） | ESCALATE | 設計書の範囲を超える変更が必要になった場合 |
| 完了時 | PHASE | /review に進むか |

### /fix

| ステップ | ゲート | 内容 |
|---------|--------|------|
| 2. 原因分析後 | APPROACH | 修正方針の選択 |
| 2. 原因分析後 | SCOPE | 影響範囲の確認（広い場合） |
| 5. 修正後 | PHASE | /review に進むか |

### /review

| ステップ | ゲート | 内容 |
|---------|--------|------|
| 3. 判定後（PASS） | PHASE | 次のフェーズへ進むか |
| 3. 判定後（FAIL） | APPROACH | どの指摘から対応するか |

## 実装ルール（AI向け）

### AskUserQuestion の使い方

```
AskUserQuestion:
  questions:
    - header: "{ゲート種別に対応する短いラベル}"    # 最大12文字
      question: "{具体的な質問文}"
      options:
        - label: "{選択肢テキスト}"
          description: "{補足説明・トレードオフ}"
        - label: "{選択肢テキスト}"
          description: "{補足説明}"
      multiSelect: false | true
```

### 必須ルール

- 推奨選択肢は **常に最初** に置き、ラベルに `(推奨)` をつける
- description にはAIの分析結果・理由を記載する（人間が判断するための材料）
- 選択肢は **2〜4個**。5個以上は情報過多
- 判断に必要な **コンテキストを質問文の前に提示** してから質問する
- 人間が「Other」を選んだ場合、追加のヒアリングを行う

### やってはいけないこと

- ゲートを飛ばして先に進む
- 「特に問題なさそうなので進めました」と事後報告する
- 選択肢なしで「どうしますか？」と聞く
- 同じゲートを何度もリトライする（人間が選んだら従う）
- 設計書どおりの通常実装前にユーザー承認を求める（Gate 以外での確認待ちは禁止）
