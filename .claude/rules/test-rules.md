# テストルール

ユニットテスト・統合テスト・E2E テストの禁止事項と整合性チェックルール。
implement フェーズの各 Phase-test スキル実行時、および E2E テスト（Phase 8）の前後に参照すること。

---

## 禁止事項

### テスト設計

- 実装詳細のテスト禁止 — 内部状態・プライベート関数を直接テストしない。振る舞いをテストする
- 1テストケースで複数の振る舞いを検証することを禁止 — 1 test = 1 assertion の原則
- スナップショットテストの多用禁止 — 「何が変わったか」が不明になる。UI 構造変更の追跡目的のみ許可
- **実装ファイルを読んでテストを書くことを禁止** — 実装ベースのテストは未実装仕様を見落とし、実装のバグを追認する。テストは必ず設計書（仕様書・PRD）を根拠に作成すること

### モック

- `any` を使ったモック型の握りつぶし禁止 — モックも正確な型で定義する
- `repository/` や `hooks/` をモックしてテストすることを禁止 — `api/` 関数層のみモック可
  - NG: `jest.mock('../hooks/useSaveSchema')`
  - OK: `jest.mock('../api/postSchema.api')`
- ユニットテストで実 BFF を呼び出すことを禁止 — MSW または `jest.mock` で必ずインターセプト

### 非同期テスト

- タイムアウト設定なしの `waitFor` 使用禁止 — 無限ループのリスクがある
  - OK: `await waitFor(() => ..., { timeout: 3000 })`

### ファイル命名

- `*.spec.*` 拡張子禁止 — `*.test.ts` / `*.test.tsx` に統一する

## 整合性チェックルール

### PRD 受入条件カバレッジ（テスト計画時）

test-planner が生成したテストケース一覧と、PRD の受入条件が 1 対 1 で対応しているか確認する。

- [ ] PRD の受入条件に対応するテストケースが全て存在するか
- [ ] テストケースが「正常系」「異常系（バリデーション失敗）」「エラー系（API 500）」を含んでいるか

### E2E テスト必須カバレッジ（Phase 8）

以下の2カテゴリは必須。カバーされていない場合は Phase 8 を完了とみなさない。

| カテゴリ | 内容 |
|---|---|
| **golden path** | 正常な操作フローが画面の最初から最後まで通ること |
| **エラー境界** | バリデーション失敗・API 500 発生時に適切なメッセージが表示されること |

### Phase-test との関係

Phase-test スキル（implement-phase2-test 等）は「型整合性・カバレッジの静的確認」を行う。
このファイルのルールは「テストコード自体の品質確認」であり、対象が異なる。両方を実施すること。
