# PoC Item Extractor サブエージェント

方式設計書（Markdownに変換済み）からPoC項目を抽出・整理する。

## 役割

- 調査（読み取り専用）
- ファイルを1本書き出す: `docs/02_アプリ基盤/{target}/00_計画書/{target}PoC開発計画.md`

## 起動方法

```
Task tool:
  subagent_type: "general-purpose"
  description: "PoC item extraction for {target}"
  prompt: 下記のプロンプトテンプレート
```

## プロンプトテンプレート

```
以下の方式設計書をもとに、PoC項目の洗い出しと設計書レビューを行ってください。

対象: {target}
方式設計書: docs/02_アプリ基盤/{target}/00_方式設計書/ 配下の全ファイル（.md / .htm / .html）を全て読む。Word HTML形式（.htm）の場合はHTMLとして解釈する
出力先: docs/02_アプリ基盤/{target}/00_計画書/{target}PoC開発計画.md

## タスク1: 方式設計書レビュー

方式設計書を読み、以下の観点で不足・不明箇所を洗い出す。
PoC項目の抽出に先立って実施し、不足があれば PoC開発計画.md に記録する。

チェック観点:
- **必須セクションの有無**: 目的・対象範囲・技術選定理由・アーキテクチャ概要・
  前提条件・制約・非機能要件（性能・セキュリティ・可用性）・運用考慮・リスク
- **TBD・未決事項**: `TBD` `TODO` `要検討` `未定` 等の記載
- **曖昧な記述**: 「〜程度」「〜想定」など、合否基準を設定できない表現
- **前提条件の不足**: PoCを実施する上で必要な環境・バージョン・依存関係が不明

## タスク2: PoC項目の抽出

PoC項目として抽出すべきもの:
- 技術の採用可否を判断するために実際に動作確認が必要な項目
- このプロジェクトの要件（パフォーマンス・セキュリティ・スケーラビリティなど）に照らして検証が必要な項目
- 既存の実績が少なく、統合リスクの高い技術要素
- **アーキテクチャの長期運用性**: 採用するアーキテクチャ（レイヤードアーキテクチャ等）のフォルダ構成・レイヤー分離が、機能追加・変更時に既存コードへの影響を最小化できるか。依存方向ルールが実装上も遵守できる構造かを検証する

抽出不要なもの:
- すでに業界標準として確立されており検証不要な項目
- 設計書だけで判断できる（PoC不要の）項目

`docs/02_アプリ基盤/{target}/00_計画書/{target}PoC開発計画.md` を以下の形式で作成する:

---
# {target} PoC開発計画

| | |
|---|---|
| 対象コンポーネント | {target} |
| 作成日 | {今日の日付} |
| 方式設計書 | docs/02_アプリ基盤/{target}/00_方式設計書/ |

## フェーズ構成

### フェーズ0: TBD解消（PoC開始前）

| タスク | 担当 | 工数見積 | 完了定義 |
|--------|------|----------|----------|
| 影響ありTBDの確認・方針決定 | 人間 | - | 影響ありTBDが全て解消またはスキップ決定されていること |

### フェーズ1: 検証環境構築

| タスク | 担当 | 工数見積 | 完了定義 |
|--------|------|----------|----------|
| {各項目に必要な環境のセットアップ（Docker等）} | 人間 | - | 検証用環境が起動できること |

### フェーズ2: PoC実施（項目別ミニサイクル）

各PoC項目を1件ずつ以下のミニサイクルで進める。詳細は `docs/02_アプリ基盤/{target}/03_PoC検証/item_NN_{略称}.md` を参照。

| # | 項目名 | 優先度 | 工数見積（実装） | 工数見積（実行） |
|---|-------|--------|----------------|----------------|
| {番号} | {項目名} | {高/中/低} | - | - |

#### 各項目の共通作業フロー

| ステップ | 内容 | 担当 | 完了定義 |
|--------|------|------|---------|
| 3-A | 実装計画作成 | AI | item_NN.md の実装計画が承認されること |
| 3-B | 実装 | AI | `sample/{target}/NN_*/` のコードが完成していること |
| 3-C | 実行 | 人間 | item_NN.md の「実行結果」セクションが記入されていること |
| 3-D | 評価 | AI | item_NN.md の「合否判定」セクションが記入されていること |

### フェーズ3: 評価・報告

| タスク | 担当 | 工数見積 | 完了定義 |
|--------|------|----------|----------|
| 総合評価 | AI | - | `03_PoC検証/result.md` が作成されていること |
| 報告書作成 | AI | - | `03_PoC検証/report.md` が作成されていること |
| 報告書承認 | 人間 | - | 報告書が承認されていること |

## 注意

- 合否基準は具体的かつ測定可能な形で記述する（「動作すること」は不可）
- 設計書の不足を理由にPoC項目の抽出を止めない。不明な箇所は `[要確認: ...]` として残す
```

## 出力

指定された出力先にファイルを書き出す。
以下を報告する:
- 方式設計書レビュー: 不足セクション数・TBD件数・曖昧記述件数
- PoC項目: 抽出件数と優先度の内訳
