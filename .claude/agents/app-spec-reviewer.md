# Spec Reviewer サブエージェント

`docs/01_アプリ` 配下の設計書をレビューするときに使う。`/review` コマンドから呼び出される。

## 役割

- 検証（読み取り専用）
- ファイルの変更はしない

## 起動方法

```
Task tool:
  subagent_type: "general-purpose"
  description: "Spec review for {対象パス}"
  prompt: 下記のプロンプトテンプレート
```

## プロンプトテンプレート

```
以下のファイルを読み、品質をレビューしてください。

対象: {ファイルパスリスト}
レイヤー: {フロントエンド | BFF | バックエンド | 複数}
調査MDディレクトリ: {.steering/YYYYMMDD-機能名/ | なし}

## 事前準備

### Step0: 調査MDの読み込み（調査MDディレクトリが「なし」の場合はスキップ）

以下のファイルが存在すれば Read して内容を把握してからレビューを開始する。

- `{調査MDディレクトリ}/research-codebase.md` — 既存コードの型定義・パターン
- `{調査MDディレクトリ}/research-cross-check.md` — 既存仕様との競合・依存関係

把握した内容は以下の追加チェックに使う：
- 設計書で定義した型・パターンが `research-codebase.md` の既存パターンと整合しているか
- `research-cross-check.md` で検出された競合が設計書で `[要確認]` として明示されているか、または解消されているか

## チェック項目

### PRD (prd.md)
- [ ] 概要が1〜3文で書かれているか
- [ ] ユーザーストーリーが存在するか
- [ ] 受入条件が全て「測定可能」か（数値・状態・有無で判定できる）
- [ ] 異常系・境界ケースが定義されているか
- [ ] スコープ外が明記されているか
- [ ] 曖昧語（適切、十分、なるべく等）が使われていないか
- [ ] 300行以内か

### 設計書 共通 (design.md)
- [ ] PRDの全受入条件に対して実現方法が書かれているか
- [ ] 技術方針が明記されているか
- [ ] ファイル構成が列挙されているか
- [ ] テスト方針が記載されているか
- [ ] 依存・影響が記載されているか
- [ ] 未決定事項が残っていないか
- [ ] 300行以内か

### フロントエンド詳細設計書（レイヤー = フロントエンドの場合）
- [ ] 複数テーブル（表示項目/入力制御/状態変数一覧）間で同一UI要素の記述が一致しているか
- [ ] モード制御の影響が全ボタン・全フィールドに明示されているか
- [ ] 表示条件・表示制御で状態変数名を使い直接値を使っていないか
- [ ] エラーフロー（ボタン押下の失敗分岐）にエラー表示設計テーブルのコードが対応しているか
- [ ] UI項目IDプレフィックス・フォーマット・コンポーネント種別が一致しているか
- [ ] 必須フィールドの未入力時動作（非活性・エラー表示）が定義されているか
- [ ] 遷移先（または「画面クローズ」）が明記されているか
- [ ] 監査ログ対象のボタン/イベントにアクションIDが対応しているか
- [ ] 条件付きセクションの選定が妥当か

### BFF詳細設計書（レイヤー = BFF の場合）
- [ ] エンドポイント・メソッド・パスが明記されているか
- [ ] リクエスト/レスポンスのフィールド名・型・必須/任意が定義されているか
- [ ] エラーレスポンス（エラーコード・HTTPステータス）が網羅されているか
- [ ] バックエンド呼び出しの責務範囲が明確か（BFF固有ロジックと委譲ロジックの区別）
- [ ] 認証・認可の扱いが記載されているか
- [ ] Upstream*型が `*.type.ts` に定義されているか（`*.clients.ts` 内への直接定義なし）
- [ ] 日付・コード値・IDフィールドに `.regex()` / `.datetime()` 等の形式バリデーションがあるか
- [ ] 条件付きセクションの選定が妥当か

### バックエンド詳細設計書（レイヤー = バックエンドの場合）
- [ ] API設計にエラー契約があるか
- [ ] DBスキーマ変更が伴う場合、マイグレーション方針が記載されているか
- [ ] トランザクション境界が明示されているか
- [ ] 排他制御・冪等性への言及があるか（必要な場合）
- [ ] 条件付きセクションの選定が妥当か

## 出力形式

判定: PASS | FAIL

High / Medium / Low に分類して指摘を列挙する。
High が1件でもあれば FAIL。

| 重要度 | 対象ファイル | 指摘内容 |
|--------|------------|---------|
```
