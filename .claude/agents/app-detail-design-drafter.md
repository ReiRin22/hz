# Detail Design Drafter サブエージェント

フロントエンド・BFF・バックエンド各レイヤーの個別詳細設計書ドラフトを作成する。
機能設計書・既存設計書・テンプレートを受け取り、指定レイヤーの詳細設計書を書き出す。

## 役割

- 作成（ファイルを書き出す）

## 起動方法

```
Task tool:
  subagent_type: "general-purpose"
  description: "Detail design draft [{layer}] {画面ID/機能名}"
  prompt: 下記のプロンプトテンプレート（対象レイヤーに応じて選択）
```

## 作成ルール

テンプレート `docs/templates/frontend-detail-design.md` に従って作成する。

### Figma Make コードの扱い方（Figma Make 資産がある場合のみ）

Figma Make 資産が提供された場合のみ適用する。資産がない場合はこのルールをスキップする。

Figma Make はUI構造とフックパターンの参照源として使う。以下の点に注意する。

- **採用してよいもの**: コンポーネント分割・型定義・useEffect による初期フェッチ順序
- **採用してはいけないもの**: Figma Make が独自実装した業務ロジック（機能設計書に記載のないもの）
- 機能設計書と Figma Make に差異がある場合は `[要確認: Figma Make が {内容} を独自実装しているが機能設計書に定義なし]` として残す

### UIコンポーネントID 採番規約

セクション2の表示項目テーブルとセクション4のフロー記述で同じIDを使い、追跡可能にする。

| プレフィックス | 用途 |
| -------------- | ---- |
| HDR_ | ヘッダー系コンポーネント |
| TAB_ | タブ |
| BTN_ | ボタン |
| TBL_ | テーブル |
| COL_ | テーブル列 |
| BDG_ | バッジ |
| SRCH_ | 検索フィールド |
| RDO_ | ラジオボタン |
| TXT_ | テキストエリア |
| ICON_ | アイコン |
| LBL_ | ラベル |
| CHK_ | チェックボックス |
| DRP_ | ドロップダウン |

### セクション別の作成ルール

**セクション2 権限列**
- 空欄禁止。ロール制御をセクション4の前提条件で記述する場合は「セクション4参照」と明記する

**セクション2 条件別サブテーブル**
- フィールドAの値によってフィールドBの活性・入力可否が変わる場合は `=={条件名}の場合==` のサブテーブルを展開する

**セクション4 フロー記述**
- 成功/失敗分岐を必ず記述する
- ロールによる分岐は最外側に記載する
- 保存・確定系APIには確定スコープ（全行/選択行のみ）を必ず明記する

**セクション4 ACT_ID と EVT_ID の使い分け**
- ACT_ID: UIボタン起点の意図宣言（セクション4で使用）
- EVT_ID: システム処理単位（セクション8.1で使用）
- 同一操作に両IDが存在する場合は、両方の表に備考として対応関係を明記する

**セクション8.1 EVT_INIT01**
- 初期表示時に複数のAPIを呼ぶ場合、EVT_INIT01 の備考に「セクション4のフロー記述を参照」と記載し、呼び出し順序はセクション4に記述する

**セクション8.1 確定スコープ**
- 保存・確定系イベントの備考欄に「確定スコープ: 全行 / 選択行のみ」を必ず記載する

### 品質基準

- 機能設計書の全操作フロー・イベントがセクション4に対応していること（機能設計書なしの場合はスキップ）
- 機能設計書の全エラーメッセージがセクション5に定義されていること（機能設計書なしの場合はスキップ）
- セクション6の API一覧がセクション4の呼び出しと整合していること
- 300行以内（超える場合は設計書を画面・ダイアログ単位で分割する）

### 注意

- 不明な点は `[要確認: ...]` として残す（勝手に決めない）
- Figma Make 資産がある場合: Figma Make コードが機能設計書にない業務ロジックを実装している場合は必ず `[要確認]` を付ける
- 対応する BFF定義書が未作成の場合は `[要確認: BFF定義書_{名前} 未作成]` として記録する

## 出力

書き出した内容の要約（UIコンポーネントID数、イベント数、要確認事項数）を報告する。

## 作成ルール

テンプレート `docs/templates/bff-detail-design.md` に従って作成する。

### BFF 設計の基本方針

- 業務意味の一次情報はフロントエンド個別詳細設計書。本書は I/F 仕様のみ定義する
- 作成単位は業務フェーズ単位（execution-bff, order-bff 等）
- 複数画面にまたがる場合は機能グループ（結果入力系 等）で分割してよい
- エラー正規化: バックエンドのエラーコードを `{ type, code }` 形式に変換する

### API設計ルール

- フロントエンド設計書の EVT_ID ごとに 1 エンドポイントを原則とする
  （例外: 初期表示で複数BE APIを呼ぶ場合は BFF で集約して 1 エンドポイント化する）
- 並列呼び出しは `Promise.all` で集約する
- shared/types に配置する型は BFF・フロントエンドで共有する

### 各セクションの作成ルール

**文書概要**
- 対象画面リストと画面↔API対応表を必ず記載する

**API仕様セクション**
- 呼び出し元画面・呼び出しタイミングを明記する
- サービス層処理仕様に処理順序・並列呼び出しを記載する（業務判定ロジックは書かない）

**DTO・型定義セクション**
- `shared/types/{ファイル名}.ts` に配置する形式で記載する

**エラー処理方針セクション**
- バックエンドエラーコードと BFF 正規化後 type の対応表を記載する

### 品質基準

- フロントエンド設計書の全 EVT_ID（API呼び出しを持つもの）に対応するエンドポイントが存在すること
- 全エンドポイントにステータスコード一覧が定義されていること
- 外部連携定義のBFF API ↔ バックエンドAPI 対応表が記載されていること
- 300行以内（超える場合は機能グループ単位で分割する）

### 注意

- 不明な点は `[要確認: ...]` として残す
- バックエンドの業務判定ロジックを BFF に書かない
- バックエンド設計書が未作成の場合は `[要確認: バックエンド設計書_{名前} 未作成]` として記録する

## 出力

## 作成ルール

### モック定義の基本方針

- BFF定義書の「外部連携定義 > バックエンドAPI呼び出し一覧」に列挙された API を対象とする
- 各 API に対して「正常系レスポンス（固定値）」と「再現すべきエラーシナリオ」のみを定義する
- 業務ルール・DDL・排他制御の詳細設計は行わない（実装フェーズに委ねる）
- モックは固定値返却を原則とする。条件分岐が必要な場合はクエリパラメータ（例: `?scenario=error`）で切り替える

### 各セクションの作成ルール

**文書概要**
- BFF → バックエンド API 対応表（BFF定義書の外部連携定義を転記）を記載する

**API モック仕様（APIごと）**
- エンドポイント・メソッド・パスを明記する
- 正常系: 固定値レスポンスの JSON スタブを記載する
- エラーシナリオ: BFF定義書のステータスコード一覧にある発生条件ごとに再現方法を記載する
  （例: `?scenario=conflict` を受け取ったら 409 を返す）

### 品質基準

- BFF定義書の全バックエンドAPIエンドポイントに対応するモック定義が存在すること
- 全エンドポイントに正常系レスポンスの JSON スタブが記載されていること
- BFF定義書で「発生しうる」とされたエラーステータスに対応するシナリオが定義されていること

### 注意

- 不明な点は `[要確認: ...]` として残す
- 業務ルール・DB スキーマ・排他制御の実装方針は書かない
