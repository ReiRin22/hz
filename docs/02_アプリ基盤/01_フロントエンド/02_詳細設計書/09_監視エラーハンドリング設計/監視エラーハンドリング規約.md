# 監視・エラーハンドリング規約

フロントエンド基盤が提供するエラー監視（GlitchTip）・Error Boundary・エラーモーダル・エラー分類ユーティリティの上で **アプリ実装チームが守るべき規約** を定義する。

| [BFFエラーレスポンス設計.md](BFFエラーレスポンス設計.md) | RFC 9457 ベースのレスポンス構造・`errors[].code` 一覧・Zod 変換ルール |

## 1. 本章の対象範囲

本章は「エラーが起きたとき何が起きたかを知る」ことに特化する。

| 観点 | 本章（09章） | 14章 操作・監査ログ基盤 | 15章 運用監視基盤 |
|---|---|---|---|
| 目的 | 障害の即時検知・原因特定・開発者通知 | 操作証跡・コンプライアンス対応 | 性能劣化・インフラ異常の予兆検知 |
| 発動条件 | エラー発生時（リアクティブ） | ユーザー操作時（常時） | 常時 |
| 利用者 | 開発者・運用担当者 | 監査部門・法務・システム管理者 | SRE・インフラ・開発者 |
| 主なツール | GlitchTip（Sentry互換OSS） | axiosClient → BFF → 監査ログ管理 | - |

**重要な区別**:
- **Breadcrumbs（本章）**: エラー発生時に GlitchTip イベントへ添付される「エラー直前の操作履歴」。開発調査用であり、法的証拠ではない
- **操作ログ（14章）**: 全操作を常時記録する業務証跡。監査証跡として長期保存

## 2. 基盤 I/F 利用規約（最重要）

> 基盤が提供する I/F を **経由しない実装は禁止する**。バイパス実装は PHI 漏洩・エラー検知漏れ・誤った業務エラー送信によるノイズ増大を引き起こす。

### 2.1 必ず経由する I/F とバイパス禁止 API

| 用途 | ✅ 経由必須 I/F | ⛔ バイパス禁止 | 詳細 |
|---|---|---|---|
| 例外送信 | `Sentry.captureException(error)`（基盤の `axiosClient` Interceptor / `error.tsx` 内が代行） | アプリコードからの直接 `Sentry.captureException` 呼び出し、`console.error` で済ませる | [GlitchTip連携設計.md](GlitchTip連携設計.md) §3 |
| エラー種別判定 | `errorClassifier(error)` | HTTP ステータス・`error.name` のアドホック分岐 | [エラー処理基盤設計.md](エラー処理基盤設計.md) §5 |
| 重度エラーのモーダル表示 | `ErrorModal` コンポーネント | 独自モーダル実装 | [エラー処理基盤設計.md](エラー処理基盤設計.md) §6.2 |
| コンポーネント単位の Error Boundary | `ErrorGuard` コンポーネント | `react-error-boundary` の `ErrorBoundary` 直接利用、独自 class component | [エラー処理基盤設計.md](エラー処理基盤設計.md) §6.1 |
| グローバル Error Boundary | Next.js の `app/error.tsx`（基盤提供パターン） | 階層的 Error Boundary の独自実装 | [エラー処理基盤設計.md](エラー処理基盤設計.md) §4、[adr/global-error-boundary-only.md](adr/global-error-boundary-only.md) |
| BFF エラーの取り扱い | `error.response.data.errors[]` を `errors[].code` で分岐 | フロント独自エラーコード体系を BFF に強要 | [BFFエラーレスポンス設計.md](BFFエラーレスポンス設計.md) §4 |
| PHI を含む可能性のあるデータの送信 | 基盤が `beforeSend` フックで `cookies` / `headers` / `email` を自動削除 | アプリコードで `Sentry.setExtra` 等に PHI を含めて送信 | [GlitchTip連携設計.md](GlitchTip連携設計.md) §4 |

### 2.2 例外

| ケース | 条件 |
|---|---|
| プロトタイプ・検証コード | 本番投入前に基盤 I/F 経由へ移すこと |
| 基盤チームによる基盤実装 | 本規約の対象外（基盤 I/F の実装側） |

### 2.3 PR レビュー観点

| 観点 | チェック内容 |
|---|---|
| 直接 Sentry 呼び出し | アプリコード（`features/**`）に `Sentry.captureException` / `Sentry.captureMessage` の直接呼び出しが無いか |
| console.error で済ませている | `catch (error)` 内に `console.error` のみで、業務エラー以外の伝播・通知が無い箇所が無いか |
| 業務エラーの誤送信 | 業務エラー判定（`status===400 && code∈{REQUIRED, INVALID_FORMAT, INVALID_TYPE}`）をバイパスして送信していないか |
| アドホック分岐 | `error.response?.status === 401` のような直接判定が hooks／Organism にないか（`errorClassifier` 経由か） |
| ErrorBoundary 独自実装 | `ErrorBoundary`（`react-error-boundary`）の直接利用が無いか（`ErrorGuard` 経由か）|
| PHI を `extra` に含めて送信 | `Sentry.setExtra('patient', ...)` のような明示的 PHI 付与が無いか |

## 3. エラー種別と対応規約

| エラー種別 | 検知方法 | UI 通知 | GlitchTip 送信 |
|---|---|---|---|
| ネットワークエラー | `axiosClient` Interceptor | トースト（再試行ボタン） | する |
| API エラー（4xx/5xx） | `axiosClient` Interceptor | ステータス別モーダル／画面 | する |
| 業務エラー（`REQUIRED` / `INVALID_FORMAT` / `INVALID_TYPE`） | `errors[].code` 判定 | フォームのフィールド単位メッセージ（React Hook Form `setError` 経由） | しない（業務ロジックの正常系） |
| ランタイムエラー | Error Boundary | `error.tsx` の全画面表示 | する |
| 認可エラー（401/403） | `errors[].code` = `UNAUTHORIZED` / `FORBIDDEN` | 401: ログイン画面リダイレクト／403: 権限不足モーダル | する |

> 詳細フロー・判定ロジックは [エラー処理基盤設計.md](エラー処理基盤設計.md) §3 を参照。
> エラー種別と Sentry 送信／UI 表示の対応マトリクスは [BFFエラーレスポンス設計.md](BFFエラーレスポンス設計.md) §5 を参照。

## 4. BFF エラーレスポンス取り扱い規約

| 規約 | 内容 |
|---|---|
| ✅ 必須 | HTTP ステータスで一次分岐し、`errors?.[0].code` が存在する場合は追加判定に使用する |
| ✅ 必須 | フォーム呼び出し側は HTTP 400 のレスポンスから `errors[].field` を React Hook Form のフィールド名と突き合わせて該当フィールドにエラー表示する（HTTP 400 では `errors[]` 必須） |
| ✅ 必須 | `errors[].message` は BFF から日本語で届くため、フロントエンドでは再翻訳しない。`errors` 省略時は `detail` をフォールバックとして使用 |
| ✅ 必須 | `errors[].meta` の参照は `errors?.[0].code` ごとに必要時のみ（例: `code === 'CONFLICT'` のときのみ `meta.lockedByUserName` を読む） |
| ✅ 必須 | `traceId` は表示せず、ログ解析時に BFF / 操作監査ログと突き合わせる用途で保持 |
| ⛔ 禁止 | フロント独自エラーコードを BFF に返却させる（フロント E-code は内部マッピングで導出） |
| ⛔ 禁止 | `errors[].message` を独自テンプレートで上書きする |

> レスポンス構造・`errors[].code` 一覧は [BFFエラーレスポンス設計.md](BFFエラーレスポンス設計.md) を参照。

## 5. UI 通知規約

| 重大度 | 通知方法 | 適用エラー種別 | 経由必須 I/F |
|---|---|---|---|
| 致命的（Critical） | 画面全体表示（Error Boundary） | サーバー側エラー（5xx）、重要 API の通信断 | 基盤の `app/error.tsx` |
| 重度（Severe） | 持続的モーダル | データ整合性エラー、更新競合、権限不足（403） | `ErrorModal` |
| 軽微（Minor） | フォームフィールド単位メッセージ | バリデーションエラー（`REQUIRED` / `INVALID_FORMAT` / `INVALID_TYPE`） | React Hook Form `setError`（`errors[].field` との突き合わせ） |
| 軽微（Minor） | トースト | ネットワーク再試行、任意項目の軽微なエラー等 | `react-hot-toast`（[08章リアルタイム通信](../08_リアルタイム通信設計/) 参照） |

| 規約 | 内容 |
|---|---|
| ✅ 必須 | 重度エラーは `ErrorModal` を使用（独自モーダルを作らない） |
| ⛔ 禁止 | エラーメッセージにスタックトレース・内部変数名等の技術的詳細をユーザー表示する |
| ⛔ 禁止 | トーストで十分な軽微エラーにモーダルを使用する |
| ⛔ 禁止 | `error.tsx` の Props 型を変更する（Next.js 規約違反） |

> 詳細仕様は [エラー処理基盤設計.md](エラー処理基盤設計.md) §6 を参照。

## 6. 実装規約（Do/Don't）

### 6.1 エラーハンドリング

**やっていいこと**:
- グローバル Error Boundary で捕捉したエラーは GlitchTip に自動送信される
- ネットワークエラー時に再試行ボタンを提供する
- 業務エラー（バリデーションエラー）はフォームの該当フィールドにメッセージを表示する（React Hook Form `setError` 経由）
- API エラーは呼び出し元で `errorClassifier` 経由で分岐し、`ErrorModal` か `react-hot-toast` で通知する

**やってはいけないこと**:
- Error Boundary 内で再度エラーを `throw` する（無限ループの危険）
- 業務ロジック内の正常系エラー（バリデーションエラー）を GlitchTip に送信する（ノイズ増大）
- エラーメッセージに技術的詳細をそのままユーザー表示する
- `try-catch` でエラーを握り潰し、GlitchTip にも UI にも伝播させない

### 6.2 GlitchTip 連携

**やっていいこと**:
- 全エラーは基盤が `tenant_id` / `user.id` / `trace_id`（API エラー時のみ）を自動付与する
- 必要に応じて `setPatientContext()` 経由で患者 ID（`tags.patient_id`）を任意付与する
- Breadcrumbs（最大50件）を活用してエラー再現手順を把握する

**やってはいけないこと**:
- `beforeSend` フックを省略・無効化し、PHI 含有可能性のあるフィールドをそのまま送信する
- 監査情報の付与をアプリコードで上書きする
- Breadcrumbs の最大記録数を過度に増やす（ブラウザメモリ圧迫）

### 6.3 ログ解析の標準化

**やっていいこと**:
- `front_bff_shared` で定義された型規約を遵守する
- エラーメッセージ・付随データ構造を統一し、BFF 側ログと突き合わせやすくする

**やってはいけないこと**:
- 各機能で独自のエラー構造を定義する

## 7. アプリ実装チームの責務サマリ

| カテゴリ | 責務 | 経由必須 I/F | 参照する基盤 |
|---|---|---|---|
| 基盤 I/F の利用 | バイパス実装をしない（§2 が最優先） | §2.1 の表 | §2 |
| エラー判定 | API エラー / ランタイムエラー / 認可エラー判定 | `errorClassifier(error)` | [エラー処理基盤設計.md](エラー処理基盤設計.md) §5 |
| 重度エラー UI | データ整合性・競合・403 | `ErrorModal` | [エラー処理基盤設計.md](エラー処理基盤設計.md) §6.2 |
| コンポーネント単位 Boundary | Organism / Page をラップ | `ErrorGuard` | [エラー処理基盤設計.md](エラー処理基盤設計.md) §6.1 |
| BFF エラー取扱 | HTTP × `errors[].code` で UI 分岐 | `axiosClient`（基盤配線済み） | [BFFエラーレスポンス設計.md](BFFエラーレスポンス設計.md) |
| GlitchTip 送信 | 基盤が自動送信。アプリは触らない | （基盤側で代行） | [GlitchTip連携設計.md](GlitchTip連携設計.md) |
