# ADR-9: `tenant_id` の取得方式をエラー経路ごとに分ける

* **ステータス**: Accepted
* **決定日**: 2026-05-22
* **関連設計書**: [エラー処理基盤設計.md](../エラー処理基盤設計.md) §3.3, [GlitchTip連携設計.md](../GlitchTip連携設計.md) §3.1
* **関連 ADR**: なし

## 背景

エラー発生時に GlitchTip イベントへ `tenant_id` を付与する必要がある。
`tenant_id` の取得元は本プロジェクトでは複数存在する。

* `axiosClient` が組み立てる `x-tenant-id` リクエストヘッダー（API 呼び出し時に明示的に付与）
* `Sentry.setTag('tenant_id', ...)` で事前設定された Sentry のグローバルタグ（ログイン時に設定）

エラー経路（フロー1: API エラー / フロー2: ランタイムエラー）によって、どちらの取得方式が正確かが異なる。

## 検討した選択肢

### 案A: 両経路とも `Sentry.setTag` に統一
* **メリット**: 取得方式が単一でシンプル
* **デメリット**: 万一テナント切替直後の競合状態（`Sentry.setTag` がまだ更新されていない瞬間）に API エラーが起きると、誤ったテナント ID で記録される

### 案B: 両経路ともリクエストヘッダーから取得
* **メリット**: 取得方式が単一
* **デメリット**: フロー2（ランタイムエラー）は API 呼び出しを経由しないため、リクエストヘッダーから取得できない

### 案C: 経路ごとに最も正確な取得方式を使う
* **メリット**: 実際にそのリクエストで使われたテナント ID を確実に記録できる
* **デメリット**: 経路ごとに異なるロジックを保守する必要がある

## 決定

**案C を採用する**。

* **フロー1（API エラー）**: `axiosClient.ts` の Interceptor で `error.config?.headers?.['x-tenant-id']` から動的取得し `Sentry.captureException` の `tags.tenant_id` に渡す。リクエストごとに実際に送信されたテナント ID で記録される
* **フロー2（ランタイムエラー）**: `Sentry.setTag('tenant_id', ...)`（ログイン時または `setTenantContext` 呼び出し時に基盤が事前設定）の値が `Sentry.captureException` 時に自動付与される

| 項目 | フロー1: API エラー | フロー2: ランタイムエラー |
|---|---|---|
| 取得元 | `error.config.headers['x-tenant-id']` | `Sentry.setTag` で事前設定 |
| タイミング | エラー捕捉時（Interceptor 内） | ログイン時 / テナント切替時 |
| 競合状態の影響 | なし（リクエスト時点の値で固定） | あり（テナント切替直後の遅延フレーム）|

## 影響

### 正の影響
* フロー1 では実際に送信されたテナント ID で記録されるため、誤ったテナントへの API 呼び出しがあった場合も正確に記録される
* フロー2 ではランタイムエラー（API を経由しないエラー）でもテナント ID が記録される

### 負の影響
* 経路ごとに異なる取得ロジックを保守する必要がある
* フロー2 はテナント切替直後の遅延フレーム中にランタイムエラーが起きると古いテナント ID が記録される可能性が残る（基盤側でテナント切替時に `Sentry.setTag` を即時更新する責務として実装する）

### 見直しトリガー
* テナント切替時の遅延フレーム中にランタイムエラーが起きるリスクが顕在化した場合
* `axios` 以外の通信ライブラリ追加でフロー1 の取得ロジックが分散した場合
