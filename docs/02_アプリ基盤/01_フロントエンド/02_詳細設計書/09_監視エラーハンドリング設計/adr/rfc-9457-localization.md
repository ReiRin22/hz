# ADR-3: BFF エラーレスポンスを RFC 9457 ベースにプロジェクトローカライズする

* **ステータス**: Accepted
* **決定日**: 2026-05-22
* **関連設計書**: [BFFエラーレスポンス設計.md](../BFFエラーレスポンス設計.md) §1
* **関連 ADR**: [frontend-error-codes.md](frontend-error-codes.md)（フロント E-code 内部マッピングと一体）

## 背景

BFF からフロントエンドへ返却されるエラーレスポンス形式を統一する必要がある。
業界標準である [RFC 9457 (Problem Details for HTTP APIs)](https://www.rfc-editor.org/rfc/rfc9457.html) はベースとして優れているが、以下の点でプロジェクト要件と完全には一致しない。

* `type` フィールドは URI 参照型で、社内専用 API では実体 URI を持たないことが多い
* `title` / `detail` は英語が標準だが、ユーザー向け表示メッセージとして直接利用できない
* `instance` は URI 規定だが、リクエストパス文字列で十分
* オブザーバビリティ連携用の `traceId` フィールドが存在しない
* バリデーションエラー詳細（フィールド単位の `code`・`message`）の形式が標準化されていない

## 検討した選択肢

### 案A: RFC 9457 を完全準拠
* **メリット**: 業界標準。外部公開 API として理想的
* **デメリット**: メッセージが英語固定では UX に流用できず、フロントで再翻訳が必要。`type` URI を社内 API 用に整備する必要がある

### 案B: 完全独自フォーマット
* **メリット**: プロジェクト最適化が完全自由
* **デメリット**: 標準を捨てるのは損失。将来の外部公開や他プロジェクトとの連携時に変換が必要

### 案C: RFC 9457 ベース＋プロジェクトローカライズ
* **メリット**: 標準形を踏襲しつつ、ユーザー向け日本語メッセージ・`traceId`・統一された `errors[]` 構造を持てる。フロントは BFF の `errors[].message` をそのまま表示できる
* **デメリット**: 厳密な意味では RFC 9457 完全準拠ではないため、外部に向けて「RFC 9457 準拠」と謳う際は注釈が必要

## 決定

**案C を採用する**。

* `type` フィールドは含めない（社内 API のため）
* `title` / `detail` / `errors[].message` は日本語
* `instance` は URI ではなくリクエストパス文字列
* `traceId` を `errors[]` の後ろに追加（オブザーバビリティ連携用）
* `errors[]` は任意フィールド。HTTP 400 バリデーションエラー時には必ず設定する。HTTP ステータスのみで意味が確定するエラー（404・401・403・5xx 等）では省略可

## 影響

### 正の影響
* フロントエンドが BFF の `errors[].message` をそのまま表示できる（再翻訳不要）
* `traceId` により Sentry / 操作監査ログとの突合が容易
* エラー詳細の構造が統一される（バリデーション / 競合 / 認可で同じ `errors[]` 形式）

### 負の影響
* 厳密な意味での RFC 9457 完全準拠ではない（外部公開時に注釈が必要）
* メッセージが日本語固定のため、多言語化時は BFF 側で言語切替が必要

### 見直しトリガー
* BFF を外部公開 API として提供する要件が発生した場合
* 多言語化が要件として追加された場合
