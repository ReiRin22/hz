# ADR-4: 業務エラー（バリデーション）を GlitchTip 送信対象外とする

* **ステータス**: Accepted
* **決定日**: 2026-05-22
* **関連設計書**: [エラー処理基盤設計.md](../エラー処理基盤設計.md) §1, [BFFエラーレスポンス設計.md](../BFFエラーレスポンス設計.md) §6
* **関連 ADR**: なし

## 背景

GlitchTip に送信されるイベントは「障害の即時検知・原因特定」を目的とする。
バリデーションエラー（必須項目未入力・形式違反等）はユーザーの正常な操作の一部として日常的に発生し、技術的な障害ではない。
これらを送信対象に含めると、

* GlitchTip ダッシュボードがバリデーションエラーで埋もれる
* アラート閾値の設定が難しくなる（業務エラーが多発するとアラート疲れ）
* GlitchTip のストレージ・送信コストが業務エラーで消費される

## 検討した選択肢

### 案A: 全エラーを GlitchTip 送信
* **メリット**: 漏れなく記録される。送信ロジックがシンプル（条件分岐不要）
* **デメリット**: ダッシュボードがノイズで埋もれる。アラート設定が困難。ストレージ・送信コストが業務エラーで消費される

### 案B: 業務エラーのみ送信対象外
* **メリット**: ダッシュボードに残るのは技術的障害のみ。アラート設定が容易
* **デメリット**: 業務エラーの統計（どのフィールドでエラーが多いか）は別経路で取得する必要がある

### 案C: 重大度フラグで送信先を分岐
* **メリット**: 業務エラーは別 DB に集計できる
* **デメリット**: 集計用基盤を別途構築する必要がある。ROI が見合わない

## 決定

**案B を採用する**。

* HTTP 400 かつ `errors[0].code` が `REQUIRED` / `INVALID_FORMAT` / `INVALID_TYPE` のいずれかである場合、GlitchTip 送信を行わない
* 上記以外（認可エラー・競合・システムエラー）は全て送信対象
* 業務エラーの統計は将来必要になった時点で別経路（例: BFF の構造化ログ集計）で取得することとする

判定ロジックは `axiosClient.ts` の Interceptor で実装する（[エラー処理基盤設計.md](../エラー処理基盤設計.md) §3.1）。

## 影響

### 正の影響
* GlitchTip ダッシュボードに残るのは技術的障害のみ。原因特定が早まる
* アラート設定が容易になる（業務エラーが多発しても誤発報しない）
* ストレージ・送信コストを業務エラーで消費しない

### 負の影響
* 業務エラーの統計（フィールド単位の発生頻度等）は別途集計基盤が必要
* `VALIDATION_DELETE` 等の業務ルール違反系コードを今後追加した際、判定ロジックに追記する運用負担が発生する

### 見直しトリガー
* 業務エラーの統計が事業的に必要になり、別経路でのコスト・運用が GlitchTip 経由より高くついた場合
* 業務エラー判定の条件が複雑化し、Interceptor のロジックがメンテ困難になった場合
