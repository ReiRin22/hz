# ADR-6: フロント E-code は `errors[].code` から内部マッピングで導出する

* **ステータス**: Accepted
* **決定日**: 2026-05-22
* **関連設計書**: [BFFエラーレスポンス設計.md](../BFFエラーレスポンス設計.md) §7
* **関連 ADR**: [rfc-9457-localization.md](rfc-9457-localization.md)（BFF レスポンス形式と一体）

## 背景

フロントエンド側ではユーザー向けエラー画面・ダイアログ・ログ集計のために独自のエラーコード体系（E001〜E999、いわゆる「フロント E-code」）を持つことが業務システムでは慣習化している。
BFF も独自にエラーコード（`REQUIRED` / `CONFLICT` 等のプロジェクト標準コード）を持つため、両者をどう連携させるかの方針が必要。

## 検討した選択肢

### 案A: BFF がフロント E-code（E001〜E999）を返す
* **メリット**: フロントは BFF が返した E-code をそのまま使えるため、変換ロジックが不要
* **デメリット**: BFF が UI 層の事情（フロント E-code）に依存する。BFF の責務範囲が肥大化する。同じエラー（例: 認可失敗）に複数のフロント E-code が割り当てられた場合、BFF 側で UI コンテキストを把握する必要がある

### 案B: BFF はプロジェクト標準コード（`UNAUTHORIZED` 等）のみ返し、フロントが内部マッピングで E-code を導出
* **メリット**: BFF と UI 層の責務が分離される。フロント E-code の追加・変更が BFF に影響しない
* **デメリット**: フロント側にマッピングテーブルを保守する必要がある

### 案C: フロント E-code 体系を廃止し、BFF のプロジェクト標準コードのみ使用
* **メリット**: 体系が一本化される
* **デメリット**: 既存の運用慣習（E-code でログ集計・運用ダッシュボード）と整合しない

## 決定

**案B を採用する**。

* BFF は `errors[].code` にプロジェクト標準コード（`REQUIRED` / `INVALID_FORMAT` / `UNAUTHORIZED` / `FORBIDDEN` / `NOT_FOUND` / `CONFLICT` / `SYSTEM_ERROR` 等）のみ返す
* フロント E-code（E001〜E999）が必要な箇所では、フロント側のマッピングテーブルで `errors[].code` から導出する
* マッピングテーブルの具体形は本章のスコープ外。機能設計書 / 共通ユーティリティで個別管理する

## 影響

### 正の影響
* BFF と UI 層の責務分離が明確
* フロント E-code 体系の変更が BFF に影響しない
* BFF レスポンスがプロジェクト標準コードのみで完結するため、外部 API として再公開する際もそのまま使える

### 負の影響
* フロント側にマッピングテーブルを保守する工数が発生する
* マッピングテーブルが機能ごとに分散すると、E-code の重複・抜けが発生しうる

### 見直しトリガー
* マッピングテーブルの保守コストが想定を大きく上回り、BFF 側に E-code 体系を持たせる方が合計コスト的に有利と判明した場合
* フロント E-code 体系自体を廃止する運用判断が出た場合（その場合は本 ADR を Superseded に更新）
