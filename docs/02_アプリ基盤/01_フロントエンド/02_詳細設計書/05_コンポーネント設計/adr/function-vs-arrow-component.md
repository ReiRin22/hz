# ADR-1: メインコンポーネントは function 宣言で定義する

* **ステータス**: Accepted
* **決定日**: 2026-05-22
* **関連設計書**: [コンポーネント設計規約.md](../コンポーネント設計規約.md) §3.2
* **関連 ADR**: なし

## 背景

React の関数コンポーネント定義には以下の2つの記法がある。

* **関数宣言（function）**: `function ComponentName() { ... }`
* **アロー関数（const）**: `const ComponentName = () => { ... }`

両者は動作上ほぼ等価であり、コードを読むだけではどちらを採用すべきかの判断材料が見えない。プロジェクト全体で統一しないとレビュー基準がぶれ、PR ごとに記法が混在する。

## 検討した選択肢

### 案A: メイン= function宣言、内部ロジック・イベントハンドラ= arrow

* **メリット**:
  * メインコンポーネントを React DevTools のコンポーネントツリーで識別しやすい（function 名がそのまま表示される）。
  * スタックトレースが読みやすい（`at PatientCard` のように関数名が出る）。
  * ホイスティング（巻き上げ）により、ファイル内の定義順序を気にせず記述できる。
  * 内部の小さな処理（イベントハンドラ・整形関数）は arrow で簡潔に書け、メインとの視覚的区別がつく。

* **デメリット**:
  * 1つのファイル内に2種類の関数記法が混在する。

### 案B: 全て arrow 関数で統一

* **メリット**:
  * 記法が1種類で揃う。
  * `const` バインディングで再代入を防げる。

* **デメリット**:
  * 匿名アロー関数を変数に代入しているため、DevTools 表示やスタックトレースで関数名が出にくいケースがある（環境によっては `Anonymous` 表示になる）。
  * ホイスティング不可のため、ファイル内の宣言順序に依存する。

### 案C: 全て function宣言で統一

* **メリット**:
  * DevTools・スタックトレース面では案A と同等の利点。

* **デメリット**:
  * 1〜2行の小さな処理（クリックハンドラ等）まで `function` で書くと冗長。`this` バインディングの考慮が（React Hooks 文脈では不要だが）混入する余地がある。

## 決定

**案A を採用する**。

* **メインコンポーネント**: `function ComponentName(props): JSX.Element { ... }` 形式の関数宣言で定義する。`export const Component = () => {}` は禁止。
* **内部のロジック・イベントハンドラ**: アロー関数で定義する（`const handleClick = () => { ... }`）。

選定理由:

* デバッグ時の識別性（DevTools・スタックトレース）が最も重要であり、案B はこの点で劣る。
* 内部処理まで全て function で書く案C は、簡潔さを失う一方で得られる利点が少ない。
* 案A は「メイン= 主体・内部= 補助」の意味的区別がコード上に表れる利点がある。

## 影響

### 正の影響

* React DevTools のコンポーネントツリーで全コンポーネントが正しい名前で識別される。
* 本番環境のエラースタックトレースから該当コンポーネントを特定しやすい。
* レビュー時に「メイン定義は function」だけ見ればよく、判断軸が単純化される。

### 負の影響

* 1ファイル内に2種類の関数記法が混在するため、新規参画者には初見で違和感がある（規約を1度読めば解消）。
* ESLint で機械的に強制するルールが必要（`react/function-component-definition` 等）。

### 見直しトリガー

* React 公式または React DevTools が arrow 関数の表示問題を完全解消した場合、案B（全 arrow 統一）への切り替えを検討する余地がある。
