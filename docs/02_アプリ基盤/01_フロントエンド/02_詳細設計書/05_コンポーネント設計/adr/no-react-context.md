# ADR-2: React Context（useContext）を採用しない

* **ステータス**: Accepted
* **決定日**: 2026-05-22
* **関連設計書**: [コンポーネント設計規約.md](../コンポーネント設計規約.md) §4.5
* **関連 ADR**: なし
* **関連章**: [04_状態管理設計/状態管理規約.md](../../04_状態管理設計/状態管理規約.md)

## 背景

コンポーネントツリーの深い階層へ値を渡す手段として、React は標準で `React.createContext` + `useContext` を提供している。一方、本プロジェクトは状態管理に以下の3技術を採用済みである。

| 状態の種類 | 採用技術 |
|---|---|
| サーバー状態（API レスポンス・キャッシュ） | React Query |
| クライアント／UI 状態（テーマ・選択中の患者ID 等） | Zustand |
| フォーム状態（入力値・バリデーション） | React Hook Form |

これに `useContext` を加えると状態管理手段が4つに分散し、「どのケースでどれを使うか」の判断軸が増える。一度コードベースに登場すると至る所に増殖しやすく、後から撤去するのは困難である。

## 検討した選択肢

### 案A: useContext を不採用とし、状況別に既存3技術を使い分ける

* **メリット**:
  * 状態管理手段を3つに固定でき、レビュー基準が明確。
  * 各技術には専用の DevTools があり、デバッグが容易（React Query DevTools / Zustand DevTools / React Hook Form DevTools）。
  * 開発者が習得すべき手段を最小化でき、新規参画者の学習コストを抑えられる。
  * Context の不適切な利用による不要な再レンダリング問題を回避できる。

* **デメリット**:
  * 「テーマ等を Context で共有する」という React 標準的な手法が使えない（→ Zustand で代替）。

### 案B: useContext も含めた4手段を併用する

* **メリット**:
  * テーマや i18n 等の React 標準的なユースケースに自然に対応できる。
  * React 公式チュートリアルで紹介される手段が使える。

* **デメリット**:
  * 状態管理手段が分散し、「どのケースで何を使うか」の判断軸が増える。
  * Context は一度導入すると至る所に増殖し、後から撤去するのが難しい。
  * 不適切な粒度の Context は不要な再レンダリングを引き起こすが、検出が難しい。

## 決定

**案A を採用する**。

* `React.createContext` および `useContext` をプロジェクト全体で原則禁止する。
* propsバケツリレーを避けたいケースは、状況に応じて以下のいずれかで代替する。
  * **フォーム状態の共有**: React Hook Form の `FormProvider` + `useFormContext`（これは React Hook Form 内部で Context を使うが、ライブラリ提供の I/F として許容する）
  * **グローバル UI 状態の共有**: Zustand ストア
  * **サーバーデータの共有**: React Query のカスタムフック（キャッシュ経由で全コンポーネントから同一データを取得）

選定理由:

* 状態管理の一元化（採用 = 3つに固定）により、レビュー・学習・デバッグの全てが容易になる。
* useContext の代替手段が既に揃っており、表現力が落ちない。
* テーマや i18n も Zustand または共有契約（front_bff_shared）で十分扱える。

## 影響

### 正の影響

* 状態管理手法の散逸を防げる。
* React DevTools 単体ではなく、各技術専用の DevTools を活用できる。
* コードレビューで「これは Context・これは Zustand」のような分類議論が発生しなくなる。

### 負の影響

* React 公式チュートリアルで紹介される Context 使用例をそのまま流用できない（Zustand 等への書き換えが必要）。
* React Hook Form の `FormProvider` は内部で Context を使うため、規約上は「ライブラリ提供の I/F としての利用は許容」という例外規定が必要になる。

### 見直しトリガー

* React の Context API が再レンダリング問題を構造的に解消する形で改善された場合、再評価する。
* Zustand が不採用となった場合、UI 状態共有の代替として Context の採用を検討する。
