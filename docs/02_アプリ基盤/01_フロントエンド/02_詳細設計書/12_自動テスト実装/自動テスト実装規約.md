## 1. テスト分類とカバレッジ規約

### 1.1 テストの 5 分類

| テスト種別 | 対象 | 検証内容 | 使用ツール | 本章での詳細 |
|---|---|---|---|---|
| **単体テスト (Unit)** | カスタム Hooks、純粋関数（バリデーション・変換） | 入力 → 出力の正確性 | Vitest | §4 |
| **コンポーネントテスト (Component)** | Molecules / Organisms 単体 | 表示・インタラクション・状態遷移 | Vitest + RTL | §4 |
| **結合テスト (Integration)** | 複数 Organism + フロント〜BFF 通信 | API 通信を含む業務フロー | Vitest + RTL + MSW | §5 |
| **E2E テスト (E2E)** | クリティカルパス（ログイン → 業務登録） | 実ブラウザでの End-to-End | Playwright | §6 |
| **ビジュアルリグレッション (Visual)** | 全階層のコンポーネント | 見た目の意図しない変化 | Storybook + Test Runner | §7 |

> 分類の責務境界・なぜ 5 分類にしたかは [adr/test-pyramid-and-classification.md](adr/test-pyramid-and-classification.md) を参照。

### 1.2 Atomic Design 階層別の実施方針

| 階層 | 単体 | Component | Integration | E2E | Visual |
|---|---|---|---|---|---|
| Atoms（shadcn/ui ラッパー） | — | **不要**（ライブラリ側でテスト済み） | — | — | 必要に応じて |
| Molecules（API 呼び出しなし） | — | **必須**（バリデーション・表示） | — | — | 必要に応じて |
| Organisms（API 呼び出しあり） | — | **必須**（MSW で API モック） | — | — | 必要に応じて |
| Pages | — | — | **必須**（複数 Organism + BFF 結合） | クリティカルパスのみ | — |
| カスタム Hooks / 純粋関数 | **必須** | — | — | — | — |

### 1.3 スコープの境界

| 通信レイヤ | テスト対象? | 担当 |
|---|---|---|
| フロント 〜 BFF | ✅ 結合テスト（MSW） | 本章 |
| BFF 〜 BE | ❌ | BFF 側の単体テスト |

### 1.4 カバレッジ目標

| 項目 | 要求水準 |
|---|---|
| 単体テスト・コンポーネントテストの合否 | 全テスト PASS |
| カバレッジ（全体） | 70% 以上 |
| ESLint | エラー 0 件 |
| TypeScript | 型エラー 0 件 |

**カバレッジ対象外**: `*.stories.tsx` / `vitest.config.ts` / `next.config.js` / `*.d.ts`

> **注記**: 本来「テスト品質基準」「カバレッジ目標」は別途「テスト計画書」で定義すべき内容。現時点では暫定的に本規約に記載している。

## 2. 基盤 I/F 利用規約（最重要）

> 基盤が提供する設定ファイル・ランナーを **経由しない実装は禁止する**。バイパス実装は CI 実行コマンドの破壊・テスト環境の分裂・ベースライン管理の崩壊を引き起こす。

### 2.1 必ず経由する I/F とバイパス禁止 API

| 用途 | ✅ 経由必須 I/F | ⛔ バイパス禁止 | 詳細 |
|---|---|---|---|
| Vitest 実行 | `frontend/vitest.config.ts` を CI / ローカルで共通利用 | テスト用に独自 `vitest.config.*.ts` を作る、`preserveSymlinks: false` 前提のテストを書く | [単体・コンポーネント・結合テスト基盤設計.md](単体・コンポーネント・結合テスト基盤設計.md) §3 |
| Vitest セットアップ | `frontend/src/shared/plugins/setup.ts` をそのまま利用 | テスト側で `cleanup()` 手動呼び出し、`@testing-library/jest-dom` 個別 import | [単体・コンポーネント・結合テスト基盤設計.md](単体・コンポーネント・結合テスト基盤設計.md) §4 |
| Playwright 実行 | `frontend/playwright.config.ts` を CI / ローカルで共通利用 | `await page.goto('http://localhost:3000/...')` の絶対 URL 直書き | [E2Eテスト基盤設計.md](E2Eテスト基盤設計.md) §2 |
| Storybook 実行 | `frontend/.storybook/main.ts` / `preview.ts` をそのまま利用 | Story ファイルを `stories` パターン外に置く、Story 内で `setupServer(...)` 直接呼び | [ビジュアルリグレッションテスト基盤設計.md](ビジュアルリグレッションテスト基盤設計.md) §2, §3 |
| Story での MSW モック | `parameters.msw.handlers` 経由 | Story 内で `setupServer` を直接起動 | [ビジュアルリグレッションテスト基盤設計.md](ビジュアルリグレッションテスト基盤設計.md) §3.3 |
| 結合テストでの BFF モック | MSW（`setupServer(...)` をテストファイル単位で起動）+ `front_bff_shared` の Response 型 | BFF を実起動して結合テスト | [単体・コンポーネント・結合テスト基盤設計.md](単体・コンポーネント・結合テスト基盤設計.md) §5 |
| E2E での BFF モック | `page.route('**/bff/...')` | BFF を実起動して E2E、`fetch` を直接 stub | [E2Eテスト基盤設計.md](E2Eテスト基盤設計.md) §3 |

### 2.2 例外

| ケース | 条件 |
|---|---|
| プロトタイプ・検証コード | 本番投入前に基盤 I/F 経由へ移すこと |
| 基盤チームによる基盤実装 | 本規約の対象外（基盤 I/F の実装側） |

### 2.3 PR レビュー観点

| 観点 | チェック内容（grep ターゲット） |
|---|---|
| 設定ファイルの分裂 | `vitest.config.*.ts` / `playwright.config.*.ts` / `.storybook/main.*.ts` がリポジトリ内に複数存在しないか |
| `*.spec.*` 命名 | `*.spec.ts(x)` 拡張子のテストファイル（E2E の `.spec.ts` 以外）。本規約は `*.test.ts(x)` / `*_test.ts(x)` を採用 |
| 絶対 URL 直書き | `page.goto('http://localhost` / `page.goto('https://` |
| `setupServer` の二重起動 | `*.stories.tsx` 内の `setupServer(` 出現 |
| BFF 実起動 | `e2e/` 配下で `npm run dev:bff` / 実 BFF への直接接続コードが無いか |
| `cleanup()` の重複 | テストコード内の `cleanup()` 直接呼び出し（基盤の `setup.ts` で自動化済み） |
| `any` モック | `vi.fn() as any` / `jest.fn() as any` の使用 |
| timeout 無し `waitFor` | `waitFor(() =>` の引数で `{ timeout }` が省略されていないか |

## 3. ディレクトリ構成と命名規則

### 3.1 配置場所

| テスト種別 | 配置場所 | 説明 |
|---|---|---|
| 単体・コンポーネントテスト | `src/features/<LV1>/<LV2>/<LV3>/test/` | 実装に近接配置。`test/` 配下は実装側ディレクトリ構造をミラーリング |
| 共通単体テスト・MSW ハンドラー | `src/shared/test/` | 全機能共通の純粋関数テスト・MSW ハンドラー |
| 結合テスト | `src/features/<LV1>/<LV2>/<LV3>/integration/` | フロント〜BFF 結合（MSW） |
| Story（ビジュアル） | `src/features/<LV1>/<LV2>/<LV3>/stories/` | Storybook Story |
| E2E テスト | `e2e/features/<LV1機能群>/` | Playwright シナリオ |

#### 配置例（単体・コンポーネント）

```
frontend/src/features/<LV1>/<LV2>/<LV3>/
├── components/
│   ├── molecules/
│   │   ├── UserSearchForm.tsx        ← 実装
│   │   └── UserTable.tsx
│   └── organisms/
│       └── UserListPanel.tsx
└── test/                             ← テスト（実装と同階層）
    └── components/                   ← 実装側ディレクトリ構造をミラー
        ├── molecules/
        │   ├── UserSearchForm_test.tsx
        │   └── UserTable_test.tsx
        └── organisms/
            └── UserListPanel_test.tsx
```

### 3.2 ファイル命名規則

| 命名形式 | 用途 |
|---|---|
| `[名前]_test.ts(x)` | 単体テスト・コンポーネントテスト |
| `[名前]_integration_test.tsx` | 結合テスト |
| `[名前].stories.tsx` | Story ファイル |
| `[シナリオ名].spec.ts` | E2E テスト（`e2e/` 配下） |

> ⛔ `*.spec.*` を E2E 以外で使わない（テストルール `.claude/rules/test-rules.md` の禁止事項）。

### 3.3 パス解決とシンボリックリンク

| 観点 | 方針 |
|---|---|
| パスエイリアス（`@/`） | `tsconfig.json` 定義をテスト環境（Vitest / Storybook）でも共通利用 |
| `front_bff_shared/` の参照 | `preserveSymlinks: true` をテスト時にも維持（基盤側で設定済み） |

## 4. 単体・コンポーネントテスト規約

### 4.1 単体テスト（純粋関数 / カスタム Hook）

| ✅ やる | ⛔ 禁止 |
|---|---|
| 関数を直接呼び出して入出力を検証 | UI レンダリングを単体テストで検証する（コンポーネントテストの責務） |
| カスタム Hook は `renderHook` でテスト | 内部実装（`state` の値）を直接検証 |
| 異常系・エッジケースを網羅 | 1 テストで複数の振る舞いを混在 |
| テストケース名は日本語で「〜であること」 | CSS クラス名・DOM 構造に依存した検証 |

#### Next.js 固有 API のモック

```typescript
const pushMock = vi.fn();
vi.mock('next/navigation', () => ({
  useRouter: () => ({ push: pushMock, replace: vi.fn(), back: vi.fn() }),
}));
```

### 4.2 コンポーネントテスト（Molecules / Organisms）

#### 要素取得の優先度

| 優先度 | メソッド | 用途 |
|---|---|---|
| 1 | `getByRole` | ボタン・テキストボックス等のロール |
| 2 | `getByLabelText` | ラベル付き入力欄 |
| 3 | `getByText` | 表示テキスト |

⛔ 禁止: `querySelector` / `getElementById` / CSS クラス名による要素取得。

#### 非同期処理

```typescript
// ✅ timeout 必須
await waitFor(() => {
  expect(screen.getByText('保存しました')).toBeInTheDocument();
}, { timeout: 3000 });
```

#### モック粒度

| ✅ モックして良い | ⛔ モック禁止 |
|---|---|
| `api/` 関数層（例: `vi.mock('../api/postSchema.api')`） | `repository/` 層 |
| `next/navigation` 等の Next.js API | `hooks/` 層（`vi.mock('../hooks/useSaveSchema')` 等） |
| 外部 BFF（MSW でインターセプト） | テスト対象コンポーネント自体 |

### 4.3 アクセシビリティ

`label` の `htmlFor` と `input` の `id` を紐付け、テストで `getByLabelText` から取得可能にする。

```tsx
<label htmlFor="user-name">名前</label>
<input id="user-name" {...register('name')} />
```

## 5. 結合テスト規約

§2.1 の通り、結合テストでは **MSW で BFF をモック** する。実 BFF 起動は禁止。

### 5.1 必須要件

| 項目 | 内容 |
|---|---|
| ハンドラーのモックデータ型 | `front_bff_shared/.../<domain>.response.ts` の Response 型に準拠 |
| 異常系の網羅 | 正常系だけでなく 404 / 500 / バリデーションエラーもモック |
| `axiosClient` の Interceptor | テスト時も通る（認証・テナント ID 付与含めて結合検証） |
| 検証範囲 | 複数 Organism + BFF 通信を含む業務フロー |
| 検証範囲外 | BFF 〜 BE 間の通信（BFF 側の単体テスト責務） |

### 5.2 ハンドラー配置

| 共有範囲 | 配置 |
|---|---|
| 機能横断 | `src/shared/test/mocks/handlers/<domain>.ts` |
| 機能内のみ | `src/features/<LV1>/<LV2>/<LV3>/integration/mocks/` |

> セットアップパターン・シーケンスは [単体・コンポーネント・結合テスト基盤設計.md](単体・コンポーネント・結合テスト基盤設計.md) §5 を参照。

## 6. E2E テスト規約

§2.1 の通り、E2E では **`page.route` で BFF をモック** する。実 BFF 起動は禁止。

### 6.1 シナリオ選定基準

| 優先度 | 対象 |
|---|---|
| 高 | PR で変更した画面・機能 |
| 高 | クリティカルパス正常系（例: ログイン → 検索 → 登録 → 確認） |
| 中 | 異常系（バリデーションエラー・404 / 500） |

⛔ 禁止: 全画面の網羅 E2E、単体・結合で検証済みの詳細ロジックの再検証。

### 6.2 セレクタ規約

| 優先度 | セレクタ | 例 |
|---|---|---|
| 1 | `data-ui-id` 属性 | `page.locator('[data-ui-id="BTN_CONFIRM"]')` |
| 2 | `role` 属性 | `page.getByRole('button', { name: '保存' })` |
| 3 | テキスト | `page.getByText(...)` |

⛔ 禁止: CSS クラス名・タグ構造に依存（`page.locator('.submit-button')`）。

### 6.3 命名規則

```typescript
test('TC-001: 画面初期表示 — タブ・ヘッダ・テーブルが表示される', async ({ page }) => { ... });
```

### 6.4 認証処理

【今後定義予定】認証基盤連携サービス詳細設計の確定後に方針を決定する。当面は `page.route` でセッション API もモックして実装する。

## 7. ビジュアルリグレッション規約

§2.1 の通り、Story ファイルは **`stories` パターンに従って配置** し、MSW モックは **`parameters.msw.handlers` 経由** で行う。

### 7.1 対象選定基準

| 優先度 | 対象 |
|---|---|
| 高 | PR で変更したコンポーネント |
| 高 | 変更コンポーネントに依存する関連コンポーネント |

> 自動検出の仕組みは今後詳細定義予定。

⛔ 禁止: 全コンポーネントの網羅 Story 化（メンテナンスコスト過大）。

### 7.2 Story 命名

| 規則 | 内容 | 例 |
|---|---|---|
| エクスポート名 | 英語、先頭大文字、状態を表す | `Default` / `Filled` / `Empty` / `Error` |
| `meta.title` | `Features/<LV1>/<LV2>/<Component>` 形式 | `'Features/Patient/Search/UserSearchForm'` |

⛔ 禁止: ストーリー名を日本語で書く（TypeScript エクスポート変数名として不適切）。

### 7.3 1 Story = 1 状態

差分検出を確実にするため、1 つの Story に複数状態を混ぜない。状態ごとに別 Story として分割する。

## 9. アプリ実装チームの責務サマリ

| カテゴリ | 責務 | 経由必須 I/F | 参照する基盤 |
|---|---|---|---|
| 基盤 I/F の利用 | バイパス実装をしない（§2 が最優先） | §2.1 の表 | §2 |
| 単体テスト実装 | 純粋関数・カスタム Hook を `*_test.ts(x)` で配置 | `vitest.config.ts` の設定値 | §4.1、[単体・コンポーネント・結合テスト基盤設計.md](単体・コンポーネント・結合テスト基盤設計.md) |
| コンポーネントテスト実装 | Molecules / Organisms を `*_test.tsx` で配置。RTL の優先度に従う | 同上 | §4.2 |
| 結合テスト実装 | `*_integration_test.tsx` で MSW + `front_bff_shared` 型を使用 | MSW + Response 型 | §5、[単体・コンポーネント・結合テスト基盤設計.md](単体・コンポーネント・結合テスト基盤設計.md) §5 |
| E2E テスト実装 | `e2e/<シナリオ名>.spec.ts` で `data-ui-id` 優先・`page.route` モック | `playwright.config.ts` の設定値 | §6、[E2Eテスト基盤設計.md](E2Eテスト基盤設計.md) |
| Story 作成 | `<Component>.stories.tsx` で 1 Story = 1 状態。`parameters.msw` で API モック | `.storybook/preview.ts` の `mswLoader` | §7、[ビジュアルリグレッションテスト基盤設計.md](ビジュアルリグレッションテスト基盤設計.md) |
| カバレッジ達成 | 全体 70% 以上 | — | §1.4 |
