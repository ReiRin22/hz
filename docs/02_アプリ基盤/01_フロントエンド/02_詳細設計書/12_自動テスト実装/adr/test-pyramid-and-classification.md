# ADR-1: テストの分類（Unit/Component/Integration/E2E/Visual）と責務境界の定義

* **ステータス**: Accepted
* **決定日**: 2026-05-28
* **関連設計書**: [自動テスト実装規約.md](../自動テスト実装規約.md) §1, §2
* **関連 ADR**: [ADR-2](vitest-as-test-runner.md)、[ADR-3](playwright-as-e2e.md)、[ADR-4](storybook-test-runner-for-visual.md)

## 背景

電子カルテはマルチテナントの医療業務を扱う多機能アプリで、以下の要請を満たす必要がある。

* 医療業務に直結するロジック（バリデーション・データ変換・状態遷移）は高速にフィードバックを得たい
* 複数 Organism と BFF をまたぐ業務フロー（フォーム入力→保存→一覧再取得）の崩れを早期検出したい
* ログイン → 検索 → 登録 → 確認 のクリティカルパスは最終的に実ブラウザでも保証したい
* UI 修正の意図しないリグレッション（フォントずれ・余白崩れ等）を検出したい

これらを単一のテストレベルで賄うとどれかが過大コストになるため、テストレベルを明示的に分割する必要があった。「全部 E2E」も「全部 Unit」も避け、テストピラミッドの形に収めることを前提に、各レベルが何を検証するかを明文化する。

## 検討した選択肢

### 案A: Unit / Component / E2E の 3 レベル構成
* メリット: 学習コストが低い。OSS チュートリアルの大半がこの構成。
* デメリット: フロントエンドが BFF と整合した Request/Response 型でやり取りできているかを検証する層が無く、Unit でモック過剰、E2E で網羅すると遅すぎる。

### 案B: Unit / Component / Integration / E2E / Visual の 5 レベル構成
* メリット: 各レベルの責務が明確で、テストごとにモック粒度・実行コスト・検証範囲が決まる。Integration は MSW で「フロント〜BFF 通信」を `front_bff_shared` の型で検証できる。Visual はビジュアルリグレッション専用に切り出し、E2E と分離できる。
* デメリット: テストファイル種別が多くなり、命名規約・配置規約の徹底が必要。

### 案C: Component と Integration を統合（同じ Vitest+RTL なのでファイル名で区別のみ）
* メリット: 設定ファイルが1セットで済む。
* デメリット: テスト対象境界が曖昧になり、Component テスト内で BFF までモックして Integration の役割を持たせる「中途半端なテスト」が発生しやすい。

## 決定

**案B を採用する**。

* テストレベルは 5 つ: Unit / Component / Integration / E2E / Visual
* それぞれの責務・対象階層・使用ツール・検証範囲を [自動テスト実装規約.md](../自動テスト実装規約.md) §1.2 / §1.3 の表で固定する
* スコープの境界:
  - 「フロント 〜 BFF」 → 結合テスト（MSW で BFF をモック）
  - 「BFF 〜 BE」 → BFF 側の責務（本章スコープ外）
  - Atoms（shadcn/ui ラッパー）は原則テスト不要。Molecules/Organisms と純粋関数・カスタム Hook を必須化

## 影響

### 正の影響
* テスト対象境界が明確になり、過剰モック・過剰 E2E を防げる
* `front_bff_shared` の型に基づく Integration が成立し、Request/Response の契約破壊を Vitest レイヤで検出できる
* Visual を E2E と分離したことで、UI 変更レビューが GitLab アーティファクトの差分画像で完結する

### 負の影響
* テストファイル拡張子・配置場所が 5 種類に分かれ、新規参画者の学習が必要
* Component と Integration の境界判断（API 通信を含むか）を都度判断する必要がある

### 見直しトリガー
* MSW の運用コストが結合テストの価値を上回った場合、Integration 層の縮小を再検討する
* BFF の API スキーマ駆動テストが整備された場合、フロント側 Integration の冗長性を見直す
