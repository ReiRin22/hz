# レンダリング設計

## 1. RSC / RCC 垂直分離

コンポーネントを「データの取得と編成を行うサーバー層（RSC）」と「ユーザー操作を制御するクライアント層（RCC）」に垂直分離する。

> 根拠: [ADR-1](adr/app-router-adoption.md)

### 1.1 宣言の対応表

| 宣言 | 技術的呼称 | 実行場所 | 主な役割 |
|---|---|---|---|
| **（なし）** | RSC（Server Components） | サーバー | データのフェッチと画面構成 |
| **`"use client"`** | RCC（Client Components） | サーバー＋ブラウザ | UIの反応・状態管理 |
| **`"use server"`** | Server Actions | サーバー | 本プロジェクトでは原則不使用 |

> `"use server"` 不使用の根拠: [ADR-2](adr/use-server-prohibition.md)

### 1.2 RSC / RCC 振り分け例

**RSC（宣言なし）にするもの** ── 「画面の骨組み」や「動かない情報」:
- `page.tsx` 本体: BFFから患者基本情報や診察履歴を取得する処理
- サイドメニュー / ナビゲーション: Linkコンポーネントだけのメニュー
- 表示専用のカード: 読み取り専用の患者名、生年月日、アレルギー情報の表示枠

**RCC（`'use client'`）にするもの** ── 「ユーザーが何かをする場所」に限定:
- 診察入力フォーム: テキスト入力やチェックボックス（`onChange` を使用）
- 保存ボタン: クリック時にBFF APIを叩く処理
- タブ切り替えスイッチ: 画面を切り替えずに表示内容を変更するUI
- モーダルダイアログ: ポップアップの開閉管理

## 2. 動的ルーティングとパラメータ解決

Next.js 16から `params` はPromiseとして届くため `await` が必要。

### 2.1 page.tsx 実装テンプレート

```tsx
/**
 * LV3: 診察入力画面
 * 物理パス: src/app/(karte)/diagnosis/record-management/clinical-entry/[id]/page.tsx
 */
import { getDiagnosisData } from '@/features/diagnosis/record-management/clinical-entry/api/getDiagnosisAPI';
import { DiagnosisOrganism } from '@/features/diagnosis/record-management/clinical-entry/components/DiagnosisOrganism';

interface PageProps {
  params: Promise<{ id: string }>;
}

export default async function Page({ params }: PageProps) {
  const { id } = await params;           // 1. paramsを非同期で解決
  const initialData = await getDiagnosisData(id);  // 2. データ取得
  return <DiagnosisOrganism initialData={initialData} />;  // 3. Props注入
}
```

### 2.2 実装の3ステップ

1. **パラメータの解決**: `await params` を実行し、URLからIDを安全に取り出す
2. **型安全な取得**: `features` 層の `repository/`（または `api/`）の関数を呼び出す。`front_bff_shared` の型定義を適用する
3. **部品への注入**: 取得したデータを `features` 層のComponent（Organism等）へPropsとして渡す

## 3. Suspense によるローディング設計

Next.jsのStreaming SSRを活用し、データ取得による待機時間を「画面全体のフリーズ」ではなく「段階的な表示」へ最適化する。

> ローディング中の表示内容はスケルトンスクリーンを原則とする。根拠: [ADR-3](adr/skeleton-screen-adoption.md)

### 3.1 3層ローディング構造

| レイヤー | 配置場所 | 発生タイミング | 表示の挙動 |
|---|---|---|---|
| **① システム起動** | `src/app/loading.tsx` | 初回アクセス / ブラウザリロード時 | 画面全体をスケルトンで覆う |
| **② ページ遷移** | `src/app/(group)/loading.tsx` | メニュー移動時 | サイドメニュー等を維持し、コンテンツ領域のみスケルトン表示 |
| **③ コンポーネント** | `React.Suspense` | 特定の重いパーツ（グラフ、画像等） | ページ表示後、特定パーツのみ後出しでロード |

### 3.2 ディレクトリ構成イメージ

```text
src/app/
├── layout.tsx
├── loading.tsx        ← ① システム起動用
│
└── (karte)/
    ├── layout.tsx
    ├── loading.tsx    ← ② ページ遷移用（サイドバーを残して中身を入れ替え）
    └── diagnosis/
        └── record-view/
            └── page.tsx
```

### 3.3 Local Suspense の適用

Page層（RSC）ですべてのデータを `await` せず、重い処理を行うコンポーネント内部で非同期処理を行う。

```tsx
// page.tsx でのローディング境界定義
<Suspense fallback={<LoadingSkeleton />}>
  <HeavyComponent />
</Suspense>
```

### 3.4 Suspense の fallback 選択基準

| パターン | 指定方法 | 適用対象・基準 |
|---|---|---|
| **型A: デフォルト** | 引数なし | 高さや形状が特定しにくい補助的なコンポーネント |
| **型B: プリセット** | `variant="list"` 等 | 一覧表、カード、アバター付きリストなど定型UIコンポーネント |
| **型C: サイズ指定** | `className="w-[x] h-[y]"` | メインコンテンツや入力フォームなど、ロード前後でサイズズレを許容しない重要コンポーネント |

**運用ガイドライン**:
- 基本は **型A** または **型B** で開発スピードを優先する
- 診療録タイムラインや画像診断エリアなど、レイアウト固定がUXに直結する箇所にのみ **型C** を適用する

### 3.5 ローディング配置の優先順位

1. **第一優先（レイアウト保護）**: ルートグループ直下の `loading.tsx` でナビゲーションを維持しつつコンテンツエリア全体を保護する
2. **第二優先（コンポーネント最適化）**: 1.5秒以上の待機が予想される重いコンポーネントに個別に `<Suspense>` を配置する
3. **第三優先（即時フィードバック）**: Client Component内の更新処理は `useTransition` でボタン活性/非活性やスピナー表示で操作完了を伝える

## 4. フロントエンド性能目標（SLO）

以下の指標をすべての画面開発における品質基準とする。

| 指標（Core Web Vitals） | 目標値（Good） | 定義・計測基準 |
|---|---|---|
| **LCP（主要コンテンツ描画）** | **2.5秒以内** | 画面の主要な要素（カルテ内容等）が描画されるまでの時間 |
| **FID（初回入力遅延）** | **100ms以内** | クリックやタップに対するブラウザの反応速度 |
| **CLS（累積レイアウトシフト）** | **0.1未満** | 描画中のガタつきの少なさ |
| **FCP（初回描画）** | **1.8秒以内** | ヘッダーや枠組みが最初に表示されるまでの時間 |
| **描画DOM数** | **100個以下** | 画面上に同時に存在するDOM要素の数（仮想化で制御） |

### 4.1 ハイドレーション最適化

- Page層（Server Component）にて `fetch` を実行し、取得したデータをClient ComponentのPropsとして渡す
- ブラウザでのJS実行後にAPIを叩く「後出し通信（Waterfalls）」を禁止し、LCPを短縮する
