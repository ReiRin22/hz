## 1. ディレクトリ構造ルール

### 1.1 app / features 分離

| ディレクトリ | 役割 | 書くもの |
|---|---|---|
| `src/app/**` | URLパスとレイアウト境界の定義 | `layout.tsx`, `loading.tsx`, `page.tsx` |
| `src/features/**` | 業務ロジックとUIの実体 | コンポーネント, フック, ストア, API |

> 根拠: [ADR-1](adr/app-router-adoption.md)

### 1.2 features 階層とディレクトリ命名

```
src/features/
  {LV1}/                         例: diagnosis（診療記録）
    {LV2}/                       例: record-management（診療記録作成）
      {LV3}/                     例: clinical-entry（診察入力）
        components/
        hooks/
        stores/
        repository/
        api/
        types/
        assets/
        test/
        style.css
        index.ts                 ← 他機能への公開窓口
```

- 物理ディレクトリ名は英語・ケバブケース（`kebab-case`）で命名する
- 機能一覧表の階層（LV1/LV2/LV3）とディレクトリ構造を完全一致させる

### 1.3 内部ディレクトリの役割

| ディレクトリ / ファイル | 役割・責務 |
|---|---|
| `components/` | 画面固有のUI部品（Molecules / Organisms） |
| `hooks/` | 画面固有の対話・表示ロジック（`useQuery` / `useMutation` 等） |
| `stores/` | 画面固有の状態管理（Zustand） |
| `repository/` | BFF通信を抽象化するデータアクセス層 |
| `api/` | BFFとのHTTP通信の実体（副作用・状態を持たない純粋関数） |
| `types/` | 画面内でのみ使用する型定義 |
| `assets/` | 画面固有の静的リソース |
| `test/` | 自動テスト（Vitest / MSW） |
| `index.ts` | 他機能へ公開する最小限の定数・型・関数の出口 |

## 2. 依存関係ルール

### 2.1 5層アーキテクチャの依存方向

依存関係は常に **上から下への一方通行** とし、下位層が上位層をインポートすることを禁止する。

```
1. page（src/app/**/page.tsx）
   ↓
2. components（src/features/**/components/）
   ↓
3. hooks / stores（src/features/**/hooks/, stores/）
   ↓
4. repository（src/features/**/repository/）
   ↓
5. api / shared（src/features/**/api/, src/shared/）
```

### 2.2 禁止される依存パターン

| 禁止パターン | 具体例 |
|---|---|
| `features` → `app` | `features/` から `app/page.tsx` を import |
| `api` → `hooks` | `api/` から `hooks/` を呼び出す |
| LV3-A → LV3-B の内部 | 他機能の `api/` や `repository/` を直接 import（`index.ts` 経由のみ許可） |
| 循環参照 | A が B を import し、B が A を import |

### 2.3 カプセル化と公開の原則

- LV3内の各ディレクトリは原則としてその画面内でのみ使用する
- 他機能から参照が必要な場合のみ `index.ts` を通じて公開する

**資産の昇格ルール**:

| 共有範囲 | 移動先 |
|---|---|
| 同一LV1ドメイン内の複数画面 | `src/features/{LV1名}_shared/` |
| システム全体 | `src/shared/` |

- LV2・LV3レベルの `_shared` ディレクトリは設置しない

### 2.4 ESLintによる依存関係の強制

詳細は [ルーティング構造設計.md §2](ルーティング構造設計.md) を参照。

| ルール | 役割 |
|---|---|
| `no-restricted-imports` | `features/` から `app/` への逆参照禁止 |
| `import/no-cycle` | 循環参照の禁止 |
| `import/order` | インポート順序の固定 |

## 3. レンダリング実装ルール

### 3.1 RSC / RCC / Server Actions の使い分け

| 宣言 | 技術的呼称 | 実行場所 | 主な役割 |
|---|---|---|---|
| **（なし）** | RSC（Server Components） | サーバー | データのフェッチと画面構成 |
| **`"use client"`** | RCC（Client Components） | サーバー＋ブラウザ | UIの反応・状態管理 |
| **`"use server"`** | Server Actions | サーバー | （本プロジェクトでは原則不使用） |

> `"use server"` 不使用方針の根拠: [ADR-2](adr/use-server-prohibition.md)

### 3.2 RCC（`'use client'`）の選定基準

以下のいずれかを含む場合のみ `'use client'` を付与する:

1. **状態管理**: `useState`, `useReducer`, `Zustand` 等を使用する場合
2. **ライフサイクル**: `useEffect`, `useLayoutEffect` 等を使用する場合
3. **イベントリスナー**: `onClick`, `onChange` 等のブラウザイベントを扱う場合
4. **ブラウザAPI**: `window`, `document`, `localStorage` 等に直接アクセスする場合

**配置**: 原則として `components` 内に配置し、Page層から初期データを受け取る。

### 3.3 page.tsx の実装ルール

| ✅ page.tsx に書くべき処理 | ❌ page.tsx に書いてはいけない処理 |
|---|---|
| `await params` によるURLパラメータ解決 | データの変換・加工・計算ロジック |
| `features/repository` または `features/api` の呼び出し（1〜3行程度） | 複数の `if / else` を含む条件分岐処理 |
| featuresコンポーネントへのProps注入 | `useState` / `useEffect`（Server Componentに使用不可） |
| `<Suspense>` でのローディング境界定義 | 複雑なスタイリング・`div` の多重ネスト |
| `metadata` の定義（ページタイトル・SEO等） | BFFとの生のaxios / fetchの直書き |

`page.tsx` は「何を・どこに表示するか」を3〜30行で記述できる状態を理想とする。

### 3.4 ルートグループとレイアウト

**ルートグループ (`(group)`)**: フォルダ名に `()` を付与することでURLパスに影響を与えず、共通レイアウトを適用するグループを作成できる。

**Group Layout の禁止事項**:
- 特定の1画面でしか使わない複雑なバリデーションや個別API呼び出しを記述すること

## 4. front_bff_shared 連携ルール

### 4.1 型定義の一元管理

- フロントエンド側でBFF通信用の型を独自に定義（二重定義）することは禁止する
- **必ず `front_bff_shared` を経由すること**

> 型SSOTの根拠: [01章ADR: front-bff-shared-ssot.md](../01_フロントエンド・BFF共通基盤設計/adr/front-bff-shared-ssot.md)

### 4.2 ファイル配置ルール

| 対象 | 配置場所 |
|---|---|
| LV3画面専用の型・スキーマ | `front_bff_shared/[LV1]/[LV2]/[LV3]/types/` および `schemas/` |
| 複数画面で共有する型 | `front_bff_shared/{LV1または_shared}/` |

詳細な階層構造は [ルーティング構造設計.md §3](ルーティング構造設計.md) を参照。

## 5. パフォーマンス実装ルール

### 5.1 リスト表示の仮想化（react-virtuoso）

- **100件を超える動的リストを扱う場合は、必ず仮想化ライブラリを使用する**
- 描画DOM数を100個以下に制限する

### 5.2 画像最適化

- 画像表示には必ず `next/image` を使用する（`<img>` タグは禁止）

### 5.3 動的読み込み（Code Splitting）

以下に該当するコンポーネントは `next/dynamic` による動的読み込みを**必須**とする:

| 適用ケース | 具体例 |
|---|---|
| 初回表示に不要 | モーダル、ドロワー、タブの2枚目以降 |
| 大きな外部ライブラリ（200KB以上） | Chart.js、PDF.js、Monaco Editor |
| 条件付き表示 | 管理者専用パネル、権限制御コンポーネント |
| 低頻度の機能 | 印刷プレビュー、CSVエクスポート |

**適用しないケース**: 初回表示に必須のコンポーネント、50KB未満の小さいコンポーネント、Atoms/Moleculesの基本UI部品。

実装パターンの詳細は [パフォーマンス最適化設計.md §2](パフォーマンス最適化設計.md) を参照。

## 6. プリフェッチ制御ルール

| 状況 | 設定 |
|---|---|
| 標準遷移（ナビゲーション・一般ボタン） | `prefetch={true}`（デフォルト） |
| 大規模リスト（カルテ履歴一覧等） | `prefetch={false}` |

実装コード例は [パフォーマンス最適化設計.md §3](パフォーマンス最適化設計.md) を参照。
