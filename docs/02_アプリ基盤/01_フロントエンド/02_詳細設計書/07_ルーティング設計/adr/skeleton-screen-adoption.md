# ADR-3: ローディング表示にスケルトンスクリーンを採用する

* **ステータス**: Accepted
* **決定日**: 2025-10-01
* **関連設計書**: [レンダリング設計.md](../レンダリング設計.md) §3

## 背景（Context）

医療システムでは患者情報・診察記録など大量のデータを扱うため、データ取得中のローディング表示が頻繁に発生する。ローディング中の表示方式を統一する必要があった。

主な要件:
- 医療従事者の業務効率を最大化する体感速度の向上
- データ読み込み後のレイアウトシフト（CLS）の抑制（CLS < 0.1 の SLO 達成）
- 統一されたUXデザインの維持

## 検討した選択肢（Options）

### 案A: スケルトンスクリーン（採用）

* **メリット**
  * 次に表示される情報の「レイアウト」をあらかじめ示すことで、データ読み込み後のレイアウトシフト（CLS）を抑制できる
  * 医療従事者の視線移動をスムーズにし、体感的な待ち時間を短縮させる
  * 統一されたUIライブラリとして管理しやすい（`LoadingSkeleton` コンポーネントを一元管理）
* **デメリット**
  * コンポーネントごとにスケルトンを設計する工数が発生する

### 案B: スピナー（グローバルローディング）（見送り）

* **メリット**: 実装コストが低い（全画面共通のスピナーを1箇所に置くだけ）
* **デメリット**
  * データ読み込み中に画面が真っ白になり、後のレイアウトシフトが大きい（CLS悪化）
  * 読み込み完了後に「ガクッ」と表示が変わるため、医療現場での素早い判断を阻害する
  * 500機能規模で全画面スピナーを使い回すと、個別の待ち時間フィードバックが不明確になる

### 案C: ページ遷移なし・即時表示（見送り）

* **デメリット**: 大量医療データのフェッチでは非現実的。描画ブロックによる体感速度の悪化

## 決定（Decision）

**案A: スケルトンスクリーンを採用する。**

CLS抑制と医療UX向上の両方を満たせる唯一の選択肢。`LoadingSkeleton` コンポーネントを共通部品として一元管理し、色調とアニメーション（Pulse）の統一性を担保する。

**3パターンの使い分け**:
- **型A（デフォルト）**: 引数なし。補助的なコンポーネントに使用
- **型B（プリセット）**: `variant="list"` 等。一覧表・カードなど定型UIに使用
- **型C（サイズ指定）**: `className="w-[x] h-[y]"` 。CLS許容ゼロの重要コンポーネントに使用

## 影響（Consequences）

* **正**: CLS < 0.1 の SLO 達成に貢献。医療従事者の体感速度向上
* **負**: 各コンポーネントに対応したスケルトンの設計・実装工数が必要
* **見直しトリガー**: デザインシステムのローディング表示方針が変更された場合
