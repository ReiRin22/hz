## バージョン管理方針

本プロジェクトでは、セキュリティとメンテナンス性のバランスを考慮し、以下の方針でライブラリバージョンを管理する。

### 更新方針

| バージョン種別 | 内容 | 更新方針 | 理由 |
|--------------|-----|---------|------|
| **メジャー** | 大規模な機能、デザイン変更 | 固定（手動更新・検証必須） | 破壊的変更により既存実装が動作しなくなる可能性があるため、慎重な検証が必要 |
| **マイナー** | 部分的な機能改善、機能追加 | `npm update` 時に自動更新 | 後方互換性があり、新機能追加・バグ修正の恩恵を受ける |
| **パッチ** | バグ、誤字脱字の修正 | `npm update` 時に自動更新 | 適用しないことがリスクとなる |

### 実装方法

**package.json での記述**:
```json
{
  "dependencies": {
    "react": "^19.0.0",        // ^ 記法: メジャー固定、マイナー・パッチ自動更新
    "next": "^16.0.0",
    "axios": "^1.0.0"
  }
}
```

**^ 記法の動作**:
- `^19.0.0` → `19.x.x` の範囲で最新版を自動取得
- `npm update` 実行時に、メジャーバージョンを固定したまま、マイナー・パッチバージョンを最新化
- `package-lock.json` に実際にインストールされた詳細バージョンが記録される

### メジャーバージョンアップの手順

1. **基盤チームで事前検証**: 破壊的変更の影響範囲を調査
2. **検証環境での動作確認**: 既存機能への影響を確認
3. **アップデート実施**: `package.json` のメジャーバージョンを更新
4. **全体動作確認**: テストスイートを実行し、問題がないことを確認

### 管理体制

| 項目 | 担当 |
| :--- | :--- |
| **package.json のバージョン指定** | 基盤チーム |
| **メジャーバージョンアップ** | 基盤チームで検証後、全体に展開 |
| **マイナー・パッチ更新** | `npm update` で自動更新 |

## TypeScript 設定

フロントエンドとBFFの各プロジェクトに `tsconfig.json` を配置し、TypeScriptのコンパイラ設定を管理する。

### 主要な設定項目

**パスエイリアス**:
```json
{
  "compilerOptions": {
    "paths": {
      "@/shared/*": ["./src/shared/*"],
      "@/features/*": ["./src/features/*"],
      "@/app/*": ["./src/app/*"],
      "@/front_bff_shared/*": ["../front_bff_shared/*"]
    }
  }
}
```
- 絶対パスでのimportを可能にし、相対パス（`../../..`）の複雑化を回避
- `@/app/*` でアプリケーション固有のモジュールを参照
- モノレポ構成における共有型定義（`front_bff_shared`）への参照を簡潔化

**strict mode（型チェックの厳格化）**:
```json
{
  "compilerOptions": {
    "strict": true,
    "noImplicitAny": true,
    "strictNullChecks": true
  }
}
```
- 型安全性を最大化し、実行時エラーを事前に検出

**ESModules 設定**:
```json
{
  "compilerOptions": {
    "module": "ESNext",
    "moduleResolution": "bundler"
  }
}
```
- Next.js 16, React 19 の最新モジュールシステムに対応

### 管理体制

| 項目 | 担当 |
| :--- | :--- |
| **設定ファイルの整備・保守** | 基盤チーム |
| **設定変更の相談窓口** | 基盤チーム |

アプリ実装チームは、設定ファイル（`tsconfig.json`）を直接修正せず、変更が必要な場合は基盤チームに相談すること。

## 環境変数の管理

環境ごとに異なる設定（接続先URL、APIキー等）をソースコード外で管理する仕組みを定義する。

### 環境変数とは

**process.env による参照**:

Node.js では、環境変数を `process.env.環境変数名` で取得できる。

```typescript
// 例：BFF の接続先URL を取得
const bffUrl = process.env.NEXT_PUBLIC_BFF_URL;
```

**NODE_ENV による環境判定**:

Node.js では、`NODE_ENV` という環境変数に `development`（開発）、`test`（テスト）、`production`（本番）を設定し、実行環境を判定する文化がある。

```typescript
if (process.env.NODE_ENV === 'development') {
  console.log('開発環境で実行中');
}
```

**参考資料**: [Node.jsの環境変数について](https://for.kobayashiii.dev/articles/nqbaxkkf8)

```
名前の構造

process.env.NEXT_PUBLIC_BFF_URL
   ↓     ↓            ↓
   │     │            └─ 環境変数の名前（自由に決められる）
   │     │
   │     └─ environment（環境）= 環境変数の集まり
   │
   └─ このNode.jsプロセス
```

---

### 環境別ファイルの使い分け

| ファイル名 | 用途 | Gitへの登録 | 配置場所 |
|---|---|---|---|
| `.env.local` | 開発者個人用（APIキー等） | 登録しない（`.gitignore`） | `frontend/`, `bff/` |
| `.env.development` | 開発環境共通設定 | 登録する | `frontend/`, `bff/` |
| `.env.production` | 本番環境設定 | 登録する | `frontend/`, `bff/` |

**目的**: ソースコードを書き換えずに、接続先URLなどを環境ごとに切り替える。

---

### 定義する環境変数

本プロジェクトで使用する環境変数を以下に定義する。現時点では開発環境と本番環境のみを対象とし、本番環境の具体的な値は今後確定次第追記する。

#### フロントエンド → BFF

フロントエンドがBFFと通信するための接続先URL。

```bash
# frontend/.env.development
# クライアント（ブラウザ）からBFFを呼ぶ用
NEXT_PUBLIC_BFF_URL=http://localhost:3001

# サーバー（Server Component）からBFFを呼ぶ用
# ※JSからは process.env.SERVER_SIDE_BFF_URL で参照
SERVER_SIDE_BFF_URL=http://bff-app:3001

# frontend/.env.production
NEXT_PUBLIC_BFF_URL=https://bff.example.com      # ※本番環境の値は今後確定次第追記
SERVER_SIDE_BFF_URL=http://bff-service:3001      # ※本番環境の値は今後確定次第追記
```

**命名規則**:
- **クライアント側（ブラウザ）で参照**: `NEXT_PUBLIC_*` 接頭辞を使用（Next.js 固有の命名規則）
- **サーバー側（Server Component）で参照**: 任意の環境変数名（`NEXT_PUBLIC_` 接頭辞なし）

---

#### BFF → バックエンド

BFFがバックエンドAPIと通信するための接続先URLと認証情報。

```bash
# bff/.env.development
BACKEND_API_URL=https://dev-api.example.com
API_SECRET_KEY=xxxxx

# bff/.env.production
BACKEND_API_URL=https://api.example.com  # ※本番環境の値は今後確定次第追記
API_SECRET_KEY=xxxxx                     # ※本番環境では CI/CD で注入
```

**BACKEND_API_URL について**:

BFFが呼び出すバックエンドマイクロサービス群のベースURLを指す。バックエンド側の設計（APIゲートウェイの有無、マイクロサービスの分割方針等）により、以下のパターンが想定される：

- **単一URL**: APIゲートウェイ経由で統一エンドポイントを使用する場合
  ```
  BACKEND_API_URL=https://api.example.com
  ```
  
- **複数URL**: マイクロサービスごとに異なるエンドポイントを使用する場合
  ```
  PATIENT_SERVICE_URL=https://patient-api.example.com
  ORDER_SERVICE_URL=https://order-api.example.com
  ```

現時点では仮の値として `BACKEND_API_URL` を記載しているが、バックエンド側の詳細設計確定後に具体的な環境変数名と値を更新する。

**命名規則**: BFF の環境変数には、特定のプレフィックスを付けない任意の環境変数名を使用する（例: `BACKEND_API_URL`, `API_SECRET_KEY`）。すべてサーバー側でのみ参照され、ブラウザには公開されない。

---

#### フロントエンドとBFFの環境変数ネーミング規則の違い

| 対象 | 実行場所 | ネーミング規則 | 例 | 理由 |
|------|---------|--------------|-----|------|
| **フロントエンド（クライアント側）** | ブラウザ | `NEXT_PUBLIC_*` 接頭辞が**必須** | `NEXT_PUBLIC_BFF_URL` | Next.js の仕様。ブラウザに埋め込まれる変数を明示的に区別 |
| **フロントエンド（サーバー側）** | Server Component | 任意の名前（接頭辞なし） | `SERVER_SIDE_BFF_URL` | ブラウザに公開されないため、接頭辞不要 |
| **BFF** | Node.js サーバー | 任意の名前（接頭辞なし） | `BACKEND_API_URL`, `API_SECRET_KEY` | すべてサーバー側のみで参照されるため、接頭辞不要 |

**ポイント**:
- `NEXT_PUBLIC_*` はNext.js固有の規則であり、BFFには適用されない
- ブラウザに埋め込む変数のみ `NEXT_PUBLIC_*` 接頭辞を付ける
- サーバー側（Server Component / BFF）の変数は任意の名前でよい

---

### セキュリティガイドライン

#### やっていいこと

- 接続先URL（`NEXT_PUBLIC_BFF_URL`、`BACKEND_API_URL`）を環境変数で管理する
- 開発環境共通設定（`.env.development`）をGitにコミットする
- サーバー側の秘密情報は `NEXT_PUBLIC_` なしで定義する

#### やってはいけないこと

- APIキー・認証トークンに `NEXT_PUBLIC_` を付ける
  ```bash
  # NG例：ブラウザに埋め込まれて漏洩する
  NEXT_PUBLIC_API_SECRET_KEY=xxxxx
  ```

- `.env.local` をGitにコミットする
  ```bash
  # .gitignore に必ず記載
  .env.local
  ```

- 本番環境の秘密情報を `.env.production` に直接書く
  ```bash
  # NG: デプロイ時にCI/CDが環境変数として注入すべき
  API_SECRET_KEY=xxxxx
  ```

## 起動・ビルド・デバッグ設定

アプリケーションの起動、ビルド、デバッグに必要な package.json の scripts 設定を定義する。

### package.json の scripts 設定

#### フロントエンド

```json
// frontend/package.json
{
  "scripts": {
    "dev": "next dev --webpack",
    "dev:debug": "NODE_OPTIONS='--inspect=0.0.0.0:9229' next dev --webpack",
    "build": "next build --webpack",
    "start": "next start",
    "lint": "eslint"
  }
}
```

| スクリプト | 説明 |
|---|---|
| `dev` | 開発サーバーを起動（ホットリロード有効） |
| `dev:debug` | デバッグポート `9229` を公開して開発サーバーを起動 |
| `build` | 本番用ビルドを実行 |
| `start` | ビルド済みアプリケーションを本番モードで起動 |
| `lint` | ESLintによるコードチェックを実行 |

---

#### BFF

```json
// bff/package.json
{
  "scripts": {
    "dev": "tsx watch src/index.ts",
    "dev:debug": "NODE_OPTIONS='--inspect=0.0.0.0:9229' tsx watch src/index.ts",
    "build": "tsc",
    "start": "tsx src/index.ts"
  }
}
```

| スクリプト | 説明 |
|---|---|
| `dev` | 開発サーバーを起動（ファイル変更時に自動再起動） |
| `dev:debug` | デバッグポート `9229` を公開して開発サーバーを起動 |
| `build` | TypeScript を JavaScript にトランスパイル |
| `start` | ビルドなしで TypeScript を直接実行 |

---

**コンテナ起動方法は『開発テスト基盤方式設計書』を参照**

### デバッグの開始手順

devcontainer環境では、launch.json を作成せずにデバッグを開始できる。

1. コンテナ内で `npm run dev:debug` を実行
2. VSCode のコマンドパレット（`Ctrl+Shift+P` / `Cmd+Shift+P`）を開く
3. `Debug: Attach to Node Process` を選択
4. `localhost:9229` を選択

**devcontainer環境の特徴**:
- VSCodeがコンテナ内で動作するため、`localhost:9229` に直接接続
- パスマッピング（`localRoot`/`remoteRoot`）が不要
- docker-compose.yml でのポート公開も不要

### tsconfig.json のソースマップ設定

TypeScript のデバッグでは、トランスパイル後の JavaScript コードではなく、元の TypeScript コードを表示してブレークポイントを設置できるようにする必要がある。これを実現するために、ソースマップを有効化する。

```json
{
  "compilerOptions": {
    "sourceMap": true  // ← .js.map ファイルを生成し、TypeScript とのマッピング情報を提供
  }
}
```

**ソースマップの役割**:
- トランスパイル後の JavaScript コードと元の TypeScript コードを紐付ける
- デバッガーが JavaScript の実行位置を TypeScript の行番号に変換する
- `.js.map` ファイルとして出力される

**設定が無い場合の問題**:
- デバッグ時にトランスパイル後の JavaScript コードが表示される
- ブレークポイントが元のコードと一致せず、デバッグが困難になる

その他の TypeScript 設定については「TypeScript 設定」セクションを参照。

## コード品質管理（ESLint）

ESLintによる静的解析とコード品質の担保を実現する。

### 基本方針

本プロジェクトでは、TypeScriptを使用する**フロントエンド（Next.js/React）とBFF（NestJS）**に対してESLintを適用する。

### 設定ファイルの構成

**配置場所**:
```
front_bff_shared/
  └── eslint/
      └── base.config.mjs  # 共通ESLint設定（フロントエンド + BFF）

frontend/
  └── eslint.config.mjs    # フロントエンド用ESLint設定（共通 + 固有）

bff/
  └── eslint.config.mjs    # BFF用ESLint設定（共通 + 固有）
```

**管理体制**:
- 設定ファイルは基盤チームが整備・保守
- 共通ルールは `front_bff_shared/eslint/base.config.mjs` で一元管理
- 各プロジェクト（frontend/bff）は共通設定をインポートし、固有設定を追加
- 変更が必要な場合は基盤チームに相談すること

### 共通設定（フロントエンド + BFF）

TypeScriptを使用するフロントエンドとBFFで共通して適用するルール。

**実装ファイル**: `front_bff_shared/eslint/base.config.mjs`

```javascript
// front_bff_shared/eslint/base.config.mjs
import js from '@eslint/js';
import tseslint from '@typescript-eslint/eslint-plugin';
import importPlugin from 'eslint-plugin-import';

export default [
  js.configs.recommended,
  {
    plugins: {
      '@typescript-eslint': tseslint,
      'import': importPlugin,
    },
    rules: {
      // 循環参照の禁止
      'import/no-cycle': 'error',
      
      // インポート順序の固定
      'import/order': ['error', {
        'groups': [
          'builtin',   // Node.js組み込みモジュール
          'external',  // node_modules
          'internal',  // @/shared, @/features
          'parent',
          'sibling',
        ],
      }],
      
      // 未使用変数の禁止（_で始まる変数は除外）
      '@typescript-eslint/no-unused-vars': ['error', {
        'argsIgnorePattern': '^_',
      }],
      
      // any型の禁止
      '@typescript-eslint/no-explicit-any': 'error',
    },
  },
];
```

**各プロジェクトでのインポート例**:

```javascript
// frontend/eslint.config.mjs
import sharedConfig from '@/front_bff_shared/eslint/base.config.mjs';

export default [
  ...sharedConfig,  // 共通設定を展開
  // フロントエンド固有の設定を追加
];
```

```javascript
// bff/eslint.config.mjs
import sharedConfig from '@/front_bff_shared/eslint/base.config.mjs';

export default [
  ...sharedConfig,  // 共通設定を展開
  // BFF固有の設定を追加
];
```

**使用ツール・プラグイン**:

| 分類 | 名称 | 役割 |
| :--- | :--- | :--- |
| **基本ルールセット** | `@eslint/js` | JavaScript推奨ルール |
| **TypeScript** | `@typescript-eslint/eslint-plugin` | TypeScript専用ルール |
| **拡張プラグイン** | `eslint-plugin-import` | ディレクトリ間の依存関係やインポート順序を専門にチェック |

**共通適用ルール**:

| ルール名 | 役割 | 具体的な運用例 |
| :--- | :--- | :--- |
| `import/no-cycle` | 循環参照の禁止 | A と B のファイルが互いに呼び出し合う循環状態を検知してビルドエラーにする |
| `import/order` | インポート順序の固定 | `ライブラリ（node_modules）` → `src/shared/`（共通） → `機能内 repository/ api/` の順に統一し、コードの可読性を均一化する |
| `@typescript-eslint/no-unused-vars` | 未使用変数の禁止 | 定義しただけで使用されていない変数・インポートをエラーとし、デッドコードの蓄積を防ぐ（`_` で始まる変数は除外） |
| `@typescript-eslint/no-explicit-any` | `any` 型の禁止 | 型定義の放棄を禁止し、大規模開発に不可欠な型安全性を強制する |

### フロントエンド特有の設定

**使用ツール・プラグイン**:

| 分類 | 名称 | 役割 |
| :--- | :--- | :--- |
| **標準ルールセット** | `eslint-config-next` | Next.js / React のベストプラクティス（Hooks の書き方、画像最適化等）を強制 |
| **React Hooks** | `eslint-plugin-react-hooks` | React Hooks の正しい使用方法を強制 |
| **アクセシビリティ** | `eslint-plugin-jsx-a11y` | アクセシビリティ対応を支援 |

**フロントエンド特有のルール**:

| ルール名 | 役割 | 具体的な運用例 |
| :--- | :--- | :--- |
| `no-restricted-imports` | 特定パスのインポート禁止 | `features/` から `app/` への逆参照を禁止。他機能の `api/` や `repository/` を `index.ts` を介さず直接参照することをエラーにする |
| `react-hooks/rules-of-hooks` | Hooks の正しい使用 | React Hooks をコンポーネント内でのみ使用することを強制 |
| `react-hooks/exhaustive-deps` | 依存配列チェック | `useEffect` の依存配列漏れを検知 |
| `jsx-a11y/alt-text` | alt 属性の必須化 | 画像に `alt` 属性を必須化 |
| `jsx-a11y/aria-props` | ARIA 属性の正しい使用 | ARIA 属性の正しい使用を強制 |

### BFF特有の設定

**BFF特有のルール**:

| ルール名 | 役割 | 具体的な運用例 |
| :--- | :--- | :--- |
| `no-console` | console.log の警告 | `console.log` を警告（本番環境では Logger 等を使用）。`console.warn` と `console.error` は許可 |
| `@typescript-eslint/no-floating-promises` | 非同期処理の適切な使用 | Promise を適切に await または catch する |
| `@typescript-eslint/explicit-function-return-type` | 戻り値の型定義 | 関数の戻り値の型を明示的に定義することを推奨（warn） |

### 依存関係ルールの強制

依存関係ルールの遵守はコードレビューに依存せず、ESLintによりビルド時に自動検出・エラー化する。

**禁止される依存の方向**:

| 禁止パターン | 具体例 | 理由 |
| :--- | :--- | :--- |
| `features` → `app` | `features/` から `app/page.tsx` を import | 逆方向参照。ルーティングと機能が密結合になる |
| `api` → `hooks` | `api/` から `hooks/` を呼び出す | 下位層が上位層を参照する逆転 |
| LV3-A → LV3-B の内部 | 他機能の `api/` や `repository/` を直接 import | カプセル化違反。`index.ts` 経由のみ許可 |
| **機能間の直接参照** | `features/A` から `features/B` を直接 import | 機能間の密結合を引き起こす。複数機能で使用するコンポーネントは `shared/` に配置すること |
| 循環参照 | A が B を import し、B が A を import | 予測不能な初期化順序を引き起こす |

**機能間参照の自動検出**:

`no-restricted-imports` ルールにより、機能間の直接参照を検出してビルドエラー化する。

```javascript
// eslint.config.mjs（設定例）
{
  rules: {
    'no-restricted-imports': [
      'error',
      {
        patterns: [
          {
            group: ['**/features/*/**'],
            message: '機能間の直接参照は禁止です。複数機能で使用するコンポーネントは shared/ に配置してください。'
          }
        ]
      }
    ]
  }
}
```

**エラー表示例**:
```
error: 機能間の直接参照は禁止です。複数機能で使用するコンポーネントは shared/ に配置してください。
  import { Button } from '@/features/patient/components/Button'
                         ^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^
```

詳細なディレクトリ階層と依存関係の設計方針については「[07.ルーティングとレンダリング設計方針.md](07.ルーティングとレンダリング設計方針.md)」を参照のこと。

### 実行方法

**手動実行**:

フロントエンドまたはBFFのディレクトリで以下を実行：

```bash
# リントチェック
npm run lint

# 自動修正可能なエラーを修正
npm run lint:fix
```

**package.json への設定追加**:

```json
{
  "scripts": {
    "lint": "eslint . --ext .ts,.tsx",
    "lint:fix": "eslint . --ext .ts,.tsx --fix"
  }
}
```

BFFの場合は `.tsx` を除外：

```json
{
  "scripts": {
    "lint": "eslint . --ext .ts",
    "lint:fix": "eslint . --ext .ts --fix"
  }
}
```

**保存時の自動実行**:

VSCode拡張機能「ESLint」をインストールすることで、ファイル保存時に自動でリントチェックと修正が実行される。

DevContainer環境では、拡張機能が自動的にインストール・有効化される設定となっている。

`.vscode/settings.json`:
```json
{
  "editor.codeActionsOnSave": {
    "source.fixAll.eslint": "explicit"
  }
}
```
