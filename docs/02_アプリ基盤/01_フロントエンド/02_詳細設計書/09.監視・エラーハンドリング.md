# 09. 監視・エラーハンドリング

本章では、**エラー発生時の即時検知と適切な UI 制御**を担う。GlitchTip（Sentry互換SDK）を活用した実行時例外の自動収集、医療システムにおいて最優先される個人情報（PHI）の保護、およびエラー再現性を高めるための操作履歴収集の規約を定義する。

**エラーモニタリングツールについて**：
- **採用ツール**: GlitchTip（Sentry互換のOSS）を採用
- **運用方針**: 詳細なエラーモニタリングツールの運用方針・構築手順・将来移行オプションについては [01_エラー監視ツール_GlitchTip設計.md](../../05_システム監視・通知サービス/02_詳細設計書/01_エラー監視ツール_GlitchTip設計.md) を参照

## 本章の対象範囲と他章との境界

本章は「エラーが起きたとき何が起きたかを知る」ことに特化する。

| 観点 | 本章（09章） | 14章 操作・監査ログ基盤 | 15章 運用監視基盤 |
|---|---|---|---|
| **目的** | 障害の即時検知・原因特定・開発者通知 | 操作証跡・コンプライアンス対応 | 性能劣化の把握・インフラ異常の予兆検知 |
| **発動条件** | エラー発生時（リアクティブ） | ユーザーが操作したとき（常時） | 常時（定期的なメトリクス収集） |
| **利用者** | 開発者・運用担当者 | 監査部門・法務・システム管理者 | SRE・インフラ担当・開発者 |
| **主なツール** | GlitchTip（Sentry互換OSS） | axiosClient → BFF → 監査ログ管理サービス | - |
| **送信データ** | スタックトレース、テナントID、Breadcrumbs | 操作種別、対象リソースID、ユーザーID、タイムスタンプ | - |
| **データフロー** | クライアント → GlitchTip API → DB | クライアント → BFF → 監査ログ DB | - |
| **保存先** | GlitchTip DB | 監査ログ DB | - |

**重要な区別**：
- **Breadcrumbs（本章）**：エラー発生時にGlitchTipイベントへ添付される「エラー直前の操作履歴」。開発調査用であり、法的証拠ではない。
- **操作ログ（14章）**：全操作を常時記録する業務証跡。監査証跡として長期保存される。

**参照**：
- 本章で登場する実装ファイル（`axiosClient.ts`、`error.tsx`、`ErrorGuard.tsx` 等）の配置場所と役割については [00.ディレクトリ構成](./00.ディレクトリ構成.md) を参照のこと

## エラー種別と対応方針

方式設計書 5.1 で定義されたエラー種別ごとに、フロントエンド実装における具体的な対応方針を示す。

| エラー種別 | 発生源と概要 | 検知方法 | フロントエンドの対応 | GlitchTip送信 |
|---|---|---|---|---|
| **ネットワークエラー** | 通信断、タイムアウト | `axiosClient` のエラーハンドラで捕捉 | 通信環境確認を促すトースト表示、再試行ボタン提供 | 送信（ネットワーク状態を含む） |
| **APIエラー** | HTTP 4xx/5xx | `axiosClient` のレスポンス検証で捕捉 | ステータスコード別に汎用エラー画面またはトースト通知 | 送信（レスポンス内容含む） |
| **業務エラー** | バリデーションエラー、論理的データ不整合 | BFF から返却されるエラーレスポンスの `errors[].code`（後述「BFFエラーレスポンス」セクション）を判定 | フォーム該当フィールドにエラーメッセージ表示 | 送信しない（業務ロジック内の正常系） |
| **ランタイムエラー** | フロントエンドスクリプト内の予期しない例外 | Error Boundary で捕捉 | エラー画面表示、操作継続不可の旨を通知 | 送信（スタックトレース含む） |
| **認可エラー** | 認証/認可失敗（HTTP 401/403） | `axiosClient` のステータスコード判定 | 401: ログイン画面へリダイレクト / 403: 権限不足メッセージ表示 | 送信（認証状態を含む） |

**実装ファイル**：
- エラー検知・判定：`frontend/src/shared/api/axiosClient.ts`（基盤側で作成）
- Error Boundary：`frontend/src/app/error.tsx`（グローバル）、`frontend/src/app/(group-name)/error.tsx`（共通レイアウトグループ）、コンポーネント単位は `ErrorBoundary`（`react-error-boundary` ベース）で実装
  - 各Error Boundaryの詳細と使い分けについては、後述の「[Error Boundary 設計](#error-boundary-設計)」を参照

## エラー処理フロー

エラー発生から通知までのフローは、**エラーの発生箇所によって2つの独立した経路**に分かれる。

### フロー1: APIエラー（axios経由）

BFFとの通信中に発生したエラー（ネットワークエラー、HTTPエラー、業務エラー等）の処理フロー。

  - コンポーネント単位で発生
  - モーダルウィンドウで表示
  - 発生頻度が高い

```
APIリクエスト送信 → BFFからエラーレスポンス返却
    ↓
【捕捉】axios.client.ts の response interceptor で捕捉
    ↓
【判定】業務エラー（REQUIRED/INVALID_FORMAT/INVALID_TYPE）か判定
    ├─ YES → GlitchTip送信しない（業務ロジック内の正常系）
    │         └─ コンソールログ出力：「Business error (not sent to GlitchTip)」
    └─ NO  → 【ログ】GlitchTipへ非同期送信
              ├─ tenant_id: リクエストヘッダー（x-tenant-id）から取得
              ├─ trace_id: BFFエラーレスポンスから取得
              ├─ extra: status, url, method, errorResponse
              └─ コンソールログ出力：「API Error sent to GlitchTip」
    ↓
Promise.reject(error) で呼び出し元に返却
    ↓
【呼び出し元】try/catch または .catch() でエラーハンドリング
    ↓
【通知】呼び出し元が決定したUI表示（モーダルウィンドウ表示）
```

**特徴**:
- error.tsx（Error Boundary）は**通らない**
- GlitchTip送信と呼び出し元への返却は**並行処理**（非同期送信）
- UI表示は呼び出し元の責任（柔軟な制御が可能）

---

### フロー2: ランタイムエラー（Error Boundary経由）

フロントエンド（React/Next.js）のコンポーネント内で発生したJavaScriptエラー（TypeError, ReferenceError等）の処理フロー。

  - システムエラー（バグ）
  - error.tsxで画面全体表示
  - 発生頻度が低い

```
コンポーネント内でエラー発生（例: null参照、undefined参照）
    ↓
【捕捉】error.tsx（グローバルError Boundary）で捕捉
    ↓
【ログ】useEffect内でGlitchTipへ非同期送信
    ├─ tenant_id: ログイン時に設定済みの値（Sentry.setTagで設定）
    ├─ trace_id: なし（BFFを経由していないため）
    ├─ 自動収集: exception, stacktrace, breadcrumbs等
    └─ コンソールログ出力：「Global Error Boundary: Error sent to GlitchTip」
    ↓
【通知】error.tsxのUIを表示（画面全体）
```

**特徴**:
- axios interceptorは**通らない**
- 呼び出し元への返却は**なし**（Error Boundaryで処理完結）
- UI表示は固定（error.tsxのデザイン）
- 画面全体がエラーUIに切り替わる

---

### エラー経路の比較表

| 項目 | フロー1: APIエラー | フロー2: ランタイムエラー |
|---|---|---|
| **発生場所** | BFF通信中 | コンポーネント内 |
| **捕捉箇所** | axios.client.ts response interceptor | error.tsx（Error Boundary） |
| **判定処理** | 業務エラー判定あり | なし |
| **GlitchTip送信** | 業務エラー以外を送信 | 全て送信 |
| **tenant_id取得** | リクエストヘッダー（`x-tenant-id`）から動的取得 | ログイン時に設定済み（`Sentry.setTag`で設定、以降自動付与） |
| **trace_id** | BFFエラーレスポンスから取得 | なし |
| **呼び出し元への返却** | あり（Promise.reject） | なし |
| **画面影響** | 部分的（モーダルウィンドウ） | 全画面（error.tsx） |

### 業務エラー判定（フロー1のみ）

**判定箇所**: `axios.client.ts` response interceptor内

**判定ロジック**:
```typescript
const isBusinessError =
  status === 400 &&
  ['REQUIRED', 'INVALID_FORMAT', 'INVALID_TYPE'].includes(errorCode);
```

**判定結果と処理**:

| 判定結果 | GlitchTip送信 | 処理内容 |
|---|---|---|
| 業務エラー | ❌ しない | コンソールログ出力のみ、呼び出し元に返却 |
| その他のエラー | ✅ する | GlitchTip送信 + コンソールログ + 呼び出し元に返却 |

**理由**: 業務エラー（バリデーションエラー）は業務ロジック内の正常系のため、エラー監視の対象外とする。

### GlitchTip送信処理の詳細

#### フロー1: APIエラーのGlitchTip送信

**送信箇所**: `axios.client.ts` response interceptor内

**実装コード**:
```typescript
// frontend/src/shared/plugins/axios.client.ts（抜粋）
axiosClient.interceptors.response.use(
  (response) => response,
  (error) => {
    const status = error.response?.status;
    const traceId = error.response?.data?.traceId;
    const errorCode = error.response?.data?.errors?.[0]?.code;
    
    // リクエストヘッダーから実際に送信したテナントIDを取得
    const tenantId = error.config?.headers?.['x-tenant-id'] as string | undefined;

    // 業務エラー判定
    const isBusinessError =
      status === 400 &&
      ['REQUIRED', 'INVALID_FORMAT', 'INVALID_TYPE'].includes(errorCode);

    if (!isBusinessError) {
      // GlitchTipへ非同期送信（メインスレッドをブロックしない）
      Sentry.captureException(error, {
        tags: {
          tenant_id: tenantId, // リクエストヘッダーから取得
          trace_id: traceId,   // BFFエラーレスポンスから取得
        },
        extra: {
          status,
          statusText: error.response?.statusText,
          url: error.config?.url,
          method: error.config?.method?.toUpperCase(),
          errorResponse: error.response?.data,
        },
      });
    }

    return Promise.reject(error); // 呼び出し元に返却
  }
);
```

**送信される情報**:
- `tags.tenant_id`: リクエストヘッダー（`x-tenant-id`）から動的取得
- `tags.trace_id`: BFFエラーレスポンスの`traceId`フィールドから取得
- `extra.*`: エラーの詳細情報（status, url, method, errorResponse）
- 自動収集: exception, stacktrace, breadcrumbs, contexts（ブラウザ・OS）, user.ip_address等

---

#### フロー2: ランタイムエラーのGlitchTip送信

**送信箇所**: `error.tsx` の `useEffect`内

**実装コード**:
```typescript
// frontend/src/app/error.tsx（抜粋）
'use client';

import * as Sentry from '@sentry/nextjs';
import { useEffect } from 'react';

export default function Error({ error, reset }: { error: Error; reset: () => void }) {
  useEffect(() => {
    // GlitchTipへ非同期送信（メインスレッドをブロックしない）
    Sentry.captureException(error);
    console.error('[Global Error Boundary] Error sent to GlitchTip:', {
      name: error.name,
      message: error.message,
    });
  }, [error]);

  return <div>{/* エラーUI */}</div>;
}
```

**送信される情報**:
- `tags.tenant_id`: SentryInitializer.tsxで事前設定済みの値（`Sentry.setTag('tenant_id', 'tenant_a')`）
- `tags.trace_id`: なし（BFFを経由していないため）
- `tags.patient_id`: 設定されている場合のみ（`setPatientContext()`呼び出し後）
- 自動収集: exception, stacktrace, breadcrumbs, contexts（ブラウザ・OS）, user.id, user.ip_address等

### データフロー（共通）

```
[クライアント側]              [GlitchTip]                    [DB]
エラー発生
   ↓
エラー捕捉
（axios interceptor または error.tsx）
   ↓
監査情報・Breadcrumbs 付与
   ↓
Sentry.captureException() ─────→ GlitchTip API で受信 ────→ DB に保存
（非同期送信）                    ↓
                           運用担当者に通知
```

**非同期処理による送信**:
- クライアント側からGlitchTipへのエラー送信は、**非同期処理**で行われる
- メインスレッドをブロックせず、ユーザーの操作を妨げない
- GlitchTipで受信したエラー情報は、GlitchTipのDBに保存され、運用担当者がダッシュボードで確認できる

### UI通知処理の詳細

#### フロー1: APIエラーのUI通知

**通知方法**: 呼び出し元の責任（柔軟な制御が可能）

axios.client.tsはエラーを`Promise.reject(error)`で呼び出し元に返却するため、呼び出し元で`try/catch`または`.catch()`でエラーハンドリングを行い、適切なUI通知を実装する。

**実装例（モーダル表示）**:
```typescript
// APIエラーの呼び出し元での処理例（モーダル表示）
import { axiosClient } from '@/shared/plugins/axios.client';

async function savePatient(data: PatientData) {
  try {
    const response = await axiosClient.post('/patients', data);
    showSuccessModal('保存しました');
  } catch (error: any) {
    const status = error.response?.status;
    const errors = error.response?.data?.errors || [];
    const errorMessage = errors[0]?.message || 'エラーが発生しました';

    if (status === 400) {
      // バリデーションエラー：エラー一覧をモーダルで表示
      const errorList = errors.map((e: any) => ({
        field: e.field,
        message: e.message,
      }));
      
      showValidationErrorModal({
        title: '入力内容に不備があります',
        errors: errorList,
      });
    } else if (status === 409) {
      // 排他競合エラー：専用モーダル
      showConflictModal({
        title: '編集が競合しました',
        message: errorMessage,
        onRetry: () => savePatient(data),
      });
    } else if (status >= 500) {
      // サーバーエラー：エラーモーダル
      showErrorModal({
        title: 'サーバーエラーが発生しました',
        message: 'しばらく時間をおいて再試行してください',
      });
    } else {
      // その他のエラー：汎用エラーモーダル
      showErrorModal({
        title: 'エラーが発生しました',
        message: errorMessage,
      });
    }
  }
}
```

**注記**: 
- バリデーションエラー（400）を含む全てのAPIエラーをモーダルで表示
- 認証エラー（401）の処理については認証・認可設計書を参照

#### フロー2: ランタイムエラーのUI通知

**通知方法**: error.tsxのUIで固定

error.tsx（グローバルError Boundary）がエラーをキャッチした時点で、画面全体がエラーUIに切り替わる。呼び出し元への返却はなく、ユーザーは「再試行」または「ホームに戻る」のいずれかを選択する。

**実装**: `frontend/src/app/error.tsx`

**表示内容**:
- エラーアイコン（赤い警告マーク）
- エラー種別（`error.name`）に応じたタイトルとメッセージ
- 再試行ボタン（`reset()`関数を呼び出してセグメントを再レンダリング）
- ホームに戻るリンク
- ページ下部にエラー詳細表示

**エラー種別別のメッセージ**:

| error.name | タイトル | 説明文 |
|---|---|---|
| `NetworkError` | 通信エラーが発生しました | ネットワーク接続を確認して、再試行してください。 |
| `TypeError` | システムエラーが発生しました | データの処理中にエラーが発生しました。再試行してください。 |
| `ReferenceError` | システムエラーが発生しました | データの処理中にエラーが発生しました。再試行してください。 |
| その他 | システムエラーが発生しました | システムが停止しました。時間をおいて再試行するか、システム管理者に連絡してください。 |

## エラー発生時の送信情報

エラー発生時にGlitchTipへ送信される情報項目と、その取得元を定義する。フロントエンド（ブラウザ）とBFF（NestJS）で送信される情報が異なるため、それぞれを明示する。

## Error Boundary 設計

Next.js App Router の `error.tsx` を使用し、**フロントエンド（React/Next.js）内で発生するランタイムエラー**を捕捉する。

本プロジェクトでは、**階層的なError Boundary（機能群単位・コンポーネント単位）は採用せず、グローバルError Boundaryに集約する**。

**理由**：
- 階層的なError Boundaryは設計・実装・テストが複雑になる
- 業務システムで予期しないReactエラーが出る時点で、システムが正常に動作していない状態
- この場合、画面全体がエラー表示になっても業務上問題ない（発生頻度も少ない）
- エラー情報は画面上と、詳細情報はGlitchTipで確認できるため十分

### グローバル Error Boundary

フロントエンド（Next.js）の React コンポーネントツリー内で発生する予期しないエラーを捕捉する最終防波堤。

**キャッチ対象（フロントエンド内のみ）**：
- React コンポーネントのレンダリング中に発生した例外（`throw new Error()` 等）
- `useEffect` 内での未捕捉例外

**キャッチ対象外**：
- BFF / BE 側で発生したエラー（BFF・BE のエラーは各サーバー側で処理される）
- `axiosClient` が捕捉した API エラー・ネットワークエラー（`axiosClient` の Interceptor で先に処理される）
- イベントハンドラ内の例外（`onClick` 等。try/catch で個別に処理する必要がある）

**配置場所**：`frontend/src/app/error.tsx`

**責任者**：基盤チームが作成・管理

**実装例**：
```tsx
'use client';

import * as Sentry from '@sentry/nextjs';
import { useEffect } from 'react';

export default function Error({ error, reset }: { error: Error; reset: () => void }) {
  useEffect(() => {
    // Sentry へエラー送信（即座に非同期実行）
    Sentry.captureException(error);
  }, [error]);

  const errorMessages: Record<string, { title: string; description: string }> = {
    NetworkError: {
      title: '通信エラーが発生しました',
      description: 'ネットワーク接続を確認して、再試行してください。',
    },
    AuthenticationError: {
      title: '認証エラーが発生しました',
      description: 'セッションが切れました。再ログインしてください。',
    },
  };

  const { title, description } = errorMessages[error.name] ?? {
    title: 'システムエラーが発生しました',
    description: 'システムが停止しました。時間をおいて再試行するか、システム管理者に連絡してください。',
  };

  return (
    <div className="p-8 text-center">
      <h2 className="text-xl font-bold text-red-600">{title}</h2>
      <p className="mt-2 text-gray-600">{description}</p>
      <button 
        onClick={() => reset()} 
        className="mt-4 px-4 py-2 bg-blue-500 text-white rounded"
      >
        再試行する
      </button>
    </div>
  );
}
```

**動作**：
- Server Component 内で `throw new Error()` が発生した場合に自動発動
- `reset()` 関数で該当セグメントの再レンダリングを試行

**確認事項**：
- Error Throw の必須性：Server Component で `error.tsx` を発動させるには `throw` による例外発生が必要
- 単に `return <ErrorUI />` では Error Boundary は発動しない

## BFFエラーレスポンス

BFF からフロントエンドへ返却されるすべてのエラーレスポンス（バリデーション失敗・認証/認可エラー・排他競合・システム障害等）について、共通の構造とエラーコード体系を定義する。本セクションは「エラー種別と対応方針」表（前述）の **業務エラー / API エラー / 認可エラー** 行に対応する。

### 方針

すべての BFF エラーレスポンスは [RFC 9457 (Problem Details for HTTP APIs)](https://www.rfc-editor.org/rfc/rfc9457.html) に準拠する。プロジェクト要件として以下のローカライズを適用する:

- `type` フィールドは含めない
- `title` / `detail` / `errors[].message` は日本語
- `instance` は URI ではなくリクエストパス文字列
- `traceId` を `errors[]` の後ろに追加（オブザーバビリティ連携用）
- 業務エラー・認可エラー・システムエラーを問わず、エラー詳細は **必ず `errors[]` に1件以上格納**する（単一エラーでも配列で表現）

### レスポンスボディ構造

| キー | 型 | 必須 | 概要 |
|---|---|---|---|
| `title` | string | 必須 | 人間可読な日本語の短い要約（例: `"不正なリクエストです。"`） |
| `status` | number | 必須 | HTTP ステータス（`status` フィールドの値と HTTP レスポンスのステータスは一致させる） |
| `detail` | string | 必須 | 日本語の詳細メッセージ |
| `instance` | string | 必須 | エラーが発生したリクエストパス（例: `"/clinical/entry/vital-info"`。URI ではない） |
| `errors` | array | 必須 | エラー詳細。少なくとも1要素を必ず格納する |
| `errors[].field` | string | 必須 | エラー対象のフィールドパス。ドット区切り（例: `items.0.name`）。フィールド単位エラーでない場合は空文字列 `""` |
| `errors[].code` | string | 必須 | プロジェクト標準のエラーコード（後述） |
| `errors[].message` | string | 必須 | ユーザー向け日本語メッセージ（i18n は `front_bff_shared/i18n` のキーから取得） |
| `errors[].meta` | object | 任意 | コードごとの拡張情報（例: CONFLICT 時の `lockedByUserName`）。値は `Record<string, unknown>` |
| `traceId` | string | 必須 | リクエスト追跡ID（UUID形式）。Sentry/操作監査ログとの紐付けに使用 |

### レスポンス例

#### 例1: バリデーションエラー（HTTP 400・複数フィールド）

      "field": "bloodPressure",
      "code": "INVALID_FORMAT",

### `errors[].code` の一覧

`errors[].code` は HTTP ステータスごとに次のコードを使用する。フロントエンドは HTTP ステータスと本コードを判定キーとして UI 側のエラー分岐を行う。

| HTTP | コード | 意味 | `errors[].field` | `errors[].meta` 例 |
|---|---|---|---|---|
| 400 | `REQUIRED` | 必須項目が未指定（`undefined` / `null` の到来） | フィールドパス | — |
| 400 | `INVALID_FORMAT` | 形式・範囲・列挙値・複合ルール違反 | フィールドパス | — |
| 400 | `INVALID_TYPE` | 型不一致（`REQUIRED` 以外） | フィールドパス | — |
| 400 | `VALIDATION_DELETE` | 削除不可業務ルール違反（自動連携行の削除試行等） | 空文字列 or フィールドパス | — |
| 401 | `UNAUTHORIZED` | 認証失敗（JWT 検証失敗・セッション切れ） | 空文字列 | — |
| 403 | `FORBIDDEN` | 認可失敗（権限不足） | 空文字列 | — |
| 404 | `NOT_FOUND` | リソース不存在 | 空文字列 | — |
| 409 | `CONFLICT` | 排他競合（編集ロック・期限切れ） | 空文字列 | `lockedByUserName: string`（他ユーザーロック中の場合のみ） |
| 500 | `SYSTEM_ERROR` | サーバー内部エラー | 空文字列 | — |
| 502 | `BAD_GATEWAY` | 上流サービス障害 | 空文字列 | — |
| 504 | `TIMEOUT` | タイムアウト | 空文字列 | — |

**コードの拡張ルール**:
- 機能固有の業務エラーコード（例: `ORDER_ALREADY_CONFIRMED` 等）を追加する場合は、HTTP 400 配下の業務エラーとして個別機能設計書で定義する
- 機能固有コードもこの統一フォーマット（`errors[].code` に格納）で返却する。ルートに `code` フィールドを別途設けない

### Zod 内部コードからプロジェクトコードへの変換ルール

BFF 側の `ZodExceptionFilter`（[03章 ZodExceptionFilter のコード例](./03.TypeScript型管理とスキーマ共有.md#バリデーションエラーのハンドリング) 参照）が Zod の `ZodIssue.code` をプロジェクトコード（`REQUIRED` / `INVALID_FORMAT` / `INVALID_TYPE`）へ変換する。フロントエンドは変換後の `errors[].code` のみを参照すればよい。

| Zod 内部コード | 条件 | プロジェクトコード |
|---|---|---|
| `invalid_type` | `received` が `undefined` / `null` | `REQUIRED` |
| `invalid_type` | 上記以外 | `INVALID_TYPE` |
| `too_small` / `too_big` | — | `INVALID_FORMAT` |
| `invalid_string` / `invalid_enum_value` 等 | — | `INVALID_FORMAT` |
| `custom`（`superRefine` 由来） | — | `INVALID_FORMAT`（固定） |

**`custom` を `INVALID_FORMAT` 固定にする理由**: `superRefine` は複数フィールドにまたがる業務ルール検証であり、「値の組み合わせが業務ルール上不正である状態」を表す。これは形式違反の一種として扱える。フロントエンドの表示は `errors[].message` をそのまま用いれば十分で、コードによる細分は不要と判断した。

### フロントエンドでの取り扱い

- `axiosClient` は HTTP ステータスごとにレスポンスを判定し、`error.response.data` をそのまま呼び出し側に渡す（[01章 axiosClient Response Interceptor](./01.フロントエンド・BFF共通基盤設計.md) 参照）
- フォーム呼び出し側は HTTP 400 のレスポンスから `errors[].field` をフォームの React Hook Form フィールド名と突き合わせて該当フィールドにエラーメッセージを表示する
- 認可エラー（401/403）・競合エラー（409）・システムエラー（5xx）は `errors[].code` をキーにフロント側の UI 制御（リダイレクト・モーダル・トースト等）へ分岐する
- `errors[].message` は BFF から日本語で届くため、フロントエンドでの再翻訳は不要
- `errors[].meta` の参照は `errors[].code` ごとに必要時のみ行う（例: `code === 'CONFLICT'` のときのみ `meta.lockedByUserName` を読む）
- `traceId` は表示せず、ログ解析時に BFF/操作監査ログと突き合わせる用途で保持する
- フロント側の E-code（E001〜E999）は本レスポンスの `errors[].code` から内部マッピングで導出する。BFF はフロント E-code を返さない

### エラー種別と Sentry 送信の関係

| HTTP / `errors[].code` | エラー種別 | Sentry 送信 | UI 表示 |
|---|---|---|---|
| 400 / `REQUIRED`・`INVALID_FORMAT`・`INVALID_TYPE` | 業務エラー（バリデーション） | しない（業務ロジック内の正常系） | フォームのフィールド単位メッセージ |
| 400 / `VALIDATION_DELETE` 等 | 業務エラー（業務ルール違反） | しない | ダイアログ |
| 401 / `UNAUTHORIZED` | 認可エラー | する | ログイン画面へリダイレクト |
| 403 / `FORBIDDEN` | 認可エラー | する | 権限エラーダイアログ |
| 404 / `NOT_FOUND` | API エラー | する | データ取得エラーダイアログ |
| 409 / `CONFLICT` | API エラー | する | 同時編集エラーダイアログ |
| 500 / `SYSTEM_ERROR`、502 / `BAD_GATEWAY`、504 / `TIMEOUT` | システムエラー | する | 共通エラー画面/トースト |

## ユーザー通知 UI 設計

方式設計書 5.3 で定義された重大度別通知方針を、具体的な UI 実装パターンに落とし込む。

**通知の分岐判定箇所**：

重大度別の通知方法（画面全体表示／モーダル／トースト／Alert）への分岐は、`② 判定（Classification）` で使用する `errorClassifier.ts` が返したエラー種別をもとに、`axiosClient.ts` の Interceptor（API エラー）または Error Boundary（ランタイムエラー）内で決定する。

```
errorClassifier.ts（種別を返す）
         ↓
axiosClient.ts（API エラー） または Error Boundary（ランタイムエラー）  ←ここで通知の分岐を判定する
         ↓
エラー種別に応じた通知メソッドを呼び出す
（致命的 / 重度 / 軽微 / 部分的）
```

| 重大度 | 通知方法 | 適用エラー種別 | UI 要素 | 実装場所 | 責任者 |
|---|---|---|---|---|---|
| **致命的（Critical）** | 画面全体表示（Error Boundary） | サーバー側エラー（5xx）、重要 API の通信断 | エラー画面、再試行ボタン | `frontend/src/app/error.tsx` | 基盤チーム |
| **重度（Severe）** | 持続的モーダル | データ整合性エラー、更新競合、権限不足（403） | モーダルダイアログ、閉じるボタン無効 | `frontend/src/shared/components/molecules/ErrorModal.tsx` | 基盤チーム |
| **軽微（Minor）** | トースト通知 | バリデーション失敗、任意項目の軽微なエラー | react-hot-toast（3秒自動消去） | `react-hot-toast` を直接呼び出し | 基盤チーム（`<Toaster />` 設置） |

### 致命的エラー：Error Boundary 画面

**ファイルパス**：`frontend/src/app/error.tsx`

**責任者**：基盤チームが作成・管理

**表示仕様**：

メッセージは固定文言ではなく、`error.name`（エラー種別）に応じて見出しと説明文を切り替える。

| `error.name` の値（例） | 見出し | 説明文 |
|---|---|---|
| `NetworkError` | 「通信エラーが発生しました」 | 「ネットワーク接続を確認して、再試行してください。」 |
| `AuthenticationError` | 「認証エラーが発生しました」 | 「セッションが切れました。再ログインしてください。」 |
| `ServerError` / その他 | 「システムエラーが発生しました」 | 「システムが停止しました。時間をおいて再試行するか、システム管理者に連絡してください。」 |

| 項目 | 内容 |
|---|---|
| 配色 | 見出し：赤（`text-red-600`）／説明：グレー（`text-gray-600`） |
| アクション | 「再試行する」ボタン（`reset()` を呼び出し、該当セグメントを再レンダリング） |
| レイアウト | 画面中央寄せ、全画面占有 |

**入力パラメータ**（Next.js App Router が自動で渡す）：

| パラメータ | 型 | 説明 |
|---|---|---|
| `error` | `Error` | 発生したエラーオブジェクト。`error.name` と `error.message` を使って表示メッセージを組み立てる |
| `reset` | `() => void` | 該当ルートセグメントを再レンダリングする関数 |

詳細な実装（エラーログ送信含む）は「Error Boundary 設計 > グローバル Error Boundary」を参照。

### 重度エラー：モーダル

**ファイルパス**：`frontend/src/shared/components/molecules/ErrorModal.tsx`

**責任者**：基盤チームが作成・管理

**表示仕様**：

| 項目 | 内容 |
|---|---|
| メッセージ | 呼び出し元から `message` として受け取る（例：「データの整合性エラーが発生しました。ページを再読み込みしてください。」） |
| 配色 | タイトル：赤（`text-red-600`）／背景オーバーレイ：半透明ブラック |

## エラー監視ツール（GlitchTip）との連携

本プロジェクトでは、エラー監視ツールとして**GlitchTip**を採用している。
GlitchTipの構築・運用については [01_エラー監視ツール_GlitchTip設計.md](../../05_システム監視・通知サービス/02_詳細設計書/01_エラー監視ツール_GlitchTip設計.md) を参照。

本章では、フロントエンドとBFFからGlitchTipへエラー情報を送信する実装方法を定義する。

### GlitchTip連携の概要

**送信タイミング**:
- フロントエンド: APIエラー（axios interceptor）、ランタイムエラー（Error Boundary）
- BFF: 未処理例外（グローバル例外フィルター）

**送信先**:
- 開発環境: `http://localhost:8080`
- 本番環境: 【参照: GlitchTip設計書】

**使用SDK**:
- フロントエンド: `@sentry/nextjs`
- BFF: `@sentry/node`

---

### フロントエンド（ブラウザ）のエラー収集

#### エラー送信方式

**使用SDK**: `@sentry/nextjs`

**初期化箇所**: `frontend/src/shared/plugins/SentryInitializer.tsx`（'use client'コンポーネント）

**送信タイミング**: エラー捕捉直後、非同期で即座に送信

**送信先**: GlitchTip API（開発環境: `http://localhost:8080`、本番環境: 【TBD】）

**送信フロー**：
```
[ブラウザ]
  ↓ エラー発生（axiosClient / Error Boundary）
  ↓
Sentry.captureException(error) 呼び出し
  ↓ Breadcrumbs付与（最大50件）
  ↓ beforeSendフック実行（PHIフィルタリング）
  ↓
GlitchTip API へ非同期送信（HTTPS）
  ↓
[GlitchTip サーバー]
  ↓ PostgreSQL に保存
  ↓ ダッシュボードに表示
  ↓ アラート通知（Critical/High のみ）
```

**実装概要**：

`SentryInitializer.tsx`では、以下の処理を行う：
1. `Sentry.init()`でGlitchTip接続を初期化（DSN、environment、tracesSampleRate、maxBreadcrumbs、beforeSendフックを設定）
2. 認証後、`Sentry.setTag('tenant_id', ...)`と`Sentry.setUser({ id: ... })`でテナント情報を設定
3. `layout.tsx`に`<SentryInitializer />`コンポーネントとして組み込み、アプリ起動時に自動実行

---

### BFF（NestJS）のエラー収集

#### エラー送信方式

**使用SDK**: `@sentry/node`

**初期化箇所**: `product/bff/src/index.ts`

**グローバル例外フィルター**: `product/bff/src/shared/filters/sentry-exception.filter.ts`

**送信タイミング**: 未処理例外発生時、自動送信

**送信先**: GlitchTip API（コンテナ間通信: `http://glitchtip:8000`）

**送信フロー**：
```
[BFF（NestJS）]
  ↓ 未処理例外発生（HTTPException / ランタイムエラー）
  ↓
SentryExceptionFilter.catch() で捕捉
  ↓ テナントID・エンドポイント・HTTPメソッド等を付与
  ↓ Sentry.captureException() 呼び出し
  ↓
GlitchTip API へ非同期送信（コンテナ間通信）
  ↓
[GlitchTip サーバー]
  ↓ PostgreSQL に保存
  ↓ ダッシュボードに表示
  ↓ アラート通知（Critical/High のみ）
```

**実装概要**：

**① index.tsでのSentry初期化**：
- `Sentry.init()`でGlitchTip接続を初期化（DSN、environment、tracesSampleRate、beforeSendフックを設定）
- グローバル例外フィルター（`SentryExceptionFilter`）を登録
- リクエストごとに`x-tenant-id`ヘッダーからテナントIDを取得し、`Sentry.setTag()`で設定するミドルウェアを追加

**② グローバル例外フィルターの実装**（`product/bff/src/shared/filters/sentry-exception.filter.ts`）：

**配置場所**: `product/bff/src/shared/filters/sentry-exception.filter.ts`

**責任者**: 基盤チームが作成・管理

**役割**:
- NestJSの`@Catch()`デコレータで全ての未処理例外を自動捕捉
- リクエストヘッダーから`x-tenant-id`を取得
- `Sentry.captureException()`でGlitchTipにエラー送信（テナントID、エンドポイント、HTTPメソッド、クエリパラメータ、リクエストボディを付与）
- クライアントには標準化されたエラーレスポンス（statusCode、message、timestamp、path）を返却

## 実装ルール

### エラーハンドリング

**やっていいこと**：
- グローバルError Boundaryで捕捉したエラーをGlitchTipに送信する
- ネットワークエラー時に再試行ボタンを提供する
- 業務エラー（バリデーションエラー等）はトースト通知で軽微に扱う
- APIエラーは呼び出し元で適切にハンドリングし、モーダルやトーストで通知する

**やってはいけないこと**：
- Error Boundary 内で再度エラーを throw する（無限ループの危険）
- 業務ロジック内の正常系エラー（バリデーションエラー等）をGlitchTipに送信する（ノイズが増大）
- エラーメッセージに技術的詳細（スタックトレース、内部変数名等）をそのままユーザーに表示する

### GlitchTip連携

**やっていいこと**：
- 全エラーに基本監査情報（ユーザーID、テナントID）を付与する
- 必要に応じて、ユーザーロール・診療科・患者ID等の任意監査情報を追加する
- PHI含有可能性のあるフィールドは `beforeSend` で必ず削除する
- Breadcrumbs を活用してエラー再現手順を把握する
- 環境変数未設定時でもログ出力だけは継続する（デバッグ用）

**やってはいけないこと**：
- `beforeSend` フックを省略し、PHI含有可能性のあるフィールドをそのままGlitchTipに送信する
- 監査情報の付与を忘れる（マルチテナント環境で影響範囲が特定できなくなる）
- Breadcrumbs の最大記録数を過度に増やす（ブラウザメモリを圧迫）
- 業務エラー（バリデーションエラー等）をGlitchTipに送信する（ノイズが増大）

### ログ解析の標準化

**やっていいこと**：
- `front_bff_shared` で定義された型規約を遵守する
- エラーメッセージや付随するデータ構造を統一し、BFF 側のログと突き合わせやすくする

**やってはいけないこと**：
- 各コンポーネントで独自のエラー構造を定義し、解析を困難にする
