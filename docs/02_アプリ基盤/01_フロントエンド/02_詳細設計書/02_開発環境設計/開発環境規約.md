## 1. 基盤設定ファイル変更禁止

基盤チームが整備・保守する設定ファイルは、アプリ実装チームが直接修正してはならない。
変更が必要な場合は必ず基盤チームに相談すること。

**変更禁止ファイル**:

| ファイル | バイパスで起こる事故 |
|---|---|
| `tsconfig.json`（frontend/bff 各配置） | 型チェック設定の崩壊・パスエイリアス解決失敗 |
| `front_bff_shared/eslint/base.config.mjs` | 共通 ESLint ルールの片方向無効化・依存関係検出の欠落 |
| `frontend/eslint.config.mjs`、`bff/eslint.config.mjs` | プロジェクト固有 ESLint ルールの無効化 |

**例外条件**:

| 条件 | 許可範囲 |
|---|---|
| 基盤チームによる実装 | 全設定ファイルの変更可 |
| 設計上の変更要件が発生した場合 | 基盤チームに相談後に実施 |

**PR レビュー観点**:

```bash
# tsconfig.json の直接変更を検出
git diff HEAD --name-only | grep tsconfig.json

# eslint.config.mjs の直接変更を検出
git diff HEAD --name-only | grep eslint.config.mjs
```

## 2. バージョン管理規約

### 2.1 package.json の記法

`package.json` のバージョン指定は `^X.0.0` 形式（キャレット記法）を使用する。

```json
{
  "dependencies": {
    "react": "^19.0.0",
    "next": "^16.0.0",
    "axios": "^1.0.0"
  }
}
```

**キャレット記法の動作**:

| 動作 | 内容 |
|---|---|
| バージョン解決範囲 | `^19.0.0` は `19.x.x` の範囲で最新版を取得（メジャーは固定） |
| `npm update` 実行時 | メジャーを固定したまま、マイナー・パッチを最新化 |
| `package-lock.json` の役割 | 実際にインストールされた詳細バージョンを記録し、環境再現性を担保（Git 管理対象） |

> 根拠: [ADR-1](adr/semver-caret-strategy.md)

### 2.2 更新方針

| バージョン種別 | 内容 | 更新方針 |
|---|---|---|
| **メジャー** | 大規模な機能・デザイン変更 | 固定（手動更新・基盤チームによる事前検証必須） |
| **マイナー** | 部分的な機能改善・機能追加 | `npm update` 時に自動更新 |
| **パッチ** | バグ・誤字脱字の修正 | `npm update` 時に自動更新 |

### 2.3 メジャーバージョンアップ手順

1. 基盤チームで破壊的変更の影響範囲を調査
2. 検証環境での動作確認
3. `package.json` のメジャーバージョンを更新
4. テストスイートを実行し問題がないことを確認

**管理体制**:

| 項目 | 担当 |
|---|---|
| `package.json` のバージョン指定 | 基盤チーム |
| メジャーバージョンアップ | 基盤チームで検証後に全体へ展開 |
| マイナー・パッチ更新 | `npm update` で自動更新 |

## 3. 環境変数命名規則

### 3.1 命名規則

| 対象 | 実行場所 | ネーミング規則 | 例 | 理由 |
|---|---|---|---|---|
| フロントエンド（クライアント側） | ブラウザ | `NEXT_PUBLIC_*` 接頭辞が**必須** | `NEXT_PUBLIC_BFF_URL` | Next.js の仕様。ブラウザに埋め込まれる変数を明示的に区別 |
| フロントエンド（サーバー側） | Server Component | 任意の名前（接頭辞なし） | `SERVER_SIDE_BFF_URL` | ブラウザに公開されないため、接頭辞不要 |
| BFF | Node.js サーバー | 任意の名前（接頭辞なし） | `BACKEND_API_URL` | すべてサーバー側のみで参照されるため、接頭辞不要 |

### 3.2 セキュリティガイドライン

**やっていいこと**:

- 接続先 URL を環境変数で管理する
- 開発環境共通設定（`.env.development`）を Git にコミットする
- サーバー側の秘密情報を `NEXT_PUBLIC_` なしで定義する

**やってはいけないこと（Do NOT）**:

```bash
# NG: APIキー・認証トークンに NEXT_PUBLIC_ を付ける（ブラウザに埋め込まれて漏洩する）
NEXT_PUBLIC_API_SECRET_KEY=xxxxx
```

```bash
# NG: .env.local を Git にコミットする
# → .gitignore に必ず記載すること
.env.local
```

```bash
# NG: 本番環境の秘密情報を .env.production に直接書く
# → デプロイ時に CI/CD が環境変数として注入すること
API_SECRET_KEY=xxxxx
```

詳細は [環境変数設計.md](環境変数設計.md) を参照。

## 4. ESLint 依存関係ルール

### 4.1 禁止される依存の方向

| 禁止パターン | 具体例 | 理由 |
|---|---|---|
| `features` → `app` | `features/` から `app/page.tsx` を import | 逆方向参照。ルーティングと機能が密結合になる |
| `api` → `hooks` | `api/` から `hooks/` を呼び出す | 下位層が上位層を参照する逆転 |
| LV3-A → LV3-B の内部 | 他機能の `api/` や `repository/` を `index.ts` を介さず直接 import | カプセル化違反。`index.ts` 経由のみ許可 |
| **機能間の直接参照** | `features/A` から `features/B` を直接 import | 機能間の密結合を引き起こす。複数機能で使用するコンポーネントは `shared/` に配置すること |
| 循環参照 | A が B を import し、B が A を import | 予測不能な初期化順序を引き起こす |

> 根拠: [ADR-2](adr/eslint-dependency-rules.md)

### 4.2 PR レビュー観点

```bash
# 機能間の直接参照を検出
grep -rn "from '@/features/" src/features/ | grep -v "index"

# 循環参照は ESLint import/no-cycle で自動検出される
npm run lint
```

## 5. 開発補助ツール推奨

### 5.1 フロントエンド向け

| ツール名 | 種類 | 目的 |
|---|---|---|
| **React Developer Tools** | ブラウザ拡張 | React コンポーネントツリーの可視化・デバッグ |
| **TanStack Query Devtools** | ライブラリ | React Query のキャッシュ状態の確認・無効化操作 |
| **Zustand Devtools** | ライブラリ | Zustand ストアの状態確認・タイムトラベルデバッグ |
| **JSON Viewer** | ブラウザ拡張 | API レスポンスの整形表示 |

**ツール詳細**:

- **React Developer Tools**: コンポーネントの Props と State をリアルタイムで確認し、再レンダリングの原因を特定する
- **TanStack Query Devtools**: サーバー状態のキャッシュがどのように管理されているかを可視化し、キャッシュの強制削除・再取得操作を行う
- **Zustand Devtools**: クライアント状態の変化を時系列で追跡し、特定の状態に巻き戻してデバッグできる（タイムトラベルデバッグ）

### 5.2 BFF 向け

| ツール名 | 種類 | 目的 |
|---|---|---|
| **Thunder Client** | VSCode 拡張 | HTTP リクエスト送信・API 動作確認 |

**ツール詳細**:

- **Thunder Client**: VSCode 上で Postman のように API リクエストを送信できる。BFF のエンドポイントを直接叩いて動作確認・レスポンス確認・認証トークンの設定が可能

> ※ 各ツールの詳細な使用方法、推奨設定、追加ツール等は今後の検証を経て確定次第追記予定。
