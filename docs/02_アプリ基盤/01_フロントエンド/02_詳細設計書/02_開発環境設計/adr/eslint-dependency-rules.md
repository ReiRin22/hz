# ADR-2: 依存関係ルールの遵守を ESLint で自動強制する

* **ステータス**: Accepted
* **決定日**: 2026-05-21
* **関連設計書**: [ESLint設定設計.md](../ESLint設定設計.md) §4、[開発環境規約.md](../開発環境規約.md) §4
* **関連 ADR**: なし

## 背景（Context）

フロントエンドでは `features/` 間の直接参照・`app/` への逆参照・循環参照が、
アーキテクチャの密結合・初期化順序の不定化・テスタビリティの低下を引き起こす。
これらのルールをコードレビューに委ねると、レビュアーの習熟度に依存して見落としが発生する。

## 検討した選択肢（Options）

### 案A: コードレビューのみで運用
* メリット: 設定コスト不要
* デメリット: レビュアーの習熟度依存。規模拡大で見落としが増加。CI でのブロックができない

### 案B: ESLint `no-restricted-imports` + `import/no-cycle` で自動検出・エラー化 — 採用
* メリット: ビルド時に機械的に検出。コードレビューの負荷を下げる。CI でのマージブロックが可能
* デメリット: 初期設定コストが発生。正規表現パターンの誤りで誤検出する可能性

### 案C: TypeScript の `paths` 制限のみ
* メリット: 設定が単純
* デメリット: 循環参照は検出できない。`features/` 間の参照を `paths` レベルで禁止する方法がない

## 決定（Decision）

案Bを採用する。`no-restricted-imports` で `features/` 間直接参照・逆参照をエラー化し、
`import/no-cycle` で循環参照を検出する。
設定は `front_bff_shared/eslint/base.config.mjs`（フロントエンド固有部分は `frontend/eslint.config.mjs`）で一元管理し、
アプリチームが個別に無効化できないようにする。

## 影響（Consequences）

* 複数機能で共用するコンポーネントは必ず `shared/` に切り出す必要がある
* 既存コードで違反が発覚した場合はリファクタリングが必要
* 見直しトリガー: ディレクトリ構造の大幅な変更（例: `features/` の廃止・統合）時
* 見直しトリガー: `eslint-plugin-import` が非推奨・メンテナンス停止になった場合
