本章のテスト戦略は、「**開発・テスト基盤方式設計書**」で定義されたテストピラミッドの方針に準拠する。

 > **注記**: 本来、「テスト品質基準」および「カバレッジ目標の考え方」
  は、別途作成する「**テスト計画書**」に記載すべき内容である。しかし、
  テスト計画書の作成が間に合わないため、暫定的に本章に記載している。将
  来的には、品質条件やテスト対象の全体戦略を定義した「テスト計画書」を
  作成する予定である。

```

1.「テスト計画書」の作成　(品質条件やテスト対象を定義)
2. テスト計画書で定義した品質担保するためのテストツールの選定
3.テスト仕様書/テストコードの作成
```

### テスト品質基準

フロントエンドの自動テストが満たすべき品質基準を以下に定義する。

| 基準項目 | 要求水準 |
| --- | --- |
| **単体テスト・コンポーネントテスト** | 全テストがPASSすること |
| **カバレッジ（全体）** | 70% 以上 |
| **ESLint** | エラー 0件 |
| **TypeScript** | 型エラー 0件 |

### カバレッジ目標の考え方

**全体目標（70%）**:
- 標準的なカバレッジ率を設定し、プロジェクト全体での品質保証ラインとする
- ビジネスロジック（純粋関数、カスタムHooks）とMolecules/Organismsを優先的にテストすることで、全体70%を達成する

**階層別のテスト方針**:
- **Atoms**: 基本的にテスト不要。shadcn/ui や Radix UI のラッパーのため、ライブラリ側でテスト済み。独自ロジックが必要な場合は Molecules として設計すべき
- **Molecules/Organisms**: 必須。ユーザーインタラクションとバリデーションを検証
- **カスタムHooks・純粋関数**: 必須。ビジネスロジックの正確性を保証
- **Pages**: 結合テスト・E2Eテストで対応（今後定義予定）

**カバレッジ対象外とするもの**:
- Storybook用のストーリーファイル（`*.stories.tsx`）
- 設定ファイル（`vitest.config.ts`, `next.config.js` 等）
- 型定義ファイル（`*.d.ts`）

### テストの分類と責務

フロントエンドで実装する自動テストのレイヤーと責務を以下に定義する。

| テスト種別 | 対象・検証内容 | 使用ツール | 本設計書での定義範囲 |
| --- | --- | --- | --- |
| **単体テスト (Unit)** | カスタムHooks、バリデーションロジック、変換関数などの純粋なロジック検証 | Vitest | ○（本章で定義） |
| **コンポーネントテスト** | UI部品単体の表示、インタラクション（クリック等）、状態変化の検証 | Vitest / RTL | ○（本章で定義） |
| **結合テスト (Integration)** | 複数コンポーネント連携、**フロントエンド〜BFF間のAPI通信**を MSW でモック化した業務フロー検証。フロントエンドコンポーネントが正しい Request 型でリクエストを送り、BFF からの Response 型を正しく処理するかを検証する | Vitest / RTL / MSW | ○（本章で定義） |
| **E2Eテスト** | ログインから主要な業務登録に至るクリティカルなパスの正常系検証 | Playwright | △（今後詳細定義予定） |
| **ビジュアルリグレッションテスト** | コード変更による意図しない見た目の変化を自動検出 | Storybook / Chromatic | △（今後詳細定義予定） |

> **スコープの境界**: フロントエンド〜BFF間の通信（Request型・Response型の整合性）が本章の結合テストのターゲットである。BFF〜バックエンド間の通信テストは BFF 側の単体テスト対象であり、本章のスコープ外とする。

### Atomic Design階層別テスト実施方針

コンポーネント設計（[05.コンポーネント設計.md](./05.コンポーネント設計.md)）で定義されたAtomic Designの各階層に対して、どのレベルのテストを実施するかを以下に定義する。

| テスト種別 | 対象階層 | 検証内容 | 使用ツール | テスト実施方針 |
| --- | --- | --- | --- | --- |
| **単体テスト (Unit)** | - | カスタムHooks、バリデーションロジック、変換関数などの純粋なロジック検証 | Vitest | ○（本章で定義） |
| **コンポーネントテスト** | **Atoms** | 基本UI部品（Button、Input等）の表示・操作検証 | Vitest / RTL | **基本的にテスト不要**。shadcn/ui や Radix UI のラッパーのため、ライブラリ側でテスト済み。 |
| **コンポーネントテスト** | **Molecules** | API呼び出しを**含まない**フォーム入力グループ、検索フォーム等の表示・インタラクション・バリデーション検証 | Vitest / RTL | ○（本章で定義） |
| **コンポーネントテスト** | **Organisms** | 機能固有のUIロジック（フォームバリデーション、状態遷移、条件付き表示等）の検証。**API呼び出しはモック化**（MSW使用）。 | Vitest / RTL / MSW | ○（本章で定義） |
| **結合テスト (Integration)** | **Pages** | 複数Organismsの連携、**フロントエンド〜BFF間のAPI通信**をMSWでモック化した業務フロー検証。正しいRequest型でリクエストを送り、Response型を正しく処理するかを検証。 | Vitest / RTL / MSW | ○（本章で定義） |
| **E2Eテスト** | **Pages** | ログインから主要な業務登録に至るクリティカルパスの正常系検証 | Playwright | △（今後詳細定義予定） |
| **ビジュアルリグレッションテスト** | **全階層** | コード変更による意図しない見た目の変化を自動検出 | Storybook / Chromatic | △（今後詳細定義予定） |

## テスト環境の構築

### 必要なライブラリ構成

テスト実行に必要な専用ライブラリを以下に定義する。

| 分類 | ライブラリ名 (パッケージ名) | 役割・用途 |
| --- | --- | --- |
| **テストランナー** | **Vitest** | テストの実行・合否判定を行うメインエンジン。高速なWatchモードを提供 |
| **UIテスト** | **React Testing Library** (`@testing-library/react`) | コンポーネントを仮想描画し、ユーザー視点で要素を取得・検証する中心ライブラリ |
| **操作再現** | **user-event** (`@testing-library/user-event`) | キーボード入力やクリックを、ブラウザの挙動に忠実に再現する |
| **検証拡張** | **jest-dom** (`@testing-library/jest-dom`) | `toBeInTheDocument` など、DOMの状態を直感的に検証する命令セット |
| **ブラウザ環境** | **jsdom** | Node.js環境（Docker内）でブラウザの挙動をシミュレートする仮想DOM環境 |
| **変換プラグイン** | **@vitejs/plugin-react** | VitestがReactコード（JSX/TSX）を正しく解釈するための公式プラグイン |

### Vitest設定（vitest.config.ts）

プロジェクトルートに配置し、テスト環境の基本設定を定義する。

**設定概要**:
- **test.environment**: `'jsdom'` を指定し、ブラウザ環境をシミュレート
- **test.setupFiles**: 各テスト実行前に読み込む共通設定ファイル（`@testing-library/jest-dom` のインポート等）
- **test.include**: `['src/**/**/test/**/*.{ts,tsx}', 'test/integration/**/*.{ts,tsx}']` で単体・コンポーネントテストと結合テストの両方を対象に含める
- **resolve.preserveSymlinks**: `true` に設定し、モノレポ構成のシンボリックリンク（`front_bff_shared`）を解決
- **resolve.alias**: `@` エイリアスを設定し、`tsconfig.json` のpathsと同じパスを使用

**上記設定ファイルの実装は基盤チームが整備**し、アプリ実装チームは直接修正しない。

### テストセットアップ設定（setup.ts）

**配置場所**: `frontend/src/shared/plugins/setup.ts`

**役割**:
- `@testing-library/jest-dom` のカスタムマッチャー（`toBeInTheDocument` 等）をインポート
- `afterEach` で各テスト後のDOM自動クリーンアップを実装

**上記設定ファイルの実装は基盤チームが整備**し、アプリ実装チームは直接修正しない。

## テストディレクトリ構成と命名規則

### ディレクトリ配置の原則

テスト種別ごとに配置場所を分離する。

| テスト種別 | 配置場所 | 説明 |
|---|---|---|
| 単体テスト・コンポーネントテスト | `src/features/<LV1>/<LV2>/<LV3>/test/` | 対象の実装ファイルに近接配置。内部構造は実装ファイルのディレクトリをミラーリング |
| 共通部品の単体テスト・MSWハンドラー | `src/shared/test/` | 全機能から参照するMSWモックハンドラーもここで一元管理 |
| 結合テスト | `src/features/<LV1>/<LV2>/<LV3>/integration/` | フロントエンド〜BFF間の通信を MSW でモック化した業務フロー検証。機能ごとのフォルダ内に配置 |
| ビジュアルリグレッションテスト | `src/features/<LV1>/<LV2>/<LV3>/stories/` | Storybook Story ファイル。機能ごとのフォルダ内に配置。Storybook 設定は `.storybook/` |

- `front_bff_shared`（Zodスキーマ等）への参照をテスト時も有効にするため、`preserveSymlinks` 設定を適用し、型定義と連動したテスト実行を保証する

## 単体テストの実装方針

計算処理、データ変換、カスタムHooksなどの純粋なロジックに対し、**Vitest**を用いた高速な検証を行う。

**テストの観点**:
- **テストする内容**: ロジックの正確性（入力→出力が正しいか）
- **検証方法**: 関数を直接呼び出して戻り値をアサート
- **観点**: 内部ロジックの正しさ

### 検証の重点

**対象とするロジック**:
- 複雑な条件分岐を持つビジネスロジック
- BFFからのデータをUI向けに再加工する変換関数（アダプター）
- カスタムHooksの状態管理ロジック

### 実装例

以下は、純粋関数とカスタムHooksの実装例である。

**純粋関数のテスト**:

```typescript
// src/shared/utils/formatDate.ts（実装）
export const formatDate = (date: Date | string): string => {
  const d = typeof date === 'string' ? new Date(date) : date;
  if (isNaN(d.getTime())) throw new Error('Invalid date');
  return `${d.getFullYear()}-${String(d.getMonth() + 1).padStart(2, '0')}-${String(d.getDate()).padStart(2, '0')}`;
};

// src/shared/test/utils/formatDate_test.ts（テスト）
describe('formatDate', () => {
  it('Date オブジェクトを YYYY-MM-DD 形式に変換すること', () => {
    expect(formatDate(new Date('2024-01-05'))).toBe('2024-01-05');
  });

  it('不正な日付の場合、エラーをスローすること', () => {
    expect(() => formatDate('invalid-date')).toThrow('Invalid date');
  });
});
```

**カスタムHooksのテスト**:

```typescript
// src/shared/hooks/useCounter.ts（実装）
export const useCounter = (initialValue = 0) => {
  const [count, setCount] = useState(initialValue);
  return { 
    count, 
    increment: () => setCount((prev) => prev + 1),
    reset: () => setCount(initialValue) 
  };
};

// src/shared/test/hooks/useCounter_test.ts（テスト）
describe('useCounter', () => {
  it('increment で値が増加すること', () => {
    const { result } = renderHook(() => useCounter(0));
    act(() => result.current.increment());
    expect(result.current.count).toBe(1);
  });
});
```

### Next.js固有機能のモック化

`useRouter` や `useParams` などのNext.js固有の機能は `vi.mock` を用いて擬似化する。

**使用場面**: 単体テスト、コンポーネントテスト、結合テストの全てで使用される。Next.jsのルーティング機能を使用するコンポーネントやロジックをテストする際に必須。

**実装例**:

```typescript
// テストファイルの最上部でモック定義（describe の外側）
const pushMock = vi.fn();
vi.mock('next/navigation', () => ({
  useRouter: () => ({ push: pushMock, replace: vi.fn(), back: vi.fn() }),
}));

// テストケース
it('保存処理成功後、一覧画面に遷移すること', async () => {
  // ... コンポーネントのレンダリングと操作 ...
  expect(pushMock).toHaveBeenCalledWith('/reception');
});
```

### テスト実装のガイドライン

**やっていいこと**:
- 関数やロジックの入出力が正しいかを検証する
  - 例: `formatDate('2024-01-05')` が `'2024-01-05'` を返すか
  - 例: `increment()` を呼ぶと `count` が1増えるか
- 複雑な条件分岐、エッジケース、異常系を網羅的にテストする
- カスタムHooksは `renderHook` を使用してテストする
- テストケース名は日本語で明確に記述する
  - 例: `it('初期状態ではボタンが非活性であること', () => { ... })`

**やってはいけないこと**:
- UIコンポーネントの描画やユーザーインタラクションを単体テストで検証する（コンポーネントテストの範疇）
- CSSクラス名やDOM構造に依存したテストを書く
- テストケース内で複数の関心事を混在させる

**テストの命名規則**:
- **describe ブロック**: コンポーネント名または機能名を記述
  - 例: `describe('formatDate', () => { ... })`
- **it/test ブロック**: 「〜であること」「〜すること」の形式で、期待する振る舞いを記述
  - 例: `it('Date オブジェクトを YYYY-MM-DD 形式に変換すること', () => { ... })`

**よくあるアンチパターン**:

| アンチパターン | 理由 | 正しい実装 |
| --- | --- | --- |
| UIコンポーネントをrenderして検証 | コンポーネントテストの範疇 | 純粋関数として切り出してテスト |
| テストケース内で複数の検証を実施 | 失敗時の原因特定が困難 | 1テストケース = 1検証項目に分割 |

## コンポーネントテストの実装方針

ユーザーの実際の操作（クリック、入力）に基づいたコンポーネントの振る舞いを、**React Testing Library (RTL)**で検証する。

**テストの観点**:
- **テストする内容**: UIロジックの正確性（バリデーション、状態遷移、条件付き表示等）
- **検証方法**: コンポーネントをレンダリングして、DOM要素の状態で検証
- **観点**: ユーザーから見える振る舞いで、内部ロジックが正しく動作するかを検証（内部実装（state、props）に直接アクセスしない）

### 重要な観点

#### ① ユーザー視点での要素取得

DOM構造の細部ではなく、`role`、`label`、`text` に基づいて要素を取得する。

| 優先度 | メソッド | 用途 |
| --- | --- | --- |
| 1 | `getByRole` | ボタン、テキストボックス等のロールで取得 |
| 2 | `getByLabelText` | ラベルに関連付けられた入力欄を取得 |
| 3 | `getByText` | 表示されているテキストで取得 |

**禁止事項**: `querySelector`, `getElementById`, CSSクラス名での要素取得（実装の詳細に依存するため）

#### ② アクセシビリティ対応

`label` の `htmlFor` と `input` の `id` を紐付け、テスト時にラベルから入力欄を特定可能にする。

```tsx
<label htmlFor="user-name">名前</label>
<input id="user-name" {...register('name')} />
```

#### ③ バリデーションと状態遷移の検証

必須項目未入力時のボタン非活性、適切入力時のボタン活性化などのインタラクションを検証する。

**実装例**:

```typescript
describe('UserUpdateForm', () => {
  it('初期状態ではボタンが非活性であること', () => {
    render(<UserUpdateForm />);
    expect(screen.getByRole('button', { name: '保存' })).toBeDisabled();
  });

  it('正しく入力するとボタンが活性化すること', async () => {
    const user = userEvent.setup();
    render(<UserUpdateForm />);
    
    await user.type(screen.getByLabelText(/名前/), '山田太郎');
    await user.type(screen.getByLabelText(/メール/), 'test@example.com');

    await waitFor(() => {
      expect(screen.getByRole('button', { name: '保存' })).toBeEnabled();
    });
  });
});
```

#### ④ 非同期処理の待機

非同期処理（データ取得、状態更新等）のテストでは、`waitFor` を使用して処理完了を待機する。

```typescript
it('保存ボタン押下後、成功メッセージが表示されること', async () => {
  const user = userEvent.setup();
  render(<UserForm />);

  await user.type(screen.getByLabelText(/名前/), '山田太郎');
  await user.click(screen.getByRole('button', { name: '保存' }));

  await waitFor(() => {
    expect(screen.getByText('保存しました')).toBeInTheDocument();
  });
});
```

### テスト実装のガイドライン

**やっていいこと**:
- ユーザー視点で要素を取得する（`getByRole`, `getByLabelText`, `getByText`）
- DOM要素の状態で検証する
  - 例: 「stateがtrueになること」ではなく「ボタンが活性化すること」を検証
- 非同期処理は `waitFor` で適切に待機する
- 外部依存（BFF API、Router等）のみモック化し、コンポーネント自体はモック化しない
- テストケース名は日本語で明確に記述する
  - 例: `it('初期状態ではボタンが非活性であること', () => { ... })`

**やってはいけないこと**:
- コンポーネントの内部実装（state, props）に直接アクセスする
- `querySelector`, `getElementById`, CSSクラス名での要素取得（実装の詳細に依存するため）
- 過度なモック化により、実装と乖離したテストを作る
- コンポーネント全体をモック化する
- テストケース内で複数の関心事を混在させる

**テストの命名規則**:
- **describe ブロック**: コンポーネント名または機能名を記述
  - 例: `describe('UserUpdateForm', () => { ... })`
- **it/test ブロック**: 「〜であること」「〜すること」の形式で、期待する振る舞いを記述
  - 例: `it('初期状態ではボタンが非活性であること', () => { ... })`

**よくあるアンチパターン**:

| アンチパターン | 理由 | 正しい実装 |
| --- | --- | --- |
| `container.querySelector('.submit-button')` でボタン取得 | CSSクラス名に依存（実装の詳細） | `screen.getByRole('button', { name: '送信' })` |
| コンポーネント全体をモック化 | 実装と完全に乖離したテストになる | 外部依存（API、Router等）のみモック化 |
| テストケース内で複数の検証を実施 | 失敗時の原因特定が困難 | 1テストケース = 1検証項目に分割 |

## 結合テストの実装方針

**テスト対象の境界**: フロントエンド〜BFF間の通信を対象とする。MSW が BFF のレスポンスをモック化し、フロントエンドコンポーネントが正しく動作するかを検証する。

**テストの観点**:
- **テストする内容**: 業務フローのロジックの正確性（複数コンポーネントの連携 + BFF API通信）
- **検証方法**: API通信を含む一連の操作で正しい結果になるかを検証
- **観点**: ユーザーから見える振る舞いで、業務フロー全体のロジックが正しく動作するかを検証

#### 実現方法：MSW による BFF レスポンスのモック化

MSW（Mock Service Worker）をテスト環境で使用し、フロントエンドが BFF へ送る HTTP リクエストを横断的にインターセプトしてレスポンスを返す。実際の BFF を起動せずに、`front_bff_shared` で定義された Response 型に準拠したデータをモック化できる。

```
【テスト時のデータフロー】
フロントエンドコンポーネント
  ↓ axiosClient でリクエスト送信
MSW（テスト環境でリクエストをインターセプト）
  ↓ モックレスポンスを返す（Response型に準拠）
フロントエンドコンポーネント
  ↓ レスポンスを受け取り画面を更新
検証（期待する表示・状態になっているか）
```

**MSW ハンドラーの定義例**（`front_bff_shared` の Response 型を使用）:

```typescript
// src/shared/test/mocks/handlers/patient.ts
import { http, HttpResponse } from 'msw';
import type { PatientDetailResponse } from '@front_bff_shared/features/patient/types/responses/patientDetail.response';

export const patientHandlers = [
  // 正常系: 患者詳細取得
  http.get('/api/patients/:id', ({ params }) => {
    const mockResponse: PatientDetailResponse = {
      id: params.id as string,
      name: '山田 太郎',
      birthDate: '1960-04-01',
      wardName: '西病棟3F',
      roomNumber: '301',
    };
    return HttpResponse.json(mockResponse);
  }),

  // 異常系: 存在しない患者
  http.get('/api/patients/not-found', () => {
    return HttpResponse.json({ message: '患者が見つかりません' }, { status: 404 });
  }),
];
```

**テストコードでの使用例**:

```typescript
// test/integration/features/.../PatientDetail_integration_test.tsx
import { render, screen, waitFor } from '@testing-library/react';
import { setupServer } from 'msw/node';
import { patientHandlers } from '@/shared/test/mocks/handlers/patient';
import { PatientDetailPanel } from '../components/organisms/PatientDetailPanel';

// MSW サーバーをセットアップ
const server = setupServer(...patientHandlers);

beforeAll(() => server.listen());
afterEach(() => server.resetHandlers());
afterAll(() => server.close());

describe('PatientDetailPanel', () => {
  it('患者詳細が正しく表示されること', async () => {
    render(<PatientDetailPanel patientId="P001" />);

    // BFF からのレスポンスを待機して表示を検証
    await waitFor(() => {
      expect(screen.getByText('山田 太郎')).toBeInTheDocument();
      expect(screen.getByText('西病棟3F')).toBeInTheDocument();
    });
  });

  it('患者が存在しない場合、エラーメッセージが表示されること', async () => {
    render(<PatientDetailPanel patientId="not-found" />);

    await waitFor(() => {
      expect(screen.getByText('患者が見つかりません')).toBeInTheDocument();
    });
  });
});
```

**検証の重点**:

- `front_bff_shared` の Response 型に準拠したモックデータを定義することで、型の契約を保証する
- 正常系だけでなく、404・500 等の異常系レスポンスもモック化して境界値を検証する
- `axiosClient` の Interceptor（認証・テナントID付与）も通るため、通信基盤ごと結合して検証できる

### テスト実装のガイドライン

結合テストは、コンポーネントテストと同じく React Testing Library を使用するため、基本的なガイドラインはコンポーネントテストと同様である。ここでは、結合テスト特有のポイントのみを記載する。

**やっていいこと**:
- MSW で BFF API をモック化し、`front_bff_shared` の Response 型に準拠したデータを返す
- 正常系だけでなく、404・500 等の異常系レスポンスもモック化する
- 複数コンポーネントの連携を検証する
- API通信を含めた一連の操作で正しい結果になるかを検証する

**やってはいけないこと**:
- BFF を実際に起動してテストする（結合テストのスコープ外）
- BFF〜バックエンド間の通信を検証する（BFF 側の単体テスト対象）

**コンポーネントテストとの共通ルール**:
- ユーザー視点で要素を取得する（`getByRole`, `getByLabelText`, `getByText`）
- 非同期処理は `waitFor` で適切に待機する
- コンポーネントの内部実装（state, props）に直接アクセスしない
- テストケース名は日本語で明確に記述する

## E2Eテストの実装方針

クリティカルな業務フローの正常動作を、実際のブラウザ操作で検証する。**Playwright**を用いて、ユーザーの操作シナリオをエンドツーエンドで自動実行する。

**テストの観点**:
- **テストする内容**: 主要な業務フローの正常系（ログイン→検索→登録→確認など）
- **検証方法**: 実際のブラウザ操作で一連のフローを検証
- **観点**: ユーザーから見て何ができるか（エンドツーエンドの業務フロー）

### テストツールと設定

**使用ツール**: Playwright

**設定ファイル**: `playwright.config.ts`（プロジェクトルートに配置）

**主要な設定項目**:

| 設定項目 | 設定値 | 説明 |
|---|---|---|
| **testDir** | `./e2e` | E2Eテストファイルの配置ディレクトリ |
| **baseURL** | `process.env.BASE_URL ?? 'http://localhost:3000'` | テスト対象のベースURL |
| **trace** | `'on-first-retry'` | 失敗時にトレース（スクリーンショット・動画）を記録 |
| **locale** | `'ja-JP'` | 日本語ロケールを設定 |
| **projects** | `chromium` | Desktop Chrome のみを対象 |
| **webServer** | ローカル環境のみ起動 | ローカルでは `npm run dev` を自動起動、CI環境では別途起動済みのサーバーに接続 |

**CI環境用の設定**（`process.env.CI` が `true` の場合）:
- `forbidOnly`: `test.only` を禁止（全テストを実行させる）
- `retries`: 失敗時に2回リトライ
- `workers`: 並列数を1に制限（リソース節約）

**上記設定ファイルの実装は基盤チームが作成・管理する**。  
CI/CD連携の詳細は「[CI/CDパイプラインとの連携](#cicdパイプラインとの連携)」を参照。

### 実行環境

**テスト実行環境**: GitLab Runner

- **現在**: ローカル（WSL）の GitLab Runner で実行
- **今後**: 専用の自動テスト用サーバーに移行予定

### シナリオの選定基準

E2Eテストの対象シナリオは、**PRで変更した箇所と、その機能が関連するクリティカルパス**を対象とする。

**選定基準**:

| 優先度 | 対象シナリオ |
|---|---|
| **高** | PRで変更した画面・機能（変更によるリグレッション検出） |
| **高** | クリティカルパス（正常系のみ。例: ログイン → 検索 → 登録 → 確認） |
| **中** | 異常系（バリデーションエラー、404/500エラーの表示確認） |

**やってはいけないこと**:
- すべての画面・機能を網羅的にE2Eテスト化する（コストが高い）
- 単体テスト・結合テストでカバーできる詳細なロジックをE2Eテストで検証する

### BFF APIのモック化とテストデータ

E2Eテストでは、**BFF APIをモック化**し、フロントエンド単体の動作を検証する。Playwright の `page.route()` を使用して、HTTP リクエストをインターセプトし、モックレスポンスを返す。

**テストデータ**: TypeScript の定数として固定データを定義（テスト実行前のDB投入不要）

**実装例**:

```typescript
// e2e/features/RES002.spec.ts

// BFF モックデータ
const mockTestResults = [
  { id: '1', itemName: '血糖', resultValue: '150', /* ... */ },
  { id: '2', itemName: '白血球数', resultValue: '', /* ... */ },
];

// 共通ルートモック設定
async function setupRouteMocks(page: Page, testResultsOverride = mockTestResults) {
  await page.route('**/bff/orders/*/test-results', async (route: Route) => {
    await route.fulfill({ json: testResultsOverride });
  });
}

test('TC-001: 画面初期表示', async ({ page }) => {
  await setupRouteMocks(page);
  await page.goto('/06/02/01/RES002');
  await page.waitForLoadState('networkidle');
  await expect(page.locator('[data-ui-id="TBL_TEST_RESULTS"]')).toBeVisible();
});
```

### 実装パターン

#### 要素の取得方法

**優先度**: `data-ui-id` 属性 > `role` 属性 > `text`

```typescript
// やっていいこと
await page.locator('[data-ui-id="BTN_CONFIRM"]').click();
await page.getByRole('button', { name: '保存' }).click();

// やってはいけないこと（CSSクラス名・DOM構造に依存）
await page.locator('.submit-button').click();
```

#### 非同期処理の待機

```typescript
await page.goto('/06/02/01/RES002');
await page.waitForLoadState('networkidle');
await expect(page.locator('[data-ui-id="TBL_TEST_RESULTS"]')).toBeVisible();

// API リクエストの完了を待機
const savePromise = page.waitForRequest('**/bff/orders/*/test-results/save');
await page.locator('[data-ui-id="BTN_CONFIRM"]').click();
await savePromise;
```

#### 共通処理の関数化

```typescript
/** ページロード完了を待つ（テーブル表示まで待機） */
async function gotoAndWait(page: Page, url: string) {
  await page.goto(url);
  await page.waitForLoadState('networkidle');
  await expect(page.locator('[data-ui-id="TBL_TEST_RESULTS"]')).toBeVisible();
}
```

### 認証処理【今後定義予定】

E2Eテストにおける認証処理（ログイン、セッション保持）の実装方針は、認証機能の詳細設計完了後に定義する。

### テスト実装のガイドライン

**やっていいこと**:
- `data-ui-id` 属性で要素を取得する（最優先）
  - 例: `await page.locator('[data-ui-id="BTN_CONFIRM"]').click();`
- `role` 属性や `text` で要素を取得する（`data-ui-id` が設定されていない場合）
  - 例: `await page.getByRole('button', { name: '保存' }).click();`
- 共通処理は関数として切り出す
  - 例: `async function gotoAndWait(page: Page, url: string) { ... }`
- BFF API をモック化し、TypeScript の定数として固定データを定義する
- テストケース名は日本語で明確に記述する
  - 例: `test('TC-001: 画面初期表示 — タブ・ヘッダ・テーブルが表示される', async ({ page }) => { ... })`

**やってはいけないこと**:
- CSSクラス名やDOM構造に依存したテストを書く
  - 例: `await page.locator('.submit-button').click();` （禁止）
- すべての画面・機能を網羅的にE2Eテスト化する（コストが高い）
- 単体テスト・結合テストでカバーできる詳細なロジックをE2Eテストで検証する
- テストケース内で複数の関心事を混在させる

**テストの命名規則**:
- **test ブロック**: テストケースIDと検証内容を明記
  - 例: `test('TC-001: 画面初期表示 — タブ・ヘッダ・テーブルが表示される', async ({ page }) => { ... })`

**よくあるアンチパターン**:

| アンチパターン | 理由 | 正しい実装 |
| --- | --- | --- |
| `page.locator('.submit-button')` でボタン取得 | CSSクラス名に依存（実装の詳細） | `page.locator('[data-ui-id="BTN_SUBMIT"]')` または `page.getByRole('button', { name: '送信' })` |
| すべての画面を網羅的にE2Eテスト化 | 実行時間が長く、メンテナンスコストが高い | クリティカルパスのみをE2Eテスト化 |
| 詳細なバリデーションロジックをE2Eで検証 | 単体・結合テストで検証すべき内容 | E2Eはクリティカルパスの正常系のみ検証 |

## ビジュアルリグレッションテストの実装方針

コード変更による意図しない見た目の変化を自動検出する。**Storybook** + **Storybook Test Runner** + **Playwright** を用いて、コンポーネントのビジュアルスナップショットを比較する。

**テストの観点**:
- **テストする内容**: コンポーネントの見た目の変化（意図しないビジュアルリグレッション）
- **検証方法**: スクリーンショット比較（ベースライン画像との差分検出）
- **観点**: ユーザーから見て何が見えるか（見た目）

### テストツールと設定

**使用ツール**: Storybook + Storybook Test Runner + Playwright

**Playwright を使用する理由**:
- Storybook Test Runner は内部で Playwright を使用してブラウザを制御
- 実際のブラウザ環境（Chromium）でレンダリングし、スクリーンショットを撮影
- E2Eテストと同じ Playwright 基盤を活用することで、テスト環境を統一

**設定ファイル**:
- **`.storybook/main.ts`**: Storybook の基本設定（ストーリーファイルの検索パス、アドオン等）
- **`.storybook/preview.ts`**: グローバルデコレーター、MSW設定等

**主要な設定項目（`.storybook/main.ts`）**:

| 設定項目 | 設定値 | 説明 |
|---|---|---|
| **stories** | `['../src/**/*.stories.@(ts|tsx)']` | ストーリーファイルの検索パターン |
| **addons** | `@storybook/addon-essentials`, `@storybook/addon-a11y` | 必須アドオン（コントロール、ドキュメント、アクセシビリティ） |
| **framework** | `@storybook/react-vite` | React + Vite を使用 |
| **viteFinal** | パスエイリアス設定 | `@`, `@shared` のエイリアスを設定 |

**主要な設定項目（`.storybook/preview.ts`）**:

| 設定項目 | 設定値 | 説明 |
|---|---|---|
| **loaders** | `mswLoader` | MSW によるAPI モック化（`msw-storybook-addon`） |
| **parameters.a11y** | アクセシビリティ検証 | コンポーネントのアクセシビリティ問題を自動検出 |

**上記設定ファイルの実装は基盤チームが作成・管理する**。

### 実行環境

**テスト実行環境**: GitLab Runner

- **現在**: ローカル（WSL）の GitLab Runner で実行
- **今後**: 専用の自動テスト用サーバーに移行予定

**実行の流れ**:
1. PRが作成されると、GitLab Runner がテストを実行
2. Storybook Test Runner が各ストーリーをレンダリングし、スクリーンショットを撮影
3. ベースライン画像（リポジトリ内に保存）と比較
4. 差分がある場合、比較レポート（HTMLレポート、差分画像）を生成
5. テスト成果物を GitLab サーバーにアップロード
6. GitLab の「アーティファクト」メニューで結果を確認

### 対象コンポーネントの選定基準

ビジュアルリグレッションテストの対象は、**PRで変更したコンポーネント + 関連コンポーネント**を対象とする。

**選定基準**:

| 優先度 | 対象コンポーネント |
|---|---|
| **高** | PRで変更したコンポーネント（変更によるビジュアルリグレッション検出） |
| **高** | 変更したコンポーネントに依存するコンポーネント（影響範囲の検証） |

**対象コンポーネントの自動検出**:
- 手動で指定するのは手間がかかるため、**自動検出する仕組み**を導入したい
- 自動検出の具体的な方法は**今後詳細定義予定**

**やってはいけないこと**:
- すべてのコンポーネントを網羅的にビジュアルテスト化する（実行時間が長くなる）

**やっていいこと**:
- PRで変更したコンポーネントのストーリーを作成する
- 複数の状態（デフォルト、入力済み、エラー等）をストーリーとして定義する
- MSWでBFF APIをモック化し、API通信を含むコンポーネントをテストする
- ストーリー名は英語で明確に記述する
  - 例: `export const Default: Story = { ... };`
  - 例: `export const Filled: Story = { ... };`

**やってはいけないこと**:
- すべてのコンポーネントを網羅的にストーリー化する（メンテナンスコストが高い）
- ストーリー内で複数の関心事を混在させる
- ストーリー名を日本語で記述する（TypeScript のエクスポート変数名として不適切）

**よくあるアンチパターン**:

| アンチパターン | 理由 | 正しい実装 |
| --- | --- | --- |
| すべてのコンポーネントをストーリー化 | メンテナンスコストが高く、実行時間が長い | PRで変更したコンポーネント + 関連コンポーネントのみ |
| ストーリー名を日本語で記述 | TypeScript のエクスポート変数名として不適切 | 英語で明確に記述（`Default`, `Filled`, `Error`） |
| 1つのストーリーに複数の状態を含める | 差分検出が困難になる | 1ストーリー = 1状態として分割 |

## テスト成果物一覧

各テストで生成される成果物とその保存先を以下に定義する。

**成果物の保持期間**:
- GitLab アーティファクトの保持期間は `.gitlab-ci.yml` の `expire_in` で設定する
- 現在は暫定で **7日間** とするが、今後の方針によって変更する


### 単体テスト（Vitest）

- テスト実行結果レポート（コンソール出力 or HTMLレポート） - **アーティファクト**
- カバレッジレポート（`coverage/` ディレクトリ） - **アーティファクト**

### コンポーネントテスト（Vitest/RTL）

- テスト実行結果レポート（単体テストと同じ） - **アーティファクト**
- カバレッジレポート（単体テストと合算） - **アーティファクト**

### 結合テスト（Vitest/RTL/MSW）

- テスト実行結果レポート（単体・コンポーネントと同じ形式） - **アーティファクト**
- カバレッジレポート - **アーティファクト**

※ 単体・コンポーネント・結合テストは全て Vitest で実行されるため、成果物の形式は同じです。

### E2Eテスト（Playwright）

1. HTMLレポート（テスト実行結果の一覧） - **アーティファクト**
2. スクリーンショット（失敗時のブラウザ画面） - **アーティファクト**
3. 動画（失敗時の操作を再現） - **アーティファクト**
4. トレースファイル（詳細な実行ログ） - **アーティファクト**

### ビジュアルリグレッションテスト（Storybook Test Runner）

1. ベースライン画像（正解画像） - **MBCサーバー**
2. 差分検出時の比較画像（変更前/変更後/差分の3枚） - **アーティファクト**
3. HTMLレポート（差分の一覧と詳細） - **アーティファクト**

#### ベースライン画像の配置場所（仮方針）

**配置先**: **MBCサーバー**

**配置方針**:
- 現時点では**MBCサーバー**にベースライン画像を配置する運用とする
- **バージョン管理**については今後の設計で決定予定
- 今後、Harz専用のサーバーに移行する際に**AWS マネージドサービスのS3**の利用も検討する

**命名規則**: `features/<LV1機能群>/<LV2業務フロー>/<LV3画面機能>/<Atomic Design階層>/<コンポーネント名>/<ストーリー名>.png`

**ディレクトリ構造例**:
```
snapshots/
└── features/
    └── patient/                           # LV1機能群
        └── search/                        # LV2業務フロー
            └── main/                      # LV3画面機能
                ├── molecules/
                │   ├── UserSearchForm/
                │   │   ├── Default.png    # デフォルト状態
                │   │   └── Filled.png     # 入力済み状態
                │   └── UserTable/
                │       ├── Default.png
                │       └── Empty.png      # データ0件状態
                └── organisms/
                    └── UserListPanel/
                        ├── Success.png    # 正常系
                        └── Empty.png      # 異常系
```

**配置ルール**:
- **機能ディレクトリ構造に準拠**（`features/<LV1>/<LV2>/<LV3>/`）
- **Atomic Design の階層ごとに分類**（`molecules/`, `organisms/` 等）
- **コンポーネントごとにディレクトリを作成**（`UserSearchForm/`, `UserTable/` 等）
- **ストーリー名をファイル名に使用**（`Default.png`, `Filled.png` 等）
- 実装ファイル（`src/features/<LV1>/<LV2>/<LV3>/components/`）との対応関係が明確

#### 承認フロー

1. **差分検出**: ビジュアルテストで差分が検出され、テストが失敗
2. **レビュー**: レビュー担当者が GitLab アーティファクトで差分を確認
3. **承認**: 意図的な変更である場合、GitLab上で承認操作を実施（具体的な方法は今後定義）
4. **自動更新**: CI環境で `npm run test-storybook -- --update-snapshots` が自動実行され、新しいベースライン画像を生成
5. **自動アップロード**: 生成されたベースライン画像が自動的にMBCサーバーにアップロード
6. **再テスト**: 更新後のベースライン画像を参照して自動的に再テストを実行し、差分がないことを確認

## CI/CDパイプラインとの連携

フロントエンドの自動テストは、GitLab CI/CD パイプラインで自動実行される。本セクションでは、フロントエンド固有の実行方法を定義する。

**パイプライン全体の設計**: 「**開発・テスト基盤方式設計書**」を参照  
**テスト成果物の詳細**: 「**テスト成果物一覧**」を参照

### 各テストの実行コマンド

| テスト種別 | 実行コマンド | 実行タイミング |
|---|---|---|
| **単体・コンポーネント・結合テスト** | `npm run test` | 毎PR |
| **E2Eテスト** | `CI=true npx playwright test` | 毎PR |
| **ビジュアルリグレッションテスト** | `CI=true npm run test-storybook` | 毎PR |

### CI環境固有の設定

CI環境でテストを実行する際に必要な環境変数を以下に定義する。

| 環境変数 | 設定値例 | 用途 |
|---|---|---|
| **CI** | `true` | CI環境であることを示すフラグ。Playwright・Storybookの挙動を調整 |
| **BASE_URL** | `http://localhost:3000`（ローカル環境での例） | E2Eテスト実行時の接続先URL。環境に応じて設定 |
