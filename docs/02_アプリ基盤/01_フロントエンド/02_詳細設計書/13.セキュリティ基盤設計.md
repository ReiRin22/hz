### XSS（クロスサイトスクリプティング）対策

#### 目的

悪意のあるスクリプトをページに埋め込み、ログインセッションの盗取・画面の改ざん・患者情報の外部送信などを引き起こす攻撃を防ぐ。本システムは電子カルテとして PHI（患者健康情報）を扱うため、スクリプトインジェクションによる情報漏洩は特に重大なリスクとなる。

#### 概要

| No | 対策内容 | 実装レイヤー | 説明 |
| --- | --- | --- | --- |
| 1 | **Reactの自動エスケープ** | フロントエンド | React の標準機能によるエスケープを基本とする | 
| 2 | **DOMPurifyによるサニタイズ** | フロントエンド | `dangerouslySetInnerHTML` を使用する場合は必ず **`DOMPurify`** でサニタイズ（無害化）を行う |
| 3 | **HttpOnly Cookie設定** | BFF | セッショントークンをJavaScriptからアクセス不可にし、XSSによるトークン窃取を防ぐ |
| 4 | **URL検証** | フロントエンド | リンク入力時に `http://`, `https://` で始まるURLのみ許可（ホワイトリスト方式） |
| 5 | **Content Security Policy (CSP)** | BFF | 許可されていない外部スクリプトの実行をブラウザレベルで遮断する。詳細は後述の「Content Security Policy (CSP) 基本設定」を参照 |

**方式設計書との対応**：
- フロントエンド方式設計書「4.セキュリティ・アクセス統制」4.1節 No.3に準拠

#### 基盤実装

##### DOMPurify サニタイズ関数

**実装ファイル（基盤チームが作成・管理）**: 
- `frontend/src/shared/utils/sanitize.ts`

**機能**：
- `sanitizeHTML(dirty: string): string` 関数を提供
- DOMPurify を使用してHTML文字列をサニタイズ
- 許可するHTMLタグと属性を制限（`ALLOWED_TAGS`、`ALLOWED_ATTR`）

**使用例**：

```tsx
import { sanitizeHTML } from '@/shared/utils/sanitize';

export function PatientNote({ note }: { note: string }) {
  const safeHTML = sanitizeHTML(note);
  return <div dangerouslySetInnerHTML={{ __html: safeHTML }} />;
}
```

##### HttpOnly Cookie 設定

**実装ファイル（基盤チームが作成・管理）**: 
- `bff/src/shared/plugins/security.middleware.ts`

**機能**：
- セッショントークンを格納するCookieに `HttpOnly` 属性を設定
- JavaScriptからのCookieアクセスを禁止し、XSSによるトークン窃取を防ぐ

**設定内容**：

```typescript
// Cookie設定例
res.cookie('session_token', token, {
  httpOnly: true,        // JavaScriptからアクセス不可
  secure: true,          // HTTPS通信のみ
  sameSite: 'strict',    // CSRF対策
  maxAge: 3600000        // 有効期限（ミリ秒）
});
```

**重要**：
- 認証トークンは必ず `HttpOnly` Cookieで管理する
- `localStorage` や `sessionStorage` にトークンを保存しない（XSS脆弱性がある場合に窃取される）

**参照**：
- 認証トークン管理の詳細：[01.フロントエンド・BFF共通基盤設計.md](01.フロントエンド・BFF共通基盤設計.md) の「1.4 Axiosインターセプターによる共通処理」

#### 実装ルール

**やっていいこと**：
- ユーザー入力を表示する際はReactの自動エスケープに任せる（`{userInput}`）

**やってはいけないこと**：
- `dangerouslySetInnerHTML` を使用する（原則禁止。使用が必要な場合は基盤チームに相談すること）
- `eval()` や `Function()` コンストラクタを使用する
- ユーザー入力をURLやスクリプトタグに直接埋め込む
- `javascript:` スキームのURLを許可する

**URL入力フィールドの検証ルール**：

リンク・URL入力フィールドでは、以下のバリデーションを必須とする：

```typescript
// Zod スキーマ例
const urlSchema = z.string().url().refine(
  (url) => url.startsWith('http://') || url.startsWith('https://'),
  { message: 'http:// または https:// で始まるURLのみ許可されています' }
);
```

**理由**：`javascript:alert(document.cookie)` のような疑似プロトコルによるXSS攻撃を防ぐため

**参照**：URL入力フィールドの詳細実装は [07.フォーム設計.md](07.フォーム設計.md) を参照

**将来 `dangerouslySetInnerHTML` が必要になった場合**：

以下のような将来の拡張要件でHTMLレンダリングが必要になる場合は、基盤チームと協議の上で対応する：

- **WYSIWYGエディタ**：退院サマリ、看護記録などで書式付きテキスト（太字、箇条書き等）を入力・表示する
- **外部システム連携**：部門連携サービス（検査・放射線等）から受領するデータがHTML形式を含む
- **HL7/FHIR取込**：標準規格で受信するデータに構造化HTMLが含まれる

上記が要件として確定した場合の対応手順：

1. 基盤チームに利用申請・ユースケースを共有する
2. 基盤提供の `sanitizeHTML()` でサニタイズしてから使用する（必須）
3. 許可するHTMLタグ・属性を `ALLOWED_TAGS` / `ALLOWED_ATTR` で最小限に絞る
4. 本設計書の実装ルールを更新する

#### XSS多層防御アプローチ（シナリオ別対策）

XSSは単一の対策だけでは防げないため、**データフローの各段階で複数の防御層**を設ける。

##### シナリオ1：ユーザー入力からの攻撃

```
[ユーザー入力] → [画面表示（即時）] → [DB保存] → [画面表示（取得後）]
     ↓              ↓                ↓           ↓
   対策1          対策2            対策3        対策4
```

| 段階 | 対策 | 実装方法 | 備考 |
|-----|------|---------|------|
| **1. 入力時** | 入力値検証（バリデーション） | React Hook Form + Zod | `<` 等の記号を業務上入力する必要があるため、スクリプトパターンの完全検出は不可能。文字数制限・文字種制限（数字のみ/英字のみ等）で**最低限の制限**のみ実施 |
| **2. 画面即時表示** | Reactの自動エスケープ | `{value}` 形式で表示 | 確認ダイアログ等での表示はエスケープされるため安全。`dangerouslySetInnerHTML` は使用禁止 |
| **3. DB保存** | エスケープせずそのまま保存 | - | サニタイズは**表示時**に行うのが一般的（保存時にサニタイズすると元データが失われる） |
| **4. DB取得後の表示** | Reactの自動エスケープ | `{value}` 形式で表示 | 通常表示では自動エスケープで安全。将来HTML表示が必要になった場合のみ `sanitizeHTML()` + `dangerouslySetInnerHTML` を使用 |

**参考**：
- 入力バリデーション実装：[07.フォーム設計.md](07.フォーム設計.md)（React Hook Form + Zod）
- DB保存時にエスケープしない理由：元データを保持し、表示コンテキストに応じて適切にエスケープ/サニタイズするため

##### シナリオ2：外部システム連携からの攻撃

```
[外部システム] → [部門連携サービス] → [DB保存] → [画面表示]
                       ↓                  ↓           ↓
                     対策1              対策2        対策3
```

| 段階 | 対策 | 実装方法 | 備考 |
|-----|------|---------|------|
| **1. 外部データ受信時** | 入力値検証（バリデーション） | BFF側でスキーマ検証 | 文字数制限・必須項目チェック等の**最低限の制限**のみ実施。部門システムの出力仕様に依存するため、完全な検証は困難 |
| **2. DB保存** | エスケープせずそのまま保存 | - | シナリオ1と同様、サニタイズは表示時に行う |
| **3. 画面表示** | Reactの自動エスケープ | `{value}` 形式で表示 | 通常表示では自動エスケープで安全。将来HTML表示が必要になった場合のみ `sanitizeHTML()` + `dangerouslySetInnerHTML` を使用 |

**重要**：
- 外部連携データは信頼できない入力として扱う（ユーザー入力と同等のリスク）
- 部門連携サービス側でのバリデーションは**最低限**とし、フロントエンド表示時の防御（Reactの自動エスケープ）を主防御層とする

##### 多層防御のまとめ

| 防御層 | 目的 | 実装 | 有効性 |
|-------|------|------|-------|
| **1. 入力検証** | 明らかに異常な値を早期に排除 | Zod, BFFバリデーション | △（完全な防御は不可能） |
| **2. Reactエスケープ** | 表示時に自動でスクリプトを無害化 | `{value}` 形式（標準） | ◎（主防御層） |
| **3. DOMPurify** | HTML表示が必要な場合に限定的に使用 | `sanitizeHTML()` | ◎（HTML表示時の必須防御） |
| **4. CSP** | ブラウザレベルで外部スクリプト実行を遮断 | BFF helmet設定 | ◎（最終防御層） |

**設計方針**：
- **主防御層は「Reactの自動エスケープ」**：通常の表示では `{value}` を使用し、`dangerouslySetInnerHTML` は原則使用しない
- **入力検証は補助的**：完全な防御は不可能なため、文字数制限等の最低限の制限に留める
- **DB保存はエスケープしない**：元データを保持し、表示コンテキストに応じてエスケープ/サニタイズする
- **HTML表示は将来対応**：現時点では不要。要件確定時に基盤チームと協議して `sanitizeHTML()` を導入する

### CSRF（クロスサイトリクエストフォージェリ）対策

#### 目的

認証済みユーザーのブラウザを悪用し、意図しないリクエスト（患者情報の変更・削除等）を本システムへ送信させる攻撃を防ぐ。セッションCookieが自動送信される性質を悪用した攻撃であり、BFF側でオリジン検証・セキュリティヘッダー設定を行うことで防御する。

**認証認可との違い**：

| 対策 | 防ぐもの | 確認内容 |
|------|---------|---------|
| **認証認可** | なりすまし | 「誰が」「何をしていいか」 |
| **CSRF対策** | 意図しない操作 | 「本人が意図して」操作したか |

認証認可は「正しいユーザーか」を確認するが、CSRF対策は「そのユーザーが本当に操作したか（悪意のサイトが勝手に送信していないか）」を確認する。両方必須。

#### 概要

| No | 対策内容 | 実装方法 | 説明 |
| --- | --- | --- | --- |
| 1 | **CSRFトークン検証** | カスタムミドルウェア | 状態変更操作（POST/PUT/DELETE）にワンタイムトークンを要求し、正規リクエストのみ受け付ける（IPA推奨の根本的解決策） |
| 2 | **セキュリティヘッダー** | `helmet` ミドルウェア | セキュリティに関連するHTTPヘッダーを一括して適切に設定する |
| 3 | **オリジン制限** | CORS設定 | 許可されたフロントエンドドメイン以外からのリクエストを拒否する |
| 4 | **SameSite Cookie属性** | Cookie設定 | `SameSite=Lax` または `SameSite=Strict` を設定し、クロスサイトからのCookie送信を制限する |

#### 基盤実装

##### CSRFトークン検証

**実装ファイル（基盤チームが作成・管理）**: 
- `bff/src/shared/plugins/csrf.middleware.ts`
- `frontend/src/shared/utils/csrf.ts`

**仕組み**：

1. **トークン発行**：ユーザーがページを読み込む際、BFFがワンタイムのCSRFトークンを生成しCookieとして送信
2. **トークン送信**：フロントエンドが状態変更操作（POST/PUT/DELETE）を行う際、カスタムヘッダー `X-CSRF-Token` にトークンを付与
3. **トークン検証**：BFF側でCookieとヘッダーのトークンを照合し、一致する場合のみリクエストを受理

**実装概要**：

```typescript
// BFF: CSRFトークン発行
@Get('/csrf-token')
getCsrfToken(@Res() res: Response) {
  const token = generateCsrfToken(); // ランダム文字列生成
  res.cookie('XSRF-TOKEN', token, { httpOnly: false }); // フロントから読み取り可能
  return { token };
}

// フロントエンド: Axiosインターセプターでトークン自動付与
axios.interceptors.request.use((config) => {
  const token = getCookie('XSRF-TOKEN');
  if (token && ['POST', 'PUT', 'DELETE'].includes(config.method?.toUpperCase())) {
    config.headers['X-CSRF-Token'] = token;
  }
  return config;
});

// BFF: ミドルウェアでトークン検証
if (['POST', 'PUT', 'DELETE'].includes(req.method)) {
  const cookieToken = req.cookies['XSRF-TOKEN'];
  const headerToken = req.headers['x-csrf-token'];
  if (!cookieToken || cookieToken !== headerToken) {
    throw new ForbiddenException('Invalid CSRF token');
  }
}
```

**導入時期**：

本システムは電子カルテとして高いセキュリティ要件を持つため、CSRFトークンの導入を推奨する。

| 導入タイミング | 実装方針 |
|--------------|---------|
| **初期開発（推奨）** | 基盤チームがミドルウェアとAxiosインターセプターを実装。アプリ開発者は意識不要 |
| **後期追加** | CORS + SameSite Cookieで運用開始し、セキュリティ監査で要求された場合に追加 |

**参照**：
- Axiosインターセプター実装の詳細：[01.フロントエンド・BFF共通基盤設計.md](01.フロントエンド・BFF共通基盤設計.md) の「1.4 Axiosインターセプターによる共通処理」

##### helmet・CORS・SameSite Cookie（保険的対策）

**実装ファイル（基盤チームが作成・管理）**: 
- `bff/src/shared/plugins/security.middleware.ts`

**機能**：
- `setupSecurity(app: NestExpressApplication)` 関数を提供
- `helmet` ミドルウェアによるセキュリティヘッダー自動設定
- CORS設定（許可オリジン、許可メソッド、許可ヘッダー）
- 環境変数 `FRONTEND_URL` に基づく動的なオリジン制御

**重要な設定内容**：
- `origin`: 環境変数 `FRONTEND_URL` で指定されたドメインのみ許可
- `credentials: true`: Cookie送信を許可
- `methods`: GET, POST, PUT, DELETE, PATCH のみ許可
- `allowedHeaders`: Content-Type, Authorization, X-Tenant-Id, X-CSRF-Token を許可

#### 実装ルール

**やっていいこと**：
- BFF起動時に基盤提供の `setupSecurity()` を呼び出す
- CORS設定は環境変数 `FRONTEND_URL` で制御する

**やってはいけないこと**：
- CORS設定で `origin: '*'`（すべてのオリジンを許可）を設定する
- `helmet` の使用を省略する
- 個別のエンドポイントで独自のCORS設定を追加する（基盤設定を上書きしない）

### Clickjacking（クリックジャッキング）対策

#### 目的

悪意のあるサイト上の `iframe` 内に本システムが表示されることを防ぐ。透明なiframeを重ねてユーザーのクリックを誘導する攻撃（クリックジャッキング）により、意図しない操作を実行させるリスクを排除する。

#### 概要

以下のヘッダーをBFF側で送出する。

| ヘッダー | 設定値 | 説明 |
|---------|-------|------|
| **X-Frame-Options** | `DENY` または `SAMEORIGIN` | フレーム内での表示を禁止または同一オリジンのみ許可 |
| **CSP frame-ancestors** | `'none'` | Content Security Policyでフレーム表示を禁止 |

#### 基盤実装

**実装ファイル（基盤チームが作成・管理）**: 
- `bff/src/shared/plugins/security.middleware.ts`

**機能**：
- `helmet` の `frameguard` オプションにより自動設定
- `X-Frame-Options: DENY` ヘッダーを送出
- CSP の `frame-ancestors 'none'` ディレクティブを設定

**効果**：
- クリックジャッキング攻撃（透明なiframeを重ねてユーザーのクリックを誘導する攻撃）を防止
- ブラウザレベルでの保護により、アプリケーション側の実装ミスによる脆弱性を排除

### Content Security Policy (CSP) 基本設定

#### 概要

Content Security Policy（CSP）は、複数のセキュリティ脅威を防ぐHTTPレスポンスヘッダーです。

| 防御対象 | 関連ディレクティブ | 参照元 |
|---------|-----------------|-------|
| **XSS** | `script-src`, `connect-src`, `default-src` 等 | 本セクション上部「XSS対策」 |
| **Clickjacking** | `frame-ancestors` | 本セクション上部「Clickjacking対策」 |

BFF層で `helmet` ミドルウェアを使用し、基本的なCSP設定を行う。詳細なディレクティブ（外部サービスのドメイン許可等）は、外部サービスのドメイン確定後に基盤チームが追加する。

#### 基盤実装

**実装ファイル（基盤チームが作成・管理）**: 
- `bff/src/shared/plugins/security.middleware.ts`

**実装方針**：
- 初期段階では `helmet` のデフォルト設定を使用
- 開発環境と本番環境で設定を分ける（開発環境では一部制限を緩和）
- 外部サービス（認証基盤、Sentry等）のドメインが確定次第、ホワイトリスト方式で詳細化

**基本設定内容**：

| ディレクティブ | 初期設定値 | 説明 |
|--------------|----------|------|
| `defaultSrc` | `'self'` | デフォルトは自サイトのみ許可 |
| `scriptSrc` | `'self'` | スクリプトは自サイトのみ許可 |
| `styleSrc` | `'self'`, `'unsafe-inline'` | スタイルは自サイト + インラインスタイル許可（Tailwind対応） |
| `imgSrc` | `'self'`, `data:`, `https:` | 画像は自サイト + data URI + HTTPS全般を許可 |
| `connectSrc` | `'self'` | API接続は自サイトのみ（外部サービス確定後に追加） |
| `frameSrc` | `'none'` | 電子カルテ自身が外部iframeを読み込むことを禁止（XSS経由のフィッシング対策） |
| `frameAncestors` | `'none'` | 電子カルテが他サイトのiframe内に埋め込まれることを禁止（Clickjacking対策） |

**詳細化が必要なディレクティブ**（外部サービス確定後、基盤チームが追加）：

| ディレクティブ | 目的 | 追加が必要なドメイン |
|--------------|------|-------------------|
| `script-src` | 実行を許可するスクリプトドメイン | 認証基盤、監視ツール（Sentry等） |
| `connect-src` | APIやWebSocketの接続先制限 | 業務API、WebSocket（Socket.io）、Sentryエンドポイント |
| `img-src` | 画像読み込み元 | CDN、医療画像ストレージ |
