# ADR-3: XSS 多層防御で React 自動エスケープを主防御層とする

* **ステータス**: Accepted
* **決定日**: 2026-05-22
* **関連設計書**: [XSS対策設計.md](../XSS対策設計.md) §1
* **関連 ADR**:
    * [httponly-cookie.md](httponly-cookie.md)（XSS 主防御を補完するトークン保護）
    * [csp-style-unsafe-inline.md](csp-style-unsafe-inline.md)（CSS インジェクション層の補完）

## 背景

電子カルテは PHI（患者健康情報）を扱うため、XSS によるスクリプトインジェクションは情報漏洩・画面改ざん・セッション盗取の温床となる。

XSS は「入力値検証で完全防御できる」と誤解されがちだが、業務上 `<` 等の記号入力を許容する必要があり、スクリプトパターンを完全に検出することは不可能。さらに、データ保存時にサニタイズすると元データが失われ、表示コンテキストに応じた適切なエスケープができなくなる。

防御層の優先度を明確化しないと、入力検証の過剰実装（バリデーションで全文字種を排除）や DB 保存時サニタイズ（元データ喪失）など、運用に支障のある対策が乱立するリスクがある。

## 検討した選択肢

### 案A: 入力検証を主防御層（厳格な文字種制限）
* **メリット**: 入口で弾くため後段の防御が薄くても済む（理論上）。
* **デメリット**: 業務要件で `<`, `>`, `&` 等を入力可能にする必要がある（医療文書）。完全な検出は不可能。誤検知で業務阻害。

### 案B: DB 保存時サニタイズ（保存前に HTML エスケープ）
* **メリット**: 保存後の表示で意識不要。
* **デメリット**: 元データが失われ、別コンテキスト（PDF 出力・CSV エクスポート）でエスケープ済み文字列が混入。表示形式変更時に元データに戻せない。

### 案C: React 自動エスケープを主防御層、入力検証は補助、HTML 表示は DOMPurify、外部スクリプトは CSP で遮断
* **メリット**: React の `{value}` 形式は自動でエスケープが効くため、開発者が意識せず安全。元データを保持できるため表示コンテキスト変更に強い。多層防御で1層が破られても次層が機能する。
* **デメリット**: `dangerouslySetInnerHTML` 利用時は明示的な DOMPurify 呼び出しが必要（規約で禁止／例外管理）。

## 決定

**案C（React 自動エスケープ主防御 + DOMPurify + CSP の多層防御）を採用する**。

| 層 | 役割 | 実装 |
|---|---|---|
| 入力検証 | 補助 | Zod スキーマで文字数・文字種制限のみ（業務上許容できる範囲で）。スクリプトパターン検出は試みない |
| 主防御: React エスケープ | 主 | `{value}` 形式で表示。`dangerouslySetInnerHTML` は原則禁止 |
| HTML 表示時の DOMPurify | 必要時 | 将来 WYSIWYG 等で HTML 表示が必要になった場合のみ `sanitizeHTML()` 経由で使用 |
| HttpOnly Cookie | トークン保護 | XSS が成立してもトークン窃取は不可能（[ADR-1](httponly-cookie.md)） |
| CSP | 最終層 | `script-src 'self'` で外部スクリプト実行を遮断 |

DB 保存時はエスケープ・サニタイズを行わず、元データをそのまま保存する。

## 影響

### 正の影響
* 業務上必要な記号入力を許容できる。
* 元データが保持されるため、表示コンテキスト変更（HTML / PDF / CSV）に対応可能。
* 1層が破られても他層で防御できる多層構造になり、単一の実装ミスがシステム全体の脆弱性につながらない。

### 負の影響
* `dangerouslySetInnerHTML` 利用時は規約で例外管理が必要（基盤チーム承認 + DOMPurify 必須）。
* 入力検証だけに頼った設計に対する誤解を解消する説明（規約への明文化）が必要。

### 見直しトリガー
* React のレンダリング方式が大きく変わり、自動エスケープの動作が変更される場合（メジャーバージョンアップ時に確認）。
* WYSIWYG エディタ等で HTML 表示が常態化した場合、DOMPurify 設定の厳格化と運用方針見直しが必要。
