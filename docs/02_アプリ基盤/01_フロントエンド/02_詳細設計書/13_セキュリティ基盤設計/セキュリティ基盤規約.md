## 2. 基盤 I/F 利用規約（最重要）

> 基盤が提供する I/F を **経由しない実装は禁止する**。
> 根拠: [adr/xss-defense-in-depth.md](adr/xss-defense-in-depth.md) / [adr/csrf-double-submit.md](adr/csrf-double-submit.md) / [adr/httponly-cookie.md](adr/httponly-cookie.md)

### 2.1 必ず経由する I/F とバイパス禁止 API

| 用途 | ✅ 経由必須 I/F | ⛔ バイパス禁止 | 詳細 |
|---|---|---|---|
| 信頼できない HTML の表示 | `sanitizeHTML(dirty)` ＋ `dangerouslySetInnerHTML` の組み合わせ（基盤チーム承認後） | サニタイズなしの `dangerouslySetInnerHTML`、独自 sanitizer 実装 | [XSS対策設計.md](XSS対策設計.md) §2 |
| URL 入力フィールドのバリデーション | Zod スキーマで `http://` / `https://` のみ許可 | プロトコル検証なしの `<a href={input}>`、`javascript:` を許可 | [XSS対策設計.md](XSS対策設計.md) §3 |
| 認証セッション/RT の保管 | `HttpOnly + Secure + SameSite` Cookie（BFF が設定） | `localStorage` / `sessionStorage`、`httpOnly: false` Cookie | [セキュリティミドルウェア設計.md](セキュリティミドルウェア設計.md) §2 / [adr/httponly-cookie.md](adr/httponly-cookie.md) |
| BFF へのフロント発状態変更（POST/PUT/DELETE/PATCH） | `axiosClient` 経由（基盤インターセプターが `X-CSRF-Token` 自動付与） | `fetch` / 別 axios インスタンスでの直接送信 | [CSRF対策設計.md](CSRF対策設計.md) §2 |
| BFF 起動時のセキュリティヘッダー設定 | `setupSecurity(app)` を `main.ts` で1度呼ぶ | helmet 省略、エンドポイント単位のCORS上書き、`origin: '*'` | [セキュリティミドルウェア設計.md](セキュリティミドルウェア設計.md) §3 |
| Sentry 等への外部送信前のPHI除去 | `beforeSend` フックで `phiPatterns.ts` 適用 | `Sentry.captureException` 直接呼び出し（フィルタなし） | [PHIマスキング設計.md](PHIマスキング設計.md) §2 |

### 2.2 例外

| ケース | 条件 |
|---|---|
| プロトタイプ・検証コード | 本番投入前に基盤 I/F 経由へ移すこと |
| 基盤チームによる基盤実装 | 本規約の対象外（基盤 I/F の実装側） |
| 将来の `dangerouslySetInnerHTML` 利用（WYSIWYG・部門連携・HL7/FHIR） | 利用申請後、基盤チーム承認＋ `sanitizeHTML()` 経由＋ `ALLOWED_TAGS`/`ALLOWED_ATTR` を最小限に絞ることを必須とする |

### 2.3 PR レビュー観点

| 観点 | チェック内容（grep ターゲット） |
|---|---|
| サニタイズ漏れ | `dangerouslySetInnerHTML=` の出現箇所すべてに `sanitizeHTML(` が同行/直前にあるか |
| 認証情報のクライアント保管 | `localStorage.setItem(.../accessToken|.../idToken|.../refreshToken|.../session)` が無いか |
| URL 検証漏れ | 入力由来の文字列を `<a href={...}>` / `window.open(...)` / `location.assign(...)` に直接渡していないか |
| 直接 fetch | `fetch(` / `new XMLHttpRequest(` 直書きが無いか（`axiosClient` 経由か） |
| CORS 緩和 | `cors({ origin: '*' })` / `cors({ origin: true })` が無いか |
| Sentry 直接送信 | `beforeSend` を介さない `Sentry.captureException` / `Sentry.captureMessage` 直接呼び出しが無いか |
| `eval` / `Function` | `eval(` / `new Function(` の出現が無いか |

## 3. XSS 対策規約

### 3.1 やっていいこと

* ユーザー入力を表示する際は React の自動エスケープに任せる（`{userInput}`）
* リンク・URL 入力フィールドでは Zod スキーマで `http://` / `https://` のみ許可

### 3.2 やってはいけないこと

* `dangerouslySetInnerHTML` をサニタイズなしで使用する（原則禁止。要件発生時は §2.2 例外）
* `eval()` や `Function()` コンストラクタを使用する
* ユーザー入力を URL やスクリプトタグに直接埋め込む
* `javascript:` スキームの URL を許可する
* 認証トークン・PHI を `localStorage` / `sessionStorage` に保管する

> 詳細な多層防御の設計と実装は [XSS対策設計.md](XSS対策設計.md) を参照。

## 4. CSRF 対策規約

### 4.1 やっていいこと

* フロントエンドの状態変更操作は基盤の `axiosClient` 経由で送信する（CSRFトークンは自動付与される）
* BFF 起動時に基盤提供の `setupSecurity()` を `main.ts` で呼び出す

### 4.2 やってはいけないこと

* `axiosClient` 以外の HTTP クライアント（生 `fetch` 等）で POST/PUT/DELETE/PATCH を送信する（CSRFトークンが付与されない）
* CORS 設定で `origin: '*'`（すべてのオリジンを許可）を設定する
* `helmet` の使用を省略する
* 個別のエンドポイントで独自の CORS 設定を追加する（基盤設定を上書きしない）
* Cookie に `httpOnly: false` で認証情報を格納してはならない（根拠: [adr/httponly-cookie.md](adr/httponly-cookie.md)）

> 詳細な発行・検証フローは [CSRF対策設計.md](CSRF対策設計.md) を参照。

## 5. PHI マスキング規約（セキュリティ観点）

| No | 規約 | 目的 |
| --- | --- | --- |
| 1 | 外部 SaaS（Sentry等）へエラー送信する場合、必ず `beforeSend` フックを通す | 機密情報の流出防止 |
| 2 | PHI パターン定義は `front_bff_shared/utils/phiPatterns.ts` の一元管理を使用する | 抜け漏れ・パターン分散の防止 |
| 3 | 監査情報（ユーザーID、テナントID、セッションID）を必ずタグ付与する | マルチテナント環境での影響範囲特定 |

> 実装詳細は [09_監視エラーハンドリング設計/GlitchTip連携設計.md](../09_監視エラーハンドリング設計/GlitchTip連携設計.md) を参照。本章では監査要件のみを定義する。
