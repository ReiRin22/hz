# ADR-3: UI コンポーネント開発に Storybook を採用する

* **ステータス**: Accepted
* **決定日**: 2025-10-01
* **関連設計書**: [Storybook基盤設計.md](../Storybook基盤設計.md) §1 位置づけ
* **関連 ADR**: なし

## 背景（Context）

上位の方式設計書 [@フロントエンド方式設計書_sheet_17_【方式検討】隔離開発環境・ドキュメンテーションツール.md](../../../01_方式設計書/@フロントエンド方式設計書_sheet_17_【方式検討】隔離開発環境・ドキュメンテーションツール.md) において、UI コンポーネントの隔離開発環境としてのツール選定の方針が示されている。

本プロジェクトは 500 機能規模の医療システムであり、画面数・コンポーネント数の増加に伴い以下の課題が予想される。

- アプリケーション内で開発したコンポーネントは、特定のページや状態でしか確認できず、全状態を網羅した検証が困難
- デザイナー・PdM がコンポーネント単位の挙動を確認する手段が乏しい
- CSS 変更による意図しない画面崩れ（ビジュアルリグレッション）が他機能に波及するリスクが高い
- Props ドキュメントが散在し、再利用性が低下する

主な要件:

- アプリ全体から **隔離された環境**でコンポーネント単体を確認できること
- 全 Props 状態を網羅したカタログとしての可視化
- ビジュアルリグレッションの早期検出
- デザインチームとの仕様共有手段

## 検討した選択肢（Options）

### 案A: Storybook を採用（採用）

* **メリット**
  * コンポーネント単体を隔離環境で表示・操作できる
  * Args による Props のインタラクティブ編集が可能
  * Decorator でグローバルスタイル・テーマ・React Query / Zustand のモックを再現できる
  * Chromatic 等との連携でビジュアルリグレッションテストが可能
  * Storybook Test Runner で Play function によるインタラクション自動化が可能
  * デファクトスタンダードであり、エコシステム・ノウハウが豊富
* **デメリット**
  * Story ファイルの追加コストが発生する
  * Storybook 自体のメンテナンス（バージョンアップ等）が必要

### 案B: アプリ内のサンプルページで確認（見送り）

* **メリット**: 追加ツール不要
* **デメリット**
  * アプリのルーティング・状態管理に依存するため、コンポーネントの全状態を網羅しにくい
  * 500 機能規模ではサンプルページの管理コストが線形以上に増大する

### 案C: Playroom / Ladle 等の代替ツール（見送り）

* **メリット**: 軽量
* **デメリット**: エコシステムが Storybook より限定的で、Chromatic 連携・Test Runner などの周辺機能が劣る

## 決定（Decision）

**案A: Storybook を採用する。**

Storybook の役割を以下に定義する:

| 役割 | 内容 |
|---|---|
| コンポーネントカタログ | 全 UI コンポーネントの状態（Props）を一覧化し、デザインシステムを可視化 |
| 隔離開発環境 | アプリのロジック・データから切り離し、コンポーネントの全状態を再現・検証 |
| ビジュアルリグレッションテスト | Chromatic 等と連携し、CSS 修正等による画面崩れを早期検出 |
| ドキュメント基盤 | Props の自動ドキュメント化、デザインチームとの共有 |

詳細仕様（Story 配置・命名・Decorator 構成・運用ルール等）は本章策定時点で未定義であり、Storybook 導入フェーズで [Storybook基盤設計.md](../Storybook基盤設計.md) §3 に追記する。

## 影響（Consequences）

* **正**: コンポーネントの隔離検証が可能になり、品質担保が容易になる。デザインチームとの仕様共有が効率化
* **負**: Story 作成・メンテナンスのコストが発生する。Story 必須化の運用ルールが必要
* **見直しトリガー**: Storybook の代替となる標準ツールが登場した場合、または Story メンテナンスコストが受容範囲を超えた場合
