# ADR-1: authStore に persist を採用しない

* **ステータス**: Accepted
* **決定日**: 2026-05-12
* **関連設計書**: [ストア基盤設計.md](../ストア基盤設計.md) §認証ストア
* **関連 ADR**: [13_セキュリティ基盤設計/adr/httponly-cookie.md](../../13_セキュリティ基盤設計/adr/httponly-cookie.md)（HttpOnly Cookie 採用と一体）

## 背景

電子カルテはマルチテナントの医療情報を扱い、XSS による認証トークンの窃取は重大な個人情報漏洩事故に直結する。
認証基盤連携サービス方式設計書 2.1.2.9 において、認証情報の保管要件として以下が定義されている。

* アクセストークン（AT、JWT、有効期限10分）
* ID トークン本体は「保管しない」
* リフレッシュトークン（RT、JWT、有効期限1日）

`localStorage` / `sessionStorage` は JavaScript から読み取り可能であるため、認証トークンを置くと XSS 被害時の影響範囲が拡大する。

## 検討した選択肢

### 案A: authStore に persist を採用（LocalStorage 永続化）
* **メリット**: ブラウザリロード後も認証状態が即座に復元され、UX が良い。
* **デメリット**: AT・ID クレームが LocalStorage に書き出されるため、XSS 攻撃により JavaScript からトークンが窃取される。被害範囲が「ブラウザを開いている期間」全体に拡大する。

### 案B: authStore は persist を使わずメモリのみ保持。RT は HttpOnly Cookie でブラウザ管理。リロード時は RT で AT を再発行
* **メリット**: XSS 被害を「メモリ存在期間」に限定できる。RT は JavaScript から触れないため XSS 耐性が確保される。
* **デメリット**: リロードのたびに AT 再発行 API を呼ぶ必要があり、初期表示が一段階遅延する。

### 案C: AT を sessionStorage に保管
* **メリット**: タブを閉じれば消える。
* **デメリット**: タブ生存期間中は XSS から読み取れるため案A と同等のリスク。複数タブ間でセッションが分離される副作用もある。

## 決定

**案B を採用する**。

* AT・ID クレームは authStore のメモリのみに保持し、`persist` を使用しない。
* RT は BFF が `HttpOnly + Secure` Cookie で発行し、ブラウザが自動送信する。
* ID トークン本体は保管しない。受信時にデコードして必要なクレーム（`userId` 等）のみメモリ展開する。
* リロード時は Cookie の RT で AT 再発行 API を呼び、authStore に再投入する。

短命（10分）な AT であれば、再発行コストは UX 上許容範囲と判断した。

## 影響

### 正の影響
* XSS 被害時のトークン窃取リスクが「メモリ存在期間」に限定される。
* 13章「セキュリティ基盤設計」XSS 対策と整合する。
* `harz:auth` という LocalStorage キーを作る必要がなく、ログアウト時のクリーンアップ手順から1ステップ削減できる。

### 負の影響
* リロード直後に AT 再発行 API 呼び出しが必須となり、初期表示シーケンスが複雑化する。
* RT 再発行 API の仕様（エンドポイント・呼び出し主体）が認証基盤連携サービス詳細設計に依存する → 残件として[ストア基盤設計.md](../ストア基盤設計.md) の「残件」#2-3 で管理。

### 見直しトリガー
* 認証基盤連携サービスが AT 寿命を大幅延長（例: 1時間以上）した場合、メモリ保持の運用負荷再評価が必要。
* CSP/Trusted Types 等で XSS リスクが構造的に低減できた場合は、UX 重視で persist を再検討する余地がある（要 ADR 起票）。
