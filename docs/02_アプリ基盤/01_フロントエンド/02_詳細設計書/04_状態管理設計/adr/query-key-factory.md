# ADR-2: クエリキー管理に @lukemorales/query-key-factory を採用

* **ステータス**: Accepted
* **決定日**: 2026-05-12
* **関連設計書**: [クエリキー基盤設計.md](../クエリキー基盤設計.md)
* **関連 ADR**: なし

## 背景

React Query のキャッシュ識別子であるクエリキーは、以下を物理的に保証する必要がある。

1. **マルチテナント安全性**: 別テナントのデータがキャッシュ越しに混入しない。
2. **リファクタ安全性**: ドメイン構造の変更時に、影響範囲を grep ではなく型で追跡できる。
3. **無効化の正確性**: `invalidateQueries` / `removeQueries` 時に、関係ないキャッシュを巻き込まない。

文字列配列を直接書く方式は、タイポ（`diagnoses` と `diagnosees`）が実行時まで検出されず、影響範囲もエディタ補完できない。

## 検討した選択肢

### 案A: 文字列配列の直書き（ライブラリなし）
* **メリット**: 依存ゼロ。学習コストなし。
* **デメリット**: タイポがコンパイルで止まらない。キー構造変更時に grep 漏れのリスクがある。`invalidateQueries` で誤って広範囲を巻き込む事故が発生しうる。

### 案B: 自前ヘルパー関数で集約
* **メリット**: ライブラリ依存ゼロのまま、ある程度の型安全性が得られる。
* **デメリット**: ヘルパー設計を社内で再発明する。階層構造識別子（`._def` 相当）を自前で実装するコストが高く、保守者が交代した際にメンテ放棄されやすい。

### 案C: `@lukemorales/query-key-factory` を採用
* **メリット**: TypeScript の型推論でドメイン・スコープが補完される。`._def` による階層的無効化が標準提供される。コミュニティで枯れたライブラリ。
* **デメリット**: 外部依存が1つ増える。`createQueryKeyStore` の構造的制約に従う必要がある（`queryKey` プロパティを返すオブジェクトを返す等）。

## 決定

**案C を採用する**。

* `src/shared/keys/queryKeyStore.ts` で `createQueryKeyStore` により全クエリキーを一元管理する。
* ユーザー定義キーは `[tenantId, params?]` 構造とし、domain と scope は factory が自動付与する（実際のキーは `[domain, scope, tenantId, params?]`）。
* 手書きクエリキーは禁止。例外はプロトタイプ・検証コードのみ。

## 影響

### 正の影響
* タイポがコンパイルエラーで検知される。
* キー構造変更が `queryKeyStore.ts` の1箇所修正で全呼び出し箇所に反映される。
* `_def` を使ったドメイン全体の無効化が型安全に行える。
* キーの一覧性が向上し、レビュー時にドメイン全体を俯瞰できる。

### 負の影響
* `@lukemorales/query-key-factory` の API 変更（major バージョンアップ等）に追随する必要がある。
* `_def` を不用意に使うと別テナントのキャッシュも巻き込むリスクがあるため、`removeQueries` では `predicate` でテナント条件を AND する規約が必要（[クエリキー基盤設計.md](../クエリキー基盤設計.md) 参照）。

### 見直しトリガー
* React Query 自体が公式にキー管理機能を統合した場合、依存削減のため移行を検討する。
* ライブラリのメンテナンスが停止した場合、案B（自前ヘルパー）への移行コストを再評価する。
