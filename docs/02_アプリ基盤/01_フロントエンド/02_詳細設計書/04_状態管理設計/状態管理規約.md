# 状態管理規約

フロントエンド基盤が提供するストア・クエリキー・クリーンアップ機構の上で **アプリ実装チームが守るべき規約** を定義する。

| 関連文書 | 内容 |
|---|---|
| [ストア基盤設計.md](ストア基盤設計.md) | 各 Store と storeRegistry の I/F |
| [クリーンアップ基盤設計.md](クリーンアップ基盤設計.md) | useTenantCleanup・ログアウトシーケンス |
| [クエリキー基盤設計.md](クエリキー基盤設計.md) | queryKeyStore.ts・キー構造・無効化／削除パターン |

---

## 1. 状態の分類と使用ツール

| 状態 | 使用ツール | 例 | 寿命 |
|---|---|---|---|
| サーバー状態 | React Query | 患者一覧、診療記録 | キャッシュ戦略（gcTime）に従う |
| クライアント／UI 状態 | Zustand | テーマ、選択中の患者 ID | アプリ起動中またはドメイン在籍中。ログアウトで明示リセット |
| フォーム状態 | React Hook Form | 入力フォーム | フォーム表示中のみ |

> 概念モデルの詳細は [ストア基盤設計.md](ストア基盤設計.md) §2 を参照。

## 2. 基盤 I/F 利用規約（最重要）

> 基盤が提供する I/F を **経由しない実装は禁止する**。バイパス実装はテナント間データ混入・ログアウト時のデータ残留・キャッシュ整合崩壊を引き起こす。

### 2.1 必ず経由する I/F とバイパス禁止 API

| 用途 | ✅ 経由必須 I/F | ⛔ バイパス禁止 | 詳細 |
|---|---|---|---|
| サーバー状態取得・無効化・削除 | `queries.{domain}.{scope}(...).queryKey` | クエリキーの配列直書き、`removeQueries` で `_def` 単独使用 | §5、[クエリキー基盤設計.md](クエリキー基盤設計.md) |
| Store のリセット登録 | `registerStore(reset)` をモジュールトップで一度呼ぶ | 個別 Store の reset を呼び出し側に書き散らす | §6.2、[ストア基盤設計.md](ストア基盤設計.md) §3.1 |
| ログアウト・テナント切替 | `useTenantCleanup().cleanup()` | `queryClient.clear()` 直接呼び出し、個別 Store の reset、`router.push('/login')` 等のソフトリダイレクト | §6.3、[クリーンアップ基盤設計.md](クリーンアップ基盤設計.md) |
| 未保存データ保護つき画面遷移 | `useNavigationGuard` | `useRouter().push/replace` を `isDirty` 中に直接呼ぶ | §3.2 |
| 認証情報の保持 | `useAuthStore` | LocalStorage / SessionStorage / Cookie を直接読み書き | [ストア基盤設計.md](ストア基盤設計.md) §5.1、[adr/auth-no-persist.md](adr/auth-no-persist.md) |

### 2.2 例外

| ケース | 条件 |
|---|---|
| プロトタイプ・検証コード | 本番投入前に基盤 I/F 経由へ移すこと |
| 基盤チームによる基盤実装 | 本規約の対象外（基盤 I/F の実装側） |

### 2.3 PR レビュー観点

| 観点 | チェック内容 |
|---|---|
| クエリキー手書き | `queryKey: [` の配列直書きが無いか（`queryKeyStore.ts` 以外で）|
| storeRegistry 漏れ | Global / Domain Store に `registerStore(...)` 呼び出しがあるか |
| ログアウト経路 | `useTenantCleanup` 以外に `queryClient.clear()`・`window.location` が無いか |
| 認証情報の保管 | `localStorage.setItem(.../accessToken|.../idToken|.../refreshToken)` 等が無いか |

## 3. フォーム管理規約（React Hook Form）

### 3.1 必須要件

| 項目 | 内容 |
|---|---|
| ライブラリ | React Hook Form + `@hookform/resolvers/zod` |
| バリデーション | `front_bff_shared/features/**/schemas/{機能名}.schema.ts` の Zod スキーマを使用 |
| 検証タイミング | `mode: 'onSubmit'`（既定）。例外時はアプリチーム設計書に記載 |
| 送信制御 | `disabled={!isDirty || !isValid}`（変更あり かつ バリデーション通過） |
| 保存後 | `reset()` で「変更あり」状態を解除 |

### 3.2 使用する API

| API | 役割 |
|---|---|
| `useForm<T>({ resolver, mode, defaultValues })` | フォームの初期化。型パラメータ `T` は `z.infer<typeof schema>` で得た型を渡す |
| `zodResolver(schema)` | Zod スキーマを React Hook Form に接続するアダプタ |
| `register('フィールド名')` | `<input>` 等に展開し、値の追跡とバリデーションを登録 |
| `handleSubmit(onSubmit)` | `<form onSubmit>` に渡す。バリデーション成功時のみ `onSubmit` を呼ぶ |
| `formState.errors` | フィールドごとのエラーメッセージ（Zod スキーマのメッセージが入る） |
| `formState.isDirty` | 初期値から変更があるか（未保存チェック・送信制御に使用） |
| `formState.isValid` | バリデーションが通っているか（送信制御に使用） |
| `reset(values?)` | フォームを初期状態（または指定値）に戻す。保存成功後に呼ぶ |

### 3.3 バリデーション境界（FE 即時 UX／BFF 最終保証）

| レイヤ | 責務 | 検証内容 |
|---|---|---|
| フロントエンド（即時 UX） | 保存ボタン押下時（`mode: 'onSubmit'`）に Zod スキーマで形式チェック | 型・必須・桁数等の形式的検証。`mode: 'onChange'`／`'onBlur'` 等の例外時はアプリチーム設計書に記載 |
| BFF（最終保証） | 同一 Zod スキーマ（**シンボリックリンク経由で FE/BFF 共有**）で受信時に再検証 | 形式検証に加え、ビジネスロジック整合性（重複・権限・参照整合）はこのレイヤで最終保証 |

### 3.4 Dirty 管理と画面遷移制御

> Next.js App Router 環境では `beforePopState` が使用できないため、`useRouter` の `push`/`replace` をラップしたカスタムフック（`useNavigationGuard`）で遷移制御を行う。

| ケース | 対応 |
|---|---|
| アプリ内遷移 | `useNavigationGuard`（`useRouter` の `push`/`replace` ラッパー）で `isDirty` 時に確認ダイアログ |
| タブ閉じ・リロード | `window.beforeunload` イベント |
| 保存失敗 | フォーム／退避 Store のデータは保持。エラーはトースト等で通知 |

### 3.5 入力データの退避（任意）

「一時保存（サーバー送信）」を行うほどではないが、画面遷移によって入力内容が消失するとユーザーの作業効率を著しく損なう場合に適用する（長大フォームで一時離脱→復帰するケース等）。

| 規約 | 内容 |
|---|---|
| 退避先 | features 配下の Page スコープ Zustand Store（下書き用） |
| 復帰時 | 退避データがあればフォームの `defaultValues` に投入 |
| 削除条件 | 「保存成功」または「明示的なキャンセル」で即削除 |

### 3.6 描画最適化

| 観点 | 内容 |
|---|---|
| 再レンダリング抑制 | `register` による非制御コンポーネント方式を維持（`useState` で値追跡しない） |
| 仮想化との共存 | 大量データ表示時の入力遅延を発生させない |
| 更新範囲 | エラー表示・該当入力項目のみ再描画されるコンポーネント構造とする |

## 4. キャッシュ制御規約（React Query）

### 4.1 データ特性別の標準値

| データ特性 | 例 | 戦略概要 | `staleTime` | `gcTime` | `refetchOnWindowFocus` |
|---|---|---|---|---|---|
| マスタ系 | 職員、病名、医薬品マスタ | 変更頻度が低く長時間キャッシュ可。フォーカス再取得は不要 | 60 分 | 60 分 | OFF |
| 動的データ | 現在のバイタル、予約状況 | 常に最新が必要。フォーカス復帰時に再取得 | 0 秒 | 5 分 | ON |
| 重い履歴データ | 1 万件の経過記録、画像一覧 | 取得コストが高く頻繁な再取得は避ける。短時間 stale 化で過剰再取得を抑制 | 1 分 | 10 分 | OFF |

> 実装パターン・無効化／削除 API の詳細は [クエリキー基盤設計.md](クエリキー基盤設計.md) §4 を参照。

### 4.2 Mutation 後の同期

| 規約 | 内容 |
|---|---|
| 同期方式 | 原則 `invalidateQueries` で再取得（Mutation 成功直後） |
| 影響範囲 | できる限り具体的なキー（特定の患者 ID 等）を指定し、無関係なキャッシュ再取得を避ける |
| 楽観的更新 | 医療データの整合性が極めて重要なため、適用は慎重に検討する（原則は再取得） |

## 5. クエリキー利用規約

§2.1 の通り、サーバー状態の取得・無効化・削除は基盤提供の `queries`（`@lukemorales/query-key-factory`）経由とする。

| 種別 | 規約 |
|---|---|
| ✅ 必須 | 第1階層に `tenantId` を含める（テナント間データ混入の物理的遮断） |
| ✅ 必須 | `useQuery` / `useMutation` / `invalidateQueries` / `removeQueries` のキー指定はすべて `queries.{domain}.{scope}(...).queryKey` 経由 |
| ⛔ 禁止 | クエリキーの手書き（`['diagnosis', 'patientList', ...]` のような配列直書き） |
| ⛔ 禁止 | `removeQueries` で `_def` を単独使用（scope 配下の全テナント分が消える） |

> 採用ライブラリの判断根拠は [adr/query-key-factory.md](adr/query-key-factory.md) を参照。

## 6. Store 利用規約

### 6.1 スコープ別の使い分け

| スコープ | 配置 | persist | storeRegistry 登録 |
|---|---|---|---|
| Global | `src/shared/stores/` | あり（partialize 必須）／なし | 必須 |
| Domain | `src/shared/stores/` | なし | 必須 |
| Page | `src/features/**/stores/` | なし | 不要 |

> 各 Store の I/F は [ストア基盤設計.md](ストア基盤設計.md) §5 を参照。

### 6.2 Store 追加時のチェックリスト

| 項目 | Global | Domain | Page |
|---|---|---|---|
| `registerStore(reset)` の呼び出し | ✅ | ✅ | — |
| layout の Providers で import | ✅ | ✅ | — |
| persist 採用時は `partialize` で永続化対象を絞る | ✅ | — | — |
| LocalStorage キーは `harz:{store-name}` | ✅ | — | — |

### 6.3 ログアウト処理

§2.1 の通り、ログアウト・テナント切替は `useTenantCleanup().cleanup()` を経由する。

| 規約 | 内容 |
|---|---|
| ✅ 必須 | `useTenantCleanup().cleanup()` を呼ぶのみ |
| ⛔ 禁止 | 個別 Store の reset・`queryClient.clear()` の直接呼び出し |
| ⛔ 禁止 | `router.push('/login')` 等のソフトリダイレクト（基盤がハードリダイレクトを実行） |

> シーケンスの詳細・採用根拠は [クリーンアップ基盤設計.md](クリーンアップ基盤設計.md)・[adr/hard-redirect-on-logout.md](adr/hard-redirect-on-logout.md) を参照。

## 7. 配置規約

> 階層構造の全体像は [00.ディレクトリ構成.md](../00.ディレクトリ構成.md) を参照。本節では状態管理に関連するコードの配置規約のみを定義する。

### 7.1 features 層（機能固有）

特定の業務機能（LV3）に密接に関連する状態・ロジックは features 配下に配置し、外部からの直接参照を制限する。

| ディレクトリ | スコープ | 役割 | 例 |
|---|---|---|---|
| `src/features/{LV1}/{LV2}/{LV3}/stores/` | Page | 画面固有の Zustand Store。画面離脱で破棄される一時状態 | タブ切り替え状態、検索パネル開閉フラグ |
| `src/features/{LV1}/{LV2}/{LV3}/hooks/` | — | React Query / React Hook Form のロジックをカプセル化したカスタムフック | `useGetMedicalRecords.ts`、`useSaveDiagnosis.ts`、`useDiagnosisForm.ts` |

> LV1 = 機能群、LV2 = 中分類、LV3 = 画面機能。階層の詳細は [00.ディレクトリ構成.md](../00.ディレクトリ構成.md) を参照。

### 7.2 shared 層（アプリ全体・ドメイン共有）

業務ドメイン内共通・ドメイン跨ぎの区別なく、機能固有でない状態・ロジックは一律で `src/shared/` 配下に配置する。

| ディレクトリ | 役割 | 配下サブディレクトリの管理方針 |
|---|---|---|
| `src/shared/stores/` | Global / Domain スコープの Zustand Store（authStore、tenantStore、themeStore、patientStore、notificationStore 等） | `stores/patient/`・`stores/auth/` 等のサブディレクトリは実装チームが実装規模に応じて作成する |
| `src/shared/hooks/` | 複数機能をまたぐカスタムフック（`useNavigationGuard.ts`、`useAuth.ts`、`useTenant.ts`、`useToast.ts` 等） | `hooks/patient/`・`hooks/navigation/` 等のサブディレクトリは実装チームが実装規模に応じて作成する |
| `src/shared/keys/queryKeyStore.ts` | クエリキー一元管理（[クエリキー基盤設計.md](クエリキー基盤設計.md)） | — |

### 7.3 ファイル命名規則

| 種別 | 命名規則 | 例 |
|---|---|---|
| Store | `[機能名]Store.ts` | `authStore.ts`、`patientStore.ts` |
| カスタムフック | `use[機能名].ts` | `useNavigationGuard.ts`、`useAuth.ts` |
| LocalStorage キー | `harz:{store-name}` | `harz:theme`（プロダクト名 prefix で他ライブラリとのキー衝突を防ぐ） |

> LocalStorage キーは Global スコープかつ persist 採用ストアのみ。Domain / Page スコープは persist を使用しないためキーは存在しない（[ストア基盤設計.md](ストア基盤設計.md) §3.2 参照）。

### 7.4 カスタムフック分類と UI コンポーネントとの責務分離

| 分類 | 命名規則 | 例 |
|---|---|---|
| データフェッチ | `useGet{Resource}.ts` | `useGetPatients.ts` |
| データ更新 | `useSave{Resource}.ts` | `useSaveDiagnosis.ts` |
| フォーム管理 | `use{Feature}Form.ts` | `useDiagnosisForm.ts` |
| UI 状態管理 | `use{Feature}State.ts` | `useModalState.ts` |

| 役割 | 責務 |
|---|---|
| UI コンポーネント（Atoms / Molecules） | 見た目・デザインの共通化。状態管理ロジックを持たず、Props で受け取った値を表示する |
| カスタムフック | ロジック・状態管理の共通化。データ取得・更新・フォーム制御等の「動作」をカプセル化する |

### 7.5 カプセル化の原則

| 規約 | 内容 |
|---|---|
| features 配下 | 同一機能内のコンポーネントのみが参照する |
| 他機能から参照 | URL パラメータ経由で渡す、または `shared` への昇格を検討 |
| Server / Client 分離 | `app` 層の `page.tsx`（Server Component）で初期取得 → features 層へ Props で渡し、React Query の `initialData` として同期 |

## 8. アプリ実装チームの責務サマリ

| カテゴリ | 責務 | 経由必須 I/F | 参照する基盤 |
|---|---|---|---|
| 基盤 I/F の利用 | バイパス実装をしない（§2 が最優先） | §2.1 の表 | §2 |
| フォーム実装 | React Hook Form + Zod。`isDirty`/`isValid` 併用、保存後 `reset()` | `useNavigationGuard`（遷移制御時） | §3 |
| キャッシュ設定 | データ特性別の `staleTime`/`gcTime`/`refetchOnWindowFocus` 設定 | — | §4、[クエリキー基盤設計.md](クエリキー基盤設計.md) |
| クエリキー追加 | `queryKeyStore.ts` の対応ドメインに追加 | `queries.{domain}.{scope}(...)` | §5、[クエリキー基盤設計.md](クエリキー基盤設計.md) |
| Page スコープ Store | `features/**/stores/` 配下に配置。`storeRegistry` 登録不要 | — | §6、[ストア基盤設計.md](ストア基盤設計.md) |
| ログアウト処理 | ログアウトボタンの onClick から呼ぶ | `useTenantCleanup().cleanup()` | §6.3、[クリーンアップ基盤設計.md](クリーンアップ基盤設計.md) |
