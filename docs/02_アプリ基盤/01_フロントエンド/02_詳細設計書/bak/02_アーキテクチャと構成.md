
# 2. アーキテクチャと構成

## 2.1. 全体構成図

本システムは Next.js (App Router) を基盤とし、フロントエンド、BFF (Node.js)、バックエンド の3層構造で構成される。
※詳細は別紙「全体構成図」シートを参照。


## 2.2. データフロー方式

本システムは、大規模データの整合性と描画パフォーマンスを両立するため、**「単一方向データフロー（Unidirectional Data Flow）」**を原則とする。データは必ず以下のライフサイクルを経てUIに到達する。

### 2.2.1. データのライフサイクルと型定義の同期

Monorepo内の `shared/types` を唯一の真実（SSOT）とし、フロントエンドとBFF間でリクエスト・レスポンスの型を厳格に同期する。

| ステップ | 実行場所 | 処理内容と規律 |
| --- | --- | --- |
| **1. 取得と検証** | **Frontend (Server)** | `fetch` を用いてBFFからデータ取得。直後に `shared/types` の **Zodスキーマ** でバリデーションを行い、不正データを遮断する。 |
| **2. 構造最適化** | **Frontend (Server)** | 受信したDTOをUI表示に最適な **ViewModel** へ変換する。重い計算やネストの解消は、ブラウザ負荷軽減のためこの段階で完了させる。 |
| **3. 脱水と復元** | **Hydration** | サーバーで得たデータを `React Query` のキャッシュ（Dehydrate/Hydrate）を介してクライアントへ引き継ぐ。これにより「戻る」操作等の再通信を防止する。 |
| **4. 描画制御** | **Frontend (Client)** | 1万件規模のデータは `Server State` として保持。フィルタやソート条件のみを `UI State (Zustand)` で管理し、両者を掛け合わせた結果を **Virtuoso** へ流し込む。 |

### 2.2.2. クライアントサイドの通信規律

ブラウザからの追加リクエスト（更新・個別取得等）は、以下の規律に従う。

* **APIクライアントの集約**:
全てのClientサイド通信は `axiosClient` インスタンスを経由する。このインスタンスには、マルチテナント用の `X-Tenant-Id` や認証ヘッダーを付与するインターセプターを実装し、通信仕様の漏れを物理的に防ぐ。
* **サーバー状態の更新（保留事項）**:
現在、更新・削除時のフロー（`Invalidate` 一択か `Optimistic Updates` 許容か）は保留とする。原則として、データ一貫性を重視し、Mutation成功後に該当クエリを無効化して最新データを再取得するフローを基本とする。

### 2.2.3. 大規模データ描画の「条件付き規律」

POCの結果に基づき、1万件を超えるデータの描画には以下の制限を設ける。

1. **仮想化の必須適用**: 100件を超えるリスト表示では、必ず `react-virtuoso` を使用し、DOM数を最小限に抑制する。
2. **BFF絞り込みの閾値**: レスポンスサイズが **5MB** または **1万件** を超えることが予測される場合は、フロントエンドでの全件保持を禁止し、BFF側での「ページネーション」または「検索条件による絞り込み」の実装を必須とする（POCでの初期HTML増大懸念への対策）。
3. **加工ロジックの所在**:
    * ソート・フィルタ等の「加工」は、`useMemo` を用いて Zustand の条件と React Query のデータを結合して算出する。
    * 加工結果を Zustand に永続保持することは避け、常に「元データ + 条件」から算出される派生状態として扱う。


## 2.3. サービス内アーキテクチャ・使用技術の定義

本システムは、保守性とスケーラビリティを担保するため、以下の三層構造を基本アーキテクチャとする。各層の依存関係は **「UI層 → 状態管理層 → サービス層」** の一方向とし、逆方向の参照を禁止する。

### 2.3.1. 各層の責務と決定スタック

| 層の名称 | 決定技術スタック | 役割と詳細設計規律（POC反映済） |
| --- | --- | --- |
| **UI層** | **React 18+, Tailwind CSS v4, Radix UI, react-virtuoso** | **【表示・入力・対話】**

・**仮想化描画**: 100件を超えるリストは `react-virtuoso` を必須とし、DOM数を一定に保つ。

・**スタイリング**: `globals.css` の `@theme` で定義した変数（`--color-primary`等）をコンポーネントで参照し、共通デザインは `@apply` で管理する。 |
| **状態管理層** | **Zustand, React Query (TanStack Query)** | **【データの同期・保持】**

・**Server State**: BFFからの取得データは React Query で管理し、キャッシュ・自動再取得を行う。

・**Client State**: 認証情報やテナントIDなど、非同期通信を伴わないグローバル状態は Zustand に限定する。 |
| **サービス層** | **TypeScript, Zod, axiosClient** | **【ロジック・通信・検証】**

・**バリデーション**: `shared/types` のZodスキーマを用い、受信データを即座に検証。型安全な `ViewModel` への変換を担う。

・**通信**: インターセプターを実装した `axiosClient` によりテナントID付与を共通化する。 |

### 2.3.3. 技術選定の決定根拠（POCエビデンス）

* **Tailwind CSS v4 の採用**:
POCにおいて、`postcss.config.js` に `@tailwindcss/postcss` を導入し、CSS変数によるテーマ管理が動作することを実証済み。これにより、将来的なマルチテナントごとのテーマ切り替え（CSS変数の上書き）に対応可能な基盤を確立した。
* **react-virtuoso の必須化**:
1万件のカルテ履歴表示において、通常の `map` 展開ではブラウザがフリーズするが、仮想化を導入することでスクロール時のメモリ使用量を一定（DOM数最小限）に抑えられることを確認。
* **Zod による「型」の物理的強制**:
BFFとの通信境界において、`shared/types` の型定義と Zod スキーマを共有することで、BFF側の仕様変更が直ちにフロントエンドのビルドエラーまたは実行時例外（Error UIへの遷移）として検知できる体制を構築した。


## 2.4. マイクロサービス方針

フロントエンドの肥大化抑制とセキュリティ担保のため、**BFF (Backend For Frontend)** の採用を必須とする。

### 2.4.1. BFFの主要責務

* **FHIRリソースの抽象化**:
複雑でネストの深いFHIRリソースをそのままフロントエンドに流さず、BFF側でUI表示に最適なフラットな **DTO (Data Transfer Object)** へ変換・選別して提供する。
* **APIアグリゲーション**:
画面表示に必要なデータが複数のバックエンドサービス（FHIRサーバー、認証基盤等）に跨る場合、BFF側で通信を集約し、フロントエンドへのレスポンスを1本化する。
* **セキュリティ境界**:
バックエンドAPIのURLや機密性の高いロジックをBFF内部に隠蔽し、フロントエンドには最小限の認可情報とデータのみを露出させる。

### 2.4.2. POCに基づく設計規律

* **ロジックの所在**:
「1万件のデータから特定のフラグを計算する」等の業務ロジックはBFF側に寄せ、フロントエンドのサービス層では **Zodによる型検証とViewModelへのマッピング** のみに専念する。
* **エラーの正規化**:
バックエンドごとの多様なエラー形式をBFFで吸収し、フロントエンドに対しては一貫したエラーレスポンス形式（`error.tsx` でハンドリング可能な形式）で返却する。


## 2.5. BFFアーキテクチャ・技術選定

BFFはフロントエンド開発チームの管理下に置き、フロントエンド（Next.js）との親和性が最も高い技術スタックを採用する。

### 2.5.1. 決定技術スタック

| 項目 | 決定事項 | 選定理由 / POCエビデンス |
| --- | --- | --- |
| **ランタイム** | **Node.js + ts-node** | **[決定]** TypeScriptを直接実行可能な標準的な環境。Monorepo内の共有型定義（@shared/）は tsconfig-paths を併用することで安全に解決。 |
| **フレームワーク** | **NestJS** | **[実証済]** 軽量で柔軟性が高く、Middleware（CORS等）や動的ルーティングの実装が容易であることを確認済み。 |
| **開発ツール** | **ts-node-dev** | **[決定]** ts-node をベースに、ファイルの変更検知（watch）と高速な再起動を両立する開発環境を確立。 |

### 2.5.2. 多層レイヤー構造の定義

単なるプロキシではなく、保守性を高めるため以下の3層構造を必須とする。

1. **Controller層 (Controllers)**:
* HTTP制御を担当。`shared/types` の型に基づき、リクエストの受信とレスポンスの送出を管理する。

2. **Service層 (Services)**:
* **[重要/実証済]** 業務ロジック、複数APIの並列集約（`Promise.all`）、およびフロントエンド向けへの **データの整形・マッピング** を行う。

3. **Client層 (Clients)**:
* バックエンドAPI（FHIRサーバー等）への通信をカプセル化し、外部依存を分離する。

### 2.5.3. セキュリティとエラーハンドリングの規律

* **CORS設定**:
`cors` パッケージを導入し、フロントエンド（Port 3000）からのアクセスを許可するように構成する。
* **多層防御（JWT検証）**:
Controller層の手前で、JWTの有効期限や署名のチェックを行うミドルウェアを今後実装予定。
* **エラーの正規化**:
**[実証済]** 下位レイヤー（Backend/Stub）での例外をサービス層でキャッチし、フロントエンドが扱いやすい一貫したエラー形式（500エラー等）で返却するフローを確立済み。


## 2.6. BFFとの連携仕様

フロントエンドとBFF間の通信は、Monorepoの利点を最大限に活かした「型安全（Type-Safe）」かつ「高レジリエンス（回復性）」な仕様に基づき実施する。

### 2.6.1. 垂直型安全（Vertical Type Safety）の規律

`shared/types` をSSOT（単一の真実の情報源）とし、フロントエンドとBFFの境界で型定義を完全同期させる。

* **Contract-First**: APIの新規作成・変更時は、まず `shared/types` 内のインターフェース（例: `UserResponse`）を更新することを起点とする。
* **型同期の強制**: **[実証済]** `shared` 側の型を変更した際、フロントエンド・BFF双方のエディタ上で即座にエラーが検知される体制を維持する。

### 2.6.2. リクエスト規律とマルチテナント対応

全ての通信には、マルチテナント環境を担保するための識別子を含める。

| 項目 | 定義 | 実装詳細（POC反映） |
| --- | --- | --- |
| **認証情報** | Bearer JWT | HTTP `Authorization` ヘッダーに付与。 |
| **テナントID** | `X-Tenant-Id` | **[決定]** axiosClientのインターセプターにより、全Clientリクエストに自動埋め込み。 |
| **通信プロトコル** | RESTful / JSON | 標準的な HTTP Methods (GET, POST, etc.) を使用。 |

### 2.6.3. 動的ルーティングと通信制御

Next.js 16 の仕様およびPOC検証結果に基づき、画面遷移時の通信を最適化する。

* **動的パス連携**: **[実証済]** `/user/[id]` 等のパスパラメータを、フロントエンドの Server Component からBFFの `app.get('/api/user/:id')` へ透過的に引き渡す。
* **プリフェッチの活用**: **[実証済]** Next.js の `<Link>` コンポーネントを用い、リンクがビューポートに入った段階でBFFからデータを事前取得（Prefetch）し、遷移速度を向上させる。
* **エラー境界の統合**: **[実証済]** BFF側で ID不一致（404）や例外（500）が発生した場合、フロントエンド側で `res.ok` 判定を行い、`throw new Error` を実行することで、`error.tsx` 境界へ処理を委譲する。


## 2.7. マルチテナント方針

本システムでは、単一のコードベースで複数顧客を支える「論理分離」を徹底する。

### 2.7.1. 識別情報の埋め込み規律

* **共通ヘッダー**: **[決定]** 全てのリクエスト（axiosClient）に `X-Tenant-Id` ヘッダーを自動付与し、BFF側で処理対象テナントを判別する。
* **識別子の保持**: ログイン時に取得したテナントIDを **Zustand** に保持し、アプリケーション全体から参照可能にする。

### 2.7.2. データリーク防止策（キャッシュ・パージ）

* **キャッシュの全破棄**: **[決定]** テナント切り替え時、またはログアウト時に React Query の `queryClient.clear()` を実行する。
* **目的**: ブラウザのメモリ上に残る旧テナントのデータを完全に抹消し、物理的なデータ混在（リーク）を防止する。

### 2.7.3. テナント固有設定の管理

* **UIパーソナライズ**: 権限情報（Role）やテナント固有のテーマカラーは Zustand で一元管理し、UIコンポーネントへ即時反映させる。


## 2.8. コンテナ方針

本システムは、実行環境の差異を排除し、オンプレミスおよびクラウド環境への一貫したデプロイを実現するため、Docker コンテナを標準のデプロイ単位とする。

### 2.8.1. マルチステージビルドの採用

イメージサイズの削減とセキュリティ向上（ビルドツールの除外）のため、マルチステージビルドを必須とする。

* **Frontend (Next.js)**:
* **スタンドアロンモード**: `next.config.js` で `output: 'standalone'` を有効化。
* **成果物**: ビルド時に生成される最小限の `server.js` と `node_modules` のみを含め、Node.js ランタイム上で動作させる。


* **BFF (NestJS)**:
* **ビルドプロセス**: ypeScript ソースを nest build (tsc) によりビルドし、生成された純粋な JavaScript ファイルを node コマンドで実行する。
* **共通資産**: ビルド時に shared ディレクトリの依存関係が適切に解決されるよう、tsconfig.build.json の設定を維持する。

### 2.8.2. 環境変数の注入と機密情報管理

「コードと設定の分離」を徹底し、イメージの再利用性を高める。

* **実行時注入（Runtime Env）**:
* APIエンドポイントやテナント共通設定は、Kubernetes の **ConfigMap** を介してコンテナ起動時に注入する。


* **機密情報の保護**:
* DB接続情報や外部サービスAPIキーは **Secret** を使用する。


* **ビルド時固定（Build Args）**:
* Next.js のクライアントサイドで参照する変数（`NEXT_PUBLIC_`）については、ビルド時に値を確定させる必要があるため、CI/CDパイプラインからビルド引数として渡す。

### 2.8.3. 軽量・セキュアなベースイメージ

* **Base Image**: セキュリティ脆弱性を最小限に抑えるため、`node:20-alpine` または `gcr.io/distroless/nodejs` 等の軽量・最小構成のイメージを採用する。
* **非ルートユーザーの実行**: セキュリティ上の理由から、コンテナ内のプロセスは `root` ではなく専用の一般ユーザー（`nextjs` / `bffuser` 等）で実行する。


## 2.9. コンポーネント設計方式

本システムは、UIの再利用性と大規模データ表示のパフォーマンスを両立するため、**Atomic Design** をベースとした階層化設計を採用する。

### 2.9.1. 階層別の定義と実装規律

| 階層 | 責務と実装ルール | 決定事項 / POCエビデンス |
| --- | --- | --- |
| **Atoms** | 最小単位のUI部品（Button, Input等）。プロジェクト固有のロジックを持たない。 | **[決定]** `src/components/ui` に配置。Radix UI / shadcn/ui ベースで構築。 |
| **Molecules** | 複数のAtomsを組み合わせた汎用部品（FieldGroup, SearchBar等）。 | **[規律]** 特定の業務コンテキスト（FHIR等）に依存しない汎用的なPropsを定義する。 |
| **Organisms** | **[重要]** 業務機能を持つ独立したセクション。BFFから取得したデータを扱う。 | **[実証済]** FHIRリソースの直接参照を禁止し、整形済みの **ViewModel** をPropsとして受け取る。 |
| **Templates** | ページのレイアウト構造（ワイヤーフレーム相当）を定義。 | **[規律]** 具体的なデータは持たず、Slot（children）を用いてコンポーネントを配置する。 |
| **Pages** | Next.js のルーティングに対応。データ取得と状態管理の接点。 | **[実証済]** `loading.tsx` や `error.tsx` と連携し、UXの最終責任を持つ。 |

### 2.9.2. スタイリング規律 (Tailwind CSS v4)

最新のCSS設計思想に基づき、保守性の高いスタイル管理を行う。

* **テーマ管理**: **[決定]** `globals.css` の `@theme` ブロックでCSS変数を一元管理する。
* **カスタムクラスの活用**: **[実証済]** 頻出するスタイル（例：`.karte-button`）は `@apply` を用いて共通化し、各コンポーネントでの記述を簡潔にする。
* **仮想化の統合**: **[実証済]** 1万件のデータリストを扱う Organisms 階層では、`react-virtuoso` を標準採用し、スタイリングと描画最適化を両立させる。

### 2.9.3. データ受け渡し制限

* **ViewModelの徹底**: Page層で取得したデータは、Organismsへ渡す前に必ずViewModelへと変換・選別されていること。
* **バケツリレーの回避**: 3階層を超えるPropsの受け渡しが必要な場合は、Context API または Zustand の利用を検討し、コンポーネントの疎結合を維持する。


## 2.10. 状態管理方式

本システムでは、状態（State）をその性質に応じて「サーバー」「クライアント」「フォーム」の3種類に明確に分離し、それぞれの特性に最適化されたライブラリを使い分ける。

### 2.10.1. 状態別の管理戦略と選定ツール

| 分類 | 決定ツール | 管理対象 | 規律とPOCエビデンス |
| --- | --- | --- | --- |
| **サーバー状態** | **React Query** | BFFから取得したデータ（カルテ、ユーザー情報等） | **[実証済]** 1万件のデータをキャッシュし、画面遷移後の「戻る」操作で再通信を行わず即時復元する。APIエラー時の `error.tsx` への委譲も一元管理する。 |
| **クライアント状態** | **Zustand** | 認証情報、テナントID、サイドバーの開閉、共通テーマ | **[決定]** サーバー通信を伴わない「純粋なUI状態」に限定。軽量な `store` として定義し、Propsバケツリレーを排除する。 |
| **フォーム状態** | **React Hook Form** | 入力中の値、バリデーションエラー、Dirty（変更）フラグ | **[決定]** 非制御コンポーネント（Ref）を活用し、1文字入力ごとの再レンダリングを抑制。Zodと連携し、送信前の型安全性を担保する。 |

### 2.10.2. 状態管理の棲み分け規律（アーキテクチャ）

* **「計算された状態」の扱い**:
1万件のデータに対する「現在の表示順」や「フィルタ結果」は、状態として保持するのではなく、`React Query` のデータと `Zustand` のフィルタ条件を組み合わせて、コンポーネント内で **`useMemo` により算出** する。
* **キャッシュのライフサイクル**:
* **有効期限（staleTime）**: 業務要件に応じて定義するが、基本は「自動再取得」を有効にし、データの最新性を担保する。
* **強制破棄**: 「2.7. マルチテナント方針」に従い、テナント切り替え時は `queryClient.clear()` で全サーバー状態を破棄する。

### 2.10.3. パフォーマンス最適化

* **セレクタの利用**: Zustand や React Query から状態を取り出す際は、必要なプロパティのみを抽出する「セレクタ」を利用し、無関係な状態変更による再レンダリングを防止する。
* **非同期処理の所在**: APIコールを伴うアクションは必ず React Query (useQuery / useMutation) に閉じ込め、Zustand の Action 内で fetch を行うことは禁止する。


## 2.11. レンダリング方式

本システムは、Next.js 15 の機能を最大限に活かし、**SSR (Server Side Rendering) と CSR (Client Side Rendering) のハイブリッド運用**を行う。

### 2.11.1. SSRによる初期表示の最適化

* **データ埋め込み**: **[実証済]** サーバー側で取得した1万件のデータを HTML ソース内の `self.__next_f.push` に直接埋め込む。
* **メリット**: クライアント側での追加APIコール（Waterfalls）を排除し、LCP（Largest Contentful Paint）を大幅に短縮する。

### 2.11.2. CSRによる対話性とハイドレーション

* **動的挙動**: **[実証済]** サーバーで描画された静的HTMLに対し、クライアント側でJavaScriptがハイドレートされることで、ボタンクリック（onClick）等の動的操作を矛盾なく有効化する。

### 2.11.3. プリフェッチによる画面遷移の高速化

* **Linkコンポーネント**: **[決定]** Next.js の `<Link>` を標準採用する。
* **背景取得**: **[実証済]** リンクがビューポートに入った際、遷移先のデータをバックグラウンドで事前取得（Prefetch）する。
* **UX効果**: 実際のクリック時には通信が発生せず、「瞬時」の画面切り替え（Zero-latency transition）を実現する。

### 2.11.4. ローディング UI との連携

* **スケルトン表示**: **[実証済]** サーバー側でのフェッチ中や、プリフェッチが間に合わない長距離遷移時には `loading.tsx` で定義したスケルトンUIを表示し、画面の白飛びを防止する。


## 2.12. 開発プロセスと品質保証方針

本プロジェクトでは、不具合の早期発見とUI品質の均一化のため、自動化された検証プロセスを開発サイクルに組み込む。

### 2.12.1. 垂直型安全性による品質担保

Monorepo構成を活かした「型」による静的解析を品質保証の第一線とする。

* **Contract-Driven Development**: **[実証済]** `shared/types` の型変更が、フロントエンド（Next.js）およびBFF（NestJS）の双方でビルドエラーを引き起こす仕組みを維持し、インターフェースの不一致を物理的に排除する。
* **Zodバリデーション**: 通信境界（BFF受信時、フロントエンド受信時）でのZodによる実行時型チェックを必須とし、不正データの伝播を防止する。

### 2.12.2. コンポーネント開発とUI品質 (Storybook)

UI開発はStorybookを用いた隔離開発を推奨し、以下の状態をカタログ化する。

* **異常系・境界値の網羅**: 正常系だけでなく、データなし（Empty）、データ過多（1万件）、通信エラー、権限不足の各状態をStoryとして定義し、表示崩れがないか検証する。
* **アクセシビリティチェック**: Storybook上のアドオンを活用し、コントラスト比やWAI-ARIAの定義が適切かを機械的に検証する。

### 2.12.3. 自動テスト戦略

効率的なテスト運用のために、テスト対象を絞り込み、効果を最大化する。

| テスト種別 | ツール | 重点対象 |
| --- | --- | --- |
| **単体テスト** | **Vitest** | **[重要]** サービス層における「FHIRリソースからViewModelへの変換ロジック」を100%カバーする。 |
| **コンポーネントテスト** | **React Testing Library** | Molecules/Organisms単位での、ボタン押下に伴うイベント発火や条件付きレンダリングの検証。 |
| **結合テスト** | **Playwright / E2E** | ログインから主要画面遷移（BFF疎通含む）までのクリティカルパスの自動巡回。 |

### 2.12.4. UX品質の標準化

* **Loading UI**: **[実証済]** `loading.tsx` を各ルートに配置。3秒以上の遅延が発生した場合でも、スケルトン表示によりユーザーに進行状況を伝え、離脱を防止する。
* **Error UI**: **[実証済]** BFFの500エラーや404エラーを検知し、`error.tsx` 経由で「再試行ボタン」を備えた専用画面を表示する。
