# ADR-5: 401 受信時は当面 authStore クリア + ログイン画面遷移を採用する

* **ステータス**: Accepted（暫定）
* **決定日**: 2026-04-15
* **関連設計書**: [Axios通信基盤設計.md](../Axios通信基盤設計.md) §2.3, [04_状態管理設計/状態管理規約.md](../../04_状態管理設計/状態管理規約.md)
* **関連 ADR**: 04 章 [auth-no-persist.md](../../04_状態管理設計/adr/auth-no-persist.md)

## 背景

axiosClient の Response Interceptor で 401 Unauthorized（`errors[].code === 'UNAUTHORIZED'`）を受信した際の挙動を定義する必要がある。

要件:

* アクセストークン（AT）失効時に、ユーザーのセッションを安全に終了させる
* 可能であれば、リフレッシュトークン（RT）による AT 自動再発行 → 元リクエスト再試行 → 再失敗時のみログアウト、というサイレントリフレッシュを実装したい

判断時点（2026 年 4 月）の制約:

* 認証基盤連携サービスの詳細設計が未確定
* RT のローテーション方針・サイレントリフレッシュの API I/F・並行リクエスト時の競合制御方針が未定
* リリース目標（2027 年 4 月）に向けて、認証完成を待たずにアプリ実装を並行で進める必要がある

## 検討した選択肢

### 案A: 401 受信時に authStore クリア + ログイン画面遷移（暫定）

* メリット
  * 実装がシンプル。認証基盤の確定を待たずに先行できる
  * セキュリティ面で安全側に倒した動作（疑わしい場合は強制ログアウト）
* デメリット
  * AT が一時的に失効しただけでもユーザーが再ログインを強いられる UX 劣化
  * リクエストの再試行が無く、ユーザー操作を一度失う

### 案B: サイレントリフレッシュ実装（本来）

* メリット: UX が滑らか。AT 失効を意識させない
* デメリット
  * 認証基盤の I/F が未確定の段階で実装すると後戻りコストが大きい
  * 並行リクエスト時の RT ローテーション競合制御が複雑
  * 失敗時のフォールバック設計（無限ループ防止）が確定仕様の影響を強く受ける

### 案C: 401 を呼び出し側に伝播し、各画面で個別処理

* メリット: 画面ごとの最適 UX を作り込める
* デメリット
  * 全 features 層で 401 処理を重複実装することになり、漏れが発生する
  * 認証はアプリ全体で一貫した動作が望ましく、画面個別判断はバラつきの原因となる

## 決定

**案 A（authStore クリア + ログイン画面遷移）を暫定採用する。**

理由:

* 認証基盤連携サービス詳細設計の確定前に、アプリ実装を並行で進めるための妥当な暫定解
* 安全側に倒した動作であり、暫定実装によるセキュリティリスクが小さい
* 確定後に Interceptor のロジックを差し替えるだけで案 B（サイレントリフレッシュ）に移行可能。features 層は変更不要

## 影響

* アプリ実装者は 401 を Interceptor の自動処理に任せる（features 層で 401 を見ない）
* `useAuthStore` は persist しない（メモリのみ）。ログアウト時に手動クリアと同等の状態を再現可能（[04 章 auth-no-persist.md](../../04_状態管理設計/adr/auth-no-persist.md)）
* リダイレクトはハードリダイレクト（`window.location.href`）を採用し、SPA キャッシュをすべて破棄する
* 401 応答の頻度・UX 劣化を Sentry 等で計測し、確定実装の優先度判断に活用
