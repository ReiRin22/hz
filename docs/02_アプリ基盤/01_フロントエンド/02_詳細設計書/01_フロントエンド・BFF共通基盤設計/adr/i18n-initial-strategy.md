# ADR-7: i18n は当面 JSON + 型推論の独自実装とする

* **ステータス**: Accepted
* **決定日**: 2026-04-15
* **関連設計書**: [技術スタック設計.md](../技術スタック設計.md) §1.3, §2.1, [03.TypeScript型管理とスキーマ共有.md](../../03.TypeScript型管理とスキーマ共有.md)
* **関連 ADR**: [front-bff-shared-ssot.md](front-bff-shared-ssot.md)

## 背景

UI 文言（「保存」「キャンセル」等）やバリデーションメッセージのコード内直書きは、用語変更時の影響範囲が広く、用語統一が困難である。リソース化の方式を判断する必要があった。

要件:

* フロントエンドと BFF で同一メッセージを使用できること（バリデーションエラーが両者で揃う）
* 型安全に文言キーを参照できること（タイポ・存在しないキーをコンパイル時に検出）
* 当初は単一言語（日本語）で運用。多言語化は将来の検討事項

## 検討した選択肢

### 案A: next-intl 等の本格 i18n ライブラリ

* メリット: 多言語切替・複雑な変数埋め込み・Server Components 対応が標準装備
* デメリット
  * 当面は単一言語のため、機能の大半が未使用
  * Server / Client コンポーネントごとの API 差異・設定の複雑度が高く、初期立ち上げコストが大きい
  * BFF 側で同じリソースを使う前提が、ライブラリの Web フレームワーク前提とずれる

### 案B: JSON + 型推論の独自実装

* メリット
  * `front_bff_shared/i18n/` に JSON を置き、TypeScript の型推論でキー補完・存在チェックを実現
  * FE/BFF 両者で同じ JSON を import 可能（[front-bff-shared-ssot.md](front-bff-shared-ssot.md) と整合）
  * 実装が薄く、当面のニーズには十分
* デメリット
  * 多言語化・複雑な変数埋め込み・Server Components 統合が必要になった時点で再設計が必要

### 案C: コード内直書き

* 検討対象外（用語統一・型安全性が損なわれる）

## 決定

**案 B（JSON + 型推論の独自実装）を採用する。**

理由:

* 当面のニーズ（単一言語・FE/BFF 共有・型安全性）を最小コストで満たせる
* `front_bff_shared` 配下に置くことで、本プロジェクトの SSOT 方針と整合
* 将来の拡張時に next-intl 等へ段階的に移行可能（JSON のキー構造を維持できる）

## 影響

* `front_bff_shared/i18n/` ディレクトリでメッセージを集約管理
* ファイル構成は種類別に分割（`labels.json` / `validation.json` / `errors.json`）
* TypeScript の型推論でキー補完・存在チェックを提供
* 詳細仕様（型生成方法・命名規則・使用例）は [03.TypeScript型管理とスキーマ共有.md](../../03.TypeScript型管理とスキーマ共有.md) に集約

### 見直しトリガー（next-intl 等への移行検討条件）

* **機能分散型管理が必要**: 500 機能規模でのスケーラビリティが要求される場合
* **変数埋め込みの強化**: `{patientName}` のような動的メッセージが多用される場合
* **Server Components 対応**: Next.js App Router でのサーバー・クライアント統合が必要な場合
* **多言語対応**: ロケール切替・複数言語の並行管理が必要な場合
