# ADR-3: フロントエンド／BFF 間の API 契約は front_bff_shared を SSOT とする

* **ステータス**: Accepted
* **決定日**: 2026-04-15
* **関連設計書**: [技術スタック設計.md](../技術スタック設計.md) §2.1, [03.TypeScript型管理とスキーマ共有.md](../../03.TypeScript型管理とスキーマ共有.md)
* **関連 ADR**: なし

## 背景

フロントエンドと BFF は同一リポジトリ（モノレポ）に配置される。両者間の通信契約（Request 型・Response 型・バリデーションルール・UI 文言）の定義場所として、以下が選択肢として上がった。

* フロントエンドと BFF それぞれが独立に型定義を持ち、API レビュー時に整合性を人手で確認する
* 共有ディレクトリ（`front_bff_shared/`）を設け、シンボリックリンクで両プロジェクトに参照させる
* OpenAPI / GraphQL Schema 等の中間形式から両プロジェクトの型を生成する

医療システムでは API 変更が安全に伝播することが極めて重要であり、型不整合が本番に到達するリスクを最小化したい。

## 検討した選択肢

### 案A: 各プロジェクトが独立に型を持つ

* メリット: 各プロジェクトが他方の存在を知らずに進化できる（疎結合）
* デメリット: 型不整合の検出は人手レビューに依存し、ヒューマンエラーのリスクが高い。BFF が Response を変えてもフロントは気づかない

### 案B: front_bff_shared/ をシンボリックリンク経由で共有（SSOT）

* メリット
  * BFF の型変更がフロントエンドのビルドエラーとして即座に検知される
  * Zod スキーマを共有することで FE 入力検証と BFF 受信検証で同一ルールを使用可能
  * 単一のレビュー対象で両者の整合性を担保できる
* デメリット
  * シンボリックリンクの取り扱いが OS／環境により差異あり（特に Windows）
  * 共有スキーマの変更は両者に影響するため、変更時のレビュー対象範囲が広がる

### 案C: OpenAPI からコード生成

* メリット: 言語非依存。将来別の BFF 実装に切り替える際も再利用可能
* デメリット
  * Zod スキーマとの統合が複雑（OpenAPI から Zod を生成するツールチェーンの追加）
  * コード生成の責務をビルドパイプラインに組み込む必要があり、初期セットアップが重い
  * 本プロジェクトでは BFF を切り替える計画が無く、過剰な抽象化となる

## 決定

**案 B（front_bff_shared/ を SSOT とする）を採用する。**

理由:

* 型不整合のビルドエラー検知が最大の利益。医療システムの安全性要件と合致
* Zod スキーマの共有により、FE バリデーションと BFF ガードロジックを同一ルールで実装でき、二重メンテナンスを防げる
* OpenAPI 生成は将来的に必要になれば本構成からも移行可能（front_bff_shared を OpenAPI から生成する形に変更すればよい）

## 影響

* 開発環境セットアップでシンボリックリンクの解決が必要（WSL2 / Docker 環境で吸収）
* 共有型・スキーマ・i18n の変更は FE/BFF 両者のレビュアーが確認する運用ルールが必要
* `front_bff_shared/i18n/` も同じ仕組みで共有する（FE のコンポーネント文言と BFF のバリデーションメッセージで同一リソースを参照可能）

### 見直しトリガー

* 別の BFF 実装への切り替えが計画された場合
* OpenAPI 経由のコード生成が業務上必須となるユースケース（例: 外部公開 API）が発生した場合
