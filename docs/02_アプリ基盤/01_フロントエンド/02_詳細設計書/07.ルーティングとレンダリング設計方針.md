# 07. ルーティングとレンダリングの設計方針

本章では、Next.js 16 を基盤とした、500機能規模の医療システムにおける画面遷移とレンダリングの実装ルールを定義する。



## 7.1. ルーティング構造と階層定義

本システムでは、機能一覧表に基づいた業務構造をソースコードに直結させるため、Next.jsの **※App Router** を採用し、「URLパスを定義するディレクトリ（app）」と「機能の実装実体を管理するディレクトリ（features）」を明確に分離する。  
これにより、500機能規模の開発においても保守性と検索性を両立させる。  

※各フォルダの詳細な役割や内部構成については、[00.ディレクトリ構成.md](00.ディレクトリ構成.md) を参照すること。  

>**App Router 選定理由:**
> 1. **500機能の管理（カプセル化と疎結合）**:  
> 各機能ディレクトリ（LV3）内に `api`, `repositories`, `components`, `hooks`, `stores` を閉じ込める「カプセル化」が可能なため、大規模開発におけるファイル管理の破綻を防ぎ、影響範囲を局所化できる。
> 2. **医療データの整合性**: Server Components により、機密性の高い API キーなどをブラウザ側に露出させることなくサーバー側で安全にデータ処理が行える 。
> 3. **階層設計との親和性**: プロジェクト独自の「LV1（機能ドメイン）→ LV2（サブドメイン/フロー）→ LV3（画面機能）」という階層構造を、Next.js のファイルシステムベースルーティングおよび `layout.tsx` のネスト機能によって、直感的にシステム構造として表現できる。



### 7.1.1. レイアウト制御（src/app）と実装実体（src/features）の分離

### ① app ディレクトリ：URL パスとレイアウトの境界定義

`src/app` 配下は、ブラウザの URL パスを決定し、共通レイアウトやローディング境界を制御する役割を担う。

* **ルートグループ (`(group)`) の活用**:
    * **定義**: `src/app/(karte)` のようにフォルダ名に `()` を付与することで、URL パスに影響を与えず、共通の `layout.tsx` や `loading.tsx` を適用する範囲をグループ化する。
    * **メリット**: 業務メニュー移動時にもサイドバーや患者情報ヘッダーなどの共通 UI を維持し、中身のコンテンツ（page）のみを切り替えることが可能になる。
    * **レイアウトが異なる場合の対応**:
      * 同一階層（例：カルテ共通）であっても、特定の画面だけ、非共通的な表示となる場合やレイアウトを大きく変えたい場合は、**別のルートグループを作成して分離**する。
      * 例：標準的な画面は `(karte)/diagnosis/` 配下に置き、特殊な全画面モード等は `(full-screen)/diagnosis/` 配下に置くことで、URL パスを維持したまま異なる `layout.tsx` を適用できる。


* **Layout 層 (`layout.tsx`) の責務**

  * **Root Layout (`src/app/layout.tsx`)**:
      * **責務**: アプリ全体の最上位階層。`html` および `body` タグの定義、全画面共通の `Provider`（認証、テーマ設定等）の配置、および `globals.css` の読み込みを行う。

  * **Group Layout (`src/app/(group)/layout.tsx`)**:
      * **責務**: 特定の業務グループ（例：電子カルテ全体）で維持されるサイドメニュー、患者ヘッダー、ドメイン共通の状態管理プロバイダー等を定義する。
      * **推奨事項**:
          * **状態の維持**: テキスト入力やスクロール位置など、ページ遷移後も保持したい状態を管理すること。
          * **ドメイン共通 Store の参照**: `useDiagnosisStore`（Zustand）などを呼び出し、患者情報の共通表示を行うこと。
      * **禁止事項**:
          * **個別ページ固有のロジック**: 特定の1画面でしか使わない複雑なバリデーションや個別 API 呼び出しを記述すること。


* **Page層 (`page.tsx`) の責務**:

    * **コンポーネントの配置・統合**: `features` ディレクトリから必要な コンポーネントを呼び出し、画面全体のレイアウト構成（どの部品をどの位置に配置するか）を最終的に決定する。

    * **周辺要素の配置**: メインコンテンツ以外に表示が必要なコンポーネントの配置位置も `page.tsx` 内で定義する。

    * **依存注入（DI）とデータフェッチ**: Server Component として `src/features/**/repository/` の関数（シンプルな単一取得の場合は `api/` も可）を用いてデータを取得し、配下のコンポーネントへ Props として注入する。

    * **ローディング境界の定義**: 各コンポーネント内部に Suspense を隠蔽せず、page.tsx 側でコンポーネントを <Suspense> でラップする。


### ② features ディレクトリ：業務ロジックと UI の実体

`src/features` 配下は、500機能超の規模を秩序立てて管理するため、**「機能一覧表の階層」と「物理ディレクトリ構造」の完全一致**を原則とする。  
`app` ディレクトリ（URL定義）と物理的に分離されているため、`features` 内では純粋な機能構造としてのディレクトリ管理を行う。  
物理ディレクトリ名は、すべて英語（ケバブケース）で命名する。  

* **対応ルール**:
  * **LV1層（機能群）**: `src/features/diagnosis` (診療記録)などの第1階層。業務ドメインを定義する。
  * **LV2層（カテゴリ）**: `src/features/diagnosis/record-management` (診療記録作成)などの第2階層。業務フローを定義する。
  * **LV3層（画面機能）**: `src/features/diagnosis/record-management/clinical-entry` (診察入力)などの第3階層。

* **メリット**: 機能一覧から該当するソースコードを即座に特定できる検索性を維持しつつ、デプロイ環境やOSに依存しない堅牢なファイルシステムを構築する。

* **標準的な内部ディレクトリ構成**:

  | ディレクトリ / ファイル | 役割・責務 | 備考 |
  | :--- | :--- | :--- |
  | **`components/`** | 画面固有のUI部品（Molecules / Organisms）。 | データの表示、フォーム、仮想スクロール（react-virtuoso）等の実装。 |
  | **`hooks/`** | 画面固有の対話・表示ロジック。 | `useQuery` / `useMutation` の呼び出しやスクロール制御などのカスタムフック。`repository/` を呼び出すことで通信詳細を隠蔽する。 |
  | **`stores/`** | 画面固有の状態管理。 | クライアント状態管理。詳細は、[04.状態管理設計.md](04.状態管理設計.md) を参照。 |
  | **`repository/`** | BFF通信を抽象化するデータアクセス層。 | `api/` の関数を組み合わせ、ドメインに必要な形でデータを取得・変換する。`hooks/` から呼び出される。 |
  | **`api/`** | BFF との HTTP 通信の実体。 | `axiosClient` を使用した純粋な通信関数。副作用・状態を持たない。 |
  | **`types/`** | 画面内でのみ使用する型定義。 | UI表示用の型（ViewModel）やAPIレスポンスの型など。 |
  | **`assets/`** | 画面固有の静的リソース。 | その機能でのみ使用する画像、アイコン、JSONファイル等。 |
  | **`test/`** | 自動テスト（Vitest / MSW）。 | 単体・結合テスト。実装ファイルの構造をミラーリングして配置。 |
  | **`style.css`** | 画面固有のスタイル定義。 | Tailwind CSS の `@apply` 等を用いた特定画面専用のスタイル。 |
  | **`index.ts`** | **機能公開窓口（バレルファイル）。** | 他機能へ公開する最小限の定数・型・関数を定義する出口。 |
  ※状態管理の詳細については、[04.状態管理設計.md](04.状態管理設計.md) を参照


### ③ app / features 間の責務分担とデータフロー

`app/page.tsx` と `features/` は「**指揮者とオーケストラ**」の関係。`page.tsx` は *何を・どこに配置するか* を決め、実際の処理（ロジック・UI・通信）はすべて `features/` に委ねる。

**データフロー（コード構造のイメージ）：**

```
src/app/(karte)/diagnosis/.../[id]/page.tsx   ← ① URLパラメータ解決 (await params)
  │
  ├─ ② features/.../repository/getDiagnosisRepository.ts  呼び出し
  │       └─ features/.../api/getDiagnosisAPI.ts           HTTP通信
  │
  └─ ③ features/.../components/DiagnosisOrganism          に initialData を Props で渡す
               └─ 以降のロジック・描画・状態管理はすべて features 側が担う
```

`page.tsx` の具体的な記述ルール（OK / NG）については、[7.2.2. コンポーネントの垂直分離](#722-コンポーネントの垂直分離rsc--rcc) の「制限事項」を参照。



### 7.1.2. カプセル化と公開の原則
 
* **内部資産の保護**: LV3内の各ディレクトリ（`api`, `components` 等）は、原則としてその画面内でのみ使用する。他画面からこれらの内部ファイルを直接インポートすることは禁止する。
* **窓口の利用**: 他の機能（別のLV3やLV1/LV2）から参照が必要な資産（共通の型や定数など）がある場合のみ、`index.ts` を通じて公開する。
* **資産の昇格（shared）**:
    * 同一 LV1 ドメイン内の複数画面で共有する資産は、`src/features/{LV1名}_shared/` へ移動させる。（例：診療記録ドメイン共通の型 → `src/features/diagnosis_shared/`）
    * システム全体で共有する資産は、`src/shared/` へ移動させる。
    * これらの共有ディレクトリにも、外部参照用の `index.ts` を配置して公開範囲を制御する。
    * **廃止ルール**: LV2・LV3 レベルの `_shared` ディレクトリは複雑化を招くため設置しない。共有範囲が狭い場合も `{LV1名}_shared/` または `src/shared/` への昇格で対処する。



### 7.1.3. ディレクトリ間の依存関係ルール

依存関係は常に **上から下への一方通行** とし、下位層が上位層をインポートすることを禁止する。この規約は ESLint によりビルド時に自動検出・エラー化する（後述）。

#### 1. 5層アーキテクチャと物理ディレクトリの対応

```
1. page（画面・ルート）
   └ src/app/(group)/**/page.tsx
   役割: URLパラメータ解決 → repository/api 呼び出し → components へ Props 注入
   ↓
2. components（UI部品）
   └ src/features/**/components/{organisms,molecules}/
   └ src/shared/components/{atoms,molecules}/
   役割: UIの構築。Hooks/Stores からデータを受け取り描画する。
   ↓
3. hooks / stores（ロジック・状態管理）
   └ src/features/**/hooks/       ← useQuery/useMutation、画面固有ロジック
   └ src/features/**/stores/      ← Zustand（Page スコープ）
   └ src/features/{LV1}_shared/stores/  ← Zustand（Domain スコープ）
   └ src/shared/stores/           ← Zustand（Global スコープ）
   役割: 「何を表示するか」「どう動くか」の判断。repository を呼び出しデータ取得を制御。
   ↓
4. repository（データアクセス抽象化）
   └ src/features/**/repository/
   役割: api/ の関数を組み合わせ、ドメインに必要な形でデータを取得・変換する。
        hooks との契約（インターフェース）を提供し、HTTP 通信の詳細を隠蔽する。
   ↓
5. api / shared（HTTP通信・共通基盤）
   └ src/features/**/api/         ← BFF との HTTP 通信（axios）を担う純粋な関数
   └ src/shared/                  ← 定数、汎用ユーティリティ、型定義
   役割: 外部との通信とアプリ全域で使う純粋な道具箱。状態・副作用を持たない。
```

#### 2. 禁止される依存の方向

| 禁止パターン | 具体例 | 理由 |
| :--- | :--- | :--- |
| `features` → `app` | `features/` から `app/page.tsx` を import | 逆方向参照。ルーティングと機能が密結合になる |
| `api` → `hooks` | `api/` から `hooks/` を呼び出す | 下位層が上位層を参照する逆転 |
| LV3-A → LV3-B の内部 | 他機能の `api/` や `repository/` を直接 import | カプセル化違反。`index.ts` 経由のみ許可 |
| 循環参照 | A が B を import し、B が A を import | 予測不能な初期化順序を引き起こす |

#### 3. ESLint による依存関係の強制（ビルド時エラー化）

依存関係ルールの遵守はコードレビューに依存せず、以下の ESLint 構成によりビルド時に自動検出・エラー化する。

**使用ツール・プラグイン**

| 分類 | 名称 | 役割 |
| :--- | :--- | :--- |
| 標準ルールセット | `eslint-config-next` | Next.js / React のベストプラクティス（Hooks の書き方、画像最適化等）を強制する。 |
| 拡張プラグイン | `eslint-plugin-import` | ディレクトリ間の依存関係やインポート順序を専門にチェックする機能を追加する。 |

**適用ルール一覧**

| ルール名 | 役割 | Hartz での具体的な運用例 |
| :--- | :--- | :--- |
| `no-restricted-imports` | 特定パスのインポート禁止 | `features/` から `app/` への逆参照を禁止。他機能の `api/` や `repository/` を `index.ts` を介さず直接参照することをエラーにする。 |
| `import/no-cycle` | 循環参照の禁止 | A と B のファイルが互いに呼び出し合う循環状態を検知してビルドエラーにする。 |
| `import/order` | インポート順序の固定 | `ライブラリ（node_modules）` → `src/shared/`（共通） → `機能内 repository/ api/` の順に統一し、コードの可読性を均一化する。 |
| `@typescript-eslint/no-unused-vars` | 未使用変数の禁止 | 定義しただけで使用されていない変数・インポートをエラーとし、デッドコードの蓄積を防ぐ。（TypeScript プロジェクトでは `no-unused-vars` の代わりにこちらを適用する。） |
| `@typescript-eslint/no-explicit-any` | `any` 型の禁止 | 型定義の放棄を禁止し、大規模開発に不可欠な型安全性を強制する。`eslint-config-next` に含まれる本ルールを有効化する。 |




## 7.2. 画面描画（レンダリング）の実装原則

Next.js (App Router) を基盤とする本プロジェクトでは、作成するすべてのコンポーネントが、自動的または明示的に「RSC（サーバー側）」か「RCC（クライアント側）」のいずれかの性質を持つ。

この技術的特性を理解し、医療システムに求められる「高速な初期表示」と「高度な対話性」を両立させるため、以下の実装原則を遵守すること。


> SSR/CSRは「ページ全体の表示戦略（いつ・どこで）」の話で、RSC/RCCは「コンポーネント単位の役割分担（なに・どこで）」の話であり、以下のように対比比較できる。

| 比較項目 | **SSR / CSR** (従来の戦略) | **RSC / RCC** (Reactの新機能) |
| --- | --- | --- |
| **対象の単位** | **ページ全体** | **コンポーネント（部品）単位** |
| **目的** | 画面を「いつ」出すか | 部品を「どこ」で動かすか |
| **データの流れ** | HTMLを丸ごと送る or JSで組み立てる | サーバーとブラウザが木構造で共存する |
| **JSの負担** | CSRだとブラウザのJSが重くなる | **RSCはブラウザにJSを送らない** |
| **UXの影響** | ページ遷移が重い or 初回表示が遅い | **表示は爆速で、操作も軽快**（いいとこ取り） |



### 7.2.1. 3つの宣言の定義と役割

Next.js (App Router) においては、コンポーネントや関数に対して以下の3つの宣言を使い分ける。

| 宣言 | 技術的呼称 | 実行場所 | 主な役割 |
| --- | --- | --- | --- |
| **（なし）** | **RSC** (Server Components) | サーバー | **【表示の土台】** デフォルトの状態。データのフェッチと画面構成。 |
| **`"use client"`** | **RCC** (Client Components) | サーバー ＋ ブラウザ | **【操作の制御】** UIの反応（クリック等）・状態管理。 |
| **`"use server"`** | **Server Actions** | サーバー | **【データの更新】** 保存・削除などの処理。 |

</br>

> **～"use server"の運用方針～**  
> 
>     Next.js にはデータ更新用の機能として `"use server"`（Server Actions）が存在するが、本プロジェクトでは以下の理由から原則として使用しない。  
> 
> * **BFF ＋ バックエンド側での機能完備**  
>   本プロジェクトでは、認証、認可、バリデーション、およびデータの永続化（DBへの保存）に関するロジックが、Next.js の外側にある BFF ＋ バックエンド側で既に完備されているため。  
>
> * **バリデーションの責務分離**  
>   フロントエンド（Zod）は即時フィードバックによる UX 向上を担い、データの正当性に関する最終的な保証は BFF ＋ バックエンド側が直接担う二段構えとするため。  
> 
> * **アーキテクチャの単純化**  
>   Client(RCC) → BFF API と直接通信することで、Next.js サーバーを中継する "use server" を介さず、データの流れを最短かつ明快に保つため。  
>
> * **標準技術の活用と保守性**  
>   ブラウザから axios や fetch で直接 API を叩く標準的な REST 通信を採用し、チームの既存知識の活用や、通信のモニタリング・デバッグを容易にするため。  



### 7.2.2. コンポーネントの垂直分離（RSC / RCC）

コンポーネントを「データの取得と編成を行うサーバー層（RSC）」と「ユーザー操作を制御するクライアント層（RCC）」に垂直分離し、関心の分離を徹底する。

* **Page層 (Server Component / RSC)**
  * LV3 の `page.tsx` は、デフォルトの性質（宣言なし）を活かし、必ず Server Component として実装する。
  * **責務**:
    * URL パラメータ（ID等）の解決。
    * `features/repository/` を介したデータの取得（Fetch）。シンプルな単一エンドポイント取得の場合は `features/api/` の直接呼び出しも可。
    * 画面全体のレイアウト構成と、Client Component への初期データ（Initial Data）の流し込み。

  * **制限事項（ロジックの集中を防ぐ）**

    | ✅ page.tsx に書くべき処理 | ❌ page.tsx に書いてはいけない処理 |
    | :--- | :--- |
    | `await params` による URL パラメータ解決 | データの変換・加工・計算ロジック |
    | `features/repository` または `features/api` の呼び出し（1〜3行程度） | 複数の `if / else` を含む条件分岐処理 |
    | features コンポーネントへの Props 注入 | `useState` / `useEffect`（Server Component に使用不可） |
    | `<Suspense>` でのローディング境界定義 | 複雑なスタイリング・`div` の多重ネスト |
    | `metadata` の定義（ページタイトル・SEO 等） | BFF との生の axios / fetch の直書き |

    > **設計の原則**: `page.tsx` が「ロジックの受け皿」にならないよう、取得・加工・判断のコードは `repository/`・`hooks/`・`utils/` に切り出す。`page.tsx` は「何を・どこに表示するか」を3〜30行で記述できる状態を理想とする。

  * **メリット**: セキュリティ（APIキー等の隠蔽）、JavaScript バンドルサイズの削減、高速な初回描画。


* **Component層 (Client Component / RCC)**
  * useState や onClick 等のブラウザ特有の機能が必要な場合にのみ、最小単位のコンポーネントに、明示的に `'use client'` を付与する。
  * **選定基準**: 以下のいずれかを含む場合は Client Component とする。
    1. **状態管理**: `useState`, `useReducer`, `Zustand` 等を使用する場合。
    2. **ライフサイクル**: `useEffect`, `useLayoutEffect` 等を使用する場合。
    3. **イベントリスナー**: `onClick`, `onChange` 等のブラウザイベントを扱う場合。
    4. **ブラウザAPI**: `window`, `document`, `localStorage` 等に直接アクセスする場合。

  * **配置**: 原則として `components` 内に配置し、Page層から「初期データ（Initial Data）」を受け取って動作する。

</br>

> **RSC（宣言なし）と RCC（'use client'）の振り分け例**
> ```
> ●RSC（デフォルト / 宣言なし）にするもの　→「画面の骨組み」や「動かない情報」等
> 
>   ・page.tsx 本体: BFFから「患者基本情報」や「過去の診察履歴」を取得する処理
>   ・サイドメニュー / ナビゲーション: リンク (Link コンポーネント) だけのメニュー
>   ・表示専用のカード: 読み取り専用の患者名、生年月日、アレルギー情報の表示枠
>   ・静的なレイアウト要素: ヘッダー、フッター、コンテンツの枠組み
> 
> 
> ●RCC（'use client'）にするもの　→「ユーザーが何かをする場所」や「時間経過で変わる場所」に限定
> 
>   ・診察入力フォーム: テキスト入力やチェックボックス（onChange を使用）
>   ・保存ボタン: クリック時に BFF API を叩く処理 (onClick を使用）
>   ・タブ切り替えスイッチ: 画面を切り替えずに表示内容を変更する UI
>   ・リアルタイムバリデーション: 入力中に「文字数オーバーです」と出す Zod の警告表示
>   ・モーダルダイアログ: 「本当に保存しますか？」といったポップアップの開閉管理
> ```



### 7.2.3. 動的ルーティングとパラメータ解決

Next.js 16から、URLに含まれるID（`params`）や検索条件（`searchParams`）の取得方法が、従来の直接参照から **非同期（Promise）** へと変更された。これに伴い、以下の手順を実装の標準とする。

#### ①. 変更のポイントと注意点

* **「Promise化」への対応**: `params` は箱に入った状態（Promise）で届くため、中身を取り出すために必ず `await` が必要となる。
* **型安全性の確保**: URLパラメータは常に「文字列（string）」として取得されるため、数値として扱う場合などは `await` で値を取り出した直後に適切な型変換を行う。
* **動的パスの構成**: `patient/30` のような動的パスを実装する場合、`[id]` のようにブラケットで囲ったディレクトリを作成し、その直下に `page.tsx` を配置する。

#### ②. 実装の標準フロー

LV3の `page.tsx` において、以下の3ステップで処理を完結させる。

1. **パラメータの「解決」**: `await params` を実行し、URLからIDを安全に取り出す。
2. **型安全な「取得」**: `features` 層の `repository/`（または直接 `api/`）に定義された関数を呼び出し、データを取得する。この際、`front_bff_shared` の型定義を適用する。
3. **部品への「注入」**: 取得したデータを、`features` 層の Component（Organism等）へ Props として渡す。

#### ③. 実装テンプレート（コードイメージ）

```tsx
/**
 * LV3: 診察入力画面
 * 物理パス: src/app/(karte)/diagnosis/record-management/clinical-entry/[id]/page.tsx
 */

// インポートパスを最新のディレクトリ構成（features）に合わせて修正
import { getDiagnosisData } from '@/features/diagnosis/record-management/clinical-entry/api/getDiagnosisAPI';
import { DiagnosisOrganism } from '@/features/diagnosis/record-management/clinical-entry/components/DiagnosisOrganism';

// 1. Propsの型定義（paramsはPromiseとして定義する）
interface PageProps {
  params: Promise<{ id: string }>; 
}

export default async function Page({ params }: PageProps) {
  // 2. [必須] パラメータを非同期で解決（中身を取り出す）
  const { id } = await params;

  // 3. 解決したIDを使用して、BFFからデータをサーバー側で取得
  // getDiagnosisDataは front_bff_shared の型を使用していること
  const initialData = await getDiagnosisData(id);

  // 4. Client Component (Organism) へ初期データを注入して描画
  return <DiagnosisOrganism initialData={initialData} />;
}

```

* **型変換とバリデーション**
  * URL パラメータは常に `string` として取得されるため、数値が必要な場合や特定のフォーマット検証が必要な場合は、BFF へのリクエスト前に適切な変換およびバリデーションを行う。



### 7.2.4. 非同期処理とローディング設計（Suspense）

Next.js の Streaming SSR 機能を活用し、データ取得による待機時間を「画面全体のフリーズ」ではなく「段階的な表示」へと最適化する。  
本システムでは、影響範囲と発生タイミングに応じて以下の **3つのローディングレイヤー** を使い分ける。  
また、ローディング中の表示内容は、 スケルトンスクリーン を原則とする。

> **スケルトンスクリーン採用理由**  
> * 次に表示される情報の「レイアウト」をあらかじめ示すことで、データ読み込み後のレイアウトシフト（CLS）を抑制する。
> * 医療従事者の視線移動をスムーズにし、体感的な待ち時間を短縮させる。


#### **ローディングの3層構造と定義**

| レイヤー | 配置場所 | 発生タイミング | 表示の挙動 |
| :--- | :--- | :--- | :--- |
| **① システム起動** | `src/app/loading.tsx` | 初回アクセス / ブラウザのリロード時 | **画面全体**をスケルトンまたはスピナーで覆う。 |
| **② ページ遷移** | `src/app/(group)/loading.tsx` | メニュー移動時（例：診察→会計） | **サイドメニュー等を維持**し、コンテンツ領域のみスケルトンを表示。 |
| **③ コンポーネント** | `React.Suspense` | 特定の重いパーツ（グラフ、画像等） | ページ表示後、**特定のパーツのみ**後出しでロードする。 |


#### **① システム起動：Root Loading**

アプリケーションのブートストラップ時に表示される。  

* **役割**: JavaScriptの初期読み込みや、全画面共通の初期認証チェック中の「真っ白な画面」を防ぐ。
* **実装**: `src/app/loading.tsx` に配置。


#### **② ページ遷移：Route Group Loading**

業務メニュー間の移動時に表示される、本システムのメインとなるローディング。

* **役割**: **サイドメニューや患者ヘッダー等の共通レイアウトを維持**したまま、中身（ページコンテンツ）のみを切り替えることで、ユーザーの操作コンテキストを断絶させない。
* **実装**: URLに影響を与えないルートグループ（例：`(karte)`）内に `loading.tsx` を配置する。

**ディレクトリ構成イメージ：**
```text
src/app/
├── layout.tsx (Root)
├── loading.tsx   <-- ① システム起動用
│
└── (karte)/      (業務エリア：サイドバー等を定義)
    ├── layout.tsx
    ├── loading.tsx <-- ② ページ遷移用（サイドバーを残して中身を入れ替え）
    └── diagnosis/
        └── record-view/
            └── page.tsx
```


#### **③ コンポーネント：Local Suspense**

ページ内の特定の重いコンポーネントに対してピンポイントで適用する。

* **役割**: 準備ができた軽量なデータから先に表示を開始し、重いデータ（例：10,000件超の画像データ、複雑な統計グラフ等）は準備ができ次第、サーバーからブラウザへ順次流し込む（Streaming）。
* **実装**: 
  * Page層（RSC）ですべてのデータを `await` せず、重い処理を行うコンポーネント内部で非同期処理を行う。
  * 呼び出し側を `<Suspense fallback={<LoadingSkeleton />}>` でラップする。


**コンポーネント別 `Suspense` の `fallback` 選択基準（3つの型）：**
各コンポーネントを `<Suspense>` でラップする際、そのコンポーネントの構造や表示領域の特性に応じて、以下の **3つのスケルトン・パターン** から最適なものを選択して適用する。

| パターン | 指定方法 | 適用対象・基準 |
| :--- | :--- | :--- |
| **型A：デフォルト** | `引数なし` | 高さや形状が特定しにくい、または重要度が低い補助的なコンポーネント。標準的な高さ（`h-32`相当）で領域を確保する。 |
| **型B：プリセット** | `variant="list"` 等 | 一覧表、カード、アバター付きリストなど、システム内で標準化されている定型UIコンポーネント。 |
| **型C：サイズ指定** | `className="w-[x] h-[y]"` | メインコンテンツや入力フォームなど、ロード前後で1ピクセルのズレも許容したくない重要コンポーネント。描画後の実サイズを算出して指定する。 |

* **運用のガイドライン**:
    * 基本的には **型A** または **型B** で開発スピードを優先する。
    * 診療録のタイムラインや、画像診断エリアなど、レイアウトの固定がUXに直結する箇所にのみ **型C** を適用し、厳密なサイズ管理を行う。
    * `LoadingSkeleton` 自体は共通部品として一元管理し、色調やアニメーション（Pulse）の統一性を担保する。



### 7.2.5. ローディング設計の優先順位

設計・実装時には、以下の優先順位でローディングを配置する。

1. **第一優先（レイアウト保護）**: ルートグループ直下の `loading.tsx` で、ナビゲーション（サイドバー等）を維持しつつコンテンツエリア全体を保護する。
2. **第二優先（コンポーネント最適化）**: 1.5秒以上の待機が予想される重いコンポーネントに対し、個別に `<Suspense>` を配置し、上記「3つの型」から最適な `fallback` を指定する。
3. **第三優先（即時フィードバック）**: Client Component 内の更新処理等は 原則として `useTransition` を用いて、ボタンの活性/非活性やスピナー表示で操作完了を伝える。




## 7.3. 垂直型安全性：front_bff_shared との連携

フロントエンドとBFF（Backend For Frontend）間の通信において、型定義の不整合によるバグを根絶するため、シンボリックリンクによる共有ディレクトリ `front_bff_shared` を活用した「垂直型安全性」を維持する。



### 7.3.1. 共有ディレクトリの階層構造

`front_bff_shared` 内の構造は、フロントエンドの `src/app` 以下のディレクトリ構造をミラーリング（同期）させる。  
これにより、どの画面で使用される型かを即座に特定可能とする。

* **配置ルール**:
  * **LV3（画面単位）**: `front_bff_shared/[LV1]/[LV2]/[LV3]/` 配下に、その画面専用の `types` および `schemas` を配置する。
  * **共通（Shared）**: 複数の画面やカテゴリで再利用する型は、それぞれの階層にある `_shared` フォルダに配置する。


* **ファイル構成**:
  * `[LV3]/types/request/`: BFFのControllerが受け取るリクエストボディ、クエリパラメータの型定義。
  * `[LV3]/types/response/`: BFFのServiceが返却し、フロントエンドが受け取るレスポンスデータの型定義。
  * `[LV3]/schemas/`: Zod等を用いたバリデーションルール。フロントの入力チェックとBFFのガードロジックで共用する。



### 7.3.2. 型安全なデータ取得フロー

Page層（Server Component）からBFFへリクエストを行う際、`front_bff_shared` の型を強制適用することで、エンドツーエンドの型安全性を確保する。

* **実装の手順**:
  1. **型の定義**: `front_bff_shared` 内の該当するLV3フォルダに、リクエストとレスポンスの型を定義する。
  2. **API層の実装**: LV3の `api/` 内で、共有された型をインポートし、Axios等のクライアントに型引数として渡す。
  3. **Page層での呼び出し**: `page.tsx` で `repository/`（または `api/`）関数を呼び出し、取得したデータをそのままPropsとしてClient Componentへ渡す。

* **実装イメージ(Frontend)**:
  ```tsx
  /**
   * LV3: 診察入力画面 API定義
   * 物理パス: src/features/diagnosis/create/entry/api/getDiagnosisAPI.ts
   */
  import axios from 'axios';
  // 共有ディレクトリから型をインポート
  import { GetDiagnosisResponse } from '@/front_bff_shared/diagnosis/create/entry/types/response/entry.api.response';

  export const getDiagnosisData = async (id: string): Promise<GetDiagnosisResponse> => {
    // 型安全なリクエスト
    const response = await axios.get<GetDiagnosisResponse>(`/api/diagnosis/${id}`);
    return response.data;
  };

  ```

* **BFF側の実装例**:  
**Controller層 (リクエストの入り口)**  
フロントエンドからのリクエストを受け取り、front_bff_shared の型を適用する。
  ```ts
  /**
   * LV3: 診察入力画面 BFF Service
   * 物理パス: bff/src/features/diagnosis/create/entry/entry.service.ts
   */
  import { Injectable } from '@nestjs/common';
  import { GetDiagnosisResponse } from 'front_bff_shared/diagnosis/create/entry/types/response/entry.api.response';

  @Injectable()
  export class EntryService {
    async findOne(id: string): Promise<GetDiagnosisResponse> {
      // データベース等から取得したデータを、共有型(GetDiagnosisResponse)の形式に整形
      // 型定義に存在しないプロパティを返そうとしたり、必要なプロパティが欠けるとエラーになる
      const data = {
        patientId: id,
        patientName: "山田 太郎",
        diagnosisDate: "2026-03-09",
        soap: {
          subjective: "頭痛がする",
          objective: "熱 37.5度",
          assessment: "感冒の疑い",
          plan: "解熱剤の処方"
        }
      };

      return data;
    }
  }
  ```

* **運用上の制約**:
  * **手動定義の禁止**: フロントエンド側でBFF通信用の型を独自に定義（二重定義）することは厳禁とする。必ず `front_bff_shared` を経由すること。
  * **不整合の検知**: BFF側でレスポンスの型を変更した場合、フロントエンドのビルド時に型エラーが発生するように構成し、デプロイ前の不整合検知を徹底する。




## 7.4. 画面描画パフォーマンスと最適化基準

医療従事者がストレスなく情報を参照・操作できるよう、Googleが提唱するCore Web Vitalsをベースに、本システムにおける性能の「合格基準」とそれを達成するための最適化ルールを定義する。



### 7.4.1. フロントエンド性能目標（SLO）

以下の指標を、すべての画面開発における品質基準とする。

| 指標 (Core Web Vitals) | 目標値 (Good) | 定義・計測基準 |
| --- | --- | --- |
| **LCP (主要コンテンツ描画)** | **2.5秒以内** | 画面の主要な要素（カルテ内容等）が描画されるまでの時間。 |
| **FID (初回入力遅延)** | **100ms以内** | クリックやタップに対するブラウザの反応速度。 |
| **CLS (累積レイアウトシフト)** | **0.1未満** | 描画中のガタつき（画像読み込みによるズレ等）の少なさ。 |
| **FCP (初回描画)** | **1.8秒以内** | ヘッダーや枠組みが最初に表示されるまでの時間。 |
| **描画DOM数** | **100個以下** | 画面上に同時に存在するDOM要素の数（仮想化で制御）。 |



### 7.4.2. 初期データ埋め込みによるハイドレーション最適化

サーバーで生成された静的HTMLにJavaScriptの挙動を紐付ける「ハイドレーション」の負荷を軽減するため、初期表示に必要なデータはすべてサーバー側で取得し、HTMLに事前注入する。

* **実装の目的**:
  * **Waterfalls（通信の数珠つなぎ）の排除**: ブラウザでのJS実行後にAPIを叩く「後出し通信」を禁止し、LCP（主要描画）を大幅に短縮する。
  * **操作の即時有効化**: HTMLと同時にデータがブラウザに届くため、表示直後から「詳細」ボタン等のクリックイベントが遅延なく有効化される。


* **実装標準**:
  * **Page層（Server Component）** にて `fetch` を実行し、取得したデータを Client Component（Organism等）の Props として渡す。これにより、Next.jsが自動的にデータをシリアライズしてHTMLへ埋め込む。



### 7.4.3. 描画負荷の制御（仮想化と画像最適化）

1万件超のデータ表示等、メインスレッドを占有しやすい処理に以下の技術制約を設ける。

* **リスト表示の仮想化 (react-virtuoso)**:
  * 100件を超える動的リストを扱う場合は、必ず仮想化ライブラリを使用する。
  * **制約**: 大量データ保持下でも描画DOM数を**100個以下**に制限し、ブラウザのフリーズを防止する。


* **画像最適化 (sharp)**:
  * 画像表示には必ず `next/image` を使用する。サーバーサイドの `sharp` エンジンにより、WebP変換・自動リサイズを行い、通信サイズをKB単位に削減する。

---

### 7.4.4. 動的読み込み（Code Splitting）

前回Harzプロジェクトでは、全ファイルのimport処理が初回読み込み時に実行され、初期表示が遅延する課題が発生した。本プロジェクトでは、`next/dynamic` を用いた動的読み込み（遅延ロード）により、初期バンドルサイズを削減し、LCP（主要コンテンツ描画）を改善する。

#### 動的読み込みの目的

| 目的 | 効果 |
|---|---|
| **初期バンドルサイズの削減** | 初回表示に不要なコードをバンドルから除外し、ダウンロード時間を短縮 |
| **並列ロード** | 必要になったタイミングで非同期にロードし、メインスレッドをブロックしない |
| **条件付きロード** | 特定条件（権限、デバイス等）でのみ必要なコンポーネントの読み込みを制御 |

#### 適用判断基準（詳細）

以下の基準に該当するコンポーネントは、動的読み込みを**必須**とする：

| 適用ケース | 具体例 | バンドルサイズ目安 | 実装パターン |
|---|---|---|---|
| **初回表示に不要** | モーダル、ドロワー、タブの2枚目以降、アコーディオンの中身 | 任意 | `{ ssr: false }` |
| **大きな外部ライブラリ** | Chart.js、Recharts、PDF.js、Monaco Editor、XLSX | 200KB以上 | `{ ssr: false }` |
| **条件付き表示** | 管理者専用パネル、特定権限でのみ表示する機能 | 任意 | `{ ssr: false }` |
| **低頻度の機能** | 印刷プレビュー、CSVエクスポート、高度な設定画面 | 任意 | `{ ssr: false }` |

**適用しない（通常のimport）ケース**:
- 初回表示に必須のコンポーネント（ヘッダー、メインコンテンツ、ナビゲーション）
- 小さなコンポーネント（50KB未満）
- Atoms/Moleculesの基本的なUI部品

#### 実装パターン

以下は、Chart.jsのような重い外部ライブラリを使用する典型的な実装例：

```tsx
// src/features/diagnosis/components/organisms/MedicalRecordChart.tsx
import dynamic from 'next/dynamic';

// Chart.jsを使用する重いコンポーネント
const ChartComponent = dynamic(
  () => import('./ChartComponent'),
  {
    ssr: false, // サーバーサイドレンダリングを無効化
    loading: () => (
      <div className="h-64 flex items-center justify-center">
        <div className="animate-spin rounded-full h-8 w-8 border-b-2 border-gray-900" />
      </div>
    ),
  }
);

export function MedicalRecordChart({ data }: Props) {
  return (
    <div>
      <h2>経過記録グラフ</h2>
      <ChartComponent data={data} />
    </div>
  );
}
```

**その他の適用例**:
- **モーダル・ドロワー**: 開くまでロード不要 → `{ ssr: false }` で遅延ロード
- **タブの2枚目以降**: 初回表示タブ以外を動的読み込み
- **権限制御**: 管理者専用パネルなど、条件付きで表示するコンポーネント

#### 実装上の注意点

| 注意点 | 詳細 |
|---|---|
| **Named Export への対応** | `dynamic(() => import('./Component').then(mod => mod.ComponentName))` のように明示的に指定 |
| **Props の型安全性** | 動的読み込みでも型情報は保持される。`ComponentProps<typeof DynamicComponent>` で型を取得可能 |
| **Suspense との併用** | `loading` プロパティの代わりに、親コンポーネントで `<Suspense>` を使用することも可能 |
| **SSR の無効化** | `{ ssr: false }` を指定することで、クライアントサイドのみでロード。ブラウザAPIを使用するコンポーネントに必須 |

## 7.5. 遷移高速化（プリフェッチ）制御

Next.jsの `<Link>` コンポーネントによるプリフェッチ（遷移先データの事前取得）を戦略的に管理し、UX向上とBFF負荷抑制を両立させる。



### 7.5.1. プリフェッチの適用ルール

* **標準遷移（ナビゲーション・一般ボタン）**:
  * 原則としてデフォルト（`prefetch={true}`）とする。リンクがビューポートに入った時点でバックグラウンド取得を行い、クリック時の「待ち時間ゼロ」を実現する。


* **大規模リスト表示時（負荷抑制）**:
  * 大量のリンクが並ぶ画面（カルテ履歴一覧等）では、BFFへのリクエスト集中を避けるため、一律の自動プリフェッチを禁止する。
  * **設定**: `prefetch={false}` を明示し、マウスオーバー（ホバー）時のみデータを取得する設定とする。

* **実装コード例**

  ```tsx
  /**
   * 状況に応じたリンクコンポーネントの使い分け
   * 物理パス: src/features/[LV1]/[LV2]/[LV3]/components/organisms/...
   */
  import Link from 'next/link';

  export function NavigationComponent({ listData }) {
    return (
      <nav>
        {/* 1. 通常の遷移：UX優先（デフォルトのプリフェッチを活用） */}
        <Link href="/dashboard" className="btn-primary">
          ダッシュボードへ戻る
        </Link>

        {/* 2. 大規模リスト：BFF負荷抑制のため、ホバー時のみ取得に制限 */}
        <div className="list-wrapper">
          {listData.map((item) => (
            <Link 
              key={item.id} 
              href={`/karte/${item.id}`} 
              prefetch={false} // 自動プリフェッチをオフにする
              className="list-item"
            >
              カルテID: {item.id} の詳細
            </Link>
          ))}
        </div>
      </nav>
    );
  }
  ```
