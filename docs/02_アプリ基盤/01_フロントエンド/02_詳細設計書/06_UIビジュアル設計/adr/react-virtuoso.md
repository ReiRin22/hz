# ADR-3: 大規模リスト仮想化に react-virtuoso を採用する

* **ステータス**: Accepted
* **決定日**: 2026-05-22
* **関連設計書**: [リスト仮想化基盤設計.md](../リスト仮想化基盤設計.md) §1, §2
* **関連 ADR**: なし

## 背景

電子カルテシステムでは、患者カルテ履歴・投薬記録・検査結果など **1万件規模のリスト表示** が頻繁に発生する。これらを通常の `Array.map()` で全件 DOM 描画すると、ブラウザのフリーズ・スクロール遅延・メモリ枯渇が起きる。

仮想化（Virtualization）= 表示領域内のみ DOM 描画して残りはオフスクリーンに退避する方式の採用は確定。本判断はライブラリ選定。

前提:
- Next.js App Router 環境（SSR + CSR ハイブリッド）
- 動的高さの行（医療画像サムネイル付きリスト等）に対応する必要がある
- アクセシビリティ要件としてキーボードフォーカス遷移が崩れないこと

## 検討した選択肢

### 案A: react-window
* **メリット**
  * 軽量（バンドルサイズ小）
  * 利用例が多い
* **デメリット**
  * 動的高さ対応が手書き必要（`VariableSizeList` の高さ計測コード）
  * SSR 環境で初期描画ちらつきが発生しやすい
  * メンテナーの活動頻度が低下傾向

### 案B: react-virtuoso
* **メリット**
  * 動的高さがデフォルトサポート（`Virtuoso` コンポーネントが自動計測）
  * SSR との親和性が高い（`initialItemCount` で初期 HTML に組み込める）
  * メンテナンスが活発で、Next.js のバージョン追従が早い
  * API がシンプル（`totalCount` + `itemContent` のみで動作）
* **デメリット**
  * react-window よりバンドルサイズがやや大きい

### 案C: TanStack Virtual
* **メリット**
  * フレームワーク非依存。Vue/Solid とも共通化できる
* **デメリット**
  * 本プロジェクトは React 一択のため、フレームワーク非依存の利点を活かせない
  * セットアップ手順が他案より長い

## 決定

**案B（react-virtuoso）を採用する。**

理由:
- 医療画像サムネイル付き行のように **行の高さがデータに依存して変わる** ケースで、案A の手書き計測を避けられる
- Next.js SSR との組合せでファーストビュー画面が滑らかに描画できる
- API がシンプルで、アプリ実装チームが配置パターンを覚えやすい

## 影響

正の影響:
- 1万件規模のリストでも `totalCount` + `itemContent` の最小コードで仮想化が成立する
- DOM 要素を再利用するため、メモリ使用量が一定値で頭打ちになる

負の影響:
- バンドルサイズが react-window より約 +20KB（gzip）。LCP 影響は許容範囲
- 動的高さの初回計測でわずかにレイアウトシフトが起きるケースあり（CLS 計測時に観察）

利用基準:
- **1000件以上のリスト** は仮想化必須
- 1000件未満でも、行内に画像・複雑な式が含まれる場合は仮想化を推奨

見直しトリガー:
- react-virtuoso のメンテナンスが停止した場合
- バンドルサイズが LCP 目標を阻害するレベルに肥大化した場合
