# ADR-4: 全画像表示で next/image を必須化する

* **ステータス**: Accepted
* **決定日**: 2026-05-22
* **関連設計書**: [画像最適化基盤設計.md](../画像最適化基盤設計.md) §1, §3
* **関連 ADR**: なし

## 背景

電子カルテシステムでは、患者プロファイル画像・医療画像サムネイル・院内告知バナーなど多種の画像を表示する。画像表示方式として **生の `<img>` タグ** と **Next.js が提供する `next/image` コンポーネント** のどちらを採用するか決定する必要がある。

前提:
- Next.js App Router 環境
- LCP 目標値はフロントエンド方式設計書「6. 性能・リソース設計」で規定
- 外部（パートナー医療機関等）から画像 URL を受け取るケースがある
- 通信帯域が病院ネットワークで制限されているケースがある

## 検討した選択肢

### 案A: 生の `<img>` タグを使用
* **メリット**
  * 標準HTML。学習コスト最小
  * ライブラリ依存なし
* **デメリット**
  * 自動最適化なし。サーバーが返した画像をそのまま表示するため通信量が膨らむ
  * WebP/AVIF 変換やレスポンシブ画像（srcset）を手書きで実装する必要がある
  * 外部ドメインのチェックが効かず、SSRF やフィッシング画像読み込みのリスクが残る

### 案B: `next/image` を必須化
* **メリット**
  * フォーマット自動変換（JPEG/PNG → WebP/AVIF）。ブラウザ対応に応じて最適なフォーマットで配信
  * ビューポート外画像の遅延読み込み（`priority` 未指定時）
  * `priority` 属性で LCP 対象画像をプリロードできる
  * `next.config.ts` の `images.remotePatterns` でホワイトリスト方式の外部ドメイン制限が可能
  * `sharp` による高速な画像処理（POC で実測済み）
* **デメリット**
  * `next/image` を経由しない画像表示が混在すると最適化の効果が薄れる → ESLint で禁止する必要あり
  * 外部ドメインを追加するたびに `next.config.ts` の更新が必要

## 決定

**案B（`next/image` 必須化）を採用する。**

理由:
- 病院ネットワークの帯域制限下では **自動フォーマット変換の通信量削減効果** が体感に直結する
- `remotePatterns` のホワイトリスト方式により、医療業務システムに求められる **外部リソース読み込み統制** を低コストで担保できる
- LCP 目標達成のために、ファーストビュー画像のプリロード（`priority`）が標準で利用できる

## 影響

正の影響:
- 画像配信の通信量・LCP が自動最適化される
- 外部画像ドメイン管理が `next.config.ts` 一箇所で完結し、レビュー対象が明確になる
- POC 実測で LCP 短縮効果（1.2〜1.8秒）を確認済み

負の影響:
- `<img>` タグ禁止を徹底するため、ESLint ルール `@next/next/no-img-element` を有効化する必要がある
- 外部ドメイン追加が基盤チーム承認制になり、機能チームの開発リードタイムが伸びる

運用ルール:
- `next.config.ts` の作成・管理は基盤チームが担当
- アプリチームは画像ドメイン追加要望を基盤チームに依頼
- `priority` はファーストビュー内（リスト上位 10件程度）に限定する

見直しトリガー:
- Next.js が `next/image` の仕様を大幅に変更した場合
- `<img>` タグでも同等の最適化が標準ブラウザ機能で達成可能になった場合
