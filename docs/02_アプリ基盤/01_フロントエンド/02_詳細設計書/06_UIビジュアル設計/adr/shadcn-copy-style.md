# ADR-2: UI コンポーネントは shadcn/ui のコピーペースト方式で導入する

* **ステータス**: Accepted
* **決定日**: 2026-05-22
* **関連設計書**: [UIライブラリ基盤設計.md](../UIライブラリ基盤設計.md) §2
* **関連 ADR**: [tailwind-v4.md](tailwind-v4.md)

## 背景

電子カルテシステムは、Button・Input・Dialog 等の汎用 UI コンポーネントを多数必要とする。これらを **npm パッケージとして外部依存とする方式** と、**shadcn/ui CLI でコピーしてリポジトリ内コードとする方式** のどちらを採用するか決定する必要がある。

前提:
- フロントエンド方式設計書で UI ライブラリは shadcn/ui を選定
- アクセシビリティ要件（フォーカス管理・キーボード操作）は Radix UI で担保する
- 医療業界のシステムとして、外部ライブラリの破壊的変更が業務影響に直結することを許容できない

## 検討した選択肢

### 案A: 通常の npm パッケージとして UI ライブラリを依存
* **メリット**
  * バージョン管理が package.json で完結
  * ライブラリ側のバグ修正・改善が自動で取り込める
* **デメリット**
  * 細かなスタイル変更や新 variant 追加に対し、ライブラリのラッパー or `cn()` 上書きが必要で、層が深くなる
  * 破壊的変更時に多数の利用箇所が一斉に壊れるリスク
  * 内部実装が読めないため、医療業界の監査・障害対応で原因特定に時間がかかる

### 案B: shadcn/ui CLI でコンポーネントをプロジェクトにコピー
* **メリット**
  * コンポーネントが `frontend/src/shared/components/atoms/ui/` 配下に存在するため、自社コードとして直接編集可能
  * 監査・障害対応で内部実装を直接読める
  * 一斉破壊リスクなし。差分は明示的に取り込む形となる
  * shadcn/ui 側のテンプレート更新は CLI で個別に再取得して比較できる
* **デメリット**
  * ライブラリ側のバグ修正を自動取り込みできない（手動で再コピー比較が必要）
  * リポジトリのコード行数が増える

## 決定

**案B（shadcn/ui コピーペースト方式）を採用する。**

理由:
- 医療業界において **動作の透明性と監査可能性** がライブラリ自動更新の利便性を上回る
- Radix UI の堅牢なアクセシビリティを土台にしつつ、Tailwind CSS v4（[ADR-1](tailwind-v4.md)）でスタイルを直接編集できる構成が、本システムのデザインシステム要件に合致する
- 破壊的変更の連鎖を遮断できる

## 影響

正の影響:
- スタイル変更・variant 追加が自由（直接編集可能）
- shadcn/ui 側の更新追従はチーム判断で個別に取り込み可

負の影響:
- バグ修正の取り込みが手動。基盤チームが定期的に shadcn/ui の更新を確認する運用が必要
- コンポーネント数が増えると初期コピー＋カスタマイズ工数が積み上がる

配置ルール:
- インストール先は `frontend/src/shared/components/atoms/ui/` で固定（[UIライブラリ基盤設計.md](../UIライブラリ基盤設計.md) §3）
- shadcn/ui に存在しない Radix UI プリミティブ（Context Menu 等）は `@radix-ui/react-*` を直接インストールしてよい

見直しトリガー:
- shadcn/ui がコピーペースト方式を廃止し npm パッケージ方式へ移行した場合
- 医療業界の監査要件が緩和され、ライブラリ自動更新を許容できるようになった場合
