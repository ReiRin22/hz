## 2. 監視ツール経由必須ルール

> **警告**: 基盤が配線済みの監視ツール送信パスを経由しない実装は禁止。アプリコードから外部監視 SaaS や Prometheus へ直接書き出すと、PHI フィルタ・テナント識別・サンプリング制御を素通りし、医療情報漏洩・コスト爆発・テナント越境の事故につながる。

| 用途 | ✅ 経由必須 | ⛔ バイパス禁止 API | 詳細 |
|---|---|---|---|
| エラー送信 | 09章の `@sentry/nextjs` SDK 経由（`captureException` / `captureMessage`）。送信先は GlitchTip | アプリコードから直接 `fetch('http://localhost:8080/...')` 等で GlitchTip API を呼ぶ実装 | [09_監視エラーハンドリング設計/GlitchTip連携設計.md](../09_監視エラーハンドリング設計/GlitchTip連携設計.md) |
| 性能カスタムメトリクス送信 | 基盤提供の `@sentry/nextjs` SDK 経由（`Sentry.setMeasurement`） | window.performance API の値をアプリで集計して独自エンドポイントへ送る実装 | [フロントエンド性能監視設計.md](フロントエンド性能監視設計.md) §3 |
| WebSocket メトリクス送信 | `frontend/src/shared/hooks/use-notification.ts` 内の基盤実装 / `bff/src/features/notification/notification.gateway.ts` 内の基盤実装 | アプリ feature 側で独自に `socket.on` をフックして外部送信する実装 | [WebSocket監視設計.md](WebSocket監視設計.md) §2 |
| BFF Prometheus メトリクス | `bff/src/shared/plugins/prometheus.ts` 経由（基盤チームが配線） | アプリ Module から直接 Prometheus クライアントを呼び出す実装 | [インフラランタイム監視設計.md](インフラランタイム監視設計.md) §3 |
| アラート設定変更 | 統合監視基盤側の構成管理（インフラチーム所管） | フロントエンド・BFF コードで個別にアラート閾値をハードコードする実装 | システム監視・通知サービス方式設計書 |

### 2.1 例外条件

| 条件 | 例外の扱い |
|---|---|
| 基盤チームによる SDK 設定ファイル（`SentryInitializer.tsx` 等）への変更 | 09章 / 本章のレビューを経て承認されたものに限り可 |
| プロトタイプ・PoC コード（`docs/` 配下に閉じる検証用） | 本番ビルドに混入しない前提で許容。CI で本番ビルド対象から除外する |

### 2.2 PR レビュー時の確認観点

| 観点 | grep ターゲット | 期待 |
|---|---|---|
| GlitchTip API への直接送信 | `fetch.*glitchtip`, `fetch.*localhost:8080`, `fetch.*datadog`, `fetch.*newrelic` | アプリコードに存在しないこと |
| `@sentry/nextjs` SDK 直接呼び出しの分散 | `Sentry\\.captureException`, `Sentry\\.captureMessage`, `Sentry\\.setMeasurement` | `frontend/src/shared/plugins/`, `frontend/src/shared/hooks/use-notification.ts` 以外で呼ばれていないこと |
| 監視メトリクス独自集計 | `performance\\.getEntriesByType`, `performance\\.now\\(\\)` | アプリ feature 側で独自集計していないこと（基盤提供の Hook 経由）|
| Prometheus 直接書き込み | `prom-client`, `register\\.metrics` | `bff/src/shared/plugins/prometheus.ts` 以外で参照していないこと |

## 3. PHI / PII 保護ルール

| 観点 | ルール |
|---|---|
| **PHI を監視データに含めない** | 患者情報・操作内容の生データを監視ツールへ送信しない。`beforeSend` フィルタの設計詳細は 09章を参照 |
| **クライアント詳細ログの抑制** | WebSocket 接続状態の詳細ログをクライアント単位で記録しない（PHI が紛れ込む経路となる） |
| **環境別サンプリングの遵守** | development 100% / staging 50% / production 10% のサンプリング比率を独断で変更しない（根拠: [adr/sampling-rate-by-env.md](adr/sampling-rate-by-env.md)） |
| **基盤 SDK 設定の独自変更禁止** | `frontend/src/shared/plugins/SentryInitializer.tsx` をアプリ feature コードから変更しない（一貫性の喪失・PHI フィルタ無効化リスク） |

## 4. アラート運用ルール

| 観点 | ルール |
|---|---|
| **アラート疲れの防止** | 一時的なネットワーク切断・短時間のスパイクを過剰にアラート発報する設計を避ける |
| **暫定閾値の更新** | 「※暫定値」表記のある閾値は、負荷試験・ベースライン測定後に必ず更新する（根拠: [adr/provisional-thresholds.md](adr/provisional-thresholds.md)） |
| **個別ユーザー追跡の禁止** | アラート対応で個別ユーザーのログを抽出する際、テナント ID・ユーザー ID 以外の PII を取得しない |
| **方式設計書との整合確認** | 検知条件は本章単独で確定せず、`システム監視・通知サービス方式設計書` の検知条件と整合させてから運用に入る |

## 5. 日常的なモニタリング規約

| 観点 | ルール |
|---|---|
| **実施主体** | システム開発者（フロントエンド担当・BFF 担当・SRE） |
| **実施頻度** | 日次（営業日の朝） |
| **確認カテゴリ** | 性能指標・接続指標・リソース指標・エラー指標の 4 カテゴリすべてを確認する（指標値の正本は [監視指標カタログ.md](監視指標カタログ.md)）|
| **異常検知時の判断** | フロントエンド側のデータだけで原因を断定しない。BFF 側・インフラ側を併せて確認する |
| **ユーザー体験の実態を無視しない** | 監視データだけで判断せず、ユーザーフィードバック・現場の声を併せて評価する（§6 順序 6 と連動）|
| **改善タスクの起票** | 性能劣化を検知した場合、影響範囲と原因を明確にした Issue を起票する。問題を放置しない |
| **改善効果の事後計測** | 改善タスクの効果を実装後に必ず計測し、目標値の達成を確認する |
| **リソース分散の回避** | すべての性能問題を同時に解決しようとせず、優先度に従って段階的に対応する |

### 5.1 4 カテゴリの確認内容（[監視指標カタログ.md](監視指標カタログ.md) 詳細値の運用観点抜粋）

| カテゴリ | 日常モニタリングで確認するポイント |
|---|---|
| **性能指標** | Core Web Vitals（LCP / FID / INP / CLS）が目標値を満たしているか、API 応答時間 P90/P99 で極端な遅延が発生していないか |
| **接続指標** | WebSocket 接続数の異常（大量切断、再接続ループ）が発生していないか |
| **リソース指標** | Grafana ダッシュボードで CPU・メモリ使用率の閾値超過が発生していないか |
| **エラー指標** | クライアント側エラー率・API エラー率が閾値を超えていないか |

## 6. 性能劣化検知時の対応フロー

**トリガー**: アラート発報時、または日常モニタリングで異常を検知

| 順序 | アクション |
|---|---|
| 1 | **影響範囲の特定**: 性能監視ツールのタグ（テナント ID / デバイス / ブラウザ）で絞り込み |
| 2 | **原因の仮説立て**: TTFB（バックエンド）とクライアント処理時間を比較しボトルネックを特定 |
| 3 | **ログ解析**: 該当時間帯の BFF ログ・WebSocket ログを確認 |
| 4 | **改善タスクの起票**: 問題を特定できた場合、Issue を起票し優先順位を設定 |
| 5 | **ロールバック判断**: 直近のデプロイが原因の場合、ロールバック実施を検討 |
| 6 | **ユーザーフィードバック突合**: 「遅い」「重い」報告と該当ユーザーの性能メトリクスを突き合わせ、改善優先度を判断 |

### 6.1 ユーザーフィードバック収集と分析

| 観点 | 内容 |
|---|---|
| **収集方法** | フィードバックウィジェット（UserVoice / Intercom 等）の組み込みによる定性的な意見の収集 |
| **分析方法** | ユーザーからの「遅い」「重い」報告と該当ユーザーの性能メトリクスを突き合わせる。特定の画面・操作に問題が集中している場合は優先的に改善タスク化する |

## 8. 責務サマリ

| 役割 | やること |
|---|---|
| **アプリ実装者** | GlitchTip API への直接送信を書かない。基盤 Hook（`use-notification` 等）と SDK 設定（`SentryInitializer.tsx`）に手を入れない |
| **基盤チーム** | `SentryInitializer.tsx` への Performance 設定追加、`use-notification.ts` のメトリクス送信処理追加、`notification.gateway.ts` の Prometheus 記録追加、`prometheus.ts` の新規作成 |
| **SRE / 運用担当** | 日次モニタリング、性能劣化検知時の対応フロー実施、暫定閾値の更新運用 |
| **PR レビュア** | §2.2 の grep 観点を確認、PHI 送信パターンの混入をチェック |
