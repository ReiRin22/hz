# フロントエンド性能監視設計

[監視指標カタログ.md](監視指標カタログ.md) で定義された **フロントエンド（ブラウザ）** コンポーネントの監視仕様。**性能指標** および **エラー指標** に基づき、GlitchTip（Sentry互換SDK: `@sentry/nextjs`）を用いて Core Web Vitals および環境・デバイス別性能を収集する設計を確定する。

> アプリ実装と運用が守るべきルールは [運用監視規約.md](運用監視規約.md) §2-§5 に集約している。本書は基盤設定とコンポーネント別実装方針のみ記述する。

## 2. Core Web Vitals 収集仕様

[監視指標カタログ.md](監視指標カタログ.md) §3 で定義した性能指標の目標値に基づき、実環境での達成状況を継続的に測定する。

| 指標 | 目標値 | 異常判定基準 | 測定対象 | 監視の観点 |
|---|---|---|---|---|
| **LCP** (Largest Contentful Paint) | 2.5 秒以内 | > 4.0 秒（要改善） | ダッシュボード表示、カルテ表示 | 初期ロード時のデータ取得とレンダリング速度 |
| **FID/INP** (First Input Delay / Interaction to Next Paint) | FID: 100ms 以内<br>INP: 200ms 以内 | FID: > 300ms<br>INP: > 500ms（要改善） | 処方入力、オーダー確定ボタン | ユーザー操作への応答性 |
| **CLS** (Cumulative Layout Shift) | 0.1 未満 | > 0.25（要改善） | 動的コンテンツ読み込み | レイアウトシフトの頻度 |
| **TTFB** (Time to First Byte) | （補助指標） | > 1.0 秒（バックエンド遅延の疑い） | BFF レスポンス待ち | フロント・バックエンドの境界特定 |

**参照**: 目標値の根拠は `フロントエンド方式設計書 6.1 性能要件と目標値` を参照のこと。

## 3. GlitchTip SDK 追加設定（Performance 監視の有効化）

`frontend/src/shared/plugins/SentryInitializer.tsx` に以下を追加する。SDK 初期化・PHI フィルタリング・監査情報付与は 09章で定義済のため、本書では `tracesSampleRate` のみ確定する。

### 3.1 設定仕様

```typescript
Sentry.init({
  dsn: process.env.NEXT_PUBLIC_SENTRY_DSN, // GlitchTip の DSN

  // Performance 監視の有効化（本章で追加）
  tracesSampleRate: process.env.NODE_ENV === 'production' ? 0.1 : 1.0,

  // 既存設定（09章参照）
  maxBreadcrumbs: 50,
  beforeSend: (event) => { /* PHI フィルタリング（09章定義） */ },
});
```

### 3.2 サンプリング比率

| 環境 | `tracesSampleRate` | 目的 |
|---|---|---|
| development | 1.0（100%） | 全トランザクション収集 |
| staging | 0.5（50%） | 検証用に高頻度収集 |
| production | 0.1（10%） | 統計的に有意なサンプル + コスト・PHI 偶発送信リスク抑制 |

> 環境別サンプリングの根拠: [adr/sampling-rate-by-env.md](adr/sampling-rate-by-env.md)

### 3.3 監査情報の付与

テナント ID・ユーザー ID・セッション情報は 09章で定義済のタグ付与経路を流用する。本章で追加するタグは存在しない。

## 4. 監視の主要観点

### 4.1 ユーザー体験（UX）の定量化

医療従事者のストレス要因となる「遅延」を数値で把握する。

| 観点 | 指標 |
|---|---|
| 初期表示パフォーマンス | LCP |
| 操作応答性 | FID / INP |
| 画面の安定性 | CLS |

### 4.2 異常検知とアラート

パフォーマンスの「悪化」を早期に検知する。

| 観点 | 検知内容 |
|---|---|
| **パフォーマンス・リグレッション（退行）** | アップデート前後で特定画面の表示速度が 20% 以上悪化 |
| **低速アウトライヤーの特定** | P90（下位 10%）、P99（下位 1%）のユーザーが極端に遅い体験をしていないか |
| **Apdex スコア** | ユーザー満足度の可視化（満足・許容・不満の割合） |

### 4.3 環境・インフラ依存の切り分け

「システムが悪いのか、病院の環境が悪いのか」を特定する。

| 観点 | 切り分け対象 |
|---|---|
| **拠点・ネットワーク別性能** | 院内 LAN（Wi-Fi）の混雑状況、プロキシサーバー経由の遅延 |
| **デバイス・ブラウザ別性能** | デスクトップ PC、タブレット、低スペック端末のハードウェア性能差 |
| **フロント・バックエンドの境界特定** | TTFB とクライアント処理時間の分離 |

**実装方法**:

| 機能 | API（GlitchTip / Sentry互換SDK 利用時） | 将来移行時（Grafana Faro） |
|---|---|---|
| 環境別タグ分類 | `Sentry.setTag('device_type' / 'browser' / 'network_type' / 'location')` | `faro.setContext()` |
| カスタムメトリクス送信 | `Sentry.setMeasurement(name, value, unit)` | Faro メトリクス送信 API |

### 4.4 医療情報保護とセキュリティ

監視データに機密情報が含まれないための保護策。

| 観点 | 対策 |
|---|---|
| **PII / PHI の除外** | [09_監視エラーハンドリング設計/GlitchTip連携設計.md](../09_監視エラーハンドリング設計/GlitchTip連携設計.md) §3.2 PHI フィルタを参照（`@sentry/nextjs` SDK の `beforeSend` で実装。将来 Grafana Faro へ移行する場合も同等のフィルタリング方針を適用） |
| **データ送信量の制御** | §3.2 のサンプリング比率により、ブラウザ負荷とコストを抑制 |
