# 監視指標カタログ

本システムで収集・監視する指標を、**監視の目的別**に 4 つのカテゴリに分類して定義する。本ファイルは複数の監視設計（フロントエンド性能監視・WebSocket 監視・インフラランタイム監視）から参照される横断定義である。

> **注**: 本ファイルで定義する指標値（目標値、異常判定基準）の一部は暫定値である。暫定値の運用方針は [adr/provisional-thresholds.md](adr/provisional-thresholds.md) を参照。

---

## 1. 監視対象コンポーネント

本システムの監視対象範囲を以下の 4 つに分類する。

| コンポーネント | 監視の主目的 | 監視データの収集先 | 収集方法 |
|---|---|---|---|
| **フロントエンド（ブラウザ）** | ユーザー体験（UX）の定量化、性能劣化の早期検知 | Sentry Performance（※） | ブラウザ上の JavaScript で収集 |
| **BFF（NestJS）** | API 応答時間、リクエスト数、エラー率の把握 | Sentry Performance（※）、Prometheus | NestJS インターセプター、ミドルウェア |
| **WebSocket 接続** | リアルタイム通信基盤の健全性、接続異常の早期検知 | フロントエンド: Sentry Performance（※）<br>BFF: Prometheus | クライアント・サーバー両面で収集 |
| **インフラ層（Node.js ランタイム）** | システムリソース（CPU、メモリ）、コンテナ状態 | Prometheus、cAdvisor、Grafana | node-exporter、cAdvisor |

**注**: ※ 現時点では Sentry を仮採用しているが、ツールが変更された場合でも、本ファイルで定義する基本的な考え方（性能メトリクスの収集、環境別分析、PHI 保護）は変わらない。

> 仮採用の根拠: [adr/sentry-tentative-adoption.md](adr/sentry-tentative-adoption.md)

**責任分担**: インフラ層の監視詳細は `システム監視・通知サービス方式設計書` で定義される統合監視基盤（Prometheus / Grafana）を参照のこと。

---

## 2. 統一監視指標カテゴリ

| カテゴリ | 目的 | 答える問い |
|---|---|---|
| **性能指標** | ユーザー体験の定量化、性能劣化の早期検知 | 「ユーザーは快適に使えているか？」 |
| **リソース指標** | システムリソース枯渇の予兆検知、スケーリング判断 | 「サーバーリソースは足りているか？」 |
| **接続指標** | リアルタイム通信基盤の健全性把握 | 「WebSocket 接続は正常か？」 |
| **エラー指標** | システム異常の早期検知、障害の影響範囲特定 | 「エラーは発生していないか？」 |

---

## 3. 性能指標

**目的**: ユーザー体験の定量化、性能劣化の早期検知

| 指標 | 目標値 | 測定層 | 異常判定基準 |
|---|---|---|---|
| **LCP** (Largest Contentful Paint) | 2.5 秒以内 | RUM（フロントエンド） | > 4.0 秒（要改善） |
| **FID/INP** (First Input Delay / Interaction to Next Paint) | FID: 100ms 以内<br>INP: 200ms 以内 | RUM（フロントエンド） | FID: > 300ms<br>INP: > 500ms（要改善） |
| **CLS** (Cumulative Layout Shift) | 0.1 未満 | RUM（フロントエンド） | > 0.25（要改善） |
| **TTFB** (Time to First Byte) | （補助指標） | RUM（フロントエンド）<br>サーバー側監視（BFF） | > 1.0 秒（バックエンド遅延の疑い） |
| **API 応答時間** (P50/P90/P99) | P50: < 200ms<br>P90: < 500ms<br>P99: < 1000ms | サーバー側監視（BFF） | P90: > 1000ms（要改善） |

**参照**: 目標値の根拠は `フロントエンド方式設計書 6.1 性能要件と目標値` を参照のこと。

---

## 4. リソース指標

**目的**: システムリソース枯渇の予兆検知、スケーリング判断

| 指標 | 異常判定基準 | 測定層 | 備考 |
|---|---|---|---|
| **メモリ使用量（Heap）** | > 80%（警告）<br>> 90%（緊急） | インフラ監視（Node.js） | Heap 枯渇による OOM（Out of Memory）の予兆 |
| **メモリ使用量（RSS）** | > 90%（警告） | インフラ監視（Node.js） | コンテナのメモリ制限到達リスク |
| **CPU 使用率** | > 80%（持続 5 分以上）（警告） | インフラ監視（Node.js） | スケーリング判断の材料 |
| **ディスク I/O** | （※） | インフラ監視（OS） | ※ 閾値は今後の設計段階で決定 |

---

## 5. 接続指標

**目的**: リアルタイム通信基盤（WebSocket）の健全性把握

| 指標 | 異常判定基準 | 測定層 | 備考 |
|---|---|---|---|
| **アクティブ接続数** | （※1） | サーバー側監視（BFF） | ※1 システム規模に応じて閾値を設定 |
| **テナント別接続数** | （※1） | サーバー側監視（BFF） | 特定テナントへの接続集中を検知 |
| **接続イベント頻度** | > 1000 回/分（※2） | サーバー側監視（BFF） | 異常な接続試行の検知 |
| **切断イベント頻度** | > 500 回/分（※2） | サーバー側監視（BFF） | 大量切断（ネットワーク障害の疑い） |
| **再接続試行回数** | > 5 回（クライアント側）（※2） | RUM（フロントエンド） | クライアント側の接続異常 |
| **接続確立時間** | > 5 秒（※2） | RUM（フロントエンド） | BFF リソース状況またはネットワーク遅延 |

**注釈**:
- ※1: アクティブ接続数・テナント別接続数の異常判定閾値は、システムの利用規模（テナント数、同時接続ユーザー数）に依存するため、今後の設計段階（負荷試験結果、運用初期のベースライン測定）に応じて決定する
- ※2: 接続・切断・再接続イベント頻度、接続確立時間の閾値は暫定値であり、今後の設計段階に応じて変更する可能性がある

> 暫定値運用の根拠: [adr/provisional-thresholds.md](adr/provisional-thresholds.md)

## 6. エラー指標

**目的**: システム異常の早期検知、障害の影響範囲特定

| 指標 | 異常判定基準 | 測定層 | 備考 |
|---|---|---|---|
| **クライアント側エラー率** | > 0.5%（警告） | RUM（フロントエンド） | JavaScript ランタイムエラー、API 通信エラー |
| **API エラー率（HTTP 5xx）** | > 1%（警告） | サーバー側監視（BFF） | BFF 内部エラー、バックエンド API 障害 |
| **API エラー率（HTTP 4xx）** | > 5%（警告） | サーバー側監視（BFF） | クライアントリクエストエラー（バリデーションエラー等） |

**参照**: エラー検知とハンドリングの詳細は [09_監視エラーハンドリング設計/](../09_監視エラーハンドリング設計/監視エラーハンドリング規約.md) を参照のこと。

## 7. 監視指標と各設計書の対応関係

上記カテゴリで定義した指標は、本章の各設計書で具体的な実装に落とし込まれる。

| 設計書 | 使用する監視指標カテゴリ | 主な監視対象 |
|---|---|---|
| [フロントエンド性能監視設計.md](フロントエンド性能監視設計.md) | 性能指標、エラー指標 | Core Web Vitals、ページロード時間、クライアント側エラー率 |
| [WebSocket監視設計.md](WebSocket監視設計.md) | 接続指標、エラー指標 | アクティブ接続数、再接続試行回数、接続確立時間 |
| [インフラランタイム監視設計.md](インフラランタイム監視設計.md) | リソース指標、性能指標（API 応答時間） | メモリ使用量、CPU 使用率、ディスク I/O、API レスポンスタイム |
| [ログ・トレース連携設計.md](ログ・トレース連携設計.md) | 全カテゴリ | 監視データの送信先、参照すべき監視画面、統合監視基盤との連携 |
