# ADR-2: Sentry Performance のサンプリング比率を環境別に設定する

* **ステータス**: Accepted
* **決定日**: 2026-05-25
* **関連設計書**: [フロントエンド性能監視設計.md](../フロントエンド性能監視設計.md) §3
* **関連 ADR**: [sentry-tentative-adoption.md](sentry-tentative-adoption.md)

## 背景

Sentry Performance は `tracesSampleRate`（0〜1）で収集トランザクションの比率を制御する。電子カルテとしての特性上、以下のトレードオフが存在する:

* 高サンプリング率: 性能異常の検出感度が上がるが、ブラウザ側計測オーバーヘッド・SaaS コスト・PHI 偶発送信リスクが増える
* 低サンプリング率: コスト・負荷を抑えられるが、稀少な性能劣化（特定テナント・特定端末）の検知が遅れる

development / staging / production はトラフィック特性が異なる。本番は実患者データが流れるため PHI 漏洩リスクと SaaS コストの両面でサンプリング抑制が必要、開発・検証は再現性のために高サンプリングが望ましい。

## 検討した選択肢

### 案A: 全環境一律に 100% 収集
* **メリット**: 設定が単純。希少事象を取りこぼさない。
* **デメリット**: 本番ではコスト・PHI フィルタの負荷が過大。トランザクション量がスパイクした際にブラウザ計測自体が UX を損なう可能性。

### 案B: 全環境一律に 10% 収集
* **メリット**: コスト最小。
* **デメリット**: 開発・検証中に性能イベントが希薄になり、デバッグ・回帰試験で再現性が下がる。

### 案C: 環境別サンプリング（development 100% / staging 50% / production 10%）
* **メリット**: 開発・検証は再現性を確保しつつ、本番はコストと PHI リスクを抑制。Web Vitals は 10% でも統計的有意なサンプルが得られる（業界一般的なベンチマーク）。
* **デメリット**: 環境変数の取り違えで設定が逆転すると検知できないため、設定値の検証手順を運用ルールに含める必要がある。

## 決定

**案C を採用する**。

| 環境 | `tracesSampleRate` | 目的 |
|---|---|---|
| development | 1.0（100%） | 全トランザクション収集による開発時のデバッグ容易性確保 |
| staging | 0.5（50%） | 検証用に高頻度収集 |
| production | 0.1（10%） | 統計的に有意なサンプル + コスト・PHI 偶発送信リスクの抑制 |

`process.env.NODE_ENV` をベースに `frontend/src/shared/plugins/sentry.client.config.ts` の `tracesSampleRate` を切り替える。

## 影響

### 正の影響
* 本番 SaaS コストを規模に応じて制御できる。
* PHI を含むトランザクションが偶発的に外部送信される確率を本番で 1/10 に抑制できる（`beforeSend` フィルタを通過した場合の二重防御）。

### 負の影響
* 本番で発生頻度の低い性能劣化（特定テナント・特定端末）の検知が、サンプリング外れにより遅れる可能性がある。重大事象は別途エラー監視（09章）で 100% 捕捉される設計のため許容する。

### 見直しトリガー
* 本番のトランザクション総数が当初想定（例: 月次 X 万件）から大幅に変動した場合
* 特定テナント・端末向けにサンプリング率を引き上げる要求が運用から出た場合（動的サンプリングの検討）
* PHI フィルタの監査要件が強化され、本番送信量をさらに抑制する必要が生じた場合
