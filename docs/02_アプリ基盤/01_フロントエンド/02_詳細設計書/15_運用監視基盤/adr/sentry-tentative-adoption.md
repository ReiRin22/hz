# ADR-1: フロントエンド性能監視ツールに Sentry を仮採用する

* **ステータス**: Superseded by [ADR-5](glitchtip-adoption.md)
* **決定日**: 2026-05-25
* **関連設計書**: [フロントエンド性能監視設計.md](../フロントエンド性能監視設計.md) §1, [ログ・トレース連携設計.md](../ログ・トレース連携設計.md) §1
* **関連 ADR**: [sampling-rate-by-env.md](sampling-rate-by-env.md), [monitoring-layer-responsibility.md](monitoring-layer-responsibility.md)

## 背景

09章で導入されたエラー監視 SaaS（Sentry）には Performance 監視機能が含まれており、Core Web Vitals（LCP / FID / INP / CLS / TTFB）を SDK 設定の追加だけで収集できる。一方で、Sentry はクラウド SaaS であり、以下のリスクが残る:

* 医療情報を扱うシステムとして、PHI の外部送信防止策を継続的に検査する必要がある
* SaaS 利用料がトラフィック規模に比例するため、本番運用フェーズでコスト評価が必要となる
* SaaS 障害時にエラー・性能監視が同時停止する単一障害点リスクがある

エラー監視と性能監視のツールを別物にすると、`beforeSend` の PHI フィルタリング・タグ統一・障害時の相関分析が二重実装になる。フロントエンド詳細設計フェーズでは「同一 SDK で完結させる」ほうが整合性が高い一方、長期的にはセルフホスト型（GlitchTip / ELK）への移行余地を残しておきたい。

## 検討した選択肢

### 案A: Sentry を本採用とする
* **メリット**: 09章のエラー監視と完全統合。PHI フィルタリング・監査タグ付与の一元化。実装が最短。
* **デメリット**: SaaS ロックイン。コスト・規制要件で後戻りする際、設計書に「Sentry 前提」のコード例が散在しているとリファクタが大規模化する。

### 案B: 性能監視のみ別ツール（GlitchTip / Datadog RUM / ELK）を初期から採用
* **メリット**: SaaS 単一障害点を最初から回避。
* **デメリット**: PHI フィルタリング・タグ・監査情報の付与を二重に実装する必要がある。フロントエンド詳細設計が現時点で過剰に複雑化する。

### 案C: Sentry を仮採用とし、ツール変更可能性を設計書に明記する
* **メリット**: 短期は 09章と統合済みの Sentry SDK を再利用して実装コストを抑制。長期は「設計の基本概念（性能メトリクス収集・環境別分析・PHI 保護）はツール非依存」と明示することで、ツール変更時の影響範囲を限定できる。
* **デメリット**: 設計書に「Sentry 利用時」「代替ツール利用時は同様の機能を使用」という条件付き記述が残り、可読性がやや下がる。

## 決定

**案C（仮採用）を採用する**。

* `frontend/src/shared/plugins/sentry.client.config.ts` に Performance 監視（`tracesSampleRate`）を追加することで Core Web Vitals を収集する。
* 設計書本文では、Sentry 固有 API（`Sentry.setMeasurement` / `Sentry.captureMessage` 等）を使用するコード例にはすべて「※ Sentry 利用時」の注記を付け、代替ツール採用時には等価機能（タグ・カスタムメトリクス送信）に置き換える前提を明示する。
* ツール変更を検討すべきトリガー条件を明文化する（影響セクション参照）。

## 影響

### 正の影響
* 09章で構築済みの SDK 初期化・PHI フィルタリング・監査情報付与をそのまま再利用できる。
* 性能監視を独立 SaaS で構築する初期コストを回避できる。

### 負の影響
* Sentry SaaS の障害時、エラー監視と性能監視が同時に途絶する。
* SaaS コストがトラフィックに比例するため、本番運用初期にコスト見積もりが必要。

### 見直しトリガー
* SaaS 利用料が許容範囲を超えた場合
* PHI 外部送信に関する規制要件が強化された場合（オンプレミス必須化等）
* 09章のエラー監視ツールが Sentry から変更される場合（連動して再評価）
* セルフホスト型 OSS（GlitchTip / SigNoz / ELK Stack）が機能・運用面で同等水準に達した場合
