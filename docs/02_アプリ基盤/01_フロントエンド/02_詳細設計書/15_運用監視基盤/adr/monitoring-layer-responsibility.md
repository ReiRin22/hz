# ADR-3: 監視責務をフロントエンド章 / 方式設計書 / インフラ層で分界する

* **ステータス**: Accepted
* **決定日**: 2026-05-25
* **関連設計書**: [運用監視規約.md](../運用監視規約.md) §1, [インフラランタイム監視設計.md](../インフラランタイム監視設計.md), [ログ・トレース連携設計.md](../ログ・トレース連携設計.md)
* **関連 ADR**: なし

## 背景

運用監視は「フロントエンド／BFF／WebSocket／Node.js ランタイム／コンテナ／OS」の各層で必要となるが、本章はフロントエンド詳細設計書という性格上、すべての層を網羅的に記述すると以下の弊害が生じる:

* インフラ基盤側で更新された監視設定（Prometheus 設定・Grafana ダッシュボード仕様）が本章に反映されず、二重管理になる
* 詳細設計書としての凝集が崩れ、フロントエンド開発者が「自分が読むべき範囲」を判別できない
* 09章（エラー監視）・14章（操作監査ログ）と境界が重複し、責務が曖昧になる

監視データの「収集」「保管」「アラート」「可視化」は層をまたぐ横断課題であり、どの章で何を確定するかを明示しないと改修時のオーナーシップが曖昧になる。

## 検討した選択肢

### 案A: 本章に全監視仕様を集約
* **メリット**: 1ヶ所で完結し参照しやすい。
* **デメリット**: 統合監視基盤の設計を本章に二重保持することになり、システム監視・通知サービス方式設計書との乖離が必ず発生する。

### 案B: 本章はフロントエンド側のみ記述、他はすべて他文書参照
* **メリット**: 凝集度が高い。
* **デメリット**: 「BFF/インフラ層を本章でどう扱うか」の境界が読者に伝わらず、監視設計の全体像が掴めなくなる。

### 案C: 層別に責任分界し、本章は「フロントエンド・BFF アプリレイヤーの監視仕様 + 統合監視基盤への接続点（送信先・参照画面）」のみ確定する
* **メリット**: 本章は「アプリレイヤーで収集すべきメトリクス・送信方式・アプリ実装者が守るルール」に責務を絞れる。インフラ層の詳細は方式設計書側、エラー詳細は 09章、監査ログは 14章へ完全委譲。
* **デメリット**: 章をまたぐ参照が増え、読者が複数文書を行き来する必要がある。各設計書冒頭に責任分界表を必ず置くことで緩和する。

## 決定

**案C を採用する**。本章の責任範囲を以下に分界する:

| 監視対象 | 本章での扱い | 他文書側の責任 |
|---|---|---|
| フロントエンド（ブラウザ） | 収集メトリクス・送信先・実装ファイル・アプリ実装ルールを確定 | — |
| BFF（NestJS）API 性能 | 監視対象指標と検討事項のみ記載（【TBD】） | バックエンド詳細設計書（API 仕様確定後） |
| WebSocket | フロントエンド側・BFF 側で何を収集するか・実装配置を確定 | 08章（Socket.io 実装本体） |
| Node.js ランタイム / コンテナ / OS | 監視項目の概要のみ記載（収集方式・保持・アラートは委譲） | システム監視・通知サービス方式設計書 |
| エラー監視・PHI フィルタ | 監視ツールへの送信方針のみ記載 | 09章（Sentry SDK 設定・PHI フィルタ詳細） |
| 操作監査ログ | 本章では扱わない | 14章 |
| アラート通知フロー・統合監視基盤 | 接続点のみ記載 | システム監視・通知サービス方式設計書 |

## 影響

### 正の影響
* 各章のオーナーシップが明確になり、改修時の影響範囲が局所化される。
* インフラ基盤側の設定変更が本章を更新せずに完結できる。
* フロントエンド開発者が「本章で読むべき範囲」を判別しやすくなる。

### 負の影響
* 監視設計の全体像を把握するには複数文書を読む必要がある。各設計書冒頭の責任分界表と「ログ・トレース連携設計.md」の送信先一覧で緩和する。

### 見直しトリガー
* バックエンド詳細設計の確定により BFF（NestJS）監視【TBD】が解除されるタイミングで、本章の責任範囲を再評価する
* 統合監視基盤の方式（Prometheus / Grafana）が変更された場合
* 09章・14章との責務重複が運用上の混乱を招いた場合
