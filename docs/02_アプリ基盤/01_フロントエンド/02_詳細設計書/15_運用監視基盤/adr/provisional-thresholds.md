# ADR-4: 異常判定閾値を暫定値として運用し、負荷試験・ベースライン測定で更新する

* **ステータス**: Accepted
* **決定日**: 2026-05-25
* **関連設計書**: [監視指標カタログ.md](../監視指標カタログ.md), [WebSocket監視設計.md](../WebSocket監視設計.md) §2
* **関連 ADR**: なし

## 背景

詳細設計フェーズでは、以下の理由で正確な異常判定閾値を確定できない:

* システムの利用規模（テナント数・同時接続ユーザー数・1日あたりトランザクション量）が確定していない
* 院内 LAN・拠点間ネットワークの実測値が無い
* 負荷試験・本番ベースライン測定が未実施

しかし、設計書段階で閾値の枠組みすら無いと、実装フェーズで以下の問題が生じる:

* アラート設定の実装方針が立たない
* レビュー時に「閾値が暫定か確定か」の区別が付かず、誤った値が固定化される
* 後から閾値だけ更新しようとしたときに、根拠不明な値が放置される

Core Web Vitals（LCP / FID / INP / CLS）は Google 公開の業界基準が存在するため例外的に確定値で記載できるが、システム規模依存の指標（WebSocket 接続数・接続イベント頻度・再接続試行回数等）は暫定で運用するしかない。

## 検討した選択肢

### 案A: 閾値を確定するまで本章を保留にする
* **メリット**: 値の正確性が担保される。
* **デメリット**: 設計→実装→運用までの間、監視設計が空白になる。実装段階で各担当者が独自閾値を設定するリスクが高い。

### 案B: 閾値を「TBD」として空欄で残す
* **メリット**: 暫定であることが明確。
* **デメリット**: アラート設定の参考値が無く、実装が進まない。

### 案C: 暫定値として記載し、暫定であることを明示・更新トリガーを定める
* **メリット**: 実装と運用が並行で進む。負荷試験結果・ベースライン測定値で更新する運用フローを最初から組み込める。
* **デメリット**: 暫定値が一人歩きするリスクがある。各設計書で「※ 暫定値」表記を必ず併記し、更新責任者を運用ルールに含めることで緩和する。

## 決定

**案C を採用する**。

* 業界基準が存在する指標（Core Web Vitals）は確定値として記載する
* システム規模依存の指標（WebSocket 接続数・テナント別接続数・各種イベント頻度・接続確立時間等）は暫定値として記載し、各値に「※ 暫定値」「※1 規模依存のため負荷試験後に決定」「※2 暫定値であり今後の設計段階に応じて変更する可能性」のいずれかを明示する
* 暫定値の更新トリガーを以下に定める:
  * 負荷試験完了時
  * 本番運用開始から 1〜3ヶ月後のベースライン測定完了時
  * 利用規模（テナント数・同時接続数）が当初想定から大幅に変動した時
* 更新時は本章の該当値を更新し、更新日と根拠（負荷試験結果ID・測定レポートID）を運用記録として残す

## 影響

### 正の影響
* 実装と運用が設計確定を待たずに進められる
* 暫定値の存在と更新トリガーが明文化されるため、放置リスクが低減する

### 負の影響
* 暫定値が初期段階のアラート発報パターンを規定するため、負荷試験前の数週間は誤検知・見逃しが起こり得る。重大事象は別途エラー監視（09章）で 100% 捕捉される設計のため許容する。

### 見直しトリガー
* 負荷試験完了後、暫定値を本値に更新する作業を実施するタイミング
* 本番運用 3ヶ月後のベースライン測定後、SLO の妥当性を再評価する
