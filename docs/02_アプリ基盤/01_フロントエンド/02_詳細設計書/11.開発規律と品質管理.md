# 開発規律と品質管理

## 本章の範囲

本章では、プロジェクト全体のコード品質を一定以上に保ち、開発者間の実装スタイルのばらつきを抑えるための規律と、それを支える自動化基盤について定義する。

**本章の対象範囲**:
- コード自動整形（Prettier）による可読性の統一
- 隔離開発環境（Storybook）によるコンポーネント品質担保
- 品質ゲートとマージ基準

**他章との関係**:
- **TypeScript・ESLintの詳細設定** → [02.開発環境.md](./02.開発環境.md) で定義
- **テストコードの書き方** → [12.自動テスト実装.md](./12.自動テスト実装.md) で定義

## Prettier による自動整形

静的解析（ESLint）が「コードの正しさ」をチェックするのに対し、Prettierは「コードの見た目」を機械的に統一する。これにより、レビュー時に本質的ではないスタイルの差分（スペースの数や改行位置など）を排除する。

### 当プロジェクトでは以下の2つの Prettier を使用する

#### ① npm prettier（プロジェクトローカル）

**必要な理由**:

| 理由 | 説明 |
| --- | --- |
| **チーム全体で統一されたバージョンを使用** | メンバー間でPrettierのバージョンが異なり、整形結果が異なる問題を防ぐ。`package.json`でバージョンを固定し、全員が同じルールで整形する。 |
| **CI/CDで実行可能** | プルリクエスト時に自動的に `npx prettier --check .` を実行し、整形チェックを品質ゲートとして機能させる。 |
| **コマンドライン実行** | 一括整形（`npx prettier --write .`）や、huskyフックでのコミット前自動整形が可能になる。 |
| **プロジェクトの設定管理** | リポジトリに含まれる `.prettierrc` の統一ルールを全員が使用できる。 |

#### ② VSCode拡張機能

**必要な理由**:

| 理由 | 説明 |
| --- | --- |
| **開発体験の向上** | 保存時に自動整形されるため、手動でコマンドを実行する必要がない。 |
| **リアルタイムフォーマット** | エディタ内で即座に整形結果を確認できる。 |

**重要**: VSCode拡張機能は、内部的に**プロジェクトの `node_modules/prettier`** とその設定（`.prettierrc`）を優先的に使用します。つまり、拡張機能は「VSCode内でPrettierを呼び出すUI」の役割を果たし、実際の整形処理はnpm prettierが行います。

#### 両方が必要な理由

```
【動作フロー】
1. npm install -D prettier         ← プロジェクトにPrettierをインストール
2. .prettierrc を作成             ← 整形ルールを定義
3. VSCode拡張機能をインストール    ← エディタUIを追加
   ↓
4. ファイル保存（VSCode内）
   ↓
5. VSCode拡張機能が node_modules/prettier を呼び出す
   ↓
6. .prettierrc のルールで整形
```

**片方だけの場合の問題**:

| パターン | 問題点 |
| --- | --- |
| **npm prettierのみ** | 保存時自動整形ができず、毎回 `npx prettier --write <file>` を手動実行する必要があり、開発効率が悪い。 |
| **VSCode拡張機能のみ** | 拡張機能内蔵のバージョンを使用するため、チームメンバー間でバージョンが異なる可能性がある。また、CI/CDで実行できない。 |

### 自動整形の目的

| 目的 | 効果 |
| --- | --- |
| **スタイルの統一** | 誰が書いても同じ見た目のコードになり、可読性が向上する。 |
| **レビュー効率化** | スタイルに関する指摘がなくなり、設計やロジックに集中できる。 |
| **マージコンフリクトの削減** | スペースや改行の違いによるコンフリクトが発生しにくくなる。 |

### 整形ルールの定義

プロジェクトルートの `.prettierrc` に定義された以下のルールを、すべてのソースコード（`.ts`, `.tsx`, `.json`, `.css` 等）に強制適用する。

**基本設定例**:
```json
{
  "semi": true,
  "singleQuote": true,
  "tabWidth": 2,
  "trailingComma": "all",
  "printWidth": 100
}
```

| 設定項目 | 値 | 説明 |
| --- | --- | --- |
| `semi` | `true` | 文末に必ず `;` を付与し、解釈の曖昧さを排除する。 |
| `singleQuote` | `true` | 文字列引用符を `'` に統一し、ダブルクォートの使用を制限する。 |
| `tabWidth` | `2` | インデントはスペース2つ分を標準とし、深い階層でも視認性を維持する。 |
| `trailingComma` | `all` | 配列・オブジェクト・関数引数の末尾カンマを可能な限り付与する。**【採用理由】** `es5`（関数引数には末尾カンマを付けない）と比較検討した結果、`all`を採用。プロジェクトは最新のTypeScript・React環境であり、全てのモダンブラウザはES2017以降をサポート済み。`all`により、新しい項目追加時のGit diffが綺麗になり（変更行が1行のみ）、レビューやマージコンフリクト解決が容易になる。 |
| `printWidth` | `100` | 1行の最大文字数を100文字に制限し、横スクロールを防ぐ。 |

### 設定ファイルの管理体制

Prettierに関連する設定ファイルは、**基盤チーム**が作成・管理する。アプリ実装チームは、これらのファイルを直接修正せず、変更が必要な場合は基盤チームに相談すること。

**基盤チームが管理する設定ファイル**:

| ファイル名 | 説明 | 配置場所 |
| --- | --- | --- |
| `.prettierrc` | Prettierの整形ルール定義（semi、singleQuote、trailingComma等） | `frontend/`、`bff/` のプロジェクトルート |
| `.prettierignore` | 整形対象外ファイル・ディレクトリの定義（node_modules、build等） | `frontend/`、`bff/` のプロジェクトルート |
| `.vscode/settings.json` | VSCodeの保存時自動整形設定（editor.formatOnSave等） | `frontend/.vscode/`、`bff/.vscode/` |

### 開発時の実行フロー

開発効率を最大化するため、以下の2段階で整形を実行する。

#### ① 保存時の自動実行（推奨）

VSCodeの設定（`editor.formatOnSave: true`）を有効化し、ファイル保存のたびに自動的に整形を完了させる。

**VSCode設定例（`.vscode/settings.json`）**:
```json
{
  "editor.formatOnSave": true,
  "editor.defaultFormatter": "esbenp.prettier-vscode",
  "[typescript]": {
    "editor.defaultFormatter": "esbenp.prettier-vscode"
  },
  "[typescriptreact]": {
    "editor.defaultFormatter": "esbenp.prettier-vscode"
  }
}
```

#### ② CI/CDおよびコマンドによる品質ゲート (TODO)

コード品質を一定に保つため、CI/CDパイプラインでのコマンド実行により、スタイルの乱れたコードがリポジトリに混入することを強制的に防止する。

* CIでの自動チェック（必須）：
  * プルリクエスト（PR）作成時に、CI上で自動的に整形チェックを実行する。
  * 整形チェックに失敗した場合はマージを不可とする品質ゲートとして機能させる。

* ローカルでの実行（任意）：
  * 開発者はコミット前やプッシュ前に以下のコマンドを実行し、スタイルを修正する
  * 今後、husky 等を用いたコミット直前の自動整形フックの導入も検討する

**チェック・整形コマンド**:
```bash
# 整形が必要なファイルを検出（エラーで終了）
npx prettier --check .

# 整形を実行（ファイルを上書き）
npx prettier --write .
```

**今後の自動化方針**:
- 本コマンドをCI/CDパイプライン（GitHub Actions等）に組み込み、プルリクエスト時に自動的に整形チェックを実行する仕組みを構築予定
- 整形チェックに失敗した場合は、マージを不可とする品質ゲートとして機能させる

### 整形効果の例

**整形前のコード例**:
```typescript
// 違反例：スペースの乱立、ダブルダブルクォートの使用
const rawData = { id: 100 };
const   uglyCode  =  "test" ;
```

**整形後のコード例**:
```typescript
// Prettier適用後：規約通りに自動修正
const rawData = { id: 100 };
const uglyCode = 'test';
```

**実行コマンド**:
```bash
# 特定のファイルをプロジェクト規約に従って上書き整形
npx prettier --write src/app/sample/sample.tsx
```

バラバラだったスペースの乱立や、ダブルクォート・シングルクォートの混在が、`.prettierrc` の設定に基づき一瞬で整理される。

### 実装ルール

**やっていいこと**:
- 保存時の自動整形を有効化する
- コミット前に `npx prettier --check .` でチェックする
- 特定のファイルやディレクトリを `.prettierignore` で除外する

**やってはいけないこと**:
- Prettierの整形結果を手動で上書きする（再保存で元に戻る）
- プロジェクト共通の `.prettierrc` を個人の好みで変更する
- 整形チェックをスキップしてコミットする

## Storybook による隔離開発環境【今後詳細定義予定】

### Storybook の位置づけ

UIコンポーネントのカタログ化および単体確認を可能にするツールとして、Storybookを導入予定。

**Storybookの役割**:

| 役割 | 説明 |
| --- | --- |
| **コンポーネントカタログ** | 全UIコンポーネントの状態（Props）を一覧化し、デザインシステムを可視化する。 |
| **隔離開発環境** | アプリケーションのロジックやデータから切り離し、コンポーネントの全状態を容易に再現・検証できる。 |
| **ビジュアルリグレッションテスト** | Chromatic等と連携し、CSS修正等による思わぬ画面崩れを早期に検出する。 |
| **ドキュメント基盤** | Propsの自動ドキュメント化やインタラクティブな編集が可能で、デザインチームとの共有が容易。 |

### 今後の定義事項

本章の執筆時点では、Storybookの詳細仕様は未定義である。以下の事項を設計フェーズで定義し、本章を更新する。

**定義が必要な項目**:
- Story 作成規約（ファイル配置、命名規則）
- 基本的な Story の構造（Args による Props のカスタマイズ）
- Decorator によるコンテキスト再現（グローバルスタイル、テーマプロバイダー、React Query / Zustand のモック化）
- Storybook Test Runner との連携（Play function によるインタラクション自動化）
- デザインレビューでの活用方法
- Story 作成の必須化と運用ルール

## 品質ゲートとマージ基準

### プルリクエストの必須条件

プルリクエスト（PR）がマージ可能となるためには、以下の条件をすべて満たす必要がある。

**注**: プルリクエストのマージ方法（マージ戦略、承認フロー等）については、別途手順書で定義されているため、そちらを参照すること → `docs/00_環境構築手順書/02_GitLab運用手順書.md`

| 条件 | 説明 |
| --- | --- |
| **静的解析の全パス** | TypeScript（型チェック）、ESLint（構文チェック）、Prettier（整形チェック）がすべてエラーなく完了すること。 |
| **自動テストの全パス** | 単体テスト、コンポーネントテスト、結合テストがすべて成功すること（詳細は `12.自動テスト実装.md` 参照）。 |
| **Storybook Story の作成** | UIコンポーネントを追加・変更した場合、対応する Story を作成すること（Storybook導入後）。 |
| **レビュー承認** | 最低1名以上のレビュアーから承認（Approve）を得ること。 |

### マージ不可の条件

以下のいずれかに該当する場合、マージは不可とする。

| 条件 | 説明 |
| --- | --- |
| **ビルドエラー** | `npm run build` が失敗する場合。 |
| **型エラー** | TypeScriptの型チェック（`tsc --noEmit`）が失敗する場合。 |
| **Lint エラー** | ESLintで `error` レベルのエラーが検出された場合（`warning` はマージ可能だが、早急に修正すべき）。 |
| **テスト失敗** | 自動テストのいずれかが失敗した場合。 |
| **レビュー未承認** | レビュアーからの承認が得られていない場合。 |
