## 監視対象範囲と監視指標

本セクションでは、システム全体の監視対象範囲を俯瞰し、各コンポーネントで何を、どこで、なぜ監視するのかを明確にする。また、後続の各セクション（フロントエンド性能監視、WebSocket監視等）で共通して使用する監視指標の定義を行う。

### 監視対象コンポーネント

本システムの監視対象範囲を以下の4つに分類する。

| コンポーネント | 監視の主目的 | 監視データの収集先 | 収集方法 |
|---|---|---|---|
| **フロントエンド（ブラウザ）** | ユーザー体験（UX）の定量化、性能劣化の早期検知 | Sentry Performance（※） | ブラウザ上のJavaScriptで収集 |
| **BFF（NestJS）** | API応答時間、リクエスト数、エラー率の把握 | Sentry Performance（※）、Prometheus | NestJSインターセプター、ミドルウェア |
| **WebSocket接続** | リアルタイム通信基盤の健全性、接続異常の早期検知 | フロントエンド: Sentry Performance（※）<br>BFF: Prometheus | クライアント・サーバー両面で収集 |
| **インフラ層（Node.js ランタイム）** | システムリソース（CPU、メモリ）、コンテナ状態 | Prometheus、cAdvisor、Grafana | node-exporter、cAdvisor |

**注**: ※ 現時点ではSentryを仮採用しているが、ツールが変更された場合でも、本章で定義する基本的な考え方（性能メトリクスの収集、環境別分析、PHI保護）は変わらない。

**責任分担**: インフラ層の監視詳細は `システム監視・通知サービス方式設計書` で定義される統合監視基盤（Prometheus / Grafana）を参照のこと。

### 統一的な監視指標

本システムで収集・監視する指標を、**監視の目的別**に4つのカテゴリに分類する。

**重要**: 本セクションで定義する指標値（目標値、異常判定基準）は暫定値である。今後の設計段階（負荷試験結果、運用初期のベースライン測定、方式設計書との統合）に応じて変更される可能性がある。

| カテゴリ | 目的 | 答える問い |
|---|---|---|
| **性能指標** | ユーザー体験の定量化、性能劣化の早期検知 | 「ユーザーは快適に使えているか？」 |
| **リソース指標** | システムリソース枯渇の予兆検知、スケーリング判断 | 「サーバーリソースは足りているか？」 |
| **接続指標** | リアルタイム通信基盤の健全性把握 | 「WebSocket接続は正常か？」 |
| **エラー指標** | システム異常の早期検知、障害の影響範囲特定 | 「エラーは発生していないか？」 |

#### 性能指標

**目的**: ユーザー体験の定量化、性能劣化の早期検知

| 指標 | 目標値 | 測定層 | 異常判定基準 |
|---|---|---|---|
| **LCP** (Largest Contentful Paint) | 2.5秒以内 | RUM（フロントエンド） | > 4.0秒（要改善） |
| **FID/INP** (First Input Delay / Interaction to Next Paint) | FID: 100ms以内<br>INP: 200ms以内 | RUM（フロントエンド） | FID: > 300ms<br>INP: > 500ms（要改善） |
| **CLS** (Cumulative Layout Shift) | 0.1未満 | RUM（フロントエンド） | > 0.25（要改善） |
| **TTFB** (Time to First Byte) | （補助指標） | RUM（フロントエンド）<br>サーバー側監視（BFF） | > 1.0秒（バックエンド遅延の疑い） |
| **API応答時間** (P50/P90/P99) | P50: < 200ms<br>P90: < 500ms<br>P99: < 1000ms | サーバー側監視（BFF） | P90: > 1000ms（要改善） |

**参照**: 目標値の根拠は `フロントエンド方式設計書 6.1 性能要件と目標値` を参照のこと。

#### リソース指標

**目的**: システムリソース枯渇の予兆検知、スケーリング判断

| 指標 | 異常判定基準 | 測定層 | 備考 |
|---|---|---|---|
| **メモリ使用量（Heap）** | > 80%（警告）<br>> 90%（緊急） | インフラ監視（Node.js） | Heap枯渇による OOM（Out of Memory）の予兆 |
| **メモリ使用量（RSS）** | > 90%（警告） | インフラ監視（Node.js） | コンテナのメモリ制限到達リスク |
| **CPU使用率** | > 80%（持続5分以上）（警告） | インフラ監視（Node.js） | スケーリング判断の材料 |
| **ディスクI/O** | （※） | インフラ監視（OS） | ※ 閾値は今後の設計段階で決定 |

#### 接続指標

**目的**: リアルタイム通信基盤（WebSocket）の健全性把握

| 指標 | 異常判定基準 | 測定層 | 備考 |
|---|---|---|---|
| **アクティブ接続数** | （※1） | サーバー側監視（BFF） | ※1 システム規模に応じて閾値を設定 |
| **テナント別接続数** | （※1） | サーバー側監視（BFF） | 特定テナントへの接続集中を検知 |
| **接続イベント頻度** | > 1000回/分（※2） | サーバー側監視（BFF） | 異常な接続試行の検知 |
| **切断イベント頻度** | > 500回/分（※2） | サーバー側監視（BFF） | 大量切断（ネットワーク障害の疑い） |
| **再接続試行回数** | > 5回（クライアント側）（※2） | RUM（フロントエンド） | クライアント側の接続異常 |
| **接続確立時間** | > 5秒（※2） | RUM（フロントエンド） | BFFリソース状況またはネットワーク遅延 |

**注釈**:
- ※1: アクティブ接続数・テナント別接続数の異常判定閾値は、システムの利用規模（テナント数、同時接続ユーザー数）に依存するため、今後の設計段階（負荷試験結果、運用初期のベースライン測定）に応じて決定する
- ※2: 接続・切断・再接続イベント頻度、接続確立時間の閾値は暫定値であり、今後の設計段階に応じて変更する可能性がある

#### エラー指標

**目的**: システム異常の早期検知、障害の影響範囲特定

| 指標 | 異常判定基準 | 測定層 | 備考 |
|---|---|---|---|
| **クライアント側エラー率** | > 0.5%（警告） | RUM（フロントエンド） | JavaScriptランタイムエラー、API通信エラー |
| **APIエラー率（HTTP 5xx）** | > 1%（警告） | サーバー側監視（BFF） | BFF内部エラー、バックエンドAPI障害 |
| **APIエラー率（HTTP 4xx）** | > 5%（警告） | サーバー側監視（BFF） | クライアントリクエストエラー（バリデーションエラー等） |

**参照**: エラー検知とハンドリングの詳細は `09.監視・エラーハンドリング` を参照のこと。

### 監視指標と設計の対応関係

上記で定義した統一的な監視指標は、後続の各セクションで具体的な設計に落とし込まれる。

| セクション | 使用する監視指標カテゴリ | 主な監視対象 |
|---|---|---|
| **フロントエンド（ブラウザ）監視** | 性能指標、エラー指標 | Core Web Vitals、ページロード時間、クライアント側エラー率 |
| **BFF（NestJS）監視** | 性能指標、エラー指標 | API応答時間、エラー率、キャッシュヒット率 |
| **WebSocket接続監視** | 接続指標、エラー指標 | アクティブ接続数、再接続試行回数、接続確立時間 |
| **インフラ層（Node.js ランタイム）監視** | リソース指標 | メモリ使用量、CPU使用率、ディスクI/O |
| **ログ・トレース連携** | 全カテゴリ | 監視データの送信先、参照すべき監視画面、統合監視基盤との連携 |

## フロントエンド（ブラウザ）監視

本セクションでは、「監視対象範囲と監視指標」で定義した **フロントエンド（ブラウザ）** コンポーネントの監視について、**性能指標** および **エラー指標** に基づき、具体的な実装方針を定義する。

### 監視の目的と方針

実ユーザーがブラウザ上で体感しているパフォーマンスを可視化し、開発環境では気づきにくい「画面が重い」「反応が悪い」といった事象を数値化する。

**使用ツール**: Sentry Performance 監視機能（09章で導入したSentryのPerformance機能を活用）

**重要**: 現時点では検証目的で **Sentry（外部 SaaS）** を仮採用しているが、`09.監視・エラーハンドリング` の方針内容や今後の設計方針・コスト要件次第で、無料の代替品（例：GlitchTip、ELK Stack）への変更を検討する可能性がある。ツールが変更された場合でも、本章で定義する基本的な考え方（性能メトリクスの収集、環境別分析、PHI保護）は変わらない。

**監視対象指標**: 「監視対象範囲と監視指標」セクションで定義した **性能指標**（Core Web Vitals: LCP、FID/INP、CLS、TTFB）を収集・監視する。

**Sentry設定**: `09.監視・エラーハンドリング > Sentry SDK 設定` を参照
- 初期化設定: `frontend/src/shared/plugins/sentry.client.config.ts`
- Performance機能の有効化:
  ```typescript
  Sentry.init({
    dsn: process.env.NEXT_PUBLIC_SENTRY_DSN,
    
    // Performance監視の有効化
    tracesSampleRate: process.env.NODE_ENV === 'production' ? 0.1 : 1.0,
    
    // 既存設定（09章参照）
    maxBreadcrumbs: 50,
    beforeSend: (event) => { /* PHIフィルタリング */ },
  });
  ```
- 監査情報の付与: テナントID、ユーザーID、セッション情報（09章で定義済み）

### Core Web Vitals 監視指標

「監視対象範囲と監視指標」セクションで定義した性能指標の目標値に基づき、実環境での達成状況を継続的に測定する。

| 指標 | 目標値 | 異常判定基準 | 測定対象 | 監視の観点 |
|---|---|---|---|---|
| **LCP** (Largest Contentful Paint) | 2.5秒以内 | > 4.0秒（要改善） | ダッシュボード表示、カルテ表示 | 初期ロード時のデータ取得とレンダリング速度 |
| **FID/INP** (First Input Delay / Interaction to Next Paint) | FID: 100ms以内<br>INP: 200ms以内 | FID: > 300ms<br>INP: > 500ms（要改善） | 処方入力、オーダー確定ボタン | ユーザー操作への応答性 |
| **CLS** (Cumulative Layout Shift) | 0.1未満 | > 0.25（要改善） | 動的コンテンツ読み込み | レイアウトシフトの頻度 |
| **TTFB** (Time to First Byte) | （補助指標） | > 1.0秒（バックエンド遅延の疑い） | BFFレスポンス待ち | フロント・バックエンドの境界特定 |

**参照**: 目標値の根拠は `フロントエンド方式設計書 6.1 性能要件と目標値` を参照のこと。

### 監視の主要観点

#### ① ユーザー体験（UX）の定量化

医療従事者のストレス要因となる「遅延」を数値で把握する。

- 初期表示パフォーマンス（LCP）
- 操作応答性（FID/INP）
- 画面の安定性（CLS）

#### ② 異常検知とアラート

パフォーマンスの「悪化」を早期に検知する。

- **パフォーマンス・リグレッション（退行）**: アップデート前後で特定画面の表示速度が20%以上悪化
- **低速アウトライヤーの特定**: P90（下位10%）、P99（下位1%）のユーザーが極端に遅い体験をしていないか
- **Apdexスコア**: ユーザー満足度の可視化（満足・許容・不満の割合）

#### ③ 環境・インフラ依存の切り分け

「システムが悪いのか、病院の環境が悪いのか」を特定する。

- **拠点・ネットワーク別性能**: 院内LAN（Wi-Fi）の混雑状況、プロキシサーバー経由の遅延
- **デバイス・ブラウザ別性能**: デスクトップPC、タブレット、低スペック端末のハードウェア性能差
- **フロント・バックエンドの境界特定**: TTFBとクライアント処理時間の分離

**実装方法**:
- Sentryタグによる分類: `device_type`, `browser`, `network_type`, `location`（※ Sentry利用時）
- カスタムメトリクスの送信: `Sentry.setMeasurement()`（※ Sentry利用時）

**注**: 上記はSentry利用を前提とした実装方法だが、監視ツールが変更された場合は、代替ツールのタグ機能・メトリクス送信機能を使用する。

#### ④ 医療情報保護とセキュリティ

監視データに機密情報が含まれないための保護策。

- **PII/PHIの除外**: `09.監視・エラーハンドリング > PHIフィルタリングの詳細` を参照（※ Sentry利用時の設定だが、代替ツール利用時も同様のフィルタリング方針を適用）
- **データ送信量の制御**: サンプリングレート設定により、ブラウザ負荷とコストを抑制
  - development: 100%（全トランザクションを収集）
  - staging: 50%（検証用に高頻度収集）
  - production: 10%（本番環境では統計的に有意なサンプル）

### 実装ルール

**やっていいこと**:
- Core Web Vitals を継続的に測定し、目標値を下回った場合は改善タスクを起票する
- サンプリングレートを環境別に調整する（development: 100%, production: 10%等）
- 性能監視ツールのタグ機能を活用し、環境・デバイス・拠点別の分析を行う
- 日次モニタリングで性能トレンドを確認し、劣化の予兆を早期検知する

**やってはいけないこと**:
- 全ユーザーの全セッションを100%サンプリングする（ブラウザ負荷とコスト増大）
- PHI/PII を含むデータを監視ツールに送信する（09章のフィルタリング設定を必ず適用）
- アラートを無視する、または過剰に発報させる（アラート疲れ）
- 監視データを定期的にレビューせず放置する
- 09章で定義されたSentry設定を独自に変更する（一貫性の喪失）

## WebSocket接続監視

本セクションでは、「監視対象範囲と監視指標」で定義した **WebSocket接続** コンポーネントの監視について、**接続指標** に基づき、具体的な実装方針を定義する。`08.リアルタイム通信` で定義されたSocket.io実装に基づき、BFF側・フロントエンド側の両面から監視を行う。

### 監視の目的

リアルタイム通知基盤（Socket.io）の健全性を把握し、接続異常の早期検知と原因特定を可能にする。

**監視対象指標**: 「監視対象範囲と監視指標」セクションで定義した **接続指標**（アクティブ接続数、接続イベント頻度、再接続試行回数等）を収集・監視する。

### 監視対象メトリクス

#### BFF側（サーバー側）の監視

**配置場所**: `bff/src/features/notification/notification.gateway.ts`

**収集メトリクス**:

| メトリクス | 説明 | 異常判定閾値 | 実装方法 |
|---|---|---|---|
| **アクティブ接続数** | 現在接続中のSocket数 | （※1） | `this.server.sockets.sockets.size` |
| **テナント別接続数** | テナントごとの接続数 | （※1） | Room名 `{tenantId}:*` でカウント |
| **接続イベント頻度** | 1分間あたりの接続数 | > 1000回/分（※2） | `handleConnection()` でカウント |
| **切断イベント頻度** | 1分間あたりの切断数 | > 500回/分（※2） | `handleDisconnect()` でカウント |
| **再接続イベント頻度** | 再接続試行回数 | > 100回/分（※2） | `connect` イベント発火時に前回接続IDと比較 |

**注釈**:
- ※1: アクティブ接続数・テナント別接続数の異常判定閾値は、システムの利用規模（テナント数、同時接続ユーザー数）に依存するため、今後の設計段階（負荷試験結果、運用初期のベースライン測定）に応じて決定する
- ※2: 接続・切断・再接続イベント頻度の閾値は暫定値であり、今後の設計段階に応じて変更する可能性がある

**実装イメージ**:
```typescript
// bff/src/features/notification/notification.gateway.ts
@WebSocketGateway({ namespace: 'notifications' })
export class NotificationGateway {
  private metrics = {
    activeConnections: 0,
    connectionsPerMinute: 0,
    disconnectsPerMinute: 0,
  };

  handleConnection(client: Socket) {
    this.metrics.activeConnections = this.server.sockets.sockets.size;
    this.metrics.connectionsPerMinute++;
    
    // Prometheusメトリクスとして記録
    this.prometheusService.recordConnection(this.metrics);
  }
}
```

#### フロントエンド側（クライアント側）の監視

**配置場所**: `frontend/src/shared/hooks/use-notification.ts`

**収集メトリクス**:

| メトリクス | 説明 | 異常判定閾値 | 実装方法 |
|---|---|---|---|
| **接続状態** | 接続中/切断中 | - | `socket.connected` の状態を監視 |
| **再接続試行回数** | 自動再接続の試行回数 | > 5回（※） | `connect_error` イベントでカウント |
| **接続確立時間** | 接続開始から`connect`イベント発火までの時間 | > 5秒（※） | タイムスタンプの差分 |
| **メッセージ受信数** | 受信した通知の数 | - | `message` イベントでカウント |

**注**: ※ 閾値は暫定値であり、今後の設計段階に応じて変更する可能性がある

**実装イメージ**:
```typescript
// frontend/src/shared/hooks/use-notification.ts
export function useNotification() {
  useEffect(() => {
    const socket = io(`${process.env.NEXT_PUBLIC_BFF_URL}/notifications`);
    let reconnectAttempts = 0;
    const connectionStartTime = Date.now();

    socket.on('connect', () => {
      const connectionTime = Date.now() - connectionStartTime;
      // 性能監視ツールにメトリクス送信（Sentry利用時）
      Sentry.setMeasurement('websocket_connection_time', connectionTime, 'millisecond');
    });

    socket.on('connect_error', () => {
      reconnectAttempts++;
      if (reconnectAttempts > 5) {
        // 異常として記録（Sentry利用時）
        Sentry.captureMessage('WebSocket reconnection attempts exceeded threshold', {
          level: 'warning',
          extra: { reconnectAttempts },
        });
      }
    });
  }, []);
}
```

### 異常検知とアラート

| 異常パターン | 検知条件 | 影響範囲 | 対応アクション |
|---|---|---|---|
| **大量切断** | 1分間に500回以上の切断 | テナント全体 | ネットワーク障害の可能性、インフラチーム通知 |
| **再接続ループ** | 特定クライアントが5回以上再接続試行 | 個別ユーザー | クライアント側ログ収集、JWT検証状態確認 |
| **接続確立遅延** | 接続確立に5秒以上 | 個別ユーザー | BFFリソース状況確認、ネットワーク遅延調査 |
| **メッセージ配信失敗** | Room宛メッセージ送信時にエラー | 特定ユーザー/テナント | Room参加状態の確認、BFF側ログ解析 |

**重要**: 上記の検知条件は、`システム監視・通知サービス方式設計書` に記載されている検知条件との整合性を確認中であり、今後の設計段階（負荷試験結果、運用初期のベースライン測定、方式設計書との統合）に応じて変更する可能性がある。

### 監視データの保存先

**BFF側のメトリクス**:
- Prometheus Exporter 経由で収集（`システム監視・通知サービス方式設計書` 参照）
- Grafanaダッシュボードで可視化

**フロントエンド側のメトリクス**:
- Sentry Performance 経由で収集（※ Sentry利用時）
- Sentryダッシュボードで可視化（※ Sentry利用時）
- 監視ツールが変更された場合は、代替ツールのメトリクス収集・可視化機能を使用

### 実装ルール

**やっていいこと**:
- BFF側で接続数・切断数のメトリクスを収集し、Prometheusに記録する
- フロントエンド側で再接続試行回数を監視し、閾値超過時に性能監視ツールに送信する
- 異常検知時は、該当ユーザーのログとメトリクスを突き合わせて原因を特定する

**やってはいけないこと**:
- 各クライアントの接続状態を詳細にログ記録する（PHI漏洩リスク）
- 一時的なネットワーク切断を異常として過剰にアラート発報する
- 監視メトリクス収集処理がWebSocket通信のパフォーマンスを阻害する

**監視対象指標**: 「監視対象範囲と監視指標」セクションで定義した **リソース指標**（メモリ使用量、CPU使用率、ディスクI/O）を収集・監視する。

## ログ・トレース連携

本セクションでは、前セクションで定義した監視指標の**収集先と監視画面**について、フロントエンド開発者の視点から整理する。システム全体の統合監視基盤の詳細は、`システム監視・通知サービス方式設計書` を参照のこと。

### フロントエンド監視データの送信先一覧

フロントエンド側で収集した監視データの送信先を以下に整理する。

| 監視データ種別 | 送信先 | 関連セクション |
|---|---|---|
| **Core Web Vitals**（LCP、FID/INP、CLS、TTFB） | Sentry Performance（※） | フロントエンド（ブラウザ）監視 |
| **クライアント側エラー**（JavaScriptランタイムエラー、API通信エラー） | Sentry | `09.監視・エラーハンドリング` |
| **WebSocket接続状態**（再接続試行回数、接続確立時間） | Sentry Performance（※） | WebSocket接続監視 |

**注**: ※ 現時点ではSentryを仮採用しているが、ツールが変更された場合でも、送信先が変わるのみで、収集する監視指標は変わらない。

### フロントエンド開発者が参照すべき監視画面

日常的なモニタリングおよび障害発生時に確認すべき監視画面を明記する。

#### 日常的なモニタリング

| 監視画面 | 確認内容 | アクセス方法 |
|---|---|---|
| **Sentryダッシュボード**（Performance） | フロントエンド性能（Core Web Vitals）、エラー率 | Sentry Web UI |
| **Grafanaダッシュボード**（統合監視） | システム全体の健全性（BFF性能、WebSocket接続数、リソース使用率） | 統合監視基盤（詳細は `システム監視・通知サービス方式設計書` 参照） |

#### 障害発生時の確認手順

1. **Sentryダッシュボード**で、エラー率の急増やパフォーマンス劣化を確認
2. **Grafanaダッシュボード**で、BFFリソース使用率、WebSocket接続数の異常を確認
3. エラーイベントに付与された監査情報（テナントID、ユーザーID、セッション情報）を元に、影響範囲を特定

### 統合監視基盤との連携

フロントエンド側で収集したデータが、システム全体の統合監視基盤でどう活用されるか、および以下の詳細については、`システム監視・通知サービス方式設計書` を参照のこと：

- **統合監視基盤の全体像**: Prometheus、Grafana、アラート管理の構成
- **ログ・トレースの統合**: 分散トレーシング（トレースID）によるフロントエンド・BFF・バックエンド間の連携
- **データ保存先・保持期間**: 各監視データの保存先、保持期間、バックアップ戦略
- **アラート設定・通知フロー**: 異常検知時の通知先、エスカレーション手順

### 実装ルール

**やっていいこと**:
- Sentryダッシュボードで日次モニタリングを実施し、異常を早期検知する
- 障害発生時は、SentryとGrafanaの両方を確認し、フロントエンド・BFFの両面から原因を特定する
- 統合監視基盤の詳細が必要な場合は、`システム監視・通知サービス方式設計書` を参照する

**やってはいけないこと**:
- フロントエンド側の監視データだけで障害原因を判断する（BFF側、インフラ側の状況も確認すること）
- 統合監視基盤の設定を独自に変更する（インフラチームと調整すること）

## 保守・運用フロー

本章で定義した監視データは、システム開発者による保守活動の中で継続的に活用される。「監視対象範囲と監視指標」セクションで定義した各指標（性能、リソース、接続、エラー）に基づき、日常的なモニタリングと性能劣化への対応フローを定義する。

### 日常的なモニタリング

**実施主体**: システム開発者（フロントエンド担当、BFF担当、SRE）

**実施頻度**: 日次（営業日の朝）

**確認項目**（「監視対象範囲と監視指標」で定義した指標に基づく）:
- **性能指標**: 性能監視ダッシュボード（Sentry等）での性能メトリクス確認
  - Core Web Vitals（LCP、FID/INP、CLS）が目標値を満たしているか
  - API応答時間（P90/P99）のユーザーに極端な遅延が発生していないか
- **接続指標**: WebSocket接続数の異常（大量切断、再接続ループ）
- **リソース指標**: Grafanaダッシュボードでのリソース使用状況確認（CPU、メモリ）
- **エラー指標**: クライアント側エラー率、APIエラー率が閾値を超えていないか

### 性能劣化の検知と対応

**トリガー**: アラート発報時、または定期モニタリングで異常を検知

**対応フロー**:
1. **影響範囲の特定**: 性能監視ツールのタグ機能（テナントID、デバイス、ブラウザ等）で影響範囲を絞り込み
2. **原因の仮説立て**: TTFB（バックエンド）とクライアント処理時間を比較し、ボトルネックを特定
3. **ログ解析**: 該当時間帯のBFFログ、WebSocketログを確認
4. **改善タスクの起票**: 問題を特定できた場合、Issueを起票し優先順位を設定
5. **ロールバック判断**: 直近のデプロイが原因の場合、ロールバック実施を検討

### ユーザーフィードバックとの突き合わせ

定量的なデータと定性的な意見の両方に基づき、改善優先度を判断する。

**収集方法**: フィードバックウィジェット（UserVoice、Intercom等）の組み込み

**分析方法**:
- ユーザーからの「遅い」「重い」といった報告と、該当ユーザーの性能メトリクスを突き合わせ
- 特定の画面・操作に問題が集中している場合、優先的に改善タスク化

### 実装ルール

**やっていいこと**:
- 性能劣化を検知した際は、影響範囲と原因を明確にしてIssueを起票する
- ユーザーフィードバックと監視データを突き合わせ、優先度を判断する
- 改善タスクの効果を実装後に計測し、目標達成を確認する

**やってはいけないこと**:
- 監視データだけで判断し、ユーザー体験の実態を無視する
- 改善タスクを起票せず、問題を放置する
- すべての性能問題を同時に解決しようとする（リソース分散）
