# ADR-1: ViewModel 変換は BFF 側で実施する

* **ステータス**: Accepted
* **決定日**: 2026-05-22
* **関連設計書**: [BFF設計規約.md](../BFF設計規約.md) §5、[BFF三層アーキテクチャ設計.md](../BFF三層アーキテクチャ設計.md) §4.2
* **関連 ADR**: なし

## 背景

バックエンド API は業務ドメインを表す DTO を返却するが、フロントエンドの UI ではそのままの形では描画しづらいケースが多い（敬称付与・年代算出・複数数値のサマリー化・null 値の初期化等）。これらの装飾ロジックをフロント／BFF のどちらに置くかを決める必要があった。

### 前提・制約

- マルチテナント・複数 LV3 画面が同じバックエンド API を共有する
- フロントエンドは Next.js（RSC + RCC）を採用している
- バックエンドはドメイン駆動型の REST API で、UI 都合の整形は責務外と位置付けられている

## 検討した選択肢

### 案A: フロントエンド（Component / カスタムフック）で整形する

* メリット
  * 画面ごとに自由なフォーマットを選べる
  * BFF を経由しないリソースでも同じパターンが使える
* デメリット
  * 整形ロジックが各 Component に散在する
  * 同一データに対する整形を複数画面で重複実装するリスク
  * バックエンド DTO の構造変更がフロントの広範囲に波及する

### 案B: BFF の Service 層で ViewModel に整形する（採用）

* メリット
  * フロントは描画に専念できる
  * 整形ロジックの所在が一意（Service 層）になり、テストが書きやすい
  * バックエンド DTO の構造変更は BFF のマッピング関数のみ修正すれば済む
* デメリット
  * BFF Service 層のコード量が増える
  * フロント側で「フォーマット違いの選択肢」が必要なケースは Response 型を分ける必要がある

### 案C: バックエンド API 側で UI 向け DTO を返す

* メリット
  * BFF の責務が薄くなる
* デメリット
  * バックエンドが UI 都合に引きずられ、ドメイン責務を逸脱する
  * 複数フロント（Web / モバイル等）が増えると整形分岐がバックエンドに溜まる

## 決定

**案B を採用する**。

採用理由:
- 「フロントは描画に専念」「バックエンドはドメイン責務」を維持しつつ、UI 都合の整形を一箇所に閉じ込められるレイヤーとして BFF が最適である
- 案A はフロント全体に整形コードが拡散し、変更影響を局所化できない
- 案C はバックエンドに UI 都合が逆流し、複数クライアント対応時の保守コストが高い

## 影響

正の影響:
- フロント Component が `displayName` `formattedDate` `isWarning` 等を Props で受け取るだけで描画できる
- 整形ロジックを BFF Service 層の単体テストで検証できる
- バックエンド DTO の改修影響を BFF マッピング関数に閉じられる

負の影響・トレードオフ:
- BFF Service 層のコード量が増える（特に画面ごとに表示形式が大きく異なる場合）
- 同一バックエンド API でもフロント要件で複数の Response 型が必要になるケースが生じる

見直しトリガー:
- フロントが別レンダリング機構（モバイルネイティブ等）を持つようになり、BFF の整形が逆に分岐源になった場合
- 整形ロジックの単体テストカバレッジが慢性的に低い場合
