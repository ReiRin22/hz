# ADR-2: NestJS カスタムデコレーターを採用しない

* **ステータス**: Accepted
* **決定日**: 2026-05-22
* **関連設計書**: [BFF設計規約.md](../BFF設計規約.md) §4、[BFF三層アーキテクチャ設計.md](../BFF三層アーキテクチャ設計.md) §2.1
* **関連 ADR**: なし

## 背景

NestJS は標準デコレーター（`@Controller` / `@Injectable` / `@Module` / `@Get` 等）に加え、開発者が独自のカスタムデコレーターを定義できる。プロジェクト内で「現在ユーザー取得」「テナント ID 抽出」等のためにカスタムデコレーターを起こすかを判断する必要があった。

## 検討した選択肢

### 案A: カスタムデコレーターを積極的に採用する

* メリット
  * Controller のメソッド宣言が短くなる（例: `@CurrentUser() user: User`）
  * 共通的なリクエスト解析処理を1箇所に集約できる
* デメリット
  * 実装ファイルが分散しやすく、新規開発者が「これは何をするのか」を追跡するコストが上がる
  * 標準で十分対応可能な処理を独自抽象化することで学習コストが二重化する
  * デコレーター内部のリフレクション処理がデバッグの障害になる場合がある

### 案B: NestJS 標準デコレーターのみを使用する（採用）

* メリット
  * NestJS 公式ドキュメントの読解とコードベースが直結する
  * 新規開発者の学習コストを下げる
  * 認証ヘッダー解析等は `AuthGuard` 内に集約済みで、追加の抽象化が不要
* デメリット
  * リクエスト解析を Controller 内で記述する必要があり、若干の重複が発生する場合がある

## 決定

**案B を採用する**。

採用理由:
- 現時点のユースケースは標準デコレーターと `AuthGuard` で十分対応可能
- 学習コストを抑えるため、独自抽象化は明確なメリットが見えるまで導入しない
- 必要が生じた場合は、本 ADR の見直しトリガーに従って再評価する

## 影響

正の影響:
- 新規参画者は NestJS 公式ドキュメントを読むだけで本プロジェクトの実装パターンを理解できる
- デコレーターのリフレクション挙動に起因するデバッグ時間を削減

負の影響・トレードオフ:
- リクエスト解析の同じパターンが Controller 内で複数箇所に現れる可能性

見直しトリガー:
- 同じリクエスト解析パターンが3箇所以上で重複し、共通化メリットが顕在化した場合
- 認証基盤確定後、トークンペイロードの抽出パターンが定着し、共通化が標準化に資する場合
