# ADR-3: 認可（権限確認）はバックエンド側のみで実施する

* **ステータス**: Accepted
* **決定日**: 2026-05-22
* **関連設計書**: [認証ガード基盤設計.md](../認証ガード基盤設計.md) §2.3
* **関連 ADR**: なし

## 背景

リクエストの正当性検証は **認証（Authentication）** と **認可（Authorization）** に分かれる。本プロジェクトでは BFF と バックエンド API の両方が認証ヘッダーを検証する位置にあるため、認可の責務をどこに置くかを判断する必要があった。

### 前提・制約

- バックエンド API はマルチテナント構造で、テナント / 部門 / ロール単位の権限を強制する
- BFF はバックエンド API のラッパーであり、データベースに直接アクセスしない
- 同一の権限ルールが複数バックエンド API で再利用される

## 検討した選択肢

### 案A: BFF と バックエンド API の両方で認可を実施する

* メリット
  * BFF 段階で不正リクエストを早期遮断できる
  * フロントから直接バックエンドにアクセスする経路がなくなる場合の二重防壁になる
* デメリット
  * 同じ認可ルールを2箇所で維持する必要がある
  * バックエンド側のルール改修時に BFF 側の更新漏れリスクが生じる
  * BFF が認可ロジックを持つことで責務が肥大化する

### 案B: 認可はバックエンド API 側のみで実施する（採用）

* メリット
  * 認可ルールがバックエンド側で一元化される（Single Source of Truth）
  * BFF はリクエスト転送と整形に集中できる
  * ルール改修時の更新漏れリスクが消える
* デメリット
  * 不正リクエストの遮断地点がバックエンドまで遅延する（ただし全リクエストはBFF経由のため、テナント横断アクセスは `X-Tenant-Id` ヘッダー検証で BFF 段階で遮断される）

### 案C: BFF のみで認可を実施する

* メリット
  * バックエンドのコードが薄くなる
* デメリット
  * BFF をバイパスする経路（運用ツール・他クライアント等）が出現した瞬間に防壁が消える
  * バックエンドが「自分のデータが誰に開示されているか」を知らない状態は監査上望ましくない

## 決定

**案B を採用する**。

採用理由:
- 認可ルールはドメインの一部であり、ドメイン責務を持つバックエンド側に置くのが自然
- 二重実装の保守コストを避け、ルール改修時の不整合リスクを排除する
- BFF は認証（ヘッダー存在確認・テナント ID 照合）に責務を絞り、認可は通過させる

## 影響

正の影響:
- 認可ルールの所在が一意になり、改修時の影響箇所が明確
- BFF の責務がシンプルに保たれる

負の影響・トレードオフ:
- 不正リクエストの遮断地点が BFF より深いレイヤー（バックエンド）になる

見直しトリガー:
- BFF 段階で頻繁にリクエストパターン解析・遮断が必要になった場合（例: レート制限・特定経路の早期遮断要件）
- 認証基盤の選定により、JWT クレームに権限情報が乗り、BFF 段階で安価にチェックできるようになった場合
