# ADR-1: Contract-First設計とバリデーション二重化の採用

* **ステータス**: Accepted
* **決定日**: 2025-01-01
* **関連設計書**: [TypeScript型管理規約.md](../TypeScript型管理規約.md) §1、[Zodスキーマ基盤設計.md](../Zodスキーマ基盤設計.md) §1
* **関連 ADR**: なし

## 背景（Context）

フロントエンドとBFF間の API 通信において、型定義とバリデーションルールをそれぞれが独自に管理した場合、以下のリスクが生じる。

- フロントエンドとBFFで異なるバリデーションルールが適用され、ユーザーには入力できているがBFFでエラーが返る状況が生まれる
- 型定義の変更が片方にしか反映されず、実行時エラーが本番環境で発覚する
- 定義を修正するたびに両側を同期する手作業が必要になる

また、フロントエンドのバリデーションはブラウザ上で実行されるため curl 等でバイパス可能であり、BFF 側での独立した検証が必要か検討が必要だった。

## 検討した選択肢（Options）

### 案A: Contract-First（front_bff_shared による SSOT）+ バリデーション二重化（採用）

フロントエンドと BFF が共通の型定義・Zod スキーマを `front_bff_shared` から参照する。バリデーションは両側で実施するが、スキーマは 1 か所で管理する。

* メリット: 型とバリデーションルールが常に一致する。変更時は 1 ファイルのみ修正。
* デメリット: `front_bff_shared` がフロントエンドと BFF 双方の依存物になるため、変更時の影響範囲が広い。

### 案B: OpenAPI スペックによる自動生成

OpenAPI 仕様書から型を自動生成し、両側で利用する。

* メリット: REST API の標準的なアプローチ。エコシステムが豊富。
* デメリット: Zod スキーマの自動生成が煩雑で、カスタムバリデーション（`.superRefine()` 等）を表現できない。スキーマ変更のたびに生成コマンドを実行する運用コストが発生する。

### 案C: BFF のみバリデーション（フロントエンドは型チェックのみ）

BFF でのみ検証し、フロントエンドは TypeScript の型チェックのみとする。

* メリット: バリデーションの管理箇所が 1 か所になる。
* デメリット: フロントエンドでのリアルタイムフィードバックが得られないため UX が著しく低下する。React Hook Form との連携が失われる。

## 決定（Decision）

案A を採用する。

Zod スキーマを `front_bff_shared` に 1 か所定義し、フロントエンド（zodResolver 経由）と BFF（`.parse()` 経由）の両方から参照する。フロントエンドのバリデーションはブラウザ上で実行されるため curl 等でバイパス可能であり、BFF 側での検証は省略できない。同一スキーマを共有するのは「二度検証する」のではなく「ルールの乖離を防ぐため」である。

案B は、カスタムバリデーションが多く生成コードの保守コストが高い。案C は UX 要件を満たせないため除外した。

## 影響（Consequences）

**正の帰結**:
- 型定義・バリデーションルールが常に一致し、片側だけ変更する漏れが構造的に防止される
- `z.infer<typeof schema>` により型の手書き定義が不要になる

**負の帰結**:
- `front_bff_shared` の変更がフロントエンドと BFF の両方に影響するため、API インターフェース変更時は両側の動作確認が必要
- `front_bff_shared` をシンボリックリンク経由で参照する開発環境セットアップが必要

**見直しトリガー**:
- フロントエンドと BFF が別リポジトリに分離される場合
- tRPC や GraphQL 等の採用を検討する場合
