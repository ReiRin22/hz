# DB・エンティティ設計

本章では、カルテドメインサービスの DB 接続設定・エンティティ定義ルール・配置方針・`ApplicationDbContext` への登録手順・EF Core マイグレーション手順を定義する。DB テーブルを追加する際は必ず本章に従うこと。

---

## DB 接続設定

### コネクションプール設定方針

コネクションプールを活用し、リソース効率と性能を確保する。接続情報は環境ごとに分離する。

EF Core（Npgsql）はデフォルトでコネクションプールを有効にする。`appsettings.json` の接続文字列にプール設定を付与する。

```json
// appsettings.json（本番環境）
"ConnectionStrings": {
  "DefaultConnection": "Host=harz-db;Port=5432;Database=harz_db;Username=harz_user;Password=password;SSL Mode=Require;Maximum Pool Size=20;Minimum Pool Size=2;Connection Idle Lifetime=300"
},
"Tenants": ["tenant_a", "tenant_b"]
```

| パラメーター | 説明 | 推奨値 |
| --- | --- | --- |
| `Maximum Pool Size` | プール内の最大コネクション数 | 20（負荷に応じて調整） |
| `Minimum Pool Size` | プール内の常時維持コネクション数 | 2 |
| `Connection Idle Lifetime` | アイドル接続を破棄するまでの秒数 | 300 |
| `SSL Mode` | TLS 接続モード | 本番: `Require`、開発: `Disable` |

開発環境では `SSL Mode=Disable` とし、プール設定は省略可。

### 環境ごとの接続情報分離

接続文字列は環境変数で上書きする。コンテナ起動時に環境変数 `ConnectionStrings__DefaultConnection` を設定することで `appsettings.json` の値を上書きできる。

```yaml
# docker-compose.yml（開発環境）
environment:
  - ConnectionStrings__DefaultConnection=Host=db;Port=5432;Database=harz_db;Username=harz_user;Password=password;SSL Mode=Disable
  - Tenants__0=tenant_a
  - Tenants__1=tenant_b
# 本番環境はシークレット管理基盤（Vault 等）から注入
```

パスワードをコードリポジトリに含めてはならない。本番環境の接続情報は CI/CD パイプラインのシークレット変数またはコンテナオーケストレーション基盤の Secret から注入する。

### Program.cs での DbContext 登録

```csharp
builder.Services.AddDbContext<ApplicationDbContext>(options =>
    options.UseNpgsql(
        builder.Configuration.GetConnectionString("DefaultConnection"),
        npgsqlOptions => npgsqlOptions.EnableRetryOnFailure(maxRetryCount: 3)
    )
    .AddInterceptors(new TenantSchemaInterceptor(tenantService))
);
```

`EnableRetryOnFailure(maxRetryCount: 3)` により、一時的な DB 接続障害に対して自動リトライを行う。

## EF Core マイグレーション

### マイグレーションとは

EF Core マイグレーションは、エンティティクラスの変更を DB スキーマの変更履歴として管理する仕組みである。マイグレーションを実行することで、C# のエンティティ定義と DB の実際のテーブル構造が同期される。

```
エンティティ変更
    ↓
dotnet ef migrations add {名前}   ← 差分を検出してマイグレーションファイルを生成
    ↓
Migrations/{タイムスタンプ}_{名前}.cs が自動生成される
    ↓
dotnet ef database update          ← 生成されたファイルを DB に適用（テーブル作成・変更）
```

### エンティティ追加の全手順

1. `Shared/Entities/{業務ドメイン名}/` にエンティティクラスを作成
2. `ApplicationDbContext` に `DbSet<T>` を追加
3. マイグレーションを生成・適用

```bash
# DevContainer 内（KarteDomainService/ ディレクトリで実行）

# ステップ3-1: マイグレーションファイルを生成
#   EF Core がエンティティ定義と現在の DB スキーマの差分を検出し、
#   Migrations/ フォルダに Up()/Down() メソッドを含む .cs ファイルを自動生成する
dotnet ef migrations add Add{エンティティ名}Table

# ステップ3-2: 生成されたマイグレーションを DB に適用
#   未適用のマイグレーションを順番に実行し、DB テーブルを作成・変更する
dotnet ef database update
```

### マイグレーションファイルの構造

自動生成されるマイグレーションファイルには `Up()`（適用）と `Down()`（ロールバック）が含まれる。

```csharp
// Migrations/20260301120000_AddTChiefComplaintsTable.cs
public partial class AddTChiefComplaintsTable : Migration
{
    // dotnet ef database update で実行される（テーブル作成）
    protected override void Up(MigrationBuilder migrationBuilder)
    {
        migrationBuilder.CreateTable(
            name: "TChiefComplaints",
            columns: table => new
            {
                Id = table.Column<int>(nullable: false)
                    .Annotation("Npgsql:ValueGenerationStrategy",
                        NpgsqlValueGenerationStrategy.IdentityByDefaultColumn),
                PatientId = table.Column<string>(nullable: false),
                Text = table.Column<string>(nullable: false),
                RecordedAt = table.Column<DateTime>(nullable: false)
            },
            constraints: table => table.PrimaryKey("PK_TChiefComplaints", x => x.Id));
    }

    // dotnet ef database update {前のマイグレーション名} で実行される（ロールバック）
    protected override void Down(MigrationBuilder migrationBuilder)
    {
        migrationBuilder.DropTable(name: "TChiefComplaints");
    }
}
```

### マルチテナントとマイグレーションの適用

本サービスはテナントごとにスキーマを分離するため、マイグレーションは **全テナントのスキーマに適用** する必要がある。`Program.cs` の起動時処理でテナントリストを走査して `MigrateAsync()` を呼ぶ。

テナントリストは `appsettings.json` の `Tenants` セクションで管理し、`IConfiguration` から読み込む。ハードコードしてはならない。


```csharp
// Program.cs（起動時の自動マイグレーション適用例）
using (var scope = app.Services.CreateScope())
{
    var context = scope.ServiceProvider.GetRequiredService<ApplicationDbContext>();
    // appsettings.json の "Tenants" セクションから読み込む（ハードコード禁止）
var tenants = app.Configuration.GetSection("Tenants").Get<string[]>()
    ?? throw new InvalidOperationException("appsettings.json に Tenants セクションが設定されていません。");

    foreach (var tenant in tenants)
    {
        await context.Database.ExecuteSqlRawAsync($"CREATE SCHEMA IF NOT EXISTS \"{tenant}\";");

        var connection = context.Database.GetDbConnection();
        if (connection.State != ConnectionState.Open) await connection.OpenAsync();

        using var cmd = connection.CreateCommand();
        cmd.CommandText = $"SET search_path TO \"{tenant}\";";
        await cmd.ExecuteNonQueryAsync();

        // このスキーマに未適用のマイグレーションを適用
        await context.Database.MigrateAsync();
    }
}
```

### マイグレーションファイルの管理ルール

- `Migrations/` フォルダ内の全ファイルは git に含める
- 一度 DB に適用したマイグレーションは **削除・修正しない**
- 後から変更が必要な場合は新しいマイグレーションを追加する
- ロールバックが必要な場合: `dotnet ef database update {直前のマイグレーション名}`

## エンティティの基本方針

### 配置ルール

全エンティティは `Shared/Entities/{業務ドメイン名}/` に集約する。`Features/` 配下には配置しない。

```
Shared/
  Entities/
    Sample/           ← 業務ドメイン名（例: Sample, Patient, Diagnosis）
      TChiefComplaints.cs
      TVitalInfos.cs
      TPrescriptionOrders.cs
      MBloodTypes.cs
      MRhFactors.cs
      MDrugs.cs
```

複数の業務ドメインが同じエンティティを参照するケースがあるため、`Shared/` に集約することで循環参照を避ける。

### 命名規則

| 種別 | プレフィックス | 例 |
| --- | --- | --- |
| トランザクションテーブル（患者ごとに記録が積み上がるデータ） | `T` | `TChiefComplaints`、`TVitalInfos`、`TPrescriptionOrders` |
| マスタテーブル（選択肢・固定データ） | `M` | `MBloodTypes`、`MRhFactors`、`MDrugs` |
| ビュー（複数テーブルを結合した読み取り専用） | `V` | `VPatientSummaries`、`VDiagnosisHistory` |

クラス名は **複数形**（テーブル名と一致させる）。

## エンティティの設定方法

### Data Annotations の使用

EF Core の設定は **Data Annotations（属性）** をエンティティクラスに直接記述する。`IEntityTypeConfiguration<T>` は使用しない。

Fluent API（`OnModelCreating` への記述）と比較すると、Data Annotations はエンティティに制約が集まり一目でわかる点で可読性が高い。`System.ComponentModel.DataAnnotations` は .NET 標準ライブラリであり EF Core への結合も低い。複合インデックス・継承マッピング等、Data Annotations で表現できない設定が増えてきた場合は Fluent API への移行を検討する。

```csharp
using System.ComponentModel.DataAnnotations;

public class TChiefComplaints
{
    /// <summary>サロゲートキー（DB自動採番）</summary>
    public int Id { get; set; }

    [Required] public string PatientId { get; set; } = string.Empty;

    /// <summary>主訴・所見テキスト</summary>
    [Required] public string Text { get; set; } = string.Empty;

    /// <summary>記録日時（UTC）。最新レコード取得の基準として使用する。</summary>
    public DateTime RecordedAt { get; set; } = DateTime.UtcNow;
}
```

#### よく使う Data Annotations

| アノテーション | 用途 |
| --- | --- |
| `[Required]` | NOT NULL 制約。string 型は必ず付ける（Nullable 有効化のため） |
| `[MaxLength(n)]` | VARCHAR(n) の桁数制限 |
| `[Key]` | 主キー（`Id` という名前なら省略可） |
| `[ForeignKey("列名")]` | 外部キー列の指定 |
| `[Column("列名")]` | DB 列名をプロパティ名と異なる名前にする場合 |
| `[Table("テーブル名")]` | DB テーブル名をクラス名と異なる名前にする場合 |

### OnModelCreating の使用方針

`ApplicationDbContext.OnModelCreating` は **Data Annotations で表現できない設定のみ** 記述する。

```csharp
// OK: string 型の FK は EF Core が自動解決できないため明示が必要
modelBuilder.Entity<TPrescriptionOrders>()
    .HasOne(e => e.Drug)
    .WithMany()
    .HasForeignKey(e => e.DrugId);

// NG: [Required] で代替できるものを OnModelCreating に書く
modelBuilder.Entity<TChiefComplaints>()
    .Property(e => e.PatientId).IsRequired();  // 禁止（[Required] を使う）
```

### ビューエンティティの定義

DB ビュー（`V` プレフィックス）はマイグレーション管理対象外のため、`OnModelCreating` で `HasNoKey()` と `ToView()` を指定する。

```csharp
// Shared/Entities/Sample/VPatientSummaries.cs
public class VPatientSummaries
{
    public string PatientId { get; set; } = string.Empty;
    public string? LatestChiefComplaint { get; set; }
    public DateTime? LastVisitedAt { get; set; }
}

// ApplicationDbContext.cs の OnModelCreating に追加
modelBuilder.Entity<VPatientSummaries>()
    .HasNoKey()
    .ToView("v_patient_summaries");  // DB上のビュー名
```

ビューエンティティは読み取り専用（INSERT/UPDATE/DELETE 不可）。DB ビュー自体の CREATE は `db_init/` の SQL で管理する。

### ナビゲーションプロパティ（外部キー参照）

```csharp
public class TPrescriptionOrders
{
    public int Id { get; set; }

    [Required] public string PatientId { get; set; } = string.Empty;

    /// <summary>薬剤マスタへの外部キー。string 型のため OnModelCreating で明示的に設定する。</summary>
    [Required] public string DrugId { get; set; } = string.Empty;

    /// <summary>ナビゲーションプロパティ。EF Core が JOIN を自動解決する。</summary>
    public MDrugs? Drug { get; set; }

    [Required] public int Quantity { get; set; }
    public DateTime OrderedAt { get; set; } = DateTime.UtcNow;
}
```

## ApplicationDbContext への DbSet 登録

エンティティを追加したら `ApplicationDbContext` に `DbSet` を追加する。

```csharp
public class ApplicationDbContext : DbContext
{
    // ── トランザクションデータ ──────────────────────────────────────────
    public DbSet<TChiefComplaints> TChiefComplaints => Set<TChiefComplaints>();
    public DbSet<TVitalInfos> TVitalInfos => Set<TVitalInfos>();
    public DbSet<TPrescriptionOrders> TPrescriptionOrders => Set<TPrescriptionOrders>();

    // ── マスタデータ ─────────────────────────────────────────────────
    public DbSet<MBloodTypes> MBloodTypes => Set<MBloodTypes>();
    public DbSet<MRhFactors> MRhFactors => Set<MRhFactors>();
    public DbSet<MDrugs> MDrugs => Set<MDrugs>();

    // ── ビュー（読み取り専用）────────────────────────────────────────
    public DbSet<VPatientSummaries> VPatientSummaries => Set<VPatientSummaries>();
}
```

`Set<T>()` 形式を使うことで、DbSet の null 許容を避けてコンパイル警告を防ぐ。

### 日時フィールドの UTC 管理

全ての日時フィールドは UTC で管理する。

```csharp
// OK
public DateTime RecordedAt { get; set; } = DateTime.UtcNow;

// NG
public DateTime RecordedAt { get; set; } = DateTime.Now;  // ローカル時刻は禁止
```

## DB データ取得/更新方針

### 論理削除 vs 物理削除

医療データは履歴・監査の観点から **論理削除（ソフトデリート）を原則** とする。
DELETE 操作は `IsDeleted` フラグを `true` にセットし、物理削除は行わない。

```csharp
// 論理削除フラグを持つエンティティの例
public class TChiefComplaints
{
    public int Id { get; set; }
    // ...
    public bool IsDeleted { get; set; } = false;
    public DateTime? DeletedAt { get; set; }
}

// 削除操作（物理削除ではなくフラグ更新）
entity.IsDeleted = true;
entity.DeletedAt = DateTime.UtcNow;
await _context.SaveChangesAsync();
```

取得クエリには必ず `.Where(x => !x.IsDeleted)` を含める。
物理削除が許容されるのは一時データ・ログ等、明示的に設計で許可された場合のみ。

### 生 SQL の使用条件

EF Core LINQ クエリを原則とし、以下の条件を満たす場合のみ生 SQL（`ExecuteSqlRaw` / `FromSqlRaw`）を使用する。

| 条件 | 例 |
|---|---|
| LINQ では表現できない複雑な集計・Window 関数 | `ROW_NUMBER()`、`PARTITION BY` を含むクエリ |
| パフォーマンス計測で LINQ 生成 SQL がボトルネックと判明した場合 | 大量レコードの集計クエリ |
| DB 固有の関数を直接呼ぶ必要がある場合 | PostgreSQL の `gen_random_uuid()` 等 |

生 SQL を使う場合はパラメータ化クエリを必ず使用する。文字列結合によるクエリ構築は禁止する（SQL インジェクション対策）。

```csharp
// OK: パラメータ化クエリ
var result = await _context.Database
    .SqlQuery<SummaryDto>($"SELECT ... WHERE patient_id = {patientId}")
    .ToListAsync();

// NG: 文字列結合（SQL インジェクション）
var sql = "SELECT ... WHERE patient_id = '" + patientId + "'";
```

### N+1 問題の回避（Include / ThenInclude）

ナビゲーションプロパティを参照するクエリでは必ず `Include()` / `ThenInclude()` で事前ロードする。
遅延ロード（Lazy Loading）は使用しない。

```csharp
// NG: ループ内でナビゲーションプロパティを参照 → N+1 発生
var orders = await _context.TPrescriptionOrders.ToListAsync();
foreach (var o in orders) { var drug = o.Drug; }  // Drug を都度クエリ

// OK: Include で一括ロード（クエリ 1 回）
var orders = await _context.TPrescriptionOrders
    .Include(o => o.Drug)
    .ToListAsync();
```

- ナビゲーションプロパティを参照する場合は必ず `Include()` を明示する
- 2 階層以上は `ThenInclude()` を使う
- 不要な関連エンティティは `Include()` しない（無駄な JOIN を防ぐ）

### 排他制御

**現フェーズの方針**: 楽観的ロック（`[Timestamp]` / `RowVersion`）で対応する。
同時更新の衝突を検知し `DbUpdateConcurrencyException` をスローする。

```csharp
public class TChiefComplaints
{
    public int Id { get; set; }
    [Timestamp] public byte[] RowVersion { get; set; } = [];  // 楽観的ロック用
    // ...
}
// 更新時に衝突があれば DbUpdateConcurrencyException が throw される
```
