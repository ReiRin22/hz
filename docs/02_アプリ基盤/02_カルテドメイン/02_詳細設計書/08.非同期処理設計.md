# 非同期処理設計

本章では、カルテドメインサービスにおける非同期処理の設計方針と実装パターンを定義する。

**インスタンス構成**：現フェーズは**シングルインスタンス**を前提とする。
fire-and-forget はジョブをインスタンスメモリ上で実行するためマルチ構成では障害時にジョブが消滅するリスクがあり、
BackgroundService はマルチ構成では全インスタンスが同時実行して二重処理が発生する。
いずれの対策（永続キュー・分散ロック）もマイクロサービス移行フェーズで設計する（[07.マイクロサービス設計.md](07.マイクロサービス設計.md) 参照）。

---

## 1. 非同期ジョブ（例：帳票出力）

### 概要

> **注意**: 帳票出力は帳票出力サービスで実施するため、カルテドメインサービスでは現時点で非同期ジョブの具体的な用途は未定である。
> 本セクションは、カルテドメインサービスで同種の処理が必要になった際の実装パターンを示す参考例として記載する。

時間がかかる処理（生成・集計等）は、リクエストを即時受け付けて HTTP 202 を返し、バックグラウンドで処理を行うパターンを使う。
フロントは一覧画面から「更新ボタン」でステータスを手動確認する（ポーリングなし）。

### 処理フロー

```
① FE で帳票出力アクション
     ↓ POST /api/v1/reports
② BE: TReportJobs に status="processing" でレコード insert
   BE: 帳票生成をバックグラウンドで即開始（await しない）
   BE: { reportJobId, status: "processing" } を HTTP 202 で即返却
     ↓ 並行して
③ バックグラウンド処理
     帳票ファイルを生成（PDF/Excel 等）
     完了 → status="completed", file_path, completed_at を更新
     失敗 → status="failed", error_message を更新

④ FE の帳票出力一覧画面
     更新ボタン押下 → GET /api/v1/reports
     status="completed" の行でダウンロードリンクを表示
     status="failed" の行でエラーメッセージを表示
```

### ステータステーブル設計（TReportJobs）

| カラム | 型 | 説明 |
| --- | --- | --- |
| `report_job_id` | UUID | ジョブID（PK） |
| `type` | VARCHAR | 帳票種別（例: `PATIENT_SUMMARY`、`PRESCRIPTION_LIST`） |
| `requested_by` | VARCHAR | 依頼ユーザーID |
| `status` | VARCHAR | `processing` / `completed` / `failed` |
| `requested_at` | TIMESTAMP | 依頼日時（UTC） |
| `completed_at` | TIMESTAMP? | 完了日時（NULL = 未完了） |
| `file_path` | VARCHAR? | 生成ファイルのパス（完了時のみ） |
| `error_message` | TEXT? | エラー内容（失敗時のみ） |

ステータス遷移：`processing` → `completed` / `failed`（戻り遷移なし）

アプリ再起動時に `processing` のまま残ったレコードは、`Program.cs` の起動処理で一括 `failed` に更新する。

### API 仕様

**POST /api/v1/reports — 帳票出力開始**

```
Request:
  { "type": "PATIENT_SUMMARY", "patientId": "..." }

Response: 202 Accepted
  { "reportJobId": "uuid", "status": "processing" }
```

**GET /api/v1/reports — 帳票出力一覧取得**

```
Response: 200 OK
[
  {
    "reportJobId": "uuid",
    "type": "PATIENT_SUMMARY",
    "status": "completed",
    "requestedAt": "2026-05-15T09:00:00Z",
    "completedAt": "2026-05-15T09:00:45Z",
    "filePath": "/reports/xxxx.pdf"
  }
]
```

### バックグラウンド処理実装方針（fire-and-forget）

`Channel` / `BackgroundService` は使わない。Controller で DB insert 後に **`_ = Task.Run(...)` で即開始**する。
リクエストスコープ（DbContext を含む）は 202 返却時点で破棄されるため、バックグラウンドタスク内で
`IServiceScopeFactory` を使って独自スコープを生成する。

```csharp
// POST /api/v1/reports
[HttpPost]
public async Task<IActionResult> CreateAsync(ReportRequest req)
{
    var jobId = Guid.NewGuid();

    // ① DB にジョブを登録する（status="processing"）
    //    → フロントはこの jobId で後から状態を確認できる
    await _service.CreateJobAsync(jobId, req);

    // ② 帳票生成を「待たずに」バックグラウンドで開始する
    //    _ = は「戻り値を捨てる」= await しないことを明示する記法
    //    この行の直後にレスポンスを返すので、フロントは待たされない
    _ = GenerateReportAsync(jobId);

    // ③ 「受け付けた」ことを示す 202 Accepted を即返す
    return Accepted(new { reportJobId = jobId, status = "processing" });
}

// バックグラウンドで動く帳票生成処理
// Controller のリクエストスコープが終わった後も動き続けるため、
// DbContext を自分で用意する必要がある（リクエストのものは使えない）
private async Task GenerateReportAsync(Guid jobId)
{
    // リクエストスコープとは別の、このタスク専用のスコープを生成する
    using var scope = _scopeFactory.CreateScope();
    var repo = scope.ServiceProvider.GetRequiredService<ReportJobRepository>();

    try
    {
        // 帳票ファイルを生成して保存先パスを返す（実装詳細は業務フェーズで設計）
        var filePath = await GenerateAsync(jobId);

        // 生成完了 → DB を status="completed" に更新
        await repo.CompleteAsync(jobId, filePath);
    }
    catch (Exception ex)
    {
        // 生成失敗 → DB を status="failed" にしてエラー内容を保存
        //            フロントの一覧画面で「失敗」と表示できる
        await repo.FailAsync(jobId, ex.Message);
        _logger.LogError(ex, "帳票生成失敗 JobId={JobId}", jobId);
    }
}
```

#### スコープ管理

| コンポーネント | ライフタイム | 取得方法 |
| --- | --- | --- |
| `ApplicationDbContext` | Scoped | `IServiceScopeFactory.CreateScope()` 経由 |
| `ReportJobRepository` | Scoped | `IServiceScopeFactory.CreateScope()` 経由 |

追加の DI 登録は不要（`IServiceScopeFactory` は標準で注入可能）。

## 2. 定期バックグラウンド処理（BackgroundService ポーリング）

「ユーザー操作なしにサーバー側で定期実行が必要な処理」に BackgroundService（`IHostedService`）を使う。
外部ライブラリ不要で、アプリケーション起動時にバックグラウンドスレッドとして常駐する。

以下の3つが本プロジェクトで発生しうる代表例。

| 処理 | 概要 |
| --- | --- |
| **外部システム連携の同期** | 検査・薬剤等の部門システムから定期的にデータを受け取り、マスタやオーダー結果を更新する |
| **期限切れデータの自動処理** | 仮予約の自動キャンセル・期限切れトークン削除など、一定時間後に状態を変更する |
| **定期レポート生成・送信** | 月次集計・日次サマリーを決まった時刻に生成し、関係者へメール送信する |

以下に「**期限切れデータの自動処理**」を実装例として示す。
パターンが同じため他の2つも同様に実装できる。

### 配置

```
Shared/
  BackgroundServices/
    ExpiredReservationCleanupService.cs   # 実装例（期限切れデータ自動処理）
```

### 実装例：期限切れ仮予約の自動キャンセル

```csharp
// Shared/BackgroundServices/ExpiredReservationCleanupService.cs
public class ExpiredReservationCleanupService : BackgroundService
{
    private readonly IServiceScopeFactory _scopeFactory;
    private readonly ILogger<ExpiredReservationCleanupService> _logger;
    private readonly TimeSpan _interval;

    public ExpiredReservationCleanupService(
        IServiceScopeFactory scopeFactory,
        ILogger<ExpiredReservationCleanupService> logger,
        IConfiguration configuration)
    {
        _scopeFactory = scopeFactory;
        _logger = logger;
        // ポーリング間隔は appsettings.json で管理（デフォルト10分）
        _interval = TimeSpan.FromMinutes(
            configuration.GetValue<int>("Cleanup:IntervalMinutes", 10));
    }

    protected override async Task ExecuteAsync(CancellationToken stoppingToken)
    {
        _logger.LogInformation("期限切れ仮予約クリーンアップ開始");

        while (!stoppingToken.IsCancellationRequested)
        {
            try
            {
                await CleanupAsync(stoppingToken);
            }
            catch (Exception ex) when (ex is not OperationCanceledException)
            {
                // 失敗してもループを継続する（サービス停止させない）
                _logger.LogError(ex, "クリーンアップ中にエラーが発生しました");
            }

            // 次の実行まで待機（アプリ停止シグナルが来たら即終了）
            await Task.Delay(_interval, stoppingToken);
        }
    }

    private async Task CleanupAsync(CancellationToken ct)
    {
        // BackgroundService は Singleton のため、Scoped な DbContext は
        // IServiceScopeFactory 経由で都度生成する（リクエストスコープとは独立）
        using var scope = _scopeFactory.CreateScope();
        var repo = scope.ServiceProvider
            .GetRequiredService<ReservationRepository>();

        // 有効期限切れ（例: 作成から24時間以上かつ status="pending"）を一括キャンセル
        var count = await repo.CancelExpiredAsync(
            expiredBefore: DateTime.UtcNow.AddHours(-24),
            ct);

        if (count > 0)
            _logger.LogInformation("{Count} 件の期限切れ仮予約をキャンセルしました", count);
    }
}
```

### DI 登録（Program.cs）

```csharp
builder.Services.AddHostedService<ExpiredReservationCleanupService>();
```

### 設定値（appsettings.json）

```json
{
  "Cleanup": {
    "IntervalMinutes": 10
  }
}
```

### スコープ管理・エラーハンドリングの共通ルール

| ルール | 内容 |
| --- | --- |
| DbContext の取得 | `IServiceScopeFactory.CreateScope()` 経由（Singleton から Scoped を直接 inject しない） |
| ループの継続 | try-catch で例外を捕捉し、ループを止めない |
| アプリ停止 | `OperationCanceledException` はキャッチせず、正常終了させる |
| ログ | エラー時は NLog ERROR レベルで出力 |
| テナント ID のログ記録 | BackgroundService は HTTP リクエストと無関係に動作するため MDLC への自動付与がされない。ログ出力時はテナント ID を必ず明示的に含めること（例: `_logger.LogError(ex, "処理失敗 TenantId={TenantId}", tenantId)`） |
