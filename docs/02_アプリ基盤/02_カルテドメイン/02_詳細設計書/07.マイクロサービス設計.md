# マイクロサービス設計

本章では、カルテドメインサービスの現フェーズにおけるモジュラーモノリス構成と、
将来のマイクロサービス移行に向けた設計方針を定義する。

---

## 1. 現フェーズ：モジュラーモノリス

### 方針

初版は **1デプロイ・1コードベースのモジュラーモノリス**として構築する。
内部をドメイン単位で論理分割し、サービス層の依存関係を疎結合に保つことで、
将来のマイクロサービス分割コストを最小化する。

### 疎結合を保つための設計要素

現時点で守るべきルールを以下に定義する。これらを守ることが将来の分割を容易にする。

| ルール | 内容 | 強制方法 |
| --- | --- | --- |
| **ドメイン間の直接参照禁止** | 異なるドメインの Repository・DbSet を直接参照しない。必要なデータはドメインサービスを介して取得する | **NetArchTest**（`dotnet test` 失敗でブロック） |
| **共有 DB テーブルの最小化** | 共有テーブルの定義基準に従い `Shared/Entities/` に配置する（詳細は下記参照） | コードレビュー |
| **インターフェース依存** | ドメイン間の呼び出しは具象クラスに直接依存せず、インターフェース経由とする（DI で差し替え可能にする） | コードレビュー |
| **循環依存の禁止** | ドメイン A が B に依存し、B が A に依存する構造を作らない | **NetArchTest**（`dotnet test` 失敗でブロック） |

#### 共有 DB テーブルの定義基準

`Shared/Entities/` に配置してよいテーブルと禁止するテーブルの基準を以下に示す。

| 区分 | 条件 | 例 |
| --- | --- | --- |
| **共有を許容** | 複数ドメインが**参照のみ**行う読み取り専用のマスタテーブル | 病名マスタ・薬品マスタ・検査項目マスタ・血液型マスタ |
| **共有を禁止** | 2つ以上のドメインが**書き込み（INSERT / UPDATE / DELETE）**を行うテーブル | — |
| **共有を禁止** | 1つのドメインが所有し、別ドメインが書き込む可能性があるテーブル | — |

書き込みが必要な場合はそのテーブルを所有するドメインの API 経由で操作し、他ドメインが直接書き込まない設計とする。
共有エンティティには所有ドメインをコメントで明記する。

```csharp
// Shared/Entities/Master/MDiseaseCodes.cs
// 所有: マスタ管理ドメイン（書き込みは MasterDomain のみ許可）
// 参照: 診療情報・看護支援ドメインからの参照は許容
public class MDiseaseCodes { ... }
```

アーキテクチャテストの実装は `product/backend/KarteDomainService.Tests/Architecture/DomainIsolationTests.cs` を参照。
`dotnet test` 実行時に違反クラスと違反内容がメッセージ付きで報告される。新しいドメインフォルダを追加してもテストコードの変更は不要（アセンブリからドメイン名を自動抽出）。

### ディレクトリ構成上の論理分割

`Features/` 配下をドメイン単位でフォルダ分割する。各フォルダが将来の独立サービスの境界線になる。

```
Features/
  診療情報/     # 診察・処方・オーダー等のカルテ情報管理
  患者情報/     # 患者登録・入退院管理
  看護支援/     # 看護記録・看護計画管理
  マスタ管理/   # 病名・薬品・検査等の固定データ管理
  認証認可/     # 認証・認可 API
  監査ログ/     # 操作履歴取得 API
```

フォルダ間の依存は上記の疎結合ルールで管理する。

### 通信方式（現フェーズ）

| 通信経路 | 方式 | 認証 |
| --- | --- | --- |
| フロントエンド → BFF → カルテドメインサービス | HTTPS（REST API） | JWT トークン（Ingress / サイドカーで検証） |
| カルテドメインサービス → 外部サービス（文書管理・電子署名等） | HTTPS（REST API）/ TLS 暗号化 | JWT トークン認証 |
| カルテドメインサービス → DB | EF Core（ORM）/ TLS 暗号化 | DB ユーザー認証 |

マルチテナント対応の詳細は [02.アーキテクチャ設計.md — マルチテナント制御](02.アーキテクチャ設計.md#マルチテナント制御) を参照。

### デプロイ構成（現フェーズ）

- モジュラーモノリスとして **1コンテナ**にデプロイ

| 環境 | 接続文字列 | TLS |
| --- | --- | --- |
| 開発環境 | `Host=db;SSL Mode=Disable` | 不要 |
| 本番環境 | シークレット管理基盤から注入 | `SSL Mode=Require` |

接続情報は環境変数 `ConnectionStrings__DefaultConnection` で上書きする。パスワードはコードリポジトリに含めない。

## 2. 将来構想：マイクロサービス化

> 本セクションは将来の移行計画の参考として記載する。現フェーズでの実装判断には影響しない。

### 分割想定ドメイン

モジュラーモノリスの `Features/` フォルダ境界をそのままサービス境界として分割する想定。

| サービス候補 | 担当業務 |
| --- | --- |
| 診療情報サービス | 診察・処方・オーダー等のカルテ情報管理 |
| 患者情報サービス | 患者登録・入退院管理 |
| 看護支援サービス | 看護記録・看護計画管理 |
| マスタ管理サービス | 病名・薬品・検査等の固定データ管理 |
| 認証認可サービス | 認証・認可 API |
| 監査ログサービス | 操作履歴取得 API |

### 移行時に検討が必要な課題

| 課題 | 内容 |
| --- | --- |
| サービス間通信 | 現在の直接呼び出しを HTTP API / メッセージキューに置き換える設計が必要 |
| 分散トランザクション | 複数サービスにまたがる書き込みの整合性保証（Saga パターン等）を設計する |
| 分散排他制御 | Redis / DB ロックテーブル等による分散ロックを設計する（現フェーズの楽観的ロックは単一サービス前提） |
| ログ集約・分散トレーシング | X-Trace-ID を使った複数サービスにまたぐログの突き合わせ基盤を整備する |
| 認証・認可の分離 | 各サービスへの JWT 検証・ABAC の適用方式を統一する |
| DB 分離 | 現在の共有 DB を各サービス専用 DB に分割するマイグレーション計画を策定する |
