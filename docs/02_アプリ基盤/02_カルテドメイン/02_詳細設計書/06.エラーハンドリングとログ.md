# エラーハンドリングとログ

本章では、カルテドメインサービスの例外処理フロー・共通エラーレスポンス仕様・ログ出力方針・NLog 設定方法を定義する。

---

## レイヤー別エラー概要

各レイヤーで発生が想定されるエラーの種類を以下に示す。

| レイヤー | エラーの概要 | エラーの種類 |
| --- | --- | --- |
| Controller | リクエスト入力に起因するエラー | 入力パラメーター不正 |
|  | 認証・認可などAPI入口でのエラー | 認証情報不備・無効トークン |
|  |  | 権限不足 |
|  |  | JSON パース失敗 |
| Service | 業務ロジックの不整合・Repository の技術例外の変換・外部 API の業務的な扱い | 業務ルール違反 |
|  |  | 対象データが存在しない |
|  |  | 状態矛盾・重複登録など |
|  |  | 外部 API 呼び出しの失敗 |
| Repository | DB/ORM の例外 | DB コネクションエラー |
|  |  | SQL/ORM 実行エラー |
|  |  | レコードが見つからない |
|  |  | DB の制約違反 |
|  |  | クエリ実行タイムアウト |
|  |  | DB コネクション確立失敗 |
|  |  | ORM → Entity の変換失敗 |

## 例外処理の設計

### 基本方針

各レイヤー（Controller / Service / Repository）で発生した例外は上位へ **伝搬** させる。伝搬時には必要に応じて例外の種類・発生箇所・リソース情報を付加して re-throw する。最終的に `ExceptionMiddleware` が一括でキャッチし、HTTP レスポンスに変換する。

```
Repository で例外発生
    ↓ 必要に応じて情報を付加して re-throw
Service
    ↓ 必要に応じて業務的な意味に変換して re-throw
Controller
    ↓ 伝搬させる（原則 try-catch しない）
ExceptionMiddleware  ← 最終キャッチ・ログ出力・HTTPレスポンス変換
```

### 各レイヤーの例外処理の責務

#### Repository

DB/ORM 例外（`DbUpdateException`・タイムアウト等）をキャッチし、**発生テーブル・操作内容** を付加して re-throw する。これにより上位レイヤーで「どのテーブル操作で失敗したか」が特定しやすくなる。

```csharp
public async Task<TChiefComplaints?> GetChiefComplaintAsync(string patientId)
{
    try
    {
        return await _context.TChiefComplaints
            .Where(x => x.PatientId == patientId)
            .OrderByDescending(x => x.RecordedAt)
            .FirstOrDefaultAsync();
    }
    catch (Exception ex)
    {
        throw new InvalidOperationException(
            $"主訴・所見の取得中にDBエラーが発生しました。PatientId={patientId}", ex);
    }
}
```

#### Service

入力バリデーションは Data Annotations（Controller の `ModelState`）が担うため、Service では行わない。Service の責務は **業務ルール違反の検知** と **Repository 例外への業務コンテキスト付加** の 2 点である。

```csharp
public async Task<TChiefComplaints?> GetChiefComplaintAsync(string patientId)
{
    _logger.LogInformation("主訴・所見を取得します。PatientId={PatientId}", patientId);

    try
    {
        return await _repository.GetChiefComplaintAsync(patientId);
    }
    catch (InvalidOperationException ex)
    {
        // Repository 例外に Service コンテキストを付加して re-throw
        throw new InvalidOperationException(
            $"主訴・所見サービスでエラーが発生しました。PatientId={patientId}", ex);
    }
}
```

#### Controller

原則として `try-catch` を書かない。`ExceptionMiddleware` に任せる。

```csharp
[HttpPost("chief-complaints")]
public async Task<IActionResult> GetChiefComplaint([FromBody] GetChiefComplaintRequest request)
{
    var result = await _service.GetChiefComplaintAsync(request.PatientId);
    if (result == null) return NotFound();
    return Ok(result);
}
```

## ExceptionMiddleware の実装

### 役割

- パイプライン全体の最外周に配置し、全例外を一元キャッチする
- `ILogger` でエラーログを出力する
- 例外を JSON 形式の統一エラーレスポンスに変換して返す

### 実装例

```csharp
using KarteDomainService.Resources;
using KarteDomainService.Shared.Exceptions;

public class ExceptionMiddleware
{
    private readonly RequestDelegate _next;
    private readonly ILogger<ExceptionMiddleware> _logger;

    public ExceptionMiddleware(RequestDelegate next, ILogger<ExceptionMiddleware> logger)
    {
        _next = next;
        _logger = logger;
    }

    public async Task InvokeAsync(HttpContext context)
    {
        try
        {
            await _next(context);
        }
        catch (Exception ex)
        {
            _logger.LogError(ex, Resources.LOG_UNEXPECTED_ERROR);
            await HandleExceptionAsync(context, ex);
        }
    }

    private static Task HandleExceptionAsync(HttpContext context, Exception exception)
    {
        // RFC 9457: Content-Type は application/problem+json
        context.Response.ContentType = "application/problem+json";

        var (type, status, title) = exception switch
        {
            ValidationException       => ("/problems/validation-error", 400, Resources.E400000),
            ArgumentException         => ("/problems/validation-error", 400, Resources.E400000),
            KeyNotFoundException      => ("/problems/not-found",        404, Resources.E404000),
            InvalidOperationException => ("/problems/conflict",         409, Resources.E409000),
            // 401/403 はここでは処理しない。
            // 認証・認可は「認証基盤連携サービス」で設計するため、
            // Ingress / サイドカーレイヤーで処理される。
            _                         => ("/problems/internal-error",   500, Resources.E500001)
        };

        context.Response.StatusCode = status;

        // 4xx: errors 必須。5xx: errors 省略
        var errors = exception switch
        {
            ValidationException ve => (object?)ve.Errors.Select(e => new
            {
                field = e.Field, code = e.Code, message = e.Message
            }),
            ArgumentException or KeyNotFoundException or InvalidOperationException => new[]
            {
                new { field = (string?)null, code = "ERROR", message = exception.Message }
            },
            _ => null
        };

        var response = new
        {
            type,
            title,
            status,
            detail   = exception.Message, // TODO: 本番環境では IHostEnvironment.IsDevelopment() で伏せること
                                          // 理由: exception.Message にはDBのテーブル名・カラム名・SQL文等が
                                          //       含まれる場合があり、本番レスポンスに出すと情報漏洩になる。
                                          // 対応: 本番デプロイ前に isDevelopment ? exception.Message : Resources.E500001 に変更する。
            instance = context.Request.Path.Value,
            traceId  = context.Items["TraceId"] as string ?? context.TraceIdentifier,
            errors
        };

        var options = new JsonSerializerOptions
        {
            DefaultIgnoreCondition = JsonIgnoreCondition.WhenWritingNull
        };

        return context.Response.WriteAsync(JsonSerializer.Serialize(response, options));
    }
}
```

### 登録順序

`Program.cs` でミドルウェアの登録順序を守ること。`ExceptionMiddleware` は **最初** に登録する。

```csharp
app.UseMiddleware<ExceptionMiddleware>();  // 最初（全例外をキャッチするため）
app.UseMiddleware<TraceIdMiddleware>();    // X-Trace-ID ヘッダーを取り出し MDLC・Items にセット
app.UseMiddleware<TenantMiddleware>();
app.UseHttpsRedirection();
app.UseAuthorization();
app.MapControllers();
```

## ミドルウェア登録順序

ミドルウェアの登録順序は重要である。リクエストは登録順に上から処理され、レスポンスは逆順（下から上）に通過する。**ExceptionMiddleware は必ず最初に登録すること。**

### 標準的な登録順序

```csharp
// Program.cs
var app = builder.Build();

// 開発環境のみ Swagger UI を有効化
if (app.Environment.IsDevelopment())
{
    app.UseSwagger();
    app.UseSwaggerUI();
}

// ミドルウェアパイプライン（この順序を厳守）
app.UseMiddleware<ExceptionMiddleware>();  // 1. 最初（全例外をキャッチ）
app.UseMiddleware<TraceIdMiddleware>();    // 2. トレース ID 取得（MDLC・Items にセット）
app.UseMiddleware<TenantMiddleware>();     // 3. テナント ID 取得
app.UseAuthentication();                   // 4. 認証
app.UseAuthorization();                    // 5. 認可
app.MapControllers();                      // 6. ルーティング

app.Run();
```

### 登録順序の理由

| 順序 | ミドルウェア | 理由 |
| --- | --- | --- |
| 1 | `ExceptionMiddleware` | 後続のミドルウェア・Controller で発生した例外をすべてキャッチする。最初に登録することで、リクエスト処理全体を `try-catch` でラップする |
| 2 | `TraceIdMiddleware` | `X-Trace-ID` ヘッダーを取り出し `HttpContext.Items["TraceId"]` と NLog MDLC にセットする。`ExceptionMiddleware` の直後に配置することでエラーレスポンスにも traceId を付与できる |
| 3 | `TenantMiddleware` | リクエストヘッダーから `X-Tenant-ID` を取得し、`TenantService` に保存する。認証処理でテナント情報が必要なため、`UseAuthentication` の前に配置する |
| 4 | `UseAuthentication` | ASP.NET Core の認証ミドルウェア。JWT トークン検証などを実施する |
| 5 | `UseAuthorization` | ASP.NET Core の認可ミドルウェア。`UseAuthentication` の後に配置する必要がある |
| 6 | `MapControllers` | ルーティング定義。最後に登録する |

### リクエスト・レスポンスの流れ

```
【リクエスト方向】
クライアント
  ↓
ExceptionMiddleware（try で囲む）
  ↓
TraceIdMiddleware（X-Trace-ID 取得 → MDLC・Items にセット）
  ↓
TenantMiddleware（テナント ID 取得）
  ↓
UseAuthentication（認証）
  ↓
UseAuthorization（認可）
  ↓
Controller

【レスポンス方向（逆順）】
Controller
  ↓
UseAuthorization
  ↓
UseAuthentication
  ↓
TenantMiddleware
  ↓
TraceIdMiddleware
  ↓
ExceptionMiddleware（例外キャッチ → JSON 変換）
  ↓
クライアント
```

### 新しいミドルウェアを追加する場合の判断基準

以下の条件を満たす場合のみミドルウェアとして追加する：

- 全 API に共通する処理である
- リクエストまたはレスポンスに対して横断的な処理を行う
- 例：リクエストログ出力、レスポンスヘッダー追加、IP アドレス検証

特定の Controller・Action のみで必要な処理は、ミドルウェアではなく `ActionFilter` または `Attribute` を使用する。

詳細な実装方法は [02.アーキテクチャ設計.md](02.アーキテクチャ設計.md) の「Middlewares 層」を参照。

## 共通エラーレスポンス仕様

### RFC 9457 準拠

エラーレスポンスは **RFC 9457（Problem Details for HTTP APIs）** に準拠する。`Content-Type` は `application/problem+json` とする。

### レスポンス JSON 構造

| フィールド | 型 | 必須 | 説明 |
| --- | --- | --- | --- |
| `type` | string | MUST | エラー種別 URI（`/problems/{種別}`）。本番・開発で固定値 |
| `title` | string | SHOULD | エラー種別の短い説明（日本語） |
| `status` | int | SHOULD | HTTP ステータスコード |
| `detail` | string | OPT | 具体的なエラー詳細。本番環境では内部情報を含めない |
| `instance` | string | OPT | エラーが発生したリクエスト URI |
| `traceId` | string | MUST | 1 BFF リクエストごとに発行するトレース ID。`HttpContext.TraceIdentifier` の値 |
| `errors` | array | 4xx 時 MUST / 5xx 時 OPT | フィールド別エラー詳細。`field`・`code`・`message` の 3 フィールドを持つ |

**バリデーションエラー（400）**:

```json
{
  "type": "/problems/validation-error",
  "title": "不正なリクエストです。",
  "status": 400,
  "detail": "入力内容に不備があります。各項目の詳細を確認してください。",
  "instance": "/api/v1/clinical-entry/vital-info",
  "traceId": "2ab1312c-aec2-4de8-a9d0-6841715ffe80",
  "errors": [
    { "field": "bloodPressure", "code": "INVALID_FORMAT", "message": "血圧は「収縮期/拡張期」の形式で入力してください。" },
    { "field": "bloodType",     "code": "REQUIRED",       "message": "血液型は必須です。" }
  ]
}
```

**サーバーエラー（500）**（`errors` は省略）:

```json
{
  "type": "/problems/internal-error",
  "title": "サーバーエラーが発生しました。管理者に連絡してください。",
  "status": 500,
  "instance": "/api/v1/clinical-entry/chief-complaints",
  "traceId": "2ab1312c-aec2-4de8-a9d0-6841715ffe80"
}
```

#### `type` URI の規則

`/problems/{エラー種別}` 形式で定義する。外部参照可能な URL ではなく、エラーコードの識別子として使用する。

| `type` | 対応する例外 | HTTP ステータス |
| --- | --- | --- |
| `/problems/validation-error` | `ValidationException`・`ArgumentException` | 400 |
| `/problems/not-found` | `KeyNotFoundException` | 404 |
| `/problems/conflict` | `InvalidOperationException` | 409 |
| `/problems/internal-error` | その他すべての例外 | 500 |

### エラーコード体系

| エラーコード | HTTP ステータス | メッセージ |
| --- | --- | --- |
| E400000 | 400 Bad Request | 不正なリクエストです。 |
| E400001 | 400 Bad Request | JSON 形式不正です。 |
| E400200 | 400 Bad Request | ステータスが「受付済み」ではないため診察開始できません。（業務ルール違反の例） |
| E401000 | 401 Unauthorized | 認証エラーです。 |
| E401001 | 401 Unauthorized | ヘッダー不正による認証エラーです。 |
| E403000 | 403 Forbidden | アクセス権がありません。 |
| E500001 | 500 Internal Server Error | システムエラーが発生しました。管理者に連絡してください。 |

### HTTP ステータスコードの使い分け

| ステータス | 返却タイミング |
| --- | --- |
| `200 OK` | GET・POST（取得系）の正常応答 |
| `201 Created` | POST（作成系）の正常応答 |
| `204 No Content` | DELETE の正常応答 |
| `400 Bad Request` | バリデーションエラー・不正なリクエスト（`ArgumentException`） |
| `401 Unauthorized` | 認証エラー |
| `403 Forbidden` | 認可エラー |
| `404 Not Found` | 対象リソースが存在しない（`KeyNotFoundException`） |
| `409 Conflict` | 業務ルール違反・重複登録（`InvalidOperationException`） |
| `500 Internal Server Error` | 予期しないサーバー内部エラー |

## ログ出力方針

### ログの種類

| 種類 | ログレベル | 出力対象 |
| --- | --- | --- |
| アクセスログ | `Information` | Service の処理開始・処理結果（正常・異常両方） |
| 警告ログ | `Warning` | リソースが見つからない・業務的に想定される異常系 |
| エラーログ | `Error` | 予期しない例外（`ExceptionMiddleware` が出力） |
| デバッグログ | `Debug` | 開発・テスト環境のみ。本番では出力しない |

### Service でのアクセスログ出力パターン

```csharp
using KarteDomainService.Resources;

public async Task<ChiefComplaintResponse?> GetChiefComplaintAsync(string patientId)
{
    _logger.LogInformation(Resources.LOG_CHIEF_COMPLAINT_GET, patientId);

    var result = await _repository.GetChiefComplaintAsync(patientId);

    if (result == null)
        _logger.LogWarning(Resources.LOG_CHIEF_COMPLAINT_NOT_FOUND, patientId);

    return result;
}
```

### 構造化ログの書き方

ログメッセージは `Resources.resx` で一元管理し、ソースコードには文字列リテラルを直接書かない（文言・ラベル管理規定に準拠）。

```csharp
// OK: Resources 参照 + プレースホルダー
_logger.LogInformation(Resources.LOG_CHIEF_COMPLAINT_GET, patientId);

// NG: 文字列リテラルの直接記述
_logger.LogInformation("主訴・所見を取得します。PatientId={PatientId}", patientId);

// NG: 文字列結合（ログ収集基盤でフィールド検索できない）
_logger.LogInformation("処理完了。PatientId=" + patientId);
```

### テナント ID のログへの付与

マルチテナント環境では全ログにテナント ID を付与する。

```csharp
_logger.LogInformation(Resources.LOG_CHIEF_COMPLAINT_GET, patientId);
// TenantId は NLog の MDLC 経由で自動付与されるため引数不要
```

## NLog の設定

### Program.cs での有効化

```csharp
// NLog の初期化（Program.cs の先頭）
var logger = LogManager.Setup().LoadConfigurationFromAppSettings().GetCurrentClassLogger();

// ロギングプロバイダーを NLog に切り替え
builder.Logging.ClearProviders();
builder.Host.UseNLog();
```

### nlog.config の基本構成

```xml
<?xml version="1.0" encoding="utf-8" ?>
<nlog xmlns="http://www.nlog-project.org/schemas/NLog.xsd">
  <targets>
    <!-- 標準出力（コンテナのログ収集基盤に転送される） -->
    <target name="console" type="Console"
            layout="${longdate}|${level:uppercase=true}|${logger}|TenantId=${mdlc:TenantId}|${message}${onexception:${newline}${exception:format=tostring}}" />
  </targets>
  <rules>
    <!-- 開発: Debug 以上を出力 -->
    <logger name="*" minlevel="Debug" writeTo="console" />
  </rules>
</nlog>
```

本番環境では `minlevel="Information"` に変更しデバッグログを抑制する。ログの出力先・保管期間は【操作・監査ログ管理サービス方式設計書】に準拠する。

### ログの標準出力設定

ログはコンテナの **標準出力（stdout）** に出力する。コンテナエンジンが標準出力を受け取り、ノード上の一時領域に JSON 形式のログファイルとして書き込み、ログ収集基盤に転送する。

nlog.config のターゲットは `type="Console"` を使用すること（ファイル出力は使用しない）。

```xml
<targets>
  <!-- type="Console" で標準出力へ出力 -->
  <target name="console" type="Console"
          layout="${longdate}|${level:uppercase=true}|TenantId=${mdlc:TenantId}|${message}${onexception:${newline}${exception:format=tostring}}" />
</targets>
```

### テナントごとのログ分離

テナント ID を全ログに付与することで、ログ収集基盤側でテナントごとにログをフィルタリング・分離できるようにする。他テナントへの情報漏洩を防止するため、**テナント ID なしのログ出力は禁止**する。

```csharp
// MDC（Mapped Diagnostic Context）にテナント ID をセット（TenantMiddleware で実施）
MappedDiagnosticsLogicalContext.Set("TenantId", tenantId);

// 以降の全ログに TenantId=${mdlc:TenantId} が自動付与される
_logger.LogInformation(Resources.LOG_CHIEF_COMPLAINT_GET, patientId);
// 出力例: 2026-04-08 10:00:00|INFO|TenantId=tenant_a|主訴・所見を取得します。PatientId=P001
```

## 自動リトライ

### リトライ対象エラー

一時的な障害（ネットワーク瞬断・外部サービスの一時停止等）は自動リトライで回復できる場合がある。以下のエラーはリトライ対象とする。

| エラー種別 | リトライ対象 | 理由 |
| --- | --- | --- |
| DB コネクションエラー（一時的） | ○ | 瞬断後に回復する可能性がある |
| クエリ実行タイムアウト | ○ | 負荷の一時的なスパイクで発生しうる |
| 外部 API 呼び出しの失敗（5xx） | ○ | 外部サービスの一時的な障害 |
| DB 制約違反（重複キー等） | × | リトライしても同じエラーが発生する |
| バリデーションエラー（4xx） | × | クライアント側の問題のため |

### リトライ実装パターン（Polly を使用）

```xml
<!-- KarteDomainService.csproj に追加 -->
<PackageReference Include="Polly" Version="8.5.2" />
```

```csharp
// Service: リトライポリシーを定義して外部 API 呼び出しに適用
private static readonly AsyncRetryPolicy RetryPolicy = Policy
    .Handle<HttpRequestException>()
    .Or<TimeoutException>()
    .WaitAndRetryAsync(
        retryCount: 3,
        sleepDurationProvider: attempt => TimeSpan.FromSeconds(Math.Pow(2, attempt - 1)),  // 指数バックオフ: 1秒・2秒・4秒
        onRetry: (exception, timespan, attempt, context) =>
        {
            // リトライ結果をログに記録
            _logger.LogWarning("リトライ {Attempt} 回目。待機: {Timespan}ms。理由: {Message}",
                attempt, timespan.TotalMilliseconds, exception.Message);
        });

// 使用例
var result = await RetryPolicy.ExecuteAsync(() => _externalApiClient.GetAsync(url));
```

#### リトライのルール

- 最大リトライ回数は **3回**（エラー種別ごとに必要に応じて調整）
- リトライ間隔は指数バックオフ（1秒・2秒・4秒）を使用してリクエスト集中を防ぐ
- リトライ結果（成功/失敗）は必ずログに記録する
- DB アクセスへのリトライは EF Core の `EnableRetryOnFailure()` を使用する

```csharp
// Program.cs: EF Core の自動リトライ設定
options.UseNpgsql(connectionString, npgsqlOptions =>
    npgsqlOptions.EnableRetryOnFailure(maxRetryCount: 3));
```
