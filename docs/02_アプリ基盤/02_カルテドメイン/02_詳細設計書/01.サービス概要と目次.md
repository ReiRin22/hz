# カルテドメインサービス サービス概要と目次

---

## サービス概要

### 目的

本サービスは、電子カルテシステムのドメイン機能に関するバックエンドサービスである。BFF 層からの要求を受け付け、カルテに関するビジネスロジックを実行し、周辺サービス（文書管理・外部システム連携など）を呼び出す。カルテドメインに関するデータベースアクセスを一元的に担い、他サービスからの直接アクセスを禁止する。

電子カルテ業務は今後の機能拡張や処理量の増加が想定されるため、本サービスはスケーラブルで高性能な構成とし、医療情報を扱うシステムとして求められるセキュリティを担保する。

### 業務スコープ

| 業務区分 | 対象業務 |
| --- | --- |
| 外来業務 | 患者管理、受付管理、診療、診療代行、オーダー管理、看護業務管理、部門連携 |
| 入院病棟業務 | 患者管理、入院管理、診療支援、オーダー管理、看護支援、栄養管理、部門連携、退院管理、情報管理 |
| その他 | マスタ管理、非機能要件対応（認証・認可 API、操作履歴取得 API 等） |

### 設計スコープ

本書が対象とする設計範囲を以下に示す。

| 区分 | 対象 |
| --- | --- |
| **対象** | カルテドメインサービス（バックエンド API）の内部アーキテクチャ・実装方針・設定 |
| **対象外** | フロントエンド、BFF（Backend for Frontend）、認証サーバー、コンテナ基盤・インフラ設計 |

カルテドメインサービスのデータベースアクセスは本サービスが一元的に担う。他サービスからデータベースへの直接アクセスは禁止する。

### 関連サービス

カルテドメインサービスが連携する外部サービスを以下に示す。各サービスとの通信は HTTPS（REST API）/ TLS 暗号化で行う。

| サービス | 連携概要 |
| --- | --- |
| アプリ通知サービス | システム監視・ユーザー通知の送受信 |
| ヘルプサイトサービス | ヘルプコンテンツの参照 |
| 文書作成・管理サービス | 診療文書の作成・保管・取得 |
| 電子署名サービス | 文書・記録への電子署名付与 |
| タイムスタンプサービス | 文書・記録へのタイムスタンプ付与 |
| 直接印刷サービス | 帳票・文書の印刷出力 |
| 部門システム連携サービス | 検査・薬剤・リハビリ等の部門システムとのデータ連携 |
| 医療DXシステム連携サービス | 外部医療DXシステムとのデータ連携 |

### マイクロサービス構成での位置づけ

カルテドメインサービスは、将来的なマイクロサービス化を見据え「モジュラモノリス」構成を採用する。内部では、以下の5つのドメインに論理分割して整理する。（詳細は [02. アーキテクチャ設計](02.アーキテクチャ設計.md) を参照）。

| 業務ドメイン | 担当業務 |
| --- | --- |
| 診療情報 | 診察・処方・オーダー等のカルテ情報管理 |
| 患者情報 | 患者登録・入退院管理 |
| 看護支援 | 看護記録・看護計画管理 |
| マスタ管理 | 病名・薬品・検査等の固定データ管理 |
| 認証認可 | 認証・認可 API |
| 監査ログ | 操作履歴取得 API |

BFF（Backend for Frontend）層からの要求を受け付け、画面に依存しない汎用的な API を提供する。バックエンド間の通信は HTTPS（REST API）/ TLS 暗号化 / JWT トークン認証で行う。

### 非機能要件の概要

| 観点 | 方針 |
| --- | --- |
| 性能 | 朝・夕のピークトラフィック時でも許容レスポンスタイムを維持。ページング・キャッシュ・クエリ最適化で対応 |
| 可用性 | 冗長構成による単一障害点の排除。無停止デプロイ |
| セキュリティ | ゼロトラスト思想。JWT 認証・ABAC 認可・TLS 暗号化。医療情報システム安全管理ガイドライン準拠 |
| スケーラビリティ | 負荷に応じたスケールアウト対応（詳細は業務要件定義フェーズで確定） |
| 運用・保守 | OpenAPI による API ドキュメント自動生成。CI/CD で静的解析・テスト・脆弱性チェック自動実行 |

### 設計方針

本システムは、保守性・拡張性・テナント分離性を確保するため、レイヤードアーキテクチャを基本とし、マルチテナント構成を前提とした設計とする。

**レイヤードアーキテクチャ方針**

プレゼンテーション層（Controller）、アプリケーション層（Service）、データアクセス層（Repository）の3層構造とする。各層の責務を明確化し、上位層から下位層への一方向依存を徹底することで、保守性・テスト容易性・再利用性を確保する。

詳細 → [02. アーキテクチャ設計](02.アーキテクチャ設計.md)

**マルチテナント方針**

本システムは複数医療機関での利用を前提とし、テナント単位でのデータ完全分離を行う。テナント識別はリクエストヘッダー（`X-Tenant-ID`）で行い、`TenantMiddleware` がヘッダーからテナント ID を取得・保持する。DB アクセス時は PostgreSQL のスキーマ分離方式でテナントごとのデータを完全に隔離する。

詳細 → [02. アーキテクチャ設計 — マルチテナント制御](02.アーキテクチャ設計.md#マルチテナント制御)

```
backend/
├─ db_init/
│  └─ init.sql                                    # 初期DBのSQL
│
└─ KarteDomainService/
   ├─ Features/                                   # 業務ごとのフォルダ。業務ドメインでサブフォルダ化する。
   │  └─ （業務ドメイン名）/                        # 例: Sample, Diagnosis など
   │     └─ （業務名）/
   │        ├─ Controllers/                       # APIの入り口。[Authorize]による認可ガードを担当。
   │        │  └─ （業務名）Controller.cs
   │        ├─ Models/                            # リクエスト・レスポンス型定義（エンティティとは分離）。
   │        │  └─ （業務名）Type.cs
   │        ├─ Repositories/                      # DB操作（データアクセス）の具体的な実装。
   │        │  └─ （業務名）Repository.cs
   │        └─ Services/                          # 複数のリポジトリを組み合わせた業務ロジック。
   │           └─ （業務名）Service.cs
   │
   ├─ Migrations/                                 # EF CoreがDBスキーマを管理する履歴。
   │  ├─ ApplicationDbContextModelSnapshot.cs     # 現在のDBスキーマの状態をスナップショットとして保持するファイル。
   │  └─ 20260219085840_InitialCreate.cs          # 最初のデータベース構築用マイグレーションスクリプト。
   │
   ├─ Properties/                                 # 起動プロファイル管理
   │  └─ launchSettings.json                      # ローカル実行時のプロファイル（ポート番号、環境変数など）。
   │
   ├─ Shared/
   │  ├─ Data/                                    # DB（SQL）の門番
   │  │  ├─ ApplicationDbContext.cs               # EF CoreにおけるDB接続の定義。全エンティティのDbSetを管理。
   │  │  └─ TenantSchemaInterceptor.cs            # マルチテナントを実現するための「自動切り替え」メカニズム。
   │  ├─ Entities/                                # DBテーブルに対応するエンティティ。業務ドメインでサブフォルダ化する。
   │  │  └─ （業務ドメイン名）/                    # 例: Sample
   │  │     ├─ T〇〇.cs                           # トランザクションテーブル（Tプレフィックス）。例: TChiefComplaints.cs
   │  │     └─ M〇〇.cs                           # マスタテーブル（Mプレフィックス）。例: MBloodTypes.cs
   │  ├─ Filters/                                # アクションフィルタ（バリデーション等の横断的前処理）
   │  │  └─ 〇〇FilterAttribute.cs
   │  ├─ Middlewares/                             # Web（HTTP）の門番
   │  │  ├─ ExceptionMiddleware.cs               # システム全体の500エラーなどを一括ハンドリング。
   │  │  ├─ TenantMiddleware.cs                  # ヘッダーからX-Tenant-IDを抜き取り保持。
   │  │  └─ 〇〇Middleware.cs
   │  └─ Services/                               # 共通ロジック（インターフェースなし・具象クラスのみ）
   │     └─ TenantService.cs                     # テナントIDをスレッドセーフに受け渡すサービス。
   │
   ├─ wwwroot/                                    # 静的ファイル（検証用の画像やHTML等）の置き場。
   │
   ├─ appsettings.json                            # 環境ごとの接続文字列およびアプリケーション設定値の管理。
   ├─ appsettings.Development.json                # デバッグ環境での設定。
   ├─ Dockerfile                                  # .NET 10 ベースのコンテナビルド定義。
   ├─ KarteDomainService.csproj                   # プロジェクト構成・パッケージ依存管理の設計図
   ├─ nlog.config                                 # ログ出力定義。
   └─ Program.cs                                  # アプリケーション起動・認証・DB・ミドルウェアの動線定義。
```

### バージョン管理方針

本プロジェクトでは、セキュリティとメンテナンス性のバランスを考慮し、以下の方針でパッケージバージョンを管理する。

| バージョン種別 | 内容 | 更新方針 | 理由 |
| --- | --- | --- | --- |
| **メジャー** | 大規模な API・動作変更 | 固定（手動更新・基盤チーム検証必須） | 破壊的変更により既存実装が動作しなくなる可能性があるため、慎重な検証が必要 |
| **マイナー** | 部分的な機能改善・機能追加 | 手動更新可（影響範囲確認後） | 後方互換性があり、バグ修正・新機能の恩恵を受ける |
| **パッチ** | バグ・セキュリティ修正 | 優先適用 | 適用しないことがリスクとなる |

`csproj` での記述方針および更新手順の詳細は `03.開発環境.md` の「NuGet パッケージ管理」を参照のこと。

### [04. API設計](04.API設計.md)

**API 設計原則**
- RESTful 設計（リソース指向・HTTP メソッドの使い分け・単一責任）
- 個人情報のプライバシー保護規約：患者 ID・氏名・生年月日等の個人情報を URL パスおよびクエリパラメーターに含めない。必ず POST Body で渡す

**URL 設計規約**
- エンドポイント命名規則：`/api/v{バージョン}/{業務ドメイン}/{リソース}`（kebab-case・複数形）
- エンドポイント例（血液型マスタ取得・主訴登録等）

**リクエスト/レスポンス形式**
- 必須ヘッダー：`X-Tenant-ID`（TenantMiddleware が検証）・`X-Trace-ID`（TraceIdMiddleware が取得）
- リクエスト Body：`record` 型・PascalCase・nullable は `?` 明示・バリデーションアノテーション付与
- 正常レスポンス形式（単一リソース / 一覧 / 作成 201 / 削除 204）
- エラーレスポンス形式：RFC 9457 準拠（`type` / `title` / `status` / `detail` / `instance` / `traceId` / `errors`）
  - 4xx エラーは `errors` 配列必須（`field` / `code` / `message`）
  - `traceId` はリクエストの `X-Trace-ID` ヘッダー値（未送信時は ASP.NET Core の TraceIdentifier）
- HTTP ステータスコードの使い分け（200 / 201 / 204 / 400 / 401 / 403 / 404 / 500）

**Controller の実装規約**
- `[ApiController]`・`[Route]`・`[ProducesResponseType]` アノテーションルール
- 禁止事項：ビジネスロジック・DB 操作を Controller に書かない

**バージョン管理方式**
- URL パスバージョニング（`/api/v1/`）
- Breaking Change 定義（フィールド削除・型変更・URL 変更・必須パラメーター追加）
- 旧バージョン廃止予告：`Deprecated` / `Sunset` レスポンスヘッダー

**Swagger UI の設定**
- 開発環境（`ASPNETCORE_ENVIRONMENT=Development`）のみ有効化
- アクセス URL：`http://localhost:7121/swagger`
