# セキュリティ設計

本章では、カルテドメインサービスにおける認証・認可・暗号化・SQLインジェクション等の脆弱性対策・APIセキュリティの設計方針を定義する。電子カルテが扱う要配慮個人情報を保護するため、アプリ実装チームは本章の方針を遵守すること。

---

## 認証・認可の方針

### 認証

カルテドメインサービス内ではユーザー認証を実装しない。認証は API Gateway およびサイドカーで実施済みとして扱う。

- フロントエンド → サイドカー間: TLS 通信 + JWT トークン検証
- サイドカー → カルテドメインサービス間: 平文 HTTP（認証済みリクエストとして受信）

カルテドメインサービスは JWT トークンを保持・検証しない。

### 認可

ABAC（属性ベースアクセス制御）方式を採用し、認可判定は専用の認可 API に委譲する。カルテドメインサービス内で認可ロジックを実装しない。

認可 API への連携パラメーターは【認証基盤連携サービス方式設計書】に準拠する。

## 暗号化方針

### 通信の暗号化

| 通信区間 | 暗号化 |
| --- | --- |
| フロントエンド ↔ サイドカー | TLS（HTTPS） |
| サイドカー ↔ カルテドメインサービス | 平文 HTTP（サイドカーが復号済み） |
| カルテドメインサービス ↔ DB | TLS/SSL（EF Core 接続オプションで設定） |

### DB 接続の TLS 設定

```json
// appsettings.json
"ConnectionStrings": {
  "DefaultConnection": "Host=harz-db;Port=5432;Database=harz_db;Username=harz_user;Password=password;SSL Mode=Require"
}
```

本番環境では `SSL Mode=Require` を付与する。開発環境では `SSL Mode=Disable` でもよい。

## 脆弱性対策

IPA「安全なウェブサイトの作り方」に準拠した対策を実施する。

### SQL インジェクション対策

- EF Core の LINQ クエリ（`.Where()`・`.Find()` 等）を原則使用する
- 複雑なクエリでやむなく生 SQL を使う場合は **プレースホルダー** を使用する
- SQL 文字列を直接組み立てることを禁止する

```csharp
// OK: EF Core LINQ
var result = await _context.TChiefComplaints
    .Where(x => x.PatientId == patientId)
    .FirstOrDefaultAsync();

// OK: やむなく生 SQL の場合はプレースホルダー
var result = await _context.Database
    .SqlQuery<SomeEntity>($"SELECT * FROM t_chief_complaints WHERE patient_id = {patientId}")
    .FirstOrDefaultAsync();

// NG: SQL 文字列直接組み立て（SQLi リスク）
var sql = $"SELECT * FROM t_chief_complaints WHERE patient_id = '{patientId}'";
```

### OS コマンドインジェクション対策

シェルを起動できる API（`Process.Start` 等）の使用を禁止する。ファイル操作は .NET 標準ライブラリ（`System.IO`）を使用する。

### ディレクトリトラバーサル対策

ファイル操作時に外部パラメーターをそのままパスに使用しない。ファイル名の検証とパス固定化を行う。

```csharp
// OK: 固定ディレクトリ + ファイル名の検証
var sanitizedFileName = Path.GetFileName(userInput);  // ディレクトリ部分を除去
var filePath = Path.Combine("/var/data/uploads", sanitizedFileName);

// NG: ユーザー入力をそのままパスに使用
var filePath = Path.Combine("/var/data", userInput);
```

### CSRF 対策

REST API は Cookie を使用しないため、CSRF リスクは低い。BFF 経由のリクエストに対する CSRF 対策は BFF 側で実施する。

### HTTP ヘッダーインジェクション対策

ヘッダー出力には ASP.NET Core のヘッダー API を使用し、改行コードを含む値を直接出力しない。

### クリックジャッキング対策

`X-Frame-Options` ヘッダーを設定して iframe 埋め込みを制限する。

```csharp
// Program.cs
app.Use(async (context, next) =>
{
    context.Response.Headers.Append("X-Frame-Options", "DENY");
    context.Response.Headers.Append("X-Content-Type-Options", "nosniff");
    await next();
});
```

## マルチテナントのデータ分離

テナントごとに PostgreSQL スキーマを分離し、テナント間のデータアクセスを物理的に遮断する。

- `TenantMiddleware` がリクエストヘッダー `X-Tenant-ID` からテナント ID を取得
- `TenantSchemaInterceptor` が DB 接続時に `SET search_path TO {tenantId}` を実行
- これにより Repository のクエリは自動的に対象テナントのスキーマのみにアクセスされる

他テナントのスキーマへのアクセスは `search_path` の制御により防止される。詳細は `01.サービス概要と目次.md` 参照。

## 個人情報の取り扱い

電子カルテが扱うデータは要配慮個人情報であるため、以下の制約を設ける。

### 患者 ID の URI 禁止

患者 ID は URL パスに含めない（POST Body で渡す）。理由はアクセスログ・ブラウザ履歴への記録リスク。詳細は `05.API設計.md` 参照。

### エラーレスポンスの情報漏洩防止

本番環境では例外の詳細（スタックトレース・SQL 等）をレスポンスに含めない。`ExceptionMiddleware` の `Detail` フィールドは開発環境のみ有効にする。

```csharp
Detail = app.Environment.IsDevelopment() ? exception.Message : null
```

## 追加脆弱性対策

### セッション管理の不備対策

REST API は Cookie を使用しないためセッション管理の多くは不要だが、JWT トークンを扱う箇所では以下を遵守する。

- セッション ID / トークンを URL パラメーターに格納しない（ヘッダーのみで伝達）
- HTTPS 通信で使用する Cookie には `Secure` 属性を付与する
- トークンには有効期限を設け、期限切れ後は無効化する

カルテドメインサービスはトークンを保持しない（サイドカーが検証済み）。セッション管理の実装は BFF 側で行う。

### メールヘッダーインジェクション対策

カルテドメインサービスがメール送信機能を持つ場合は以下を遵守する。

- メールヘッダーを固定値にし、外部からの入力はすべてメール本文に出力する
- メールヘッダーを固定値にできない場合、.NET 標準の `SmtpClient` や `MailKit` 等のメール送信 API を使用する
- 外部からの入力に含まれる改行コード（`\r\n`）を削除・エスケープする

```csharp
// NG: 改行コードを含む入力をそのままヘッダーに設定する可能性がある
message.Subject = userInput;

// OK: 改行コードを除去してから設定
message.Subject = userInput.Replace("\r", "").Replace("\n", "");
```

### バッファオーバーフロー対策

.NET はマネージドランタイムのため、直接メモリアクセスによるバッファオーバーフローリスクは低い。ただし以下を遵守する。

- `unsafe` コードブロックの使用を禁止する
- P/Invoke（ネイティブ DLL 呼び出し）を使用する場合は最小限に留め、入力値を厳格にバリデーションする
- NuGet パッケージは定期的にセキュリティアップデートを適用し、脆弱性が修正されたバージョンを使用する（`dotnet list package --vulnerable` で確認）

## APIセキュリティ

### WAF/WAAP 方針

- リリース時点は WAF により基本的な Web/API 攻撃対策を実施する
- API 利用状況・運用負荷を確認した上で、必要に応じて WAAP への移行を検討する
