# アーキテクチャ設計

本章では、カルテドメインサービスのディレクトリ構成・レイヤー構成・各レイヤーの責務・実装パターン・共有基盤（Shared/）の設計を定義する。新機能を追加する際はこの章を参照し、どこに何を書くか、どのレイヤーに何を配置するかを判断する。

---

## アーキテクチャ方針（モジュラーモノリス）

現構成は、患者・オーダー・診察記録といった業務ごとに **ソリューションを分けておらず、デプロイ単位も 1 つ**である。これはマイクロサービスではなく、**モジュラーモノリス**に分類される。

マイクロサービスへの移行は技術的・運用的なハードルが高いため、当面はモノリスとして開発する。ただし、将来的な業務ドメイン分割を見越して、業務ドメイン間の**疎結合**を設計段階から意識する。

| 方針 | 内容 |
| --- | --- |
| 現在 | モジュラーモノリス。1 デプロイ・1 コードベース |
| 将来 | 業務量・チーム規模に応じて段階的に業務ドメイン分割（診療情報・患者情報・看護支援・マスタ管理等） |
| 疎結合の担保 | `Features/` 配下の業務ドメインを独立したモジュールとして扱い、モジュール間の直接参照を禁止する |

---

## ディレクトリ構成

### Features/ 配下の業務ドメイン別フォルダ構成

業務ドメインは `Features/` 配下に業務ドメイン別にフォルダを作成する。

```
Features/
  {業務ドメイン名}/        ← 例: ClinicalEntry, Master, Patient
    {業務名}/             ← 例: ChiefComplaint, VitalInfo
      Controllers/
        {業務名}Controller.cs
      Models/
        {業務名}Models.cs
      Repositories/
        {業務名}Repository.cs
      Services/
        {業務名}Service.cs
```

**業務ドメインの例:**
- `ClinicalEntry` — 診療記録関連（主訴・所見、バイタル、処方等）
- `Patient` — 患者情報関連
- `Master` — マスタデータ管理（血液型、Rh因子、薬品等）

### Shared/ 配下の共通基盤コンポーネント配置

複数の業務ドメインから横断的に参照される共通コンポーネントを `Shared/` 配下に配置する。

```
Shared/
  Data/                   # ApplicationDbContext, TenantSchemaInterceptor
  Entities/               # 全エンティティ（業務ドメイン別サブフォルダ）
    {業務ドメイン名}/
      TXxx.cs             # トランザクションテーブル
      MXxx.cs             # マスタテーブル
      VXxx.cs             # ビュー
  Exceptions/             # ValidationException など共通例外クラス
  Filters/                # ValidationFilterAttribute など共通 ActionFilter
    {業務ドメイン名}/      # 業務固有フィルターはサブフォルダに配置
  Middlewares/            # ExceptionMiddleware, TraceIdMiddleware, TenantMiddleware
  Services/               # TenantService
```

**詳細:**
- **Data層:** [04.DB・エンティティ設計.md](04.DB・エンティティ設計.md)
- **Entities層:** [04.DB・エンティティ設計.md](04.DB・エンティティ設計.md)
- **Filters層:** 本章の「Filters 層」
- **Middlewares層:** 本章の「Middlewares 層」
- **Services層:** 本章の「マルチテナント制御」

### エンティティ・ミドルウェア・サービスの配置ルール

| コンポーネント | 配置場所 | 配置基準 |
| --- | --- | --- |
| エンティティ | `Shared/Entities/{業務ドメイン名}/` | 全エンティティを集約（DbContext が一元管理） |
| ミドルウェア | `Shared/Middlewares/` | リクエストパイプラインに横断的処理を挿入（全 API 共通） |
| フィルター（共通） | `Shared/Filters/` | 複数 Feature で再利用する ActionFilter |
| フィルター（業務固有） | `Shared/Filters/{業務ドメイン名}/` | 特定の業務ドメインにのみ使用する ActionFilter |
| 共有サービス | `Shared/Services/` | 業務固有ロジックを持たず、複数 Feature から参照される |
| 業務サービス | `Features/{業務ドメイン名}/{業務名}/Services/` | 業務固有ロジックを含む |

## レイヤー構成と責務分離

### Controller / Service / Repository の3層構成

```
HTTP リクエスト
      ↓
┌──────────────────────────────────────┐
│         Middleware パイプライン          │  ExceptionMiddleware / TraceIdMiddleware / TenantMiddleware
└─────────────────┬────────────────────┘
                  ↓
┌──────────────────────────────────────┐
│          Filter パイプライン             │  ValidationFilter（ActionFilter）
└─────────────────┬────────────────────┘
                  ↓
┌─────────────┐
│  Controller  │  ルーティング・HTTPステータス返却
└──────┬──────┘
       ↓ （Models で型変換）
┌─────────────┐
│   Service    │  業務ロジック・アクセスログ
└──────┬──────┘
       ↓
┌─────────────┐
│  Repository  │  DB アクセス（EF Core）
└──────┬──────┘
       ↓
   Database（PostgreSQL）
```

### 各レイヤーの責務

| レイヤー | 責務 | 持ってはいけないもの |
| --- | --- | --- |
| Controller | ルーティング・HTTP ステータス決定・レスポンス返却 | ビジネスロジック・DB 操作 |
| Service | 入力バリデーション・業務ロジック・アクセスログ出力 | DB 操作の直接実装 |
| Repository | EF Core による DB アクセス・クエリ組み立て | ビジネスロジック |
| Models | リクエスト/レスポンス型定義 | ロジック |

### 依存の方向ルール

上位レイヤーから下位レイヤーへの **一方向依存のみ** を許可する。

```
Controller → Service → Repository
```

Controller が Repository を直接呼ぶことは禁止。逆方向の依存（Repository → Service 等）も禁止。

---

### Controller レイヤー

#### 責務と実装パターン

Controller はリクエストを受け取り、Service に処理を委譲し、結果を HTTP レスポンスに変換するだけに留める。

```csharp
[ApiController]
[Route("api/v1/[controller]")]
public class ClinicalEntryController : ControllerBase
{
    private readonly ClinicalEntryService _service;

    public ClinicalEntryController(ClinicalEntryService service)
    {
        _service = service;
    }

    [HttpPost("chief-complaints")]
    [ProducesResponseType(typeof(ChiefComplaint), StatusCodes.Status200OK)]
    [ProducesResponseType(StatusCodes.Status404NotFound)]
    public async Task<ActionResult<ChiefComplaintResponse>> GetChiefComplaint([FromBody] ChiefComplaintRequest request)
    {
        var result = await _service.GetChiefComplaintAsync(request.PatientId);
        if (result == null) return NotFound();
        return Ok(result);
    }
}
```

##### Controller の実装チェックリスト

- [ ] `ControllerBase` を継承（`Controller` は MVC 向けのため使用しない）
- [ ] `[ApiController]`・`[Route]` 属性を付与
- [ ] Service をコンストラクタ注入
- [ ] メソッドは `async Task<IActionResult>` を返す
- [ ] ビジネスロジックを書かない
- [ ] リクエスト・レスポンスの型は BFF と共有している型（`Models/` の `record` 型）を使用する。ただし、エンティティをそのまま返す場合など、専用の型定義が不要であれば新設しなくてよい

### Service レイヤー

#### 責務と実装パターン

Service は業務ロジック・アクセスログを担当する。バリデーションは Controller 側の `[ValidationFilter]` と Data Annotations に委ねるため、Service には書かない（詳細は本章末尾「バリデーション」参照）。

```csharp
public class ClinicalEntryService
{
    private readonly ClinicalEntryRepository _repository;
    private readonly ILogger<ClinicalEntryService> _logger;

    public ClinicalEntryService(ClinicalEntryRepository repository, ILogger<ClinicalEntryService> logger)
    {
        _repository = repository;
        _logger = logger;
    }

    public async Task<ChiefComplaint?> GetChiefComplaintAsync(string patientId)
    {
        // 1. アクセスログ（処理開始）
        _logger.LogInformation(Res.LOG_CHIEF_COMPLAINT_GET, patientId);

        // 2. Repository 呼び出し
        var result = await _repository.GetChiefComplaintAsync(patientId);

        // 3. 結果の後処理ログ
        if (result == null)
            _logger.LogWarning(Res.LOG_CHIEF_COMPLAINT_NOT_FOUND, patientId);

        return result;
    }
}
```

##### Service の実装チェックリスト

- [ ] Repository と `ILogger<T>` をコンストラクタ注入
- [ ] 処理開始時に `LogInformation` でアクセスログを出力
- [ ] バリデーションを Service に書かない（Data Annotations + `[ValidationFilter]` で完結させる）
- [ ] DB 操作を直接書かない

#### ログの構造化ログ記法

構造化ログの書き方・禁止パターンの詳細は [06.エラーハンドリングとログ.md](06.エラーハンドリングとログ.md) の「構造化ログの書き方」を参照。

### Repository レイヤー

#### 責務と実装パターン

Repository は EF Core を使った DB アクセスに専念する。

```csharp
public class ClinicalEntryRepository
{
    private readonly ApplicationDbContext _context;

    public ClinicalEntryRepository(ApplicationDbContext context)
    {
        _context = context;
    }

    public async Task<ChiefComplaint?> GetChiefComplaintAsync(string patientId)
    {
        return await _context.ChiefComplaints
            .Where(x => x.PatientId == patientId)
            .OrderByDescending(x => x.CreatedAt)
            .FirstOrDefaultAsync();
    }
}
```

##### Repository の実装チェックリスト

- [ ] `ApplicationDbContext` をコンストラクタ注入
- [ ] EF Core LINQ クエリを使用（生 SQL は原則禁止。複雑な場合のみプレースホルダー使用）
- [ ] WHERE 条件でテナント ID を明示しない（`TenantSchemaInterceptor` が自動切り替え）
- [ ] ビジネスロジックを書かない

##### マルチテナントと Repository の関係

Repository のクエリ内にテナント ID フィルターを書く必要はない。詳細は本章の「[マルチテナント制御](#マルチテナント制御)」を参照。

### Models レイヤー

#### 責務と配置

Models はリクエスト・レスポンス型および業務内で使用する型（列挙型・DTO・値オブジェクト等）の定義を行う。エンティティ（`Shared/Entities/`）とは分離する。

```
Features/
  {業務ドメイン名}/
    Models/
      ClinicalEntryModels.cs   ← リクエスト/レスポンス型・業務内型をまとめて定義
```

```csharp
// リクエスト型
public record ChiefComplaintRequest(string PatientId);
public record ChiefComplaintRequest(string PatientId, string ChiefComplaint, string? Findings);

// レスポンス型（必ず Models に定義する。エンティティをそのまま返してはならない）
public record ChiefComplaintResponse(string PatientId, string ChiefComplaint, string? Findings, DateTime RecordedAt);
```

##### Models と Entities の使い分け

| 型 | 配置 | 用途 |
| --- | --- | --- |
| `Models/` | `Features/{group}/{name}/Models/` | API の入出力型。Controller・Service が使用 |
| `Entities/` | `Shared/Entities/{group}/` | DB テーブルに対応する型。Repository・DbContext が使用 |

##### API レスポンスは必ず Models（DTO）を使用する

**エンティティをそのまま API レスポンスに返してはならない。** 必ず `Models/` にレスポンス型（DTO）を定義し、Service 層でマッピングして返すこと。

理由: DB のテーブル構造（カラム名・型・内部 ID 等）が API のインターフェースに直接露出すると、DB 変更が即 API 変更となり BFF・フロントエンドへの影響が波及する。DTO を挟むことで DB とAPIの変更を独立させる。

```csharp
// NG: エンティティをそのまま返す
return Ok(entity);   // TChiefComplaints の全カラムが露出する

// OK: DTO にマッピングして返す
var response = new ChiefComplaintResponse(
    entity.PatientId,
    entity.ChiefComplaint,
    entity.Findings,
    entity.RecordedAt
);
return Ok(response);
```

## Shared/ 共通基盤

### Data 層（Shared/Data）の詳細

#### 責務

EF Core による DB アクセスの基盤を提供する。

#### 配置するコンポーネント

**ApplicationDbContext**

全エンティティの `DbSet` を管理し、EF Core の接続設定を行う。

```csharp
public class ApplicationDbContext : DbContext
{
    public ApplicationDbContext(DbContextOptions<ApplicationDbContext> options) : base(options) { }

    // 全エンティティの DbSet を登録
    public DbSet<TChiefComplaints> TChiefComplaints { get; set; }
    public DbSet<MBloodTypes> MBloodTypes { get; set; }
    
    protected override void OnModelCreating(ModelBuilder modelBuilder)
    {
        // Data Annotations で表現できない設定のみここに記述
        base.OnModelCreating(modelBuilder);
    }
}
```

**TenantSchemaInterceptor**

DB 接続オープン時に `SET search_path TO {tenantId}` を自動実行し、マルチテナント対応を実現する。

```csharp
public class TenantSchemaInterceptor : DbConnectionInterceptor
{
    private readonly TenantService _tenantService;

    public TenantSchemaInterceptor(TenantService tenantService)
    {
        _tenantService = tenantService;
    }

    public override async ValueTask<InterceptionResult> ConnectionOpeningAsync(...)
    {
        await connection.ExecuteAsync($"SET search_path TO {_tenantService.GetTenantId()}");
        return result;
    }
}
```

#### Program.cs への登録ルール

`TenantSchemaInterceptor` は `AddDbContext` より前に Scoped 登録し、DbContext のファクトリ内で取得して `AddInterceptors` に渡す。

```csharp
// 1. インターセプターを先に Scoped 登録
builder.Services.AddScoped<TenantSchemaInterceptor>();

// 2. DbContext 登録時にインターセプターを注入
builder.Services.AddDbContext<ApplicationDbContext>((serviceProvider, options) =>
{
    options.UseNpgsql(builder.Configuration.GetConnectionString("DefaultConnection"));
    var interceptor = serviceProvider.GetRequiredService<TenantSchemaInterceptor>();
    options.AddInterceptors(interceptor);
});
```

| 登録順序 | 理由 |
| --- | --- |
| `TenantSchemaInterceptor` を先に登録 | `AddDbContext` のファクトリ内で `GetRequiredService` するため、先に DI に存在している必要がある |
| `AddDbContext` でインターセプターを注入 | `TenantSchemaInterceptor` は `TenantService`（Scoped）に依存するため、コンストラクタ注入ではなくファクトリ経由で解決する |

#### 新しいコンポーネントを追加する基準

- **DbContext:** 基本的に `ApplicationDbContext` 1つのみ。複数の DbContext が必要になることは稀
- **Interceptor:** DB 接続・コマンド実行時に横断的な処理を挿入したい場合に追加する

**詳細:** [04.DB・エンティティ設計.md](04.DB・エンティティ設計.md)

### Middlewares 層（Shared/Middlewares）の詳細

#### 責務

リクエストパイプラインに横断的な処理を挿入する層。全 API に共通する前処理・後処理を実装する。

#### 配置するミドルウェアの例

- `ExceptionMiddleware` — 全例外の一括処理・RFC 9457 準拠の統一エラーレスポンス返却
- `TraceIdMiddleware` — `X-Trace-ID` ヘッダーからトレース ID を取得し MDLC・`HttpContext.Items` にセット
- `TenantMiddleware` — `X-Tenant-ID` ヘッダーからテナント ID を取得

#### ミドルウェアの基本実装パターン

```csharp
public class TenantMiddleware
{
    private readonly RequestDelegate _next;

    public TenantMiddleware(RequestDelegate next)
    {
        _next = next;
    }

    public async Task InvokeAsync(HttpContext context, TenantService tenantService)
    {
        if (context.Request.Headers.TryGetValue("X-Tenant-ID", out var tenantId))
        {
            tenantService.SetTenantId(tenantId.ToString());
        }
        else
        {
            throw new UnauthorizedAccessException("テナントIDが指定されていません。");
        }

        await _next(context);
    }
}
```

#### Program.cs への登録順序ルール

登録順序の詳細は [03.開発環境.md](03.開発環境.md) の「ミドルウェアパイプライン登録順序」を参照。

#### 新しいミドルウェアを追加する基準

- 全 API に共通する処理である
- リクエストまたはレスポンスに対して横断的な処理を行う
- 例：認証トークン検証、リクエストログ出力、レスポンスヘッダー追加

**詳細:** [06.エラーハンドリングとログ.md](06.エラーハンドリングとログ.md)、本章の「マルチテナント制御」

### Filters 層（Shared/Filters）の詳細

#### 責務

Controller / Action の前後に介入し、**ModelState にアクセスできる** 横断的処理を実装する層。Middleware では取得できない Controller 情報（Action 名・ModelState・Action 引数）が必要な処理をここに置く。

#### Middleware との違い

| 比較軸 | Middleware | Filter |
|---|---|---|
| 適用範囲 | 全リクエスト | Controller / Action 単位で個別指定 |
| 実行タイミング | ルーティング前も含む | Controller 到達後 |
| ModelState へのアクセス | 不可 | 可能 |
| 登録方法 | `Program.cs` に `UseMiddleware<T>()` | Action / Class に属性付与 |

#### Filter の種類と実行順序

| Filter 種別 | 実行順 | 主な用途 |
|---|---|---|
| `AuthorizationFilter` | 1 | 認可チェック（早期終了） |
| `ResourceFilter` | 2 | キャッシュ・ショートサーキット |
| `ActionFilter` | 3 | Action 前後の共通処理（バリデーション等） |
| `ExceptionFilter` | 例外発生時 | Controller 内例外のレスポンス整形 |
| `ResultFilter` | 4 | ActionResult 生成前後の加工 |

#### 配置するフィルターの例

| フィルター | 種別 | 動作 |
|---|---|---|
| `ValidationFilterAttribute` | `ActionFilter` | `ModelState.IsValid` が `false` のとき `ValidationException` を throw し 400 に変換する |
| `RequireRoleAttribute`（将来） | `AuthorizationFilter` | JWT クレームのロールが不足する場合に 403 を返す |
| `AuditLogFilterAttribute`（将来） | `ActionFilter` | Action 実行前後に操作ログ（操作者・対象リソース・実行時間）を記録する |

**`ValidationFilterAttribute` の動作例:**

```
POST /api/v1/clinical-entries/chief-complaints
Body: { "patientId": "" }   ← Required 違反
        ↓
[ValidationFilter] が ModelState を確認
        ↓
ValidationException をスロー（errors に field/code/message を付与）
        ↓
ExceptionMiddleware が 400 Bad Request に変換して返却
```

#### 登録方法

属性として Action またはクラスに付与する。

```csharp
[HttpPost("chief-complaint")]
[ValidationFilter]  // このActionのみに適用
public async Task<ActionResult> Post([FromBody] ChiefComplaintRequest request) { ... }
```

#### 新しいフィルターを追加する基準

- Controller / Action 情報（ModelState・Action 引数等）が必要な横断処理である
- 特定の Controller / Action にのみ適用したい処理である
- 全 API 共通の処理は Middleware で実装する

### Services 層（Shared/Services）の詳細

#### 責務

業務ドメインに依存しない横断的なサービスを配置する層。複数の業務ドメインから参照される共通ロジックを提供する。

#### 配置するサービスの例

- `TenantService` — テナント ID の DI スコープ内保持

#### 共有サービスの基本実装パターン

```csharp
public class TenantService
{
    private string? _tenantId;

    public void SetTenantId(string tenantId)
    {
        _tenantId = tenantId;
    }

    public string GetTenantId()
    {
        return _tenantId ?? throw new InvalidOperationException("テナントIDが設定されていません。");
    }
}
```

- ステートレスまたはリクエストスコープのステートのみを持つ
- 業務固有ロジックを含まない

#### Features/ 配下の Service との違い

| 項目 | Shared/Services | Features/.../Services |
| --- | --- | --- |
| 配置基準 | 業務固有ロジックを持たない | 業務固有ロジックを含む |
| 参照元 | 複数の業務ドメインから参照される | 通常は同じ業務ドメイン内から参照される |
| 例 | `TenantService`, `CacheService` | `PatientService`, `VitalInfoService` |

#### 新しい共有サービスを追加する基準

- 業務固有ロジックを持たない
- 複数 Feature から参照される
- 横断的な関心事（テナント管理、キャッシュ、ログ等）を扱う

業務固有ロジックは必ず `Features/(ドメイン名)/(業務名)/Services/` に配置する。

---

### 新機能追加時のファイル作成順序

1. **Models** — リクエスト/レスポンス型を定義（設計の出発点）
2. **Entity**（`Shared/Entities/`）— DB テーブルに対応する型を定義
3. **Repository** — Entity を使った DB アクセスを実装
4. **Service** — バリデーション・ログ・Repository 呼び出しを実装
5. **Controller** — エンドポイントと HTTP ステータスを実装

## トランザクション管理

### 基本方針

EF Core 標準のトランザクション管理機能を使用する。単一 `SaveChangesAsync()` で完結する操作は EF Core が自動でトランザクションを管理するため、明示的なトランザクション制御は不要。複数の Repository 操作をひとまとめにコミット/ロールバックする場合のみ Service レイヤーで明示的に制御する。

### 暗黙トランザクション（単一操作）

```csharp
// Service: 単一の SaveChangesAsync は EF Core が自動でトランザクション管理
public async Task CreateChiefComplaintAsync(string patientId, string text)
{
    var entity = new TChiefComplaints { PatientId = patientId, Text = text };
    _context.TChiefComplaints.Add(entity);
    await _context.SaveChangesAsync();  // ← 暗黙トランザクション
}
```

### 明示的トランザクション（複数操作を一括コミット）

複数のエンティティ操作を一括でコミット/ロールバックしたい場合は `BeginTransactionAsync()` を使用する。

```csharp
// Service: 複数操作を原子的に処理する場合
public async Task CreateConsultationWithVitalAsync(string patientId, string chiefComplaint, VitalData vital)
{
    await using var transaction = await _context.Database.BeginTransactionAsync();
    try
    {
        _context.TChiefComplaints.Add(new TChiefComplaints { PatientId = patientId, Text = chiefComplaint });
        _context.TVitalInfos.Add(new TVitalInfos { PatientId = patientId, BloodPressure = vital.BloodPressure });
        await _context.SaveChangesAsync();

        await transaction.CommitAsync();
    }
    catch
    {
        await transaction.RollbackAsync();
        throw;  // 上位へ伝搬させる
    }
}
```

#### トランザクション管理のルール

- トランザクション制御は **Service レイヤーのみ** で行う（Repository に書かない）
- 明示的トランザクションは複数操作が必要な場合のみ使用する（過剰なトランザクション使用はパフォーマンス劣化を招く）
- ロールバック後は必ず `throw` で例外を上位に伝搬させる

## ページング実装

### 基本方針

大量データを取得する API は必ずページングを実装し、一度に返却するレコード数を制限する。ページングなしで全件取得するとメモリ・ネットワーク・DB に過大な負荷がかかる。

### リクエスト型の定義

```csharp
// Models/ に共通ページングリクエスト型を定義
public record PagedRequest(
    int Page = 1,       // 1始まり
    int PageSize = 20   // デフォルト20件
);

// レスポンス型
public record PagedResponse<T>(
    IEnumerable<T> Items,
    int TotalCount,
    int Page,
    int PageSize
);
```

### Repository でのページング実装

```csharp
public async Task<(IEnumerable<TChiefComplaints> Items, int TotalCount)> GetPagedAsync(
    string patientId, int page, int pageSize)
{
    var query = _context.TChiefComplaints
        .Where(x => x.PatientId == patientId)
        .OrderByDescending(x => x.RecordedAt);

    var totalCount = await query.CountAsync();
    var items = await query
        .Skip((page - 1) * pageSize)
        .Take(pageSize)
        .ToListAsync();

    return (items, totalCount);
}
```

#### ページングのルール

- デフォルト `PageSize` は 20 件。最大値は業務要件ごとに決定する（無制限は禁止）
- `Skip().Take()` の組み合わせを使用する
- `TotalCount` をレスポンスに含め、クライアントが総ページ数を計算できるようにする

## マルチテナント制御

### 基本方針

複数テナント（複数病院）による同一サービス共有を実現する。アプリ実装チームはテナントを意識せずにコードを書けるよう、基盤側が自動で処理する。

### テナントIDの取得と伝播（TenantMiddleware）

`X-Tenant-ID` ヘッダーからテナントIDを抜き取り、リクエストスコープ内で `TenantService` に保持する。

```csharp
// Shared/Middlewares/TenantMiddleware.cs
public class TenantMiddleware
{
    private readonly RequestDelegate _next;

    public TenantMiddleware(RequestDelegate next)
    {
        _next = next;
    }

    public async Task InvokeAsync(HttpContext context, TenantService tenantService)
    {
        if (context.Request.Headers.TryGetValue("X-Tenant-ID", out var tenantId))
        {
            tenantService.SetTenantId(tenantId.ToString());
        }
        else
        {
            throw new UnauthorizedAccessException("テナントIDが指定されていません。");
        }

        await _next(context);
    }
}

// Shared/Services/TenantService.cs
public class TenantService
{
    private string? _tenantId;

    public void SetTenantId(string tenantId)
    {
        _tenantId = tenantId;
    }

    public string GetTenantId()
    {
        return _tenantId ?? throw new InvalidOperationException("テナントIDが設定されていません。");
    }
}
```

Controller・Service・Repository では `TenantService` を直接呼ぶ必要はない（`TenantSchemaInterceptor` が自動で使用する）。

### DBスキーマ切り替え（TenantSchemaInterceptor）

DB 接続オープン時に `SET search_path TO {tenantId}` を自動実行する。

```csharp
// Shared/Data/TenantSchemaInterceptor.cs
public class TenantSchemaInterceptor : DbConnectionInterceptor
{
    private readonly TenantService _tenantService;

    public TenantSchemaInterceptor(TenantService tenantService)
    {
        _tenantService = tenantService;
    }

    public override async ValueTask<InterceptionResult> ConnectionOpeningAsync(
        DbConnection connection,
        ConnectionEventData eventData,
        InterceptionResult result,
        CancellationToken cancellationToken = default)
    {
        await connection.ExecuteAsync($"SET search_path TO {_tenantService.GetTenantId()}");
        return result;
    }
}
```

この仕組みにより、Repository のクエリ内でテナント ID をフィルター条件に含める必要がない。接続後は対象テナントのスキーマのみにアクセスされる。

### テナントIDの Swagger UI での入力方法

開発時に Swagger UI で `X-Tenant-ID` ヘッダーを指定する設定は [05.API設計.md](05.API設計.md) を参照。

```csharp
// Program.cs での Swagger 設定例
builder.Services.AddSwaggerGen(c =>
{
    c.SwaggerDoc("v1", new OpenApiInfo { Title = "Karte Domain API", Version = "v1" });
    c.AddSecurityDefinition("X-Tenant-ID", new OpenApiSecurityScheme
    {
        In = ParameterLocation.Header,
        Name = "X-Tenant-ID",
        Type = SecuritySchemeType.ApiKey,
        Description = "テナントID"
    });
});
```

## バリデーション

### 基本方針

Controller でのバリデーションチェックは、.NET 標準ライブラリの `System.ComponentModel.DataAnnotations` 名前空間を用いたモデル検証機能を利用する。モデル検証結果の判定およびエラーハンドリング処理は、属性フィルタ（`ValidationFilterAttribute`）を利用し、共通ロジックで行う。

### モデル検証とは

モデルクラス内に検証ルールを指定することで、アプリケーションのあらゆる場所に検証ルールを適用できる機能。`Models/` に定義するリクエスト型に Data Annotations を付与して使用する。

### 実装方法

#### 1. 検証属性を付与したリクエスト型を定義する

```csharp
// Features/{グループ}/{業務}/Models/{業務}Type.cs
public record ChiefComplaintRequest(
    [Required(ErrorMessage = "患者IDは必須です。")]
    string PatientId);
```

よく使われる検証属性：

| 属性 | 用途 |
| --- | --- |
| `[Required]` | 必須チェック |
| `[StringLength(max)]` | 文字数上限 |
| `[RegularExpression(pattern)]` | 正規表現チェック |
| `[Range(min, max)]` | 数値範囲チェック |

検証属性は複数付与可能。カスタム検証属性が必要な場合は `Shared/Filters/` に `XxxValidationAttribute` を作成する。

#### 2. バリデーション対象のアクションに `[ValidationFilter]` を付与する

```csharp
// Features/{グループ}/{業務}/Controllers/{業務}Controller.cs
[HttpPost("chief-complaint")]
[ValidationFilter]
public async Task<ActionResult<TChiefComplaints>> GetChiefComplaint([FromBody] ChiefComplaintRequest request)
{
    // ここに到達した時点でバリデーション済み
    var result = await _service.GetChiefComplaintAsync(request.PatientId);
    if (result == null) return NotFound();
    return Ok(result);
}
```

`[ValidationFilter]` は `ModelState.IsValid` が `false` の場合に `ArgumentException` を throw する。`ExceptionMiddleware` がこれを 400 Bad Request に変換する。

#### ValidationFilterAttribute の実装（`Shared/Filters/`）

```csharp
[AttributeUsage(AttributeTargets.Method)]
public class ValidationFilterAttribute : ActionFilterAttribute
{
    public override void OnActionExecuting(ActionExecutingContext context)
    {
        if (!context.ModelState.IsValid)
            throw new ArgumentException("リクエストのバリデーションに失敗しました。");
    }
}
```

### バリデーションのルール

- 検証属性はリクエスト型（`Models/`）に付与する。エンティティ（`Shared/Entities/`）には付与しない
- `[ValidationFilter]` はリクエストボディを受け取る `POST` / `PUT` アクションに付与する
- バリデーションロジックを Service に書かない（型レベルで完結させる）
- Data Annotations で表現できない複雑なルール（例: 他フィールドとの相関チェック）は Service 内の `private static` メソッドで実装する
