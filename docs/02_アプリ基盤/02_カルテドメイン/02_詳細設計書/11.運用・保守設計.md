# 運用・保守設計

本章では、カルテドメインサービスの API バージョン管理・コード品質管理・CI/CD パイプライン・依存ライブラリ管理の方針を定義する。ブランチ戦略については `docs/00_環境構築手順書/02_GitLab運用手順書.md` に準拠する。

---

## API バージョン管理

### バージョニング方針

API はURLパスバージョニングを採用する。

```
/api/v1/clinical-entries/chief-complaints
/api/v2/clinical-entries/chief-complaints   ← 後方互換性のない変更が必要な場合
```

**後方互換性を持たない変更（Breaking Change）が発生した場合のみ** バージョンを上げる。フィールドの追加・レスポンスの拡張は同一バージョンで対応する。

#### Breaking Change の定義

以下の変更は Breaking Change として新バージョンを発行する：

- 既存フィールドの削除・リネーム
- 既存フィールドの型変更
- 既存エンドポイントの URL 変更
- 必須パラメーターの追加

### 旧バージョンのサポート方針

旧バージョンの API は新バージョンリリース後も一定期間サポートし、利用状況を踏まえて廃止時期を定める。廃止予告は `Deprecated` レスポンスヘッダーで通知する。

```
Deprecated: true
Sunset: 2027-04-01
```

## コード品質管理

### コーディング規約

C# / .NET 標準ガイドライン（Microsoft C# Coding Conventions）に準拠する。命名規則は `02.アーキテクチャ設計.md` を参照。

### 静的解析

.NET プロジェクトはビルド時に Roslyn アナライザーが自動実行される。CI パイプラインでは静的解析の結果をチェックし、警告がある場合はマージを禁止する。

## CI/CD パイプライン

### CI（Continuous Integration）の構成

PR 作成時に自動実行される。

```
PR 作成
  ↓
ビルド（dotnet build）
  ↓
静的解析（Roslyn アナライザー）
  ↓
単体テスト（dotnet test）
  ↓
脆弱性チェック（NuGet パッケージのセキュリティスキャン）
  ↓
全 PASS → マージ可能
いずれか FAIL → マージ不可
```

### CD（Continuous Delivery）の構成

`main` / `develop` ブランチへのマージ時に自動実行される。

```
マージ
  ↓
コンテナイメージのビルド（Docker build）
  ↓
コンテナレジストリへの登録（docker push）
  ↓
ステージング環境へのデプロイ（ローリングアップデート）
```

### ローリングアップデート

コンテナオーケストレーション基盤のローリングアップデート機能を使用し、サービス停止なしに新バージョンへ切り替える。リリース失敗時は前バージョンへ自動ロールバックする。

## 依存ライブラリ管理

### 管理方針

- NuGet でパッケージを管理し、`.csproj` にバージョンを固定して記載する（`*` 指定禁止）
- CI パイプラインでパッケージ構成の整合性チェック（`dotnet restore` の成功確認）を実施する
- 不要なパッケージは定期的に削除する

### セキュリティアップデートの方針

- 脆弱性が報告されたパッケージは優先的に更新する
- パッケージ更新時は単体テストが全件 PASS することを確認してからマージする

```bash
# 脆弱性のあるパッケージを確認
dotnet list package --vulnerable

# 古いパッケージを確認
dotnet list package --outdated
```

## キャッシュ戦略

### MemoryCache の活用

.NET 標準の `MemoryCache` を使用してサーバーメモリにデータをキャッシュし、DB 負荷を軽減する。

#### キャッシュ対象データ

- セッション情報
- マスタデータ（参照頻度が高い固定データ。例: 血液型・Rh 因子）

#### キャッシュの保持期間

期限付きで保持し、一定期間経過後に自動破棄する。保持期間は業務グループごとに設定する。

#### キャッシュ更新

DB 更新後に該当キャッシュを明示的に更新/削除する。

```csharp
// キャッシュから取得し、存在しない場合は DB から取得してキャッシュに登録
if (!_cache.TryGetValue("blood-types", out var bloodTypes))
{
    bloodTypes = await _repository.GetAllAsync();
    _cache.Set("blood-types", bloodTypes, TimeSpan.FromMinutes(30));
}
```

### 複数コンテナ環境での注意点

`MemoryCache` はコンテナ内のプロセス単位で保持されるため、**複数コンテナ間でキャッシュが共有されない**。スケールアウト時にコンテナごとにキャッシュが異なる状態になる可能性がある。

高可用性・スケールアウトが必要な場合は Redis 等の分散キャッシュの併用を検討する。

## パフォーマンス管理

### ピークトラフィック時の性能目標

朝の診療開始直後や夕方の診療終了前にトラフィックのピークが発生する。これらのピーク時においても安定したレスポンスを提供できるよう、開発初期に同時接続数・スループットの目標値を確認し、設計に反映する。

性能目標は業務要件定義フェーズで定める。指標の例：

| 指標 | 目安（例） | 備考 |
| --- | --- | --- |
| 平常時 API レスポンスタイム（P95） | < 300 ms | DB クエリ + ネットワーク込み |
| ピーク時 API レスポンスタイム（P95） | < 800 ms | 朝・夕のアクセス集中時 |
| 同時接続数（ピーク） | 業務要件に基づく | スケールアウト台数設計に使用 |

目標値は実際の病院規模・在院患者数・外来患者数から算出する。開発初期に業務担当者と合意の上で `.steering/` に記録する。

### DB 実行計画の定期確認方針

本番環境に近いデータ量での動作確認時、および定期的な運用監視において、PostgreSQL の実行計画（`EXPLAIN ANALYZE`）とパフォーマンスログを確認し、SQL やインデックスのボトルネックを特定する。

```sql
-- 実行計画の確認
EXPLAIN ANALYZE
SELECT * FROM t_chief_complaints
WHERE patient_id = 'P001'
ORDER BY recorded_at DESC;
```

確認観点：

- `Seq Scan` が発生していないか（インデックスが利用されているか）
- 実行時間が許容範囲内か
- 結合が多い場合にネストループではなくハッシュ結合が選択されているか

ボトルネックを発見した場合は、インデックス追加・クエリ最適化・統計情報の更新（`ANALYZE`）で対処する。

## API ドキュメント管理

OpenAPI（Swagger）を使用して API 仕様を自動生成・管理する。

- `ASPNETCORE_ENVIRONMENT=Development` の場合に Swagger UI が有効化される（`http://localhost:7121/swagger`）
- コントローラーの `[ProducesResponseType]` アノテーションで型情報を付与する
- API 変更時は Swagger 定義も同時に更新する（実装と自動同期）
