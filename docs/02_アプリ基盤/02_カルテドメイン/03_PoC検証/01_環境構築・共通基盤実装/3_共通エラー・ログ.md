# 技術検証報告書：共通例外ハンドリングと構造化ログ（NLog）の実装

## 1. 検証の目的

アプリケーション全体で発生する例外を統一された形式でクライアントにレスポンスし、同時にシステム内部では、運用・保守に耐えうる詳細な「構造化ログ（JSON）」を記録する基盤を構築・検証する。

## 2. 実装コード（検証済み）

### ① 共通例外ハンドラーの実装

アプリのパイプライン最上流でエラーを捕捉し、一貫したJSONレスポンスを返却する。

**Shared/Middlewares/ExceptionMiddleware.cs**

```csharp
using System.Net;
using System.Text.Json;

namespace KarteDomainService.Shared.Middlewares;

public class ExceptionMiddleware
{
    private readonly RequestDelegate _next;
    private readonly ILogger<ExceptionMiddleware> _logger;

    public ExceptionMiddleware(RequestDelegate next, ILogger<ExceptionMiddleware> logger)
    {
        _next = next;
        _logger = logger;
    }

    public async Task InvokeAsync(HttpContext context)
    {
        try
        {
            await _next(context); // 次の処理を実行
        }
        catch (Exception ex)
        {
            // NLogを介して詳細なエラーログを出力
            _logger.LogError(ex, "予期せぬエラーが発生しました。");
            await HandleExceptionAsync(context, ex);
        }
    }

    private static Task HandleExceptionAsync(HttpContext context, Exception exception)
    {
        context.Response.ContentType = "application/json";
        context.Response.StatusCode = (int)HttpStatusCode.InternalServerError;

        var response = new
        {
            StatusCode = context.Response.StatusCode,
            Message = "サーバーエラーが発生しました。管理者に連絡してください。",
            Detail = exception.Message // 検証用（本番では詳細を隠蔽することを推奨）
        };

        return context.Response.WriteAsync(JsonSerializer.Serialize(response));
    }
}

```

### ② NLogによる構造化ログの設定

ログをテキスト形式ではなく、属性（時間、レベル、テナントID、例外内容）ごとに分割されたJSON形式で出力する。

**nlog.config (抜粋)**

```xml
<targets>
  <target xsi:type="File" name="jsonFile" fileName="logs/app-${shortdate}.json">
    <layout xsi:type="JsonLayout">
      <attribute name="time" layout="${longdate}" />
      <attribute name="level" layout="${level:upperCase=true}" />
      <attribute name="message" layout="${message}" />
      <attribute name="exception" layout="${exception:format=tostring}" />
      <attribute name="tenantId" layout="${mdlc:item=TenantId}" /> 
    </layout>
  </target>
</targets>

```

## 4. 評価と考察

* **一貫性の確保**: 個別のControllerで `try-catch` を書く必要がなくなり、全エンドポイントでエラーレスポンスが統一された。
* **分析の容易性**: JSON形式でログを保存するため、将来的なクラウド監視ツール（Azure Monitor, Datadog等）への統合が容易。
* **安全性**: `ExceptionMiddleware` 内でレスポンス内容を制御できるため、スタックトレース等の機密情報が不用意にフロントエンドへ露出するリスクを低減。
