# 技術検証報告書：.NET 10 vs Python によるドメインモデル実装と AI（GitHub Copilot）保守性検証

## 1. 検証の背景と目的

大規模医療カルテシステムの開発において、**GitHub Copilot** を活用した際の開発効率と、将来的な仕様変更時の安全性を比較する。特に、複雑なリレーションを持つドメインモデルの構築と、その破壊的変更に対する各言語の「AI親和性」を明らかにすることを目的とした。

---

## 2. 検証プロセスと実施内容

### STEP 1：開発環境のセットアップと初期疎通

両言語において、最小構成の API サーバーと DB 接続基盤を構築した。

* **.NET 10**: `dotnet new webapi` で基盤作成。C# 14 ランタイムの正常稼働を確認。
* **Python**: `venv` による仮想環境構築後、`FastAPI` および `Uvicorn` を導入。
* **共通**: PostgreSQL をバックエンドに想定し、.NET（EF Core）および Python（SQLAlchemy）で接続定義を完了。

### 使用ツール

* **AIアシスタント**: GitHub Copilot (VS Code 拡張機能)
* **ランタイム**: .NET 10 (C# 14) / Python 3.12 (FastAPI)

### STEP 2：ドメインモデルの初期実装（AIによる生成）

「診察（Consultation）に処方（Prescription）を追加し、薬品名の重複をチェックする」という指示を Copilot に出し、コードを生成。

#### **Python (初期実装)**

AIは非常にシンプルかつ直感的な、リスト操作ベースのコードを提案。

```python
# models.py
# 診察クラス
class Consultation:
    def __init__(self, patient_id: int):
        self.patient_id = patient_id
        self.prescriptions = []  # 処方リスト

    def add_prescription(self, prescription):
        if self.is_duplicate_medicine(prescription.medicine_name):
            raise ValueError(f"薬品 '{prescription.medicine_name}' はすでに追加されています。")
        self.prescriptions.append(prescription)

    def is_duplicate_medicine(self, medicine_name: str) -> bool:
        return any(p.medicine_name == medicine_name for p in self.prescriptions)


# 処方クラス
class Prescription:
    def __init__(self, medicine_name: str, dose: str, days: int):
        self.medicine_name = medicine_name  # 薬品名
        self.dose = dose  # 用量
        self.days = days  # 日数
```

### STEP 3：破壊的リファクタリングの実施（AIによる修正）

「薬品名（文字列）を廃止し、独立した **Drug クラス（Id/Code/Name）** を参照する構造へ変更せよ」と Copilot に指示。

#### **Python (修正後)**

Copilot は `hasattr` や `getattr` を使い、実行時の柔軟性を担保するコードを生成。

```python
# 薬品モデル
class Drug(Base):
    __tablename__ = "Drugs"

    Id = Column(Integer, primary_key=True, index=True)
    Code = Column(String, unique=True, index=True)
    Name = Column(String)


# 診察クラス
class Consultation:
    def __init__(self, patient_id: int):
        self.patient_id = patient_id
        self.prescriptions = []  # 処方リスト

    def add_prescription(self, prescription):
        # prescription は Prescription インスタンスで、drug 属性を持つ想定
        if not hasattr(prescription, "drug") or not hasattr(prescription.drug, "Code"):
            raise ValueError("処方は有効な Drug を参照している必要があります。")

        if self.is_duplicate_medicine(prescription.drug.Code):
            raise ValueError(f"薬品 '{prescription.drug.Name}' (Code={prescription.drug.Code}) はすでに追加されています。")
        self.prescriptions.append(prescription)

    def is_duplicate_medicine(self, drug_code: str) -> bool:
        return any(getattr(p, "drug", None) is not None and getattr(p.drug, "Code", None) == drug_code for p in self.prescriptions)


# 処方クラス
class Prescription:
    def __init__(self, drug: Drug, dose: str, days: int):
        # drug は Drug のインスタンス（DBから取得したものや新規インスタンス）
        self.drug = drug
        self.dose = dose  # 用量
        self.days = days  # 日数

```

#### **.NET 10 (修正後)**

Copilot は `DrugId` 外部キーと `Drug` エンティティのリレーションを正確に構築。

```csharp
// KarteDomainService\Features\Karte\Entities\Consultation.cs
namespace KarteDomainService.Features.Karte.Entities;

public class Consultation
{
    public int Id { get; set; }
    public DateTime ConsultationDate { get; set; } = DateTime.UtcNow;

    public int PatientId { get; set; }
    public Patient? Patient { get; set; }

    public List<Prescription> Prescriptions { get; set; } = new();

    /// <summary>
    /// 指定した処方を追加します。既存の処方と Drug.Code または DrugId で比較し重複がある場合は追加せず false を返します。
    /// </summary>
    public bool TryAddPrescription(Prescription prescription)
    {
        if (prescription == null) return false;

        // 1) DrugId が設定されている場合は ID で比較
        if (prescription.DrugId != 0)
        {
            var existsById = Prescriptions.Any(p => p.DrugId == prescription.DrugId && p.DrugId != 0);
            if (existsById) return false;
        }

        // 2) Drug オブジェクトの Code が設定されている場合はコードで比較（大文字小文字を無視）
        var newCode = prescription.Drug?.Code;
        if (!string.IsNullOrWhiteSpace(newCode))
        {
            var existsByCode = Prescriptions.Any(p => !string.IsNullOrWhiteSpace(p.Drug?.Code) && string.Equals(p.Drug!.Code, newCode, StringComparison.OrdinalIgnoreCase));
            if (existsByCode) return false;
        }

        // 3) 上記いずれの情報もない場合はチェックできないためそのまま追加する
        Prescriptions.Add(prescription);
        return true;
    }
}

```

## 3. 分析結果：GitHub Copilot との協調性
### 3.1.1.比較分析：AIコーディングとドメイン表現力

・Python の挙動

Python側は非常に直感的で、AIが「たったこれだけ」で動くものを出してくれました。

* **AI生成のメリット**:
コードが圧倒的に短いです。AIに「メソッドを追加して」と頼めば、数秒でこのシンプルな `add_prescription` を生成します。
* **大規模開発での懸念**:
`add_prescription(self, prescription)` の引数 `prescription` に型が指定されていません。AIが間違えて全く別のオブジェクトを渡すコードを生成しても、**実行するまでエラーになりません。**
> **AIリスク:** 大規模化してモデルが100個を超えたとき、AIが「似た名前の別のクラス」を引数に紛れ込ませるミス（ハルシネーション）を検知しにくい。



・.NET の挙動

.NET側は、EF Coreの設定（`OnModelCreating`）まで含めた「完成されたシステム構造」をAIが提案しています。

* **AI生成のメリット**:
`Consultation` と `Prescription` の関係性が DB レベルまで定義されています。`TryAddPrescription(Prescription prescription)` のように型が厳格なため、AIがこのメソッドを呼び出すコードを書く際、**型を間違えれば即座に赤波線（コンパイルエラー）が出ます。**
* **大規模開発での利点**:
`StringComparison.OrdinalIgnoreCase`（大文字小文字の区別なし）のような、医療現場で必須の「厳密な比較」をAIが自然に組み込んでいます。
> **AIプロンプト効率:** 「この `Consultation` クラスを使って、処方データを保存する API を作って」とAIに投げたとき、DB 構造（DbContext）まで理解している C# の方が、**「そのまま動く、より安全なコード」**を吐き出しやすいです。

### 3.2. ドメイン知識の継承（リレーションの整合性）

・Python の挙動

`Consultation` クラスが独立した `__init__` を持っており、DBモデル（Base）との繋がりがこのコード片だけでは曖昧です。

> **大規模化への懸念:** AIが「DBのDrugテーブル」と「メモリ上のDrugインスタンス」を混同しやすく、保存時に「新しい薬品として二重登録される」といったデータ不整合バグを生成するリスクがあります。

・.NET の挙動

`DrugId` と `Drug` オブジェクトの両方を保持し、`DbContext` で外部キー制約まで定義されています。

> **大規模化への利点:** AIは `DrugId` が `int` であることを知っているため、DBから取得した既存データとの照合ロジックを正確に書けます。医療データのように整合性が命のシステムでは、この「構造のガチガチさ」がAIのハルシネーションを防ぐ重石になります。


| 観点 | Python × Copilot | .NET 10 × Copilot |
| --- | --- | --- |
| **生成速度** | **極めて速い**。最小限の記述で動くものが完成する。 | **速い**。ボイラープレートが多いが、Copilot の補完で相殺される。 |
| **変更の安全性** | **懸念あり**。属性名変更時、Copilot が古い名称（medicine_name）を残しても**静的に検知できない**。 | **極めて高い**。モデル変更時に IDE が出すエラーを Copilot が読み取り、**連鎖的な修正を完遂**する。 |
| **推論の精度** | 文脈が「名前」に依存しやすく、大規模化でハルシネーション（誤認）リスク増。 | 「型」が強力な文脈となるため、複雑なリレーションでも Copilot の提案が正確。 |

## 4. 結論：本プロジェクトにおける採用指針

検証の結果、医療システムの特性に合わせ、以下の**ハイブリッド戦略**を提案する。

### 1. カルテコア・主要ドメイン（.NET 10）

**「AIに壊されない、堅牢な基盤」**
カルテ、処方、オーダー等の基幹機能は .NET を採用する。GitHub Copilot を活用した大規模な法改正対応やリファクタリングにおいて、C# の厳格な型システムが「AIへの強力な制約」として機能し、品質の平準化とバグの早期発見を物理的に強制できるため。

### 2. 周辺連携・データ分析・試作機能（Python）

**「AIで加速する、柔軟な周辺系」**
外部API連携、統計分析、AI診断支援等のサブシステムは Python を採用する。開発スピードが重要であり、かつ「特定の入出力」に特化した軽量なサービスであれば、Copilot の爆速な生成能力を最大限に活かし、最小の工数で実装・改善を回せるため。
