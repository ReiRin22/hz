## 1. 共通ヘッダー仕様

全APIエンドポイントで以下のリクエストヘッダーを処理すること。

| ヘッダー名 | 型 | 必須 | 説明 |
| ---------- | -- | :--: | ---- |
| `X-Tenant-Id` | `string` | ○ | テナントID。マルチテナント境界の識別に使用する |
| `X-Correlation-ID` | `string` | △ | 相関ID。監査ログに記録する。付与義務は各APIの仕様に従う |
| `Authorization` | `string` | ○ | Bearer トークン（認可モジュールで検証） |

### マルチテナント境界ルール

- `X-Tenant-Id` が異なるリソースへのアクセスは禁止する
- テナント境界チェックはコントローラー層の入口で実施する
- チェック失敗時は `403 Forbidden` を返す

## 2. 認証・認可

- 認証は `authorization-domain-service` が発行するトークンで行う
- コントローラー層はトークンの検証を行わない（APIゲートウェイ・認可モジュールに委譲）
- ユーザーID・ユーザー名はトークンから取得し、コントローラー経由でサービス層に渡す

### コントローラーが取得するユーザー情報

```typescript
type AuthenticatedUser = {
  userId: string;
  userName: string;
  tenantId: string;
  roles: string[];
};
```

## 3. リクエスト共通規約

### パスパラメータ

- リソース識別子には UUID を使用する（例: `{orderUuid}`, `{patientId}`）
- パスパラメータの存在確認はサービス層で行う（404 は Service が throw）

### リクエストボディ

- Content-Type: `application/json`
- 文字コード: UTF-8
- 日時形式: ISO 8601（例: `2026-04-21T09:00:00+09:00`）
- 日付形式: `YYYY-MM-DD`

### バリデーション

- 必須項目の欠落チェックはコントローラー層で行う
- 業務ルールに関するバリデーションはサービス層で行う
- バリデーションエラーは `400 Bad Request` + エラーコード `VALIDATION_ERROR` を返す

## 4. レスポンス共通規約

### ステータスコード方針

| ケース | ステータスコード |
| ------ | :--------------: |
| 正常取得 | 200 |
| 正常作成 | 201 |
| 正常受付（非同期） | 202 |
| 正常（レスポンスボディなし） | 204 |
| バリデーションエラー | 400 |
| 認証失敗 | 401 |
| 認可失敗 | 403 |
| リソース不在 | 404 |
| 競合・排他エラー | 409 |
| サーバー内部エラー | 500 |

### Content-Type

- レスポンス: `application/json`（204 を除く）

## 5. エラーレスポンス共通形式

エラー時は以下の形式で返す。

```typescript
type ErrorResponse = {
  errorCode: string;   // ドメイン固有のエラーコード（例: ORDER_NOT_FOUND）
  message: string;     // 英語のエラーメッセージ（ログ・デバッグ用）
};
```

競合エラー（409）など追加情報が必要な場合は `errorCode` に加えてフィールドを追加してよい。
追加フィールドは各API仕様書に定義する。

### 共通エラーコード

以下のエラーコードは全サービス共通で使用する。
ドメイン固有のエラーコードは各実装計画書に定義する。

| エラーコード | HTTP | 説明 |
| ----------- | :--: | ---- |
| `VALIDATION_ERROR` | 400 | 必須項目欠落または形式不正 |
| `UNAUTHORIZED` | 401 | 認証トークン無効または未提供 |
| `FORBIDDEN` | 403 | テナント境界違反またはロール不足 |
| `SYSTEM_ERROR` | 500 | サーバー内部エラー |

## 6. モック実装規約

> **モックとは**: DB設計・外部依存が未確定のため、コントローラー層のI/F定義のみを先行実装する方式。
> モックコントローラーは固定レスポンスを返すのみでよい。

### モック対象の条件

以下のいずれかに該当するAPIはモック実装とする。

- DB設計が未確定
- 外部サービスとの連携仕様が未確定
- 依存するドメインサービスが未実装

### モック実装ルール

1. コントローラーのエンドポイント（パス・メソッド・ヘッダー）は正式仕様と同一にする
2. リクエストのバリデーションは省略してよい
3. レスポンスは固定値（ハードコード）を返す
4. エラーケースの実装は不要（常に 200 を返す）
5. モックコントローラーには `// TODO: DB設計確定後に本実装へ置き換えること` コメントを付与する

### モックレスポンス記載場所

- モックレスポンスの固定値は各サービスの実装計画書内「API仕様」セクションに記載する
- 画面単位の設計書には記載しない
