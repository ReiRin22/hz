## 本書の位置づけ

本書は **BFF共通設計書（`docs/01_アプリ/BFF/BFF共通設計書.md`）のフロントエンド側対応ルール**を定義する。

アーキテクチャ・通信方針・エラー方針の原則は `docs/02_アプリ基盤/01_フロントエンド/02_詳細設計書/` に定義されており、本書はそこに含まれない **「BFF連携固有のフロントエンド実装ルール」のみ**を対象とする。個別機能設計書はこれら両設計書を参照し、機能固有のルールのみを記載する。

## BFFエラーレスポンスのUIハンドリングルール

### type別UI処理ルール

BFFから返却される `BffErrorResponse.type`（BFF共通設計書 6.1参照）に応じて、以下のUIルールを全機能共通で適用する。

| type | code（代表例） | UI表示形式 | 操作継続 | 挙動 |
| ---- | ------------- | ---------- | :------: | ---- |
| `SYSTEM_ERROR` | `SYSTEM_ERROR` / `BAD_GATEWAY` / `TIMEOUT` | 共通エラーダイアログ（全画面） | 不可 | `error.tsx`（Error Boundary）に委譲。再試行ボタンを提供する |
| `AUTH_ERROR` | `UNAUTHORIZED` | ログイン画面へリダイレクト | 不可 | セッション切れとして扱い、Keycloak再認証フローへ |
| `AUTH_ERROR` | `FORBIDDEN` | 権限エラーダイアログ | 不可 | 「この操作を行う権限がありません」を表示して画面を維持 |
| `CONFLICT` | `CONFLICT` | 同時編集エラーダイアログ | 不可 | `lockedByUserName` がある場合は「{名前}さんが編集中です」を表示。参照モードへ移行（4章参照） |
| `NOT_FOUND` | `NOT_FOUND` | データ取得エラーダイアログ | 不可 | 「データが存在しません」を表示 |
| `BUSINESS_ERROR` | 機能固有コード | エラーラベルまたはダイアログ | 可 | `code` に応じた挙動は個別機能設計書に定義する |

**原則**: `BUSINESS_ERROR` 以外はすべて操作継続不可とする。`BUSINESS_ERROR` のみ入力修正による再試行を許容する。

### 複数エラー発生時の表示優先度

画面内で複数のAPIエラーが発生した場合（並列呼び出し等）、以下の優先度で最上位のエラーを **1件だけ**表示する。優先度はBFF側（BFF共通設計書 6.3）と一致させる。

| 優先度 | type | 理由 |
| :----: | ---- | ---- |
| 1（最高） | `SYSTEM_ERROR` | システム異常中の操作継続を防ぐ（医療安全） |
| 2 | `AUTH_ERROR` | アクセス権なし（操作続行不可） |
| 3 | `CONFLICT` | 排他競合は即座に通知が必要 |
| 4 | `NOT_FOUND` | リソース未発見 |
| 5（最低） | `BUSINESS_ERROR` | 入力値の問題（最も軽微） |

同一優先度のエラーが複数ある場合は最初に発生したエラーを採用する。

## X-Correlation-ID 管理

### 発番ルール

- **発番タイミング**: 画面ロード時（初期表示API呼び出し前）にフロントエンドが発番する
- **フォーマット**: UUIDv4（`crypto.randomUUID()` を使用）
- **発番単位**: 画面（ページ）ロードごとに1件。同一画面内の後続API呼び出しには同じ値を使い回す

### axiosへの注入

`frontend/src/shared/api/axiosClient.ts` のリクエストインターセプターで自動注入する。個別機能のコードで手動設定しない。

```typescript
// axiosClient.ts（注入部分のみ抜粋）
axiosInstance.interceptors.request.use((config) => {
  config.headers['X-Correlation-ID'] = getCorrelationId(); // 画面ロード時に発番済みのUUID
  config.headers['X-Tenant-Id'] = getTenantId();
  return config;
});
```

ヘッダ名・転送ルールはBFF共通設計書 4.1を参照。

## 排他制御（占有制御）共通UIルール

編集ロックを使用する全画面で以下のルールを適用する。個別機能設計書での再定義は不要。

### ロック状態とUI制御

| ロック状態 | `isEditable` | UI制御 |
| --------- | :----------: | ------ |
| 自分がロック保持中（`lockBy = 'SELF'`） | `true` | 編集モード：入力フィールド活性、確定ボタン活性、「編集中」バッジ表示 |
| 他ユーザーがロック保持中（初期表示で HTTP 409） | `false` | 参照モード：全入力フィールド読み取り専用、確定ボタン非活性、「参照中」バッジ表示 |
| ロック期限切れ（確定時に HTTP 409） | `false` | 排他エラーダイアログ表示後に参照モードへ移行 |

### CONFLICTエラーダイアログの表示内容

| ケース | `lockedByUserName` | 表示内容 |
| ------ | :----------------: | -------- |
| 初期表示時の409（他ユーザーロック中） | あり | 「{lockedByUserName}さんが編集中です。参照モードで表示します。」 |
| 初期表示時の409（lockedByUserNameなし） | なし | 「他のユーザーが編集中です。参照モードで表示します。」 |
| 確定時の409（ロック期限切れ） | — | 「編集ロックが期限切れになりました。再度開き直してください。」 |

`lockedByUserName` の付与有無はAPIごとに異なる。個別機能設計書のステータスコード一覧で確認すること（BFF共通設計書 6.2補足参照）。

### ロック延長トリガー

以下のいずれかを検知した場合、ロック延長APIを呼び出す。

- マウス操作（クリック、ダブルクリック）
- キーボード入力（keydown、input）
- フォーカス変更
- スクロール操作
- 明示的なUI操作（ボタン押下、選択変更）

上記が一定時間検知されない場合（無操作状態）は延長を行わない。閾値は排他制御仕様に従う。ロック有効期限を超過した場合は 4.1「ロック期限切れ」ルールを適用する。

## 実装前提ルール・実装対象範囲（AI実装制約）

全フロントエンド個別設計書に共通して適用する。個別設計書への再掲不要。

### 実装前提ルール

- 本設計書は Claude Code による自動実装を前提とする
- 記載のない業務ロジックは実装しない
- 記載のない例外処理・最適化・省略実装は禁止
- 命名規則・構造は個別設計書に従う

### 実装対象範囲

- 個別設計書は以下のコードのみを生成対象とする
  - UI / 状態表示 / 操作イベント
- 他層（BFF・バックエンド）のコードは生成しない
- 業務ルール判定・状態遷移・データ永続化は実装しない

## 命名規則・構造

全フロントエンド個別設計書に共通して適用する。個別設計書への再掲不要。

### UIコンポーネントID

表示項目テーブルおよび操作イベント定義で使用するIDのプレフィックス規約。

| プレフィックス | 対象 | 例 |
| ------------ | ---- | -- |
| `HDR_` | ヘッダ | `HDR_USER`, `HDR_PATIENT` |
| `TAB_` | タブ | `TAB_EDIT`, `TAB_REF` |
| `BTN_` | ボタン | `BTN_CONFIRM`, `BTN_CANCEL` |
| `TBL_` | テーブル | `TBL_TEST_RESULTS` |
| `COL_` | テーブル列 | `COL_RESULT`, `COL_UNIT` |
| `BDG_` | バッジ | `BDG_EDIT`, `BDG_REF` |
| `SRCH_` | 検索入力欄 | `SRCH_TEST_ITEM` |
| `RDO_` | ラジオボタン | `RDO_EDIT_REASON` |
| `TXT_` | テキストエリア | `TXT_EDIT_REASON` |
| `LBL_` | ラベル | `LBL_ERROR` |
| `CHK_` | チェックボックス | `CHK_ROW_SELECT` |
| `DRP_` | ドロップダウン | `DRP_UNIT` |
| `ICON_` | アイコン | `ICON_CALENDAR` |
| `MENU_` | メニュー | `MENU_LEFT`, `MENU_RIGHT` |

- SCREAMING_SNAKE_CASE で記述する
- セクション「表示項目」とセクション「操作イベント定義」で同じIDを使い追跡可能にする

### 操作イベントID・アクションID

**イベントID（EVT_xxx）**

| パターン | 規則 | 例 |
| ------- | ---- | -- |
| 初期表示 | `EVT_INIT01`（全画面で固定） | `EVT_INIT01` |
| 業務系（BFF呼び出しあり） | `EVT_{操作名}` SCREAMING_SNAKE_CASE | `EVT_TEST_RESULT_CONFIRM` |
| UI操作系（BFF呼び出しなし） | `EVT_UI_{連番}` | `EVT_UI_01`, `EVT_UI_02` |

- 業務系（8.1.1）とUI操作系（8.1.2）を必ずテーブルで分けて定義する
- 両テーブルに定義されていないイベントの実装は禁止

**アクションID（ACT_xxx）**

- `ACT_{操作名}` SCREAMING_SNAKE_CASE
- UIボタン起点の「意図宣言」として使用する（例: `ACT_CONFIRM_RESULT`）
- EVT_xxx との対応は操作イベント定義テーブルの備考に記載する

### エラーコード

| 範囲 | 種別 | 割り当てルール |
| ---- | ---- | -------------- |
| `E001〜E899` | 機能固有エラー | 画面スコープの連番。フロント検証エラーから採番する |
| `E997` | タイムアウト | `TIMEOUT`（HTTP 504）に対応。全画面共通で予約 |
| `E998` | 上流エラー | `BAD_GATEWAY`（HTTP 502）に対応。全画面共通で予約 |
| `E999` | システムエラー | `SYSTEM_ERROR`（HTTP 500）に対応。全画面共通で予約 |

- HTTP が `−` のエラーはフロント検証エラー（API通信なし）
- 表示形式は `ラベル`（入力項目直下）/ `ダイアログ` / `共通エラーダイアログ` の3種
- E997〜E999 は全画面で番号・表示形式を統一する

### 状態変数

| 規則 | 例 |
| ---- | -- |
| camelCase | `testResults`, `selectedRows` |
| boolean は `is{状態}` / `has{状態}` | `isEditable`, `hasTestDate` |
| 配列は複数形 | `testResults`, `availableUnits` |
| disabled 系は `{対象}Disabled` | `confirmButtonDisabled` |

- BFFレスポンスのフィールドをそのまま保持する変数は「状態管理ルール（画面固有）」テーブルに記載する
- UI制御のみに使う一時変数（例: ダイアログ表示フラグ）はテーブル記載不要
- 業務判定ロジックのための派生値（例: `isConfirmed`）は実装しない
