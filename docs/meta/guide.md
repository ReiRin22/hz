# AI駆動開発 ガイド（人間向け）

このガイドは、本フレームワークを使ってAIと一緒に開発を進める**人間のための手順書**です。

---

## このフレームワークの考え方

- **あなたが判断し、AIが実行する**
- AIは仕様を書き、コードを書き、レビューする。しかし「何を作るか」「これでよいか」「次に進むか」はすべてあなたが決める
- 1つの作業は複数のセッション（会話）にまたがる。途中で中断してよい
- AIは `CLAUDE.md` を読んで前回の続きから再開する

---

## セットアップ

### 1. CLAUDE.md を編集する

プロジェクトルートの `CLAUDE.md`（または `.claude/CLAUDE.md`）を開き、以下を埋める:

```yaml
# プロジェクト名をここに書く

> プロジェクトの1行説明をここに書く
```

### 2. /init を実行する

```
/init
```

AIが対話しながら以下を順に作成する:

#### Step 1: プロダクト概要（最初にやる）

AIが「何を作るか」をヒアリングする。**アイデア.md や企画書があれば、パスを伝えると読み込んでくれる。**

- 何を作るか（ビジョン・課題）
- 誰のためか（ターゲットユーザー）
- 何ができればよいか（コア機能の優先度）
- 何をやらないか（スコープ外）
- 制約はあるか

→ `docs/02_アプリ基盤/product-brief.md` として出力される。確認して承認する。

#### Step 2: 技術基盤

プロダクト概要を踏まえて、技術的な基盤を作る:

- `docs/02_アプリ基盤/tech-stack.md` — 技術選定
- `docs/02_アプリ基盤/system-design.md` — システム構造
- `docs/02_アプリ基盤/directory-structure.md` — ファイル配置ルール
- `docs/02_アプリ基盤/guidelines.md` — 開発規約

**1セッションで全部作らなくてよい。** 1つずつ丁寧に作り、セッションを分けてOK。

#### Step 3: ドメインを決める

プロダクト概要のコア機能をもとに、AIがドメイン（機能グループ）を提案する。例:
- `auth` — 認証・認可
- `dashboard` — ダッシュボード
- `notification` — 通知

最初から完璧にしなくてよい。後から追加できる。

## 日常の開発フロー

### 技術検証（PoC）が必要なとき

採用する技術に不確実性がある場合（「本当に要件を満たせるか？」「性能は出るか？」）は、設計の前にPoCを実施する。

```
/poc 01_フロントエンド・BFF
```

#### PoCの全体の流れ

```
/poc → PoC項目洗い出し → あなたが承認 → 1項目ずつ実装・実行 → 採用判断
```

#### あなたがやること（フェーズ別）

**Step 1-2: 項目洗い出し・承認**
1. `/poc {target}` を実行する
2. AIが方式設計書を読み込んでPoC開発計画を作成する
3. PoC項目の一覧が提示されるので、内容・優先度を確認して承認する

**Step 3-0: TBD解消**
- AIが「PoCへの影響あり」のTBD（未決定事項）を確認してくる
- 各TBDの方針を答える（決定 or スキップ）

**Step 3（各項目のミニサイクル）: 実装 → 実行 → 評価**

| ステップ | 誰が | 内容 |
|---------|------|------|
| 3-A: 実装計画 | AI | 合否基準・実装方針を `item_NN.md` に記載。承認する |
| 3-B: 実装 | AI | サンプルコードを `sample/{target}/` に実装 |
| 3-C: 実行 | **あなた** | ローカル環境でコードを実行し、ログ・測定値を `item_NN.md` に貼り付ける |
| 3-C: 評価 | AI | 実行結果と合否基準を数値照合し、`item_NN.md` に判定を記入 |
| 3-D: 総合判定 | AI | 定量評価 + あなたの定性評価を統合 |
| 3-E: 承認 | **あなた** | この項目の結果を承認する。納得できなければ再検証を指示 |

> **ポイント: 3-C の「実行」はあなたがやる。**
> AIはコードを実行できない。`docker compose up` や `npm run dev` で環境を起動し、
> 実行ログや測定値を `item_NN.md` の「実行結果」セクションに貼り付けてから
> `/poc {target}` を再実行することで、AIが評価フェーズに進む。

**最終: 採用判断**
- 全項目完了後、AIが `report.md`（PoC報告書）を作成する
- 内容を確認し、**採用 / 条件付き採用 / 不採用** を判断する
- 採用後は `/design 02_アプリ基盤/{component}/` で詳細設計に進む

#### PoCのセッション再開

PoCは複数セッションにまたがる。`/poc {target}` を再実行するだけで、
AIが `state.md` を読んで途中から再開する。

### 新しい機能を作るとき

#### Phase 1: 設計（/design）

```
/design auth/F01_login
```

**あなたがやること:**

1. **要件を伝える** — 「何を作りたいか」を自由に話す
2. **AIの調査結果を見る** — 既存コードとの関係、競合がないかの報告が来る
3. **方針を決める** — AIが選択肢を出したら選ぶ
4. **PRDドラフトを確認する** — AIがPRDを書く。`[要確認]` の箇所を判断する
5. **設計書ドラフトを確認する** — AIが設計書を書く。技術選択を承認する
6. **レビューを指示する** — `PASS` になるまで修正を繰り返す

```
/review docs/01_アプリ/auth/F01_login/
```

**判断ポイント:**
- PRDの受入条件は十分か？
- 設計の技術方針に納得できるか？
- 異常系は考慮されているか？

#### Phase 2: 実装（/implement）

レビューPASS後、あなたが判断して実装に進む:

```
/implement auth/F01_login
```

**あなたがやること:**

1. **タスク分解を確認する** — AIがタスクリストを作る。粒度・順序に意見があれば伝える
2. **実装の進捗を見守る** — AIがタスクを1つずつ実装する
3. **疑問に答える** — AIが判断に迷ったら聞いてくる。回答する
4. **レビューを指示する**

```
/review src/features/login/
```

#### Phase 3: 完了

レビューPASS後、AIが `INDEX.md` を `done` に更新して完了。

---

### バグを直すとき

```
/fix auth/F01_login ログイン時に500エラー
```

**あなたがやること:**
1. **バグの症状を伝える** — 再現手順、期待動作、実際の動作
2. **AIの原因分析を確認する** — 原因と修正方針の報告が来る
3. **修正方針を承認する** — 仕様外の変更が必要なら `/design` に切り替え判断
4. **修正結果を確認する**

---

### リファクタリングするとき

```
/design refactor/認証モジュールの分割
```

**あなたがやること:**
1. **何を改善したいか伝える**
2. **影響分析を確認する** — AIが影響範囲を報告する
3. **実施するか判断する** — 範囲が広すぎれば絞る or 中止もあり
4. **ADRを承認する** — 判断理由の記録

## セッションの始め方・終わり方

### 始め方

AIに何も言わなくても、AIは `CLAUDE.md` を読んで前回の状態を把握する。

- **新しい作業を始めるとき** → コマンドを実行する（`/poc`, `/design`, `/implement`, `/fix`）
- **前回の続きのとき** → 同じコマンドを実行する。AIが `session_progress` を読んで続きから再開する

### 終わり方

特別なことは不要。AIがセッション終了時に自動的に:
- `CLAUDE.md` の `session_progress` を更新する
- `session-log.md` にエントリを追記する

**「ここで終わり」と伝えるだけでOK。**

次のセッション（別の日でも、別のAIでも）が `session_progress` を読んで再開できる。

## 判断ゲート — AIがあなたに判断を求めるとき

作業の要所で、AIはあなたに **選択肢付きの質問** を出します。これを「判断ゲート」と呼びます。

### 画面の見え方

AIが判断ゲートに到達すると、以下のようなUIが表示されます:

```
┌─────────────────────────────────────────┐
│ [スコープ]                               │
│                                         │
│ 以下のスコープで設計を進めてよいですか？    │
│                                         │
│ ○ このスコープでOK (推奨)                │
│ ○ スコープを広げたい                     │
│ ○ スコープを絞りたい                     │
│ ○ Other                                │
│                                         │
│              [Submit]                   │
└─────────────────────────────────────────┘
```

- **選択肢をクリックして選ぶだけ** でOK
- 最初の選択肢がAIの推奨（`(推奨)` 表示あり）
- 各選択肢には理由・トレードオフの説明がつく
- 「Other」を選ぶと自由入力できる

### 判断ゲートの種類

| ゲート | いつ出るか | あなたが決めること |
|--------|-----------|------------------|
| **スコープ** | 作業開始時 | 何を作る/直すかの範囲 |
| **方針** | 複数アプローチがあるとき | どの技術方針で進めるか |
| **承認** | ドラフト完成後 | この内容で次へ進んでよいか |
| **要決定** | `[要確認]` がある場合 | AIが決められない事項を人間が決定 |
| **次のフェーズ** | レビューPASS後 | 次のフェーズに進むか |
| **確認（想定外）** | 問題発見時 | 続行するか中断するか |
| **GO/NOGO** | PoC報告書確認時 | 技術を採用するか否か |

### ゲートが出るタイミング一覧

#### /poc（技術検証）
1. PoC項目洗い出し後 → **承認**: 項目・優先度の確認
2. TBD確認 → **確認**: 未決定事項の方針決定
3. 各項目の実装計画後 → **承認**: 計画の確認
4. 各項目の評価後 → **承認**: 結果の受け入れ
5. 全項目完了後 → **確認**: 追加検証が必要か
6. 報告書作成後 → **GO/NOGO**: 技術採用の最終判断

#### /init（初期化）
1. プロダクト概要ドラフト後 → **承認**: この内容で技術選定に進んでよいか

#### /design（機能設計）
1. ヒアリング後 → **スコープ**: 要件の範囲を確定
2. 調査結果提示後 → **方針**: 設計アプローチを選択
3. PRDドラフト後 → **要決定** + **承認**: 未決定事項の解決 → PRD承認
4. 設計書ドラフト後 → **要決定** + **方針** + **承認**: 技術選択 → 設計承認
5. 検証後 → **次のフェーズ**: /reviewに進むか

#### /implement（実装）
1. タスク分解後 → **承認**: タスクリストの確認
2. 実装中（必要時） → **確認**: 仕様外の問題が見つかった場合
3. 全タスク完了時 → **次のフェーズ**: /reviewに進むか

#### /fix（バグ修正）
1. 原因分析後 → **方針**: 修正方針の選択
2. 原因分析後（影響大） → **スコープ**: 影響範囲の確認
3. 修正完了時 → **次のフェーズ**: /reviewに進むか

#### /review（レビュー）
1. PASS時 → **次のフェーズ**: 次に進むか
2. FAIL時 → **方針**: どの指摘から対応するか

### 重要なルール

- **AIはゲートを飛ばさない** — 必ずあなたの判断を待つ
- **AIは勝手に進まない** — 「特に問題なさそうなので進めました」はやらない
- **あなたの選択に従う** — 同じ質問を何度もしない

## あなたの判断が必要な場面（まとめ）

| 場面 | 判断内容 |
|------|---------|
| PoC項目確認 | 検証すべき項目・優先度は適切か |
| PoC実行 | ローカルでサンプルコードを実行し結果を貼り付ける |
| PoC採用判断 | 報告書を読んで技術を採用するか決める |
| 要件ヒアリング | 「何を作るか」「なぜ作るか」を伝える |
| PRDドラフト確認 | 受入条件は十分か。`[要確認]` を解決する |
| 設計書ドラフト確認 | 技術方針に納得できるか。`[要確認]` を解決する |
| フェーズ遷移 | design → implement に進むか（AIは勝手に進まない） |
| 仕様変更 | 実装中に仕様変更が必要になったとき、design に戻すか判断 |
| ADR承認 | 横断変更の判断理由を承認する |
| レビュー結果対応 | FAIL時に何を直すか判断する |
| リファクタリング判断 | やるか、やらないか、範囲をどうするか |

## AIに任せてよいこと

| 作業 | AIの担当 |
|------|---------|
| 方式設計書レビュー | サブエージェントがPoC項目を洗い出す |
| PoCサンプルコード実装 | メインエージェントが `sample/{target}/` に実装する |
| PoC定量評価 | サブエージェントが実行結果と合否基準を数値照合する |
| PoC報告書作成 | サブエージェントが全項目を集約して報告書を生成する |
| コードベース調査 | サブエージェントが既存コードを調べて報告する |
| 仕様間の競合チェック | サブエージェントが全仕様を走査する |
| PRDの起草 | サブエージェントがテンプレートに沿って書く |
| 設計書の起草 | サブエージェントがPRD + 調査結果から書く |
| テスト計画の作成 | サブエージェントがPRDの受入条件から生成する |
| コードの実装 | メインエージェントがtasklist通りに実装する |
| レビュー実行 | サブエージェントがチェックリストで検証する |
| 状態管理 | AIがCLAUDE.md, INDEX.md, session-log.mdを更新する |

## プロジェクトの状態を確認する方法

| 何を知りたいか | 見るファイル |
|---|---|
| 今どの機能を作業中か | `CLAUDE.md` の `session_feature` |
| 全機能の進捗 | `docs/01_アプリ/INDEX.md` |
| 今のセッションの続き | `CLAUDE.md` の `session_progress` |
| PoCの進捗 | `docs/02_アプリ基盤/{component}/03_PoC検証/state.md` |
| 実装タスクの進捗 | `.steering/{対象}/tasklist.md` |
| 過去のセッションで何をしたか | `.steering/{対象}/session-log.md` |
| 技術的負債 | `docs/meta/debt.md` |
| 過去の設計判断 | `docs/adr/` |

## よくある操作

### 複数機能を並行で進めたいとき

問題ない。`INDEX.md` で複数の機能が同時に `design` / `implement` 状態であってよい。

セッション開始時に「auth/F01 の続き」「payment/F03 を始めたい」と伝えるだけ。
AIが `CLAUDE.md` の `session_feature` を切り替える。

### 設計を途中でやめたいとき

そのまま放置してよい。`INDEX.md` のステータスは `design` のまま残る。
再開したくなったら同じコマンドを実行する。

### PoCを途中でやめたいとき

そのまま放置してよい。`state.md` に進捗が保存されている。
`/poc {target}` を再実行すれば途中から再開できる。

### AIが間違ったことをしたとき

1. **即座に止める** — 「待って」「それは違う」と言う
2. **何が間違いか伝える** — AIは修正する
3. **深刻な場合** — gitで戻す。AIの作業は全てgit管理されている

### AIの調査結果が不十分なとき

「もっと詳しく調べて」「〇〇も調べて」と伝える。
AIはサブエージェントを再実行する。

## ファイル構成の概要

```
あなたが見るもの:
  CLAUDE.md                          ← プロジェクトの状態（AIが更新する）
  docs/02_アプリ基盤/product-brief.md ← プロダクト概要（/init で最初に作る）
  docs/01_アプリ/INDEX.md            ← 全機能の一覧と進捗
  docs/01_アプリ/{domain}/           ← 機能ごとの仕様（PRD + 設計書）
  docs/02_アプリ基盤/                ← 技術基盤・方式設計書・PoC成果物
  docs/meta/debt.md                  ← 技術的負債リスト
  docs/adr/                          ← 設計判断の記録

あなたが触らなくてよいもの:
  .claude/commands/      ← AIへの指示書（コマンド定義）
  .claude/skills/        ← AIの知識パック
  .claude/agents/        ← サブエージェントの定義
  .steering/             ← AIの作業ワークスペース
  docs/templates/        ← ドキュメントのテンプレート
  docs/meta/rules.md     ← AI向けの開発ルール
```
