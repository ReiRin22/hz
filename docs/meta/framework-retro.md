# フレームワーク改善トラッカー（検出ログ）

開発中にAIが検出したフレームワーク自体の問題点・改善案を記録する。
ここは**検出ログ**であり、タスク管理は `framework-tasks.md` で行う。

---

## 記録ルール

- AIは開発作業中に問題を検出したら、このファイルに追記する
- 1件1エントリ。重複は避ける（既存エントリを確認してから追記）
- レビュー時に分析し `framework-tasks.md` へタスク化したら `タスク化済` に変更する

## カテゴリ

| カテゴリ | 対象 |
|---|---|
| `prompt` | コマンド・エージェント定義の指示が不明確/不足/矛盾 |
| `template` | テンプレートのセクション過不足・使いにくさ |
| `rule` | ルールの矛盾・曖昧さ・現実との乖離 |
| `workflow` | 作業フローのステップが実践で機能しない |
| `skill` | スキル定義の不足・品質基準の問題 |
| `structure` | ディレクトリ構造・ファイル配置の問題 |

## ステータス

| ステータス | 意味 |
|---|---|
| `新規` | 検出済み、未分析 |
| `タスク化済` | 分析完了、framework-tasks.md にタスクとして移行済み |

## エントリ

### R-01 [prompt] アプリ基盤PoC専用エージェントのみ整備済み、他は汎用定義のまま
- **ステータス**: タスク化済
- **検出日**: 2026-03-24
- **検出時の作業**: PoCフェーズ完了後のエージェントカタログ確認
- **問題**: `poc-item-extractor` と `poc-evaluator` は実プロジェクト（アプリ基盤PoC）に合わせて整備済みだが、`design-drafter` / `prd-drafter` / `spec-reviewer` / `design-validator` 等の汎用エージェントはデフォルト定義のまま。実際の `/design` フェーズで使うと「このプロジェクトのドメイン知識（病院・療養病棟・電子カルテ）」が欠けた成果物が出力されるリスクがある。
- **提案**: `/design` フェーズを実際に動かしながら各エージェントをプロジェクト向けに調整する。初回設計セッション終了時にエージェントの不足・ズレを RETRO に記録する運用とする

### R-02 [prompt] アプリ基盤詳細設計専用エージェントが未定義
- **ステータス**: タスク化済
- **検出日**: 2026-03-24
- **検出時の作業**: アプリ基盤詳細設計フェーズの準備
- **問題**: `docs/02_アプリ基盤/{component}/02_詳細設計書/` を作成する専用エージェントがない。`core-design-drafter` は `docs/02_アプリ基盤/` 直下の横断設計書（tech-stack.md・system-design.md 等）向けであり、コンポーネント別の詳細設計書（実装規約・シーケンス・データフロー等）には対応していない。`design-drafter` は機能（`docs/01_アプリ/`）向けで、基盤設計の出力フォーマット・参照規約が異なる。
- **提案**: アプリ基盤詳細設計専用エージェント（例: `infra-design-drafter`）を追加する。またはPoC報告書（report.md）の「詳細設計への引き継ぎ事項」を入力とし、02_詳細設計書/ の各ドキュメントを出力できるよう `core-design-drafter` を拡張する

### R-03 [structure] design.md・design-drafter.md・INDEX.md のパス参照が実際の構造と不一致
- **ステータス**: タスク化済
- **検出日**: 2026-03-24
- **検出時の作業**: /design コマンドとエージェント定義のレビュー
- **問題**: `design.md` コマンドは `docs/spec/INDEX.md` `docs/core/` を参照。`design-drafter.md` の出力先も `docs/spec/{domain}/Fxx/design.md`。`INDEX.md` のドメインパスも `docs/spec/{domain}/`。一方、CLAUDE.md と `core-design-drafter.md` は `docs/01_アプリ/` `docs/02_アプリ基盤/` を使用しており、実際の構造と乖離している。
- **提案**: `design.md` / `design-drafter.md` / `INDEX.md` のパスを `docs/01_アプリ/` `docs/02_アプリ基盤/` に統一する

### R-04 [prompt] /design B.基盤設計がアプリ基盤詳細設計書（02_詳細設計書/）に未対応
- **ステータス**: タスク化済
- **検出日**: 2026-03-24
- **検出時の作業**: PoCフェーズ完了後の詳細設計フェーズ準備
- **問題**: `/design` B. の対象ファイル一覧は横断基盤設計書（tech-stack.md 等）のみ。`docs/02_アプリ基盤/{component}/02_詳細設計書/` を作成するコマンドパスが未定義。PoCフェーズ終了後「詳細設計書を作成できる状態」と案内されるが、実際の作業手順がない。
- **提案**: `/design` コマンドにセクションD「アプリ基盤詳細設計（`/design 02_アプリ基盤/{component}/xxx`）」を追加し、フロー・専用エージェント（R-02）と合わせて整備する

### R-05 [prompt] codebase-researcher が実装前フェーズ（設計フェーズ）で機能しない
- **ステータス**: タスク化済
- **検出日**: 2026-03-24
- **検出時の作業**: /design ステップ2のサブエージェント構成レビュー
- **問題**: `/design` ステップ2で `codebase-researcher` を起動するが、`/implement` 前は `src/` が存在しない。調査対象がなく空の報告が返るか、仕様ドキュメントを調査する内容になって `spec-cross-checker` と役割が重複する。
- **提案**: `codebase-researcher` の起動条件を「実装コードが存在する場合のみ（`/fix` / `/implement` フェーズ等）」に限定し、設計フェーズ初期は `spec-cross-checker` のみ起動するよう `/design` ステップ2を修正する

### R-06 [prompt] /poc のフィールド名が CLAUDE.md の実際の構造と不一致
- **ステータス**: タスク化済
- **検出日**: 2026-03-24
- **検出時の作業**: /poc コマンドのレビュー
- **問題**: `poc.md` は「CLAUDE.md の `active_feature` と `phase` を更新する」と指示しているが、CLAUDE.md の実際のフィールド名は `session_feature` と `session_phase`。同様に `progress` も `session_progress` が正しい。誤ったフィールド名で更新するとセッション引き継ぎが機能しない。
- **提案**: `poc.md`（および他コマンドも確認）の CLAUDE.md 更新指示を `session_feature / session_phase / session_progress` に統一する
