# 開発ルール

本ドキュメントは CLAUDE.md のルールの詳細版である。

---

## 共通制約

### ディレクトリ作成の禁止

`mkdir` コマンドを使わない。ディレクトリは Write ツールでファイルを書き出す際に自動作成される。空ディレクトリが必要な場面はないため、常にファイル書き出しの副作用としてディレクトリを作成する。

---

## 0. 文書規約 — RFC 2119 準拠

### なぜ
要件や制約の強度を曖昧なまま書くと、AIも人間も解釈がブレる。RFC 2119 のキーワードで強度を明示することで、「必須」と「推奨」の区別が機械的にできる。

### ルール
- `docs/` 配下の仕様書（PRD・設計書・ADR）では、要件の強度を示す際に以下のキーワードを使用する
- AIエージェントは仕様書作成時にこの規約に従う（サブエージェント定義の品質基準で参照される）

### キーワード対応表

| RFC 2119 キーワード | 日本語表記 | 強度 |
|---|---|---|
| **MUST** / **REQUIRED** / **SHALL** | **しなければならない** | 絶対的な要求 |
| **MUST NOT** / **SHALL NOT** | **してはならない** | 絶対的な禁止 |
| **SHOULD** / **RECOMMENDED** | **すべきである** | 正当な理由がない限り従う |
| **SHOULD NOT** / **NOT RECOMMENDED** | **すべきではない** | 正当な理由がない限り避ける |
| **MAY** / **OPTIONAL** | **してもよい** | 完全に任意 |

### 書き方の指針
- キーワードは **太字** で記載する（例: 認証トークンは**しなければならない（MUST）**）
- 日本語文書では「日本語表記（RFC 2119 キーワード）」の形式を推奨する
- 強度の区別が不要な箇所では通常の日本語表現を使う（すべてに付ける必要はない）

## 1. 仕様が先、実装は後

### なぜ
AIは仕様なしにコードを書くと、暗黙の前提で実装してしまい、後から整合性が取れなくなる。

### ルール
- コードに触れる前に `docs/spec/{domain}/Fxx_機能名/prd.md` と `design.md` を完成させる
- 仕様が `/review` を通過してから実装に入る
- 実装中に仕様変更が必要になったら、先に仕様を更新し再レビューする

### 例外
- バグ修正（`/fix` コマンド。既存仕様の範囲内）
- テスト追加（既存仕様のカバレッジ向上）

## 2. 1機能 = 1フォルダ（ドメイン配下）

### なぜ
AIが「この機能に関する情報」を1フォルダ読むだけで完結するようにする。トークン節約の核心。

### ルール
- `docs/spec/{domain}/Fxx_機能名/` に prd.md と design.md を置く
- Fxx はグローバル連番（F01, F02, ...）。ドメインをまたいでも通し番号
- 機能名はkebab-case（例: `F01_user-auth`）
- ドメインは機能の論理グループ（例: `auth`, `payment`）。ドメイン名もkebab-case
- 他機能の仕様ファイルを読む必要がある場合は design.md の「依存」セクションに明記する

---

## 3. スコープ宣言

### なぜ
AIが無関係なファイルを読み書きすることを防ぐ。

### ルール
- 実装フェーズ開始時に `.steering/YYYYMMDD-機能名/` を作成する
- `requirements.md` にスコープ宣言 + 受入条件を記述する
- `design.md` に実装方針を記述する
- `tasklist.md` に具体的なタスクを列挙する
- `session-log.md` にセッション履歴を追記する
- 作業中はこのフォルダの tasklist.md を進捗管理の正とする

### スコープ宣言の書き方

```yaml
scope:
  read:
    - docs/spec/{domain}/Fxx_機能名/
  write:
    - docs/spec/{domain}/Fxx_機能名/
    - src/features/機能名/
  out_of_scope:
    - docs/spec/ の他機能
    - 既存APIの破壊的変更
```

## 4. 300行制限

### なぜ
1ファイルが大きいとAIが全部読もうとしてトークンを浪費する。人間にとっても読みにくい。

### ルール
- `docs/` 配下の全 Markdown は300行以内
- 超えそうになったら論理単位で分割する
- 分割時は元ファイルからリンクを貼る

---

## 5. セッション引き継ぎ

### なぜ
大規模開発では1セッションで作業が完結しない。次のセッションのAIが迷わず再開できる状態を残す。

### ルール
- 毎セッション終了時に CLAUDE.md の `progress` を更新する
- progress には「次のAIが何から始めればよいか」がわかる粒度で書く
- 実装フェーズでは tasklist.md の状態を最新に保つ
- 実装・修正フェーズでは session-log.md にエントリを追記する
- AIがフェーズを勝手に進めない（design→implement の遷移は人間が判断する）

### progressの書き方

NG:
```yaml
progress: "作業中"
```

OK:
```yaml
progress: "auth/F03のPRDドラフト完了。受入条件#3,#4が未確定。次回ユーザーに確認要"
```

OK:
```yaml
progress: "tasklist 8/12完了。次はタスク9（API統合テスト）から"
```

## 6. INDEX.mdが正（Single Source of Truth）

### なぜ
複数の機能を並行で開発する場合、状態の管理元が分散すると矛盾が生じる。

### ルール
- `docs/spec/INDEX.md` が全機能のステータスの正
- CLAUDE.md の `active_feature` は「今のセッションの焦点」を示す（=作業中の1機能）
- 複数の機能が同時に design / implement 状態であってよい
- 機能のステータス変更時は INDEX.md を更新する
- ドメインの追加・変更時も INDEX.md のドメイン一覧を更新する

## 7. フレームワーク改善フィードバック

### なぜ
フレームワーク（プロンプト・テンプレート・ルール・エージェント定義）は机上で完璧にはできない。実際の開発で見つかった問題を記録し、継続的に改善する。

### ルール
- AIは開発作業中にフレームワーク自体の問題を検出したら `docs/meta/framework-retro.md` に追記する（検出ログ）
- 検出対象: プロンプトの曖昧さ、テンプレートの過不足、ルールの矛盾、ワークフローの非効率
- 追記前に既存エントリを確認し、重複しない
- 開発作業の本筋を止めない（記録は簡潔に。詳細な改善案は後回しでよい）
- レビュー時に分析した問題は `docs/meta/framework-tasks.md` にタスク化し、RETRO側は `タスク化済` に更新する
- RETRO は検出ログ、TASKS はタスク管理。役割を混在させない

### 検出のトリガー
- テンプレートのセクションを毎回削除 or 大幅に書き換えている → `template` カテゴリ
- エージェントの指示が不足で意図と違う出力が出た → `prompt` カテゴリ
- ルール同士が矛盾して判断に迷った → `rule` カテゴリ
- ワークフローのステップが実態と合わない → `workflow` カテゴリ
- スキルの品質基準が不足/過剰 → `skill` カテゴリ
- ファイルの置き場所に迷った → `structure` カテゴリ
